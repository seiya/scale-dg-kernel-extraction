# p=31 (Nq=32) — 同一 DOF ギャップの 6 点目、そして曲線の極大点

測定環境: RIKYU NVIDIA GB200 1 GPU（152 SM）、`make CUDA=1 GPUFLAGS=-gpu=cc100`。
コミット: 本レポートを追加したコミット（親は `1c36e92`）。
実行ファイルは `scale-dg_extraction.p31` に凍結し、実測・nsys・ncu すべてで同じものを使った。
nsys は Slurm job `58753`（`job_nsys_p31.sh`）、ncu は `58754`（`job_ncu_p31.sh`、`--set full`）と
`58777`（`job_ncu_p31b.sh`、バンクコンフリクト実測と素の GEMM）。
入力: `conf_perf_p31*.conf`（`NeX=NeY=NeZ=8, PolyOrder=31, dt=1.0D-6, nstep=200,
UseCudaGraph=.false.`）。検証: `input_p31_val*.conf`（`Ne=2³`、`nstep=1`、
`SCALE_DG_VARYING_COEFF=1`）。

## 1. なぜ p=31 か

同一 DOF（16.78 M = 256³）を立方一様メッシュで保つ条件 `NeX*Nq = 256` から埋められるのは
p = 15, 31, 63, 127 の 2 冪だけで（`p15_gap_study.md` §1）、**p=31 が唯一の未着手**だった
（`p127_gap_study.md` §10）。`NeX=NeY=NeZ=8`、`Ne=512`、`Nq=32`、`NfpTot=6144`。
1 フィールド 134 MB、work 込みで約 1.6 GB。

ここを埋める意味は 2 つあった。**融合が勝つ p≤15 と GEMM が勝つ p≥63 の交差点が
p=31 に挟まっている**こと（`README.md`）と、Nq=32 が **1 要素の `q`（256 KB）が
227 KB/SM を超える最初の次数**であること（`p15_gap_study.md` §9）である。

## 2. 先行レポートの誤りの訂正 —— CUTLASS 経路は p=31 で使える

`p63_gap_study.md` §9 と `p127_gap_study.md` §10 は

> p=31 (Nq=32, `Ne=8³`) は未着手。`Nq*Ne = 262144` なので **CUTLASS 経路は使えず**

と書いていたが、**これは誤りである**。`Ne = 8³ = 512` なので `Nq*Ne = 32*512 = 16384` で、
`grid.z` batch 上限 65535 に十分収まる。262144 は `p63_gap_study.md` §2.3 の表の
**p=7（`Nq=8, Ne=32³`）の行の値**であり、それが p=31 の行に転記されていた。

**実測で確認した。** `CUDAFORTRAN_GEMM_FUSED` と `CUDAFORTRAN_GEMM_CUTE` は
`mod_advect3d_eq.f90:172,186` と `mod_cuda_dg_kernels.cuf:908,1007` のゲートを
素通りし、無改造で走って基準実装と一致した（§4）。

## 3. ホスト側で必要になった変更

**既存 5 経路（`OPENACC_SPLIT` / `CUDAFORTRAN_SPLIT` / `GEMM` / `GEMM_FUSED` /
`GEMM_CUTE`）はコード変更ゼロで走った。** p=63 の作業で入れた一般化がそのまま効いている:
`mod_mesh.f90:272` は `operator_data/p31.dat` が無いので `generate_lgl_operators` に落ち、
`dense_lift = (Nq <= 128)` が真なので `Lift_mat(32,32,32,6)` = 1.57 MB が実体化され、
`mod_dg_optr_kernel.f90` の 4 か所の `select case(Nq-1)` は `case default` に落ちる。
ERB の `AUTOGEN_PMAX = 15` は上げていない（p=31 の OPT1 特殊化が効くのは CUDA 経路ではなく
参照用の OpenACC/CPU 経路だけである）。

変更したのは `CUDAFORTRAN_FUSED` を p=31 に開く部分だけである:
`mod_advect3d_eq.f90:142`（設定時ゲート）と `:769`（実行時はしご）、
`mod_cuda_dg_kernels.cuf` のガードとディスパッチ、および新規カーネル 2 本。
**`CUDAFORTRAN_FUSED_TC` は開いていない**（`mod_advect3d_eq.f90:153,815` はそのまま）:
Nq=32 の TC カーネルが無いのでゲートを開けても `error stop` が後ろにずれるだけであり、
GB200 では FP64 TC ピークが CUDA core ピークと等しく（`AGENTS.md`）、
`p15_gap_study.md` が「TC の優位は Nq とともに伸びない」（1.21 → 1.17 倍）と
記録している以上、CUDA core 版が §6 のとおり負けている状況で書く根拠が無い。

## 5. Nq=32 融合カーネルの設計

### 5.1 律速は shared ではなくレジスタファイルだった

`p15_gap_study.md` §9 は「Nq=32 以降は要素が shared に載らないので p=31 は別の構造
（タイル化）を要する」と書いていた。前半は正しいが、**実際に効いてくる制約は
shared メモリではなくレジスタファイルである**。

方向 `a` の縮約に対し、ブロックが所有するノード集合は `a` 方向の完全なペンシルで
なければ再読み込みが要る。`(a,b,c)` の箱を所有すると global 読み出しの冗長度は
x で `Nq/a`、y で `Nq/b`、z で `Nq/c` になり、**3 方向すべてで冗長度 1 になるのは
要素まるごとだけ**である。これが p=15 の設計が p=31 で使えない理由の正確な内容である。

しかし `sbuf` は**所有ノード集合を保持する必要がない**。x の縮約は一度に 1 枚の
`(l,k)` 平面（`Nq²` = 1024 double = **8 KB**）しか要らない。8 KB なら余裕で載る。
一方 1024 スレッド/ブロックでは 64 レジスタ/スレッド = **32 double** しか無く、
長さ `TJ` の累算配列を持つと `2*TJ` レジスタがそれだけで消える。
**設計問題は「要素を shared にどう載せるか」ではなく「方向をまたぐ長寿命の
累算器をどう避けるか」だった。**

### 5.2 x と z は同じスレッド写像を共有する

スレッドを `(i,k)`、`j` を内側**ループ**にすると:

- x（固定 j）: `Σ_l D1D(i,l)·f_x(l,j,k)` は `(l,k)` 平面 1024 値で足りる。
- z（固定 j）: `Σ_l D1D(k,l)·f_z(i,j,l)` は `(i,l)` 平面 1024 値で足りる。

**両方が同じ j 反復の中で完結する**ので累算器はスカラで済み、`j` を全長回しても
レジスタを消費しない。しかもスレッド `(i,k)` が読む `q(i,j,k)` は自分のノードで、
x 用と z 用に同じ値を再利用できる。y だけがこの写像に乗らないので第 2 カーネルに
別の写像（スレッド `(i,j)`、`k` を内側ループ）を与えた。

| | `tendency_fused_p31_xz_kernel` | `tendency_fused_p31_y_kernel` |
|---|---|---|
| grid / block | `<<<512,1024>>>` | `<<<512,1024>>>` |
| 静的 shared | **42496 B** | **16384 B** |
| レジスタ | **64**（スピル 0） | **44**（スピル 0） |
| 占有率 | 50.0%（理論 50%） | 50.0% |
| 担当 | x, z 体積項と**6 面すべて**の数値フラックスと lift | y 体積項を `dqdt` に加算 |

### 5.3 面フラックスをループ外に括り出す —— カーネルの 31%

最初の実装は面フラックスを j ループの中で計算していた。faces 2,4 は `(j,k)` 平面なので
`i==1` の 32 スレッドが、faces 5,6 は `(i,j)` 平面なので `k==1` の 32 スレッドが埋める形で、
**1024 スレッド中 32 本しか生きていない分岐を 32 回まわす**ことになる。

括り出して全 1024 スレッドで一度に評価する形に変えたところ、
**1287.4 → 1001.7 µs/stage（−22.2%）**。アブレーション（面 gather を丸ごと外した
不正な版）は 884.4 µs だったので、括り出し前は面フェーズが **403 µs = カーネルの 31%**、
括り出し後は約 28 µs である。総面点数は変わっていない。**変わったのは並列度だけ**である。

括り出しにあたり、faces 2,4 は `(j,k)` 平面なのでスレッド `(i,k)` が `j=i` の点を評価し、
j 反復では**ワープシャッフル**で取り出す（`k` がワープ番号なので必要なレーンは `j`）。
faces 5,6 は `(i,j)` 平面で別ワープに載るので shared 経由にした。
faces 1,3 は `(i,k)` 平面でスレッドが自分の点をちょうど 1 つ持つのでレジスタに置く。

> **CUDA Fortran の `__shfl` は 1-based である。** `__shfl(x,3)` は
> `threadIdx%x == 3` のスレッドの値を返し、`__shfl(x,0)` はレーン 32 に回り込む。
> 0-based のつもりで `j-1` を渡した版は、`Ne=2³` の検証で相対差が
> 2.08e-16 から **7.29e-15** に悪化して見つかった。O(1) の誤差にならないので、
> 粗い検証では見逃しうるバグである。

### 5.4 バンクコンフリクトは設計どおりゼロ

レーン = `i-1`、ワープ = `k-1` なので `k` はワープ一様。x の縮約が読む
`sQU(l+(k-1)*32)` はワープ内で同一アドレス（ブロードキャスト）、z の縮約が読む
`sQW(i+(l-1)*32)` は 32 連続 double、`sD1D(i+(l-1)*32)` は連続、
`sD1D(k+(l-1)*32)` はブロードキャストである。**swizzle は一切要らない。**

ncu で実測（job `58777`）:

| カーネル | shared wavefronts | ld コンフリクト | st コンフリクト |
|---|---|---|---|
| `..._p31_xz_kernel` | 1.119e8 | 121,470（**0.11%**） | 496,150（**0.44%**） |
| `..._p31_y_kernel` | 5.191e7 | 160,164（**0.31%**） | 283,985（**0.55%**） |

## 7. 予測と当否

作業前に立てた予測と、途中で設計を詰めた段階で立て直した予測の両方を記録する。

1. **「GEMM 経路は 550〜650 µs/stage に出る」 —— 外れ。** 実測 725.3 µs で、
   p=63 の 593.8 µs より**遅い**。転送量が Nq 非依存という §8 の性質は成り立っていたが、
   それを償却する演算量が p=63 の半分しかないという含意を読み違えていた。
2. **「融合カーネルが GEMM に勝つ」（当初）→「僅差で負ける」（設計後）—— 後者が当たり。**
   ただし理由は当たっていない。設計段階の見積もりは転送量 106 B/ノードで
   演算強度 2.0 FLOP/B というものだったが、**実測は 133.4 B/ノード、1.62 FLOP/B** で、
   GEMM 経路の 1.43 に対する優位は **1.13 倍**しかなかった（§9）。
3. **「交差点は p=31 と p=63 の間にある」 —— 外れ。** 交差点は **p=15 と p=31 の間**にある。
   p=31 では既に GEMM 側が勝っている。
4. **「`Nq <= 64` の cuBLAS x-GEMM 閾値は変わらない」 —— 当たり**（§10）。
5. **「`CutlassMmaShape` は動かない」 —— 当たり**（§10）。
6. **「側ストリームの `Nq >= 64` 閾値は p=31 では損の側」 —— 当たり**（§10）。

## 8. 理論仕事量と達成効率

1 ノードあたり体積 `6*Nq + 20` = **212 FLOP**、1 面点あたり 21 FLOP、
面点率 `6/Nq` = **18.75%**。16.78 M ノードで **3.6228 GFLOP/stage**。
仮定するピークは FP64 演算 40.1 TFLOP/s、帯域 7.92 TB/s（マシンバランス 5.06 FLOP/B）。

| | 転送量 [GB/stage] | B/ノード | 演算強度 | 達成 |
|---|---|---|---|---|
| `CUDAFORTRAN_GEMM`（最速） | ≒2.48 | ≒148 | 1.43 FLOP/B | 5.00 TFLOP/s（**12.5%**）/ 3.42 TB/s（43%） |
| `CUDAFORTRAN_FUSED`（新規、実測） | **2.238** | **133.4** | **1.62 FLOP/B** | 3.62 TFLOP/s（9.0%）/ 2.23 TB/s（28%） |
| （設計時の見積もり） | 1.78 | 106 | 2.00 | — |
| （p=15 型の理想融合） | 0.671 | 40 | 5.30 | — |

**同一 DOF 6 点の FP64 ピーク比は単調ではない。**

| p | 7 | 15 | **31** | 63 | 127 | 255 |
|---|---|---|---|---|---|---|
| ピーク比 | 13.0% | 14.9% | **12.5%** | 28.6% | 46.5% | 65.8% |
| 最速経路 | `FUSED_TC` | `FUSED_TC` | **`GEMM`** | `GEMM_FUSED` | `GEMM_FUSED` | `GEMM_FUSED` |

同一ビルド・同一 `nstep` で並べた 3 点は **434.8（p=15、CUDA core `FUSED`）→
725.3（p=31）→ 593.8（p=63）µs/stage** で、**p=31 は両隣より遅い曲線の極大点**である。
`p127_gap_study.md` が 5 点で観測した単調性は、6 点目を入れると崩れる。

## 9. なぜ p=31 が谷なのか

ncu（job `58777`、`--set full`）による素の `CUDAFORTRAN_GEMM` の内訳:

| カーネル | dur [µs] | DRAM% | SM% | L1/TEX% | 占有率% |
|---|---|---|---|---|---|
| `dqdt_assembly_kernel` | 146.9 | **91.4** | 39.5 | 45.1 | 82.7 |
| `volume_flux_kernel` | 135.7 | **83.3** | 43.2 | 69.4 | 80.2 |
| `elembnd_flux_kernel` | 113.6 | **81.2** | 12.8 | 61.9 | 85.2 |
| `separable_lift_kernel` | 182.8 | 6.8 | **68.5** | 50.6 | 91.4 |
| cuBLAS d884gemm ×3 | 110.5〜124.9 | 22.6〜25.5 | 46.6〜54.2 | **75.3〜89.7** | **23.8〜29.5** |

**3 本が DRAM の屋根に張り付いている。** GEMM 経路のノードあたり転送量は Nq に依存せず
（`volume_flux_kernel` は p=31 で 125.9 µs、同一実行ファイルの p=63 で 129.3 µs、
p=127 / 255 の記録は 129.0 / 129.3 µs —— **4 次数目でも成立**）、
一方で償却すべき演算量は `6*Nq+20` で Nq に比例する。
**p=31 は「Nq 非依存の転送量を、p=63 の半分の演算量で払わされる」点**である。
加えて `K = Nq = 32` は `TileK=16` で mainloop **2 反復**しかなく、
GEMM 自体も占有率 24〜30%、L1/TEX 75〜90% で効率が出ていない。

新規融合カーネルの側（job `58754`）:

| | dur [µs] | DRAM% | SM% | **L1/TEX%** | L1 hit% | L2 hit% |
|---|---|---|---|---|---|---|
| `..._p31_xz_kernel` | 666.6 | 18.5 | 39.4 | **84.4** | **0.38** | 9.8 |
| `..._p31_y_kernel` | 319.0 | 15.5 | 41.9 | **78.0** | 19.9 | 20.1 |

（dur は nsys の値。ncu 計装下の値はそれぞれ 1085 / 530 µs。）

**融合カーネルは DRAM でも演算でもなく L1/TEX で詰まっている。** 占有率 50% は
`Block Limit Registers` と `Block Limit Shared Mem` が**どちらも 1** で、
`p127_gap_study.md` §7 が CUTLASS について観測したのと同じ「両方に同時に張り付く」形である。
より本質的なのは **L1 ヒット率 0.38%** で、縮約を 1 要素ずつ shared 経由で回すため
shared wavefront が 1 stage あたり 1.64e8 本発生し、
**shared wavefront 1 本あたり 22 FLOP** にしかならない。
レジスタタイリングと mma で償却する CUTLASS / cuBLAS に対してここで負けている。

そして 2 パスに割ったことで `q` の再読み込みが L2 に当たらない
（1 要素 256 KB × 512 要素 = 134 MB の作業集合を流すため）。
**融合の転送量優位が 133.4 対 148 B/ノード = 1.13 倍まで縮んだ**のが、
p≤15 で効いた「融合すれば帯域が浮く」という論法が p=31 で成立しない直接の理由である。
p=7 では 40 対 148 = 3.7 倍あった。

| `UseCudaGraph` | `.true.` | `GEMM` −3.3%、`FUSED` −1.0% | 採用（既定は入力側） |

**側ストリームの `Nq >= 64` は、これで Nq ∈ {8, 32, 64, 256} の 4 点で確認できた。**
なお実装を読むと、この `Nq >= 64` の検査は `cuda_cal_dqdt_gemm`（素の GEMM 経路）
**だけ**にあり、`GEMM_CUTE`（`:936,:946,:959`）と `GEMM_FUSED`（`:1039,:1049,:1085`）は
`dg_side_enabled` を見るだけで `Nq` を見ていない。この 2 経路は Nq=32 で既に
側ストリームを使っている。

**x GEMM は p=63 の 1.59 倍より差が開いた。** `K` の深さと cuBLAS の優位の関係は
Nq=32 で 2 反復（+10.6%）、Nq=64 で 4 反復（+10.5%）、Nq=128 で 8 反復（±0.3%）、
Nq=256 で 16 反復（互角）となり、**閾値 `Nq <= 64` は 4 次数で裏が取れた**。

## 11. 結論

- **同一 DOF 族が 6 点で完結した。** p=31 の最速は **`CUDAFORTRAN_GEMM`**、
  Main **2.4403 ms/step** / **725.3 µs/stage**（graph on 2.3582、−3.3%）。
  `GEMM_FUSED` の 1.18 倍、`CUDAFORTRAN_SPLIT` の 3.4 倍速い。
- **p=31 は曲線の極大点である。** 同一ビルドで 434.8（p=15）→ **725.3（p=31）**
  → 593.8（p=63）µs/stage。同一 DOF で p=63 の半分の演算量しか無いのに
  p=63 より 1.22 倍遅い。FP64 ピーク比 12.5% は 6 点で最小で、
  **5 点で観測されていた単調性は 6 点目で崩れる。**
- **理由は「Nq 非依存の転送量を半分の演算量で払う」ことである。** GEMM 経路の
  3 本のカーネルが DRAM の屋根（81〜91%）に張り付き、GEMM 自体も `K=32` の浅さで
  占有率 24〜30% しか出ない。
- **融合が勝つ次数の上限は p=15 のままである。** 交差点は p=15 と p=31 の間にあり、
  p=63 と p=31 の間ではない。新規の `tendency_fused_p31_*_kernel` は
  1001.7 µs/stage で GEMM に 1.38 倍負けた。
- **負けた理由は設計の失敗ではなく、Nq=32 で融合の前提が崩れることである。**
  転送量優位は p=7 の 3.7 倍から **1.13 倍**（133.4 対 148 B/ノード）まで縮み、
  カーネルは L1/TEX 84% で詰まる（shared wavefront 1 本あたり 22 FLOP）。
  1 要素 256 KB を 2 パス間で保持できない以上、これは実装ではなく次数の性質である。
- **`Nq*Ne` の見積もり誤りを訂正した**（§2）。p=31 で CUTLASS 経路は使える。
- 次数依存ノブは 6 種類掃引して**採用ゼロ**（§10）。副産物として
  cuBLAS x-GEMM 閾値と側ストリーム閾値がそれぞれ 4 点で裏付けられた。

## 12. 残っている手

`p31_gap_study` の枠内では手が無い。融合カーネルを GEMM 経路に勝たせるには
**L1/TEX を通る shared wavefront を減らす**しかなく、それは縮約をレジスタタイリングと
mma に載せ替えるということ、すなわち CUTLASS を書き直すのと同じ作業になる。
GB200 では FP64 TC ピークが CUDA core ピークと等しいので、
`FUSED_TC` を Nq=32 に開いても命令数は減るが L1/TEX 圧は減らない
（`p15_gap_study.md` §9 が「mma は命令数を削るがレジスタは減らさない」と記録している）。

GEMM 経路の側は、3 本が DRAM の屋根に張り付いている以上、
`p63_gap_study.md` §11 と `p127_gap_study.md` §10 が挙げて否定した
「`volume_flux` を mainloop に畳む」案がこの次数では最も効きうる —— 
`volume_flux_kernel` と `dqdt_assembly_kernel` で 282.6 µs、tendency の 39% を占める。
ただしそれは本作業のスコープ（既存経路を p=31 に開いて測り、融合カーネルの
可否を決める）の外である。
