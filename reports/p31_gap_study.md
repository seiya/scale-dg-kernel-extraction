# p=31 (Nq=32) — 同一 DOF ギャップの 6 点目、そして曲線の極大点

測定環境: RIKYU NVIDIA GB200 1 GPU（152 SM）、`make CUDA=1 GPUFLAGS=-gpu=cc100`。
コミット: 本レポートを追加したコミット（親は `1c36e92`）。
実行ファイルは `scale-dg_extraction.p31` に凍結し、実測・nsys・ncu すべてで同じものを使った。
nsys は Slurm job `58753`（`job_nsys_p31.sh`）、ncu は `58754`（`job_ncu_p31.sh`、`--set full`）と
`58777`（`job_ncu_p31b.sh`、バンクコンフリクト実測と素の GEMM）。
入力: `conf_perf_p31*.conf`（`NeX=NeY=NeZ=8, PolyOrder=31, dt=1.0D-6, nstep=200,
UseCudaGraph=.false.`）。検証: `input_p31_val*.conf`（`Ne=2³`、`nstep=1`、
`SCALE_DG_VARYING_COEFF=1`）。

## 1. なぜ p=31 か

同一 DOF（16.78 M = 256³）を立方一様メッシュで保つ条件 `NeX*Nq = 256` から埋められるのは
p = 15, 31, 63, 127 の 2 冪だけで（`p15_gap_study.md` §1）、**p=31 が唯一の未着手**だった
（`p127_gap_study.md` §10）。`NeX=NeY=NeZ=8`、`Ne=512`、`Nq=32`、`NfpTot=6144`。
1 フィールド 134 MB、work 込みで約 1.6 GB。

ここを埋める意味は 2 つあった。**融合が勝つ p≤15 と GEMM が勝つ p≥63 の交差点が
p=31 に挟まっている**こと（`README.md`）と、Nq=32 が **1 要素の `q`（256 KB）が
227 KB/SM を超える最初の次数**であること（`p15_gap_study.md` §9）である。

## 2. 先行レポートの誤りの訂正 —— CUTLASS 経路は p=31 で使える

`p63_gap_study.md` §9 と `p127_gap_study.md` §10 は

> p=31 (Nq=32, `Ne=8³`) は未着手。`Nq*Ne = 262144` なので **CUTLASS 経路は使えず**

と書いていたが、**これは誤りである**。`Ne = 8³ = 512` なので `Nq*Ne = 32*512 = 16384` で、
`grid.z` batch 上限 65535 に十分収まる。262144 は `p63_gap_study.md` §2.3 の表の
**p=7（`Nq=8, Ne=32³`）の行の値**であり、それが p=31 の行に転記されていた。

**実測で確認した。** `CUDAFORTRAN_GEMM_FUSED` と `CUDAFORTRAN_GEMM_CUTE` は
`mod_advect3d_eq.f90:172,186` と `mod_cuda_dg_kernels.cuf:908,1007` のゲートを
素通りし、無改造で走って基準実装と一致した（§4）。

## 3. ホスト側で必要になった変更

**既存 5 経路（`OPENACC_SPLIT` / `CUDAFORTRAN_SPLIT` / `GEMM` / `GEMM_FUSED` /
`GEMM_CUTE`）はコード変更ゼロで走った。** p=63 の作業で入れた一般化がそのまま効いている:
`mod_mesh.f90:272` は `operator_data/p31.dat` が無いので `generate_lgl_operators` に落ち、
`dense_lift = (Nq <= 128)` が真なので `Lift_mat(32,32,32,6)` = 1.57 MB が実体化され、
`mod_dg_optr_kernel.f90` の 4 か所の `select case(Nq-1)` は `case default` に落ちる。
ERB の `AUTOGEN_PMAX = 15` は上げていない（p=31 の OPT1 特殊化が効くのは CUDA 経路ではなく
参照用の OpenACC/CPU 経路だけである）。

変更したのは `CUDAFORTRAN_FUSED` を p=31 に開く部分だけである:
`mod_advect3d_eq.f90:142`（設定時ゲート）と `:769`（実行時はしご）、
`mod_cuda_dg_kernels.cuf` のガードとディスパッチ、および新規カーネル 2 本。
**`CUDAFORTRAN_FUSED_TC` は開いていない**（`mod_advect3d_eq.f90:153,815` はそのまま）。
p=31 で選ぶと `CUDAFORTRAN_FUSED_TC requires PolyOrder=7, 15 or 255` で停止する。
`cuda_dg_kernels_tc.cu` に Nq=32 のカーネルが無いので、ゲートだけ開けても
`error stop` が後ろにずれるだけである。

> **（追記 2026-08-27）その後 §14 で開いた。** `cuda_dg_kernels_tc.cu` に
> Nq=32 のカーネル 2 本を起こし、`mod_advect3d_eq.f90:153,815,833` の
> ゲートを広げた。**p=31 の最速経路は `CUDAFORTRAN_FUSED_TC` である。**

> **（訂正 2026-08-27）当初ここに書いた「開かない根拠」は誤っていた。**
> 「GB200 では FP64 TC ピークが CUDA core ピークと等しいので書く根拠が無い」と
> 書いたが、**このカーネルは演算律速ではない**（§9: L1/TEX 84%、SM 39%、DRAM 18%）ので
> 演算天井の議論は当たらない。「TC の優位は Nq とともに伸びない（1.21 → 1.17 倍）」の
> ほうは有効な論拠だが、それだけである。
> **実測はむしろ TC を支持する。** §13.5 に測り直した内訳を置いた。

## 5. Nq=32 融合カーネルの設計

### 5.1 律速は shared ではなくレジスタファイルだった

`p15_gap_study.md` §9 は「Nq=32 以降は要素が shared に載らないので p=31 は別の構造
（タイル化）を要する」と書いていた。前半は正しいが、**実際に効いてくる制約は
shared メモリではなくレジスタファイルである**。

方向 `a` の縮約に対し、ブロックが所有するノード集合は `a` 方向の完全なペンシルで
なければ再読み込みが要る。`(a,b,c)` の箱を所有すると global 読み出しの冗長度は
x で `Nq/a`、y で `Nq/b`、z で `Nq/c` になり、**3 方向すべてで冗長度 1 になるのは
要素まるごとだけ**である。これが p=15 の設計が p=31 で使えない理由の正確な内容である。

しかし `sbuf` は**所有ノード集合を保持する必要がない**。x の縮約は一度に 1 枚の
`(l,k)` 平面（`Nq²` = 1024 double = **8 KB**）しか要らない。8 KB なら余裕で載る。
一方 1024 スレッド/ブロックでは 64 レジスタ/スレッド = **32 double** しか無く、
長さ `TJ` の累算配列を持つと `2*TJ` レジスタがそれだけで消える。
**設計問題は「要素を shared にどう載せるか」ではなく「方向をまたぐ長寿命の
累算器をどう避けるか」だった。**

### 5.2 x と z は同じスレッド写像を共有する

スレッドを `(i,k)`、`j` を内側**ループ**にすると:

- x（固定 j）: `Σ_l D1D(i,l)·f_x(l,j,k)` は `(l,k)` 平面 1024 値で足りる。
- z（固定 j）: `Σ_l D1D(k,l)·f_z(i,j,l)` は `(i,l)` 平面 1024 値で足りる。

**両方が同じ j 反復の中で完結する**ので累算器はスカラで済み、`j` を全長回しても
レジスタを消費しない。しかもスレッド `(i,k)` が読む `q(i,j,k)` は自分のノードで、
x 用と z 用に同じ値を再利用できる。y だけがこの写像に乗らないので第 2 カーネルに
別の写像（スレッド `(i,j)`、`k` を内側ループ）を与えた。

| | `tendency_fused_p31_xz_kernel` | `tendency_fused_p31_y_kernel` |
|---|---|---|
| grid / block | `<<<512,1024>>>` | `<<<512,1024>>>` |
| 静的 shared | **42496 B** | **16384 B** |
| レジスタ | **64**（スピル 0） | **44**（スピル 0） |
| 占有率 | 50.0%（理論 50%） | 50.0% |
| 担当 | x, z 体積項と**6 面すべて**の数値フラックスと lift | y 体積項を `dqdt` に加算 |

### 5.3 面フラックスをループ外に括り出す —— カーネルの 31%

最初の実装は面フラックスを j ループの中で計算していた。faces 2,4 は `(j,k)` 平面なので
`i==1` の 32 スレッドが、faces 5,6 は `(i,j)` 平面なので `k==1` の 32 スレッドが埋める形で、
**1024 スレッド中 32 本しか生きていない分岐を 32 回まわす**ことになる。

括り出して全 1024 スレッドで一度に評価する形に変えたところ、
**1287.4 → 1001.7 µs/stage（−22.2%）**。アブレーション（面 gather を丸ごと外した
不正な版）は 884.4 µs だったので、括り出し前は面フェーズが **403 µs = カーネルの 31%**、
括り出し後は約 28 µs である。総面点数は変わっていない。**変わったのは並列度だけ**である。

括り出しにあたり、faces 2,4 は `(j,k)` 平面なのでスレッド `(i,k)` が `j=i` の点を評価し、
j 反復では**ワープシャッフル**で取り出す（`k` がワープ番号なので必要なレーンは `j`）。
faces 5,6 は `(i,j)` 平面で別ワープに載るので shared 経由にした。
faces 1,3 は `(i,k)` 平面でスレッドが自分の点をちょうど 1 つ持つのでレジスタに置く。

> **CUDA Fortran の `__shfl` は 1-based である。** `__shfl(x,3)` は
> `threadIdx%x == 3` のスレッドの値を返し、`__shfl(x,0)` はレーン 32 に回り込む。
> 0-based のつもりで `j-1` を渡した版は、`Ne=2³` の検証で相対差が
> 2.08e-16 から **7.29e-15** に悪化して見つかった。O(1) の誤差にならないので、
> 粗い検証では見逃しうるバグである。

### 5.4 バンクコンフリクトは設計どおりゼロ

レーン = `i-1`、ワープ = `k-1` なので `k` はワープ一様。x の縮約が読む
`sQU(l+(k-1)*32)` はワープ内で同一アドレス（ブロードキャスト）、z の縮約が読む
`sQW(i+(l-1)*32)` は 32 連続 double、`sD1D(i+(l-1)*32)` は連続、
`sD1D(k+(l-1)*32)` はブロードキャストである。**swizzle は一切要らない。**

ncu で実測（job `58777`）:

| カーネル | shared wavefronts | ld コンフリクト | st コンフリクト |
|---|---|---|---|
| `..._p31_xz_kernel` | 1.119e8 | 121,470（**0.11%**） | 496,150（**0.44%**） |
| `..._p31_y_kernel` | 5.191e7 | 160,164（**0.31%**） | 283,985（**0.55%**） |

## 7. 予測と当否

作業前に立てた予測と、途中で設計を詰めた段階で立て直した予測の両方を記録する。

1. **「GEMM 経路は 550〜650 µs/stage に出る」 —— 外れ。** 実測 725.3 µs で、
   p=63 の 593.8 µs より**遅い**。転送量が Nq 非依存という §8 の性質は成り立っていたが、
   それを償却する演算量が p=63 の半分しかないという含意を読み違えていた。
2. **「融合カーネルが GEMM に勝つ」（当初）→「僅差で負ける」（設計後）—— 後者が当たり。**
   ただし理由は当たっていない。設計段階の見積もりは転送量 106 B/ノードで
   演算強度 2.0 FLOP/B というものだったが、**実測は 133.4 B/ノード、1.62 FLOP/B** で、
   GEMM 経路の 1.43 に対する優位は **1.13 倍**しかなかった（§9）。
3. **「交差点は p=31 と p=63 の間にある」 —— 外れ。** 交差点は **p=15 と p=31 の間**にある。
   p=31 では既に GEMM 側が勝っている。
4. **「`Nq <= 64` の cuBLAS x-GEMM 閾値は変わらない」 —— 当たり**（§10）。
5. **「`CutlassMmaShape` は動かない」 —— 当たり**（§10）。
6. **「側ストリームの `Nq >= 64` 閾値は p=31 では損の側」 —— 当たり**（§10）。

## 9. なぜ p=31 が谷なのか

ncu（job `58777`、`--set full`）による素の `CUDAFORTRAN_GEMM` の内訳:

| カーネル | dur [µs] | DRAM% | SM% | L1/TEX% | 占有率% |
|---|---|---|---|---|---|
| `dqdt_assembly_kernel` | 146.9 | **91.4** | 39.5 | 45.1 | 82.7 |
| `volume_flux_kernel` | 135.7 | **83.3** | 43.2 | 69.4 | 80.2 |
| `elembnd_flux_kernel` | 113.6 | **81.2** | 12.8 | 61.9 | 85.2 |
| `separable_lift_kernel` | 182.8 | 6.8 | **68.5** | 50.6 | 91.4 |
| cuBLAS d884gemm ×3 | 110.5〜124.9 | 22.6〜25.5 | 46.6〜54.2 | **75.3〜89.7** | **23.8〜29.5** |

**3 本が DRAM の屋根に張り付いている。** GEMM 経路のノードあたり転送量は Nq に依存せず
（`volume_flux_kernel` は p=31 で 125.9 µs、同一実行ファイルの p=63 で 129.3 µs、
p=127 / 255 の記録は 129.0 / 129.3 µs —— **4 次数目でも成立**）、
一方で償却すべき演算量は `6*Nq+20` で Nq に比例する。
**p=31 は「Nq 非依存の転送量を、p=63 の半分の演算量で払わされる」点**である。
加えて `K = Nq = 32` は `TileK=16` で mainloop **2 反復**しかなく、
GEMM 自体も占有率 24〜30%、L1/TEX 75〜90% で効率が出ていない。

新規融合カーネルの側（job `58754`）:

| | dur [µs] | DRAM% | SM% | **L1/TEX%** | L1 hit% | L2 hit% |
|---|---|---|---|---|---|---|
| `..._p31_xz_kernel` | 666.6 | 18.5 | 39.4 | **84.4** | **0.38** | 9.8 |
| `..._p31_y_kernel` | 319.0 | 15.5 | 41.9 | **78.0** | 19.9 | 20.1 |

（dur は nsys の値。ncu 計装下の値はそれぞれ 1085 / 530 µs。）

**融合カーネルは DRAM でも演算でもなく L1/TEX で詰まっている。** 占有率 50% は
`Block Limit Registers` と `Block Limit Shared Mem` が**どちらも 1** で、
`p127_gap_study.md` §7 が CUTLASS について観測したのと同じ「両方に同時に張り付く」形である。
より本質的なのは **L1 ヒット率 0.38%** で、縮約を 1 要素ずつ shared 経由で回すため
shared wavefront が 1 stage あたり 1.64e8 本発生し、
**shared wavefront 1 本あたり 22 FLOP** にしかならない。
レジスタタイリングと mma で償却する CUTLASS / cuBLAS に対してここで負けている。

そして 2 パスに割ったことで `q` の再読み込みが L2 に当たらない
（1 要素 256 KB × 512 要素 = 134 MB の作業集合を流すため）。
**融合の転送量優位が 133.4 対 148 B/ノード = 1.13 倍まで縮んだ**のが、
p≤15 で効いた「融合すれば帯域が浮く」という論法が p=31 で成立しない直接の理由である。
p=7 では 40 対 148 = 3.7 倍あった。

## 10. 次数依存ノブの掃引 —— 採用ゼロ

> **2026-09-02 訂正:** 「x GEMM を CUTLASS にすると +10.6%、閾値 `Nq<=64` は

> threadblock の N が Nq に当たり、汎用 64×128 タイルが N の `(128−Nq)/128` を
> 述語で捨てていたことである。次数専用タイル（Nq=32 は 32×32 / warp 16×16 / 3 stage）
> では **−1.64%（CUTE）/ −0.81%（FUSED）** で CUTLASS が勝つ。K は逆向きに効き、
> `TileK=32` は +0.42%。下の表は当時の測定として残す。

## 11. 結論

- **同一 DOF 族が 6 点で完結した。** p=31 の最速は **`CUDAFORTRAN_GEMM`**、
  Main **2.4403 ms/step** / **725.3 µs/stage**（graph on 2.3582、−3.3%）。
  `GEMM_FUSED` の 1.18 倍、`CUDAFORTRAN_SPLIT` の 3.4 倍速い。
- **p=31 は曲線の極大点である。**（**訂正: §14.2 で否定された。**同じ土俵で
  並べ直すと 6 点は単調である。）同一ビルドで 434.8（p=15）→ **725.3（p=31）**
  → 593.8（p=63）µs/stage。同一 DOF で p=63 の半分の演算量しか無いのに
  p=63 より 1.22 倍遅い。FP64 ピーク比 12.5% は 6 点で最小で、
  **5 点で観測されていた単調性は 6 点目で崩れる。**
- **理由は「Nq 非依存の転送量を半分の演算量で払う」ことである。** GEMM 経路の
  3 本のカーネルが DRAM の屋根（81〜91%）に張り付き、GEMM 自体も `K=32` の浅さで
  占有率 24〜30% しか出ない。
- **融合が勝つ次数の上限は p=15 のままである。**（**訂正: §14.1 で否定された。**
  正しくは「**CUDA core の**融合が勝つ上限が p=15」であり、Tensor Core の融合は
  p=31 でも `GEMM` に 1.67 倍勝つ。交差点は p=31 と p=63 の間にある。）
  交差点は p=15 と p=31 の間にあり、
  p=63 と p=31 の間ではない。新規の `tendency_fused_p31_*_kernel` は
  1001.7 µs/stage で GEMM に 1.38 倍負けた。
- **負けた理由は設計の失敗ではなく、Nq=32 で融合の前提が崩れることである。**
  転送量優位は p=7 の 3.7 倍から **1.13 倍**（133.4 対 148 B/ノード）まで縮み、
  カーネルは L1/TEX 84% で詰まる（shared wavefront 1 本あたり 22 FLOP）。
  1 要素 256 KB を 2 パス間で保持できない以上、これは実装ではなく次数の性質である。
  （**訂正: §14 で否定された。**転送量ではなく shared wavefront が律速であり、
  同じ 2 パス構造のまま縮約を mma に替えるだけで 2.66 倍になった。）
- **`Nq*Ne` の見積もり誤りを訂正した**（§2）。p=31 で CUTLASS 経路は使える。
- 次数依存ノブは 6 種類掃引して**採用ゼロ**（§10）。副産物として
  cuBLAS x-GEMM 閾値と側ストリーム閾値がそれぞれ 4 点で裏付けられた。

## 12. 残っている手（§13 の前に書いたもの）

> **（訂正 2026-08-27）本節の後半は誤りで、§13.5 と §14 が置き換える。**
> 「`FUSED_TC` を Nq=32 に開いても命令数は減るが L1/TEX 圧は減らない」と
> 書いたが、**shared wavefront は実測で 7.6〜9.1 分の 1 になり**（§14.3）、
> カーネルは **2.66 倍**速くなった（§14.1）。前半の「勝たせるには shared
> wavefront を減らすしかない」という診断のほうは正しく、それが §14 で実行された。
> なお「CUTLASS を書き直すのと同じ作業になる」も外れで、実際に要ったのは
> 平面ごとの縮約を m8n8k4 に置き換える 2 本のカーネルである。

`p31_gap_study` の枠内では手が無い。融合カーネルを GEMM 経路に勝たせるには
**L1/TEX を通る shared wavefront を減らす**しかなく、それは縮約をレジスタタイリングと
mma に載せ替えるということ、すなわち CUTLASS を書き直すのと同じ作業になる。
GB200 では FP64 TC ピークが CUDA core ピークと等しいので、

（`p15_gap_study.md` §9 が「mma は命令数を削るがレジスタは減らさない」と記録している）。

GEMM 経路の側は、3 本が DRAM の屋根に張り付いている以上、
`p63_gap_study.md` §11 と `p127_gap_study.md` §10 が挙げて否定した
「`volume_flux` を mainloop に畳む」案がこの次数では最も効きうる —— 
`volume_flux_kernel` と `dqdt_assembly_kernel` で 282.6 µs、tendency の 39% を占める。

### 13.1 lift と assembly の融合 —— 採用、**−12.0%**

§12 が名指しした 2 本のうち、`dqdt_assembly_kernel` の側に手がある。
`separable_lift_kernel` が書く `lift_out(Np,Ne)` を、次に走る
`dqdt_assembly_kernel` **以外に誰も読まない**。分かれていたのは

### 13.3 elembnd_flux の gather —— 着手前に潰した

残る最大の未飽和カーネルは `elembnd_flux_kernel`（111.4 µs、有効帯域 40% に対し
DRAM セクタ 81%、すなわち過剰フェッチ）である。**`volume_flux_kernel` に融合すれば
M 側の値は既にレジスタにあるので gather が消える**、という案を検討した。

演算を保ったままアドレスパターンだけを変えるアブレーションで見積もった:

| | Main [ms/step] | Δ |
|---|---|---|
| 基準 | 2.15474 | — |
| M 側のみ coalesced | 2.13937 | −0.7% |
| P 側のみ coalesced | 2.15279 | −0.1% |
| **両側 coalesced** | **1.97269** | **−8.4%** |

**片側だけ直しても効かない。** 散在している側が残る限りセクタの過剰フェッチが支配する。

### 13.5 `FUSED_TC` を Nq=32 に書く価値 —— 測って見積もった（未実装）

§3 の「開かない根拠」が誤っていたので、L1/TEX の中身を測り直した
（Slurm job `59145`、`l1tex__data_pipe_lsu_wavefronts_mem_shared/…` の明示指定）。

| カーネル | shared wavefront | LSU 総計 | shared の割合 | FLOP / shared wavefront |
|---|---|---|---|---|
| `..._p31_xz_kernel` | 1.120e8 | 1.283e8 | **87.3%** | **21.6** |
| `..._p31_y_kernel` | 5.19e7 | 5.721e7 | **90.7%** | **21.3** |

**L1/TEX を詰まらせているのは shared であって global ではない。**
これは p=15 の結論（「実際の律速は global ロードの L1/TEX トランザクション」、
`p15_gap_study.md` §12）とは別の状態である。

手計算とも合う: 内側ループ 1 反復あたり warp は 6 wavefront を出す
（`sD1D(i+…)` 連続 2 + `sQU(l+…)` broadcast 1 + `sD1D(k+…)` broadcast 1 +
`sQW(i+…)` 連続 2）。16384 warp × 32 j × 32 l × 6 = 1.007e8 で、実測 1.120e8 に一致する。

**mma はここを直接攻める。** m8n8k4 の FP64 mma は 1 warp 命令で 512 FLOP を出し、
オペランドは A 32 + B 32 double = 512 B = 4 wavefront なので **128 FLOP/wavefront**、
現状の 21.6 に対し **5.9 倍**である。shared wavefront が 5.9 分の 1 になれば
LSU 総計は 3.7 分の 1 になり、L1/TEX は 72% から **20% 前後**まで落ちる。
その先で律速になるのは DRAM で、転送量 2.24 GB/stage に対し
ピークの 65% なら **435 µs/stage** である。

**それでも勝てるとは限らない。** `CUDAFORTRAN_GEMM` の 631 µs/stage を
CUDA core 版の 1001.7 µs から上回るには **1.59 倍**が要るが、
手書き TC がこれまで実際に出した倍率は **p=7 で 1.21、p=15 で 1.17** である。
差が理論値（p=15 でも命令数は SM 36.0% → 19.8% に落ちていた）ほど出ないのは、
`p15_gap_study.md` §11 が記録するとおり **mma は命令数を削るがレジスタは減らさず、
占有率 50% の壁が残る**ためで、p=31 の 2 本も
`Block Limit Registers` と `Block Limit Shared Mem` が**どちらも 1** の同じ状態にある（§9）。

まとめると、**律速の所在は TC 書き換えを支持し、前例 2 点は否定する。**
必要 1.59 倍に対し前例は 1.21 倍で、賭けとしては分が悪い。
本作業では書いていない。書くとすれば `cuda_dg_kernels_tc.cu` に
Nq=32 用の 2 本（`(i,k)` 写像と `(i,j)` 写像）を新規に起こす作業で、
p=15 の TC カーネルの swizzle をそのまま流用はできない（`NQ15` 前提のため）。

## 14. `FUSED_TC` を Nq=32 に書いた —— §13.5 の賭けは当たった（採用）

と `59388`（バンクコンフリクト）。入力は `conf_perf_p31*.conf`

> 使用率 90% 前後にあり、そこで測ると全経路が一律に 22% 遅く出た

> §13.1 が記録した 631.3 と 0.7%、`FUSED` 995.1 は 1001.7 と 0.7% 一致する。

### 14.1 結論を先に —— p=31 の最速経路が入れ替わり、極大点は消えた

### 14.4 §13.5 の予測の採点 —— 数は当たり、機構の説明は外れ

1. **「shared wavefront が 5.9 分の 1 になる」 —— 当たり**（実測 7.65 / 9.10 分の 1）。
2. **「L1/TEX が 72% から 20% 前後まで落ちる」 —— 外れ。** 実測は 84.4% → **76.2%**
   にしか落ちていない。shared を 7.6 分の 1 にしたのに L1/TEX が下がらないのは、
   **global 側の wavefront が逆に 1.7 倍に増えた**からである
   （xz で 1.63e7 → 2.81e7）。j を 2 スラブに割ったぶん face 1,3 を 2 回評価し、
   ブロックあたりのスレッドが 1024 から 512 に減っている。
   **L1/TEX に占める shared の割合が 87% から 34% に替わっただけで、L1/TEX 自体は
   依然として天井に近い。**
3. **「その先で律速になるのは DRAM で 435 µs/stage」 —— 方向は当たり、値は保守的すぎた。**
   DRAM は 18.5% → 45.3%（xz）/ 15.5% → 64.3%（y）に上がり、実測は **374.8 µs/stage** で
   見積もりより速い。

   実測 **2.66 倍**。前例 2 点が低かったのは、p=7 / p=15 では

   **「TC の優位は Nq とともに伸びない」という §3 の唯一残っていた論拠も、

### 14.5 実装

`cuda_dg_kernels_tc.cu` に 2 本と launcher 1 本。ホスト側は
`mod_cuda_dg_kernels.cuf`（interface とディスパッチ）と
`mod_advect3d_eq.f90:153,815,833` のゲートだけである。

構造は CUDA core 版の踏襲で、平面ごとに回し、y を第 2 カーネルに分ける。
固定 j での仕事は 32×32×32 の GEMM 2 本:

```
x: C(i,k) = Σ_l D(i,l) · FU(l,j,k)      z: C(i,k) = Σ_l FW(i,j,l) · D(k,l)
```

Nq=32 が Nq=8 / 16 より易しい点が 2 つある。

1. **x と z の出力添字が同じ (i,k) である。** `sDz` に相当する
   アキュムレータの shared 往復が存在せず、§5 / 本ファイル先頭が記録した
   「16 B ストアはコンフリクトを消すが GB200 では遅い」というトレードオフも起きない。
   ただし `Escale` は方向ごとに違うので**アキュムレータ対は 2 組**必要で、
   1 本の鎖にまとめると O(1) の誤りになる。
2. **転置形にすると D1D 側のフラグメントが j に依存しない。**
   x の B オペランドも z の A オペランドも `D[8*t + lane/4][4*ks + lane%4]` で、
   16 double をレジスタに置いて j ループ全体で使い回せる。

ブロックは 512 スレッド（16 warp、8×8 タイル 4×4）、**1 要素を j で 2 スラブに割る**。
理由は shared ではなく波の効率で、152 SM に対し 512 ブロックは 4 波（84%）、
1024 ブロックは 7 波（96%）である。重複するのは j に依存しない face 1,3 の評価だけ。

swizzle は **1 本**で足りる:

```c
sw31(idx) = idx ^ (((idx >> 5) & 3) << 2)
```

どのパネルも `low + 32*high` で並び、mma オペランド読みでは縮約添字と
タイル行が 2 つのフィールドに分かれて入るので、**アドレス bit 2-3 が phase 不変、
bit 5-6 がレーンとともに変動する**という同じ形になる。x パネル、z パネル、
y パネル、および face 2,4 平面がこれで conflict free になる（p=15 は 3 本要した）。
face 5,6 は (i,j) 平面で j がループ一様なので既に 4-way ブロードキャストであり、
**当てても得が無いので当てていない**（§10.4 の戒め）。

face 1,3 は (i,k) 平面で、`(スレッド, {0,1}) → i0 + 32*kout` と `+1` が
**512 スレッド×2 点から 1024 面点への全単射**なので、各スレッドが自分の消費する
2 点をそのまま評価する。再配布は不要で、gather は warp あたり 64 B × 8 本になる。
face 2,4 を warp shuffle で配る案は、TC 写像では `k` が warp 一様でなく
レーンあたり 32 レジスタを食ううえ結局 shared 往復が要るので採らなかった。

`q,u,w`（y カーネルは `q,v`）の平面ロードは **j+1 を先に発行**する。
xz カーネルは占有率 25%（`Block Limit Registers` と `Block Limit Shared Mem` が
どちらも 1、レジスタ 126、shared 42496 B）で、重ねる相手のブロックが無い。

`-Xptxas -v`: xz は 126 レジスタ / 42496 B shared、y は 64 レジスタ / 8192 B shared、
**どちらもスピル 0**。shared 使用量は CUDA core 版 xz の 42496 B と偶然一致する。

### 18.4 閉じた筋と残さない理由

- **面 2,4 の M 側 coalesced 化**は天井 −17.8% あるが、実装可能な 2 形
  （ループ内 2 レーン / 先行フル平面ステージ）はどちらも **+25.6%**。
  体積パスの通りがかりに端だけ書く p=15 の形は、こちらでは面を
  **全 j についてプロローグで**使うため先に平面が揃っていない。
  追加パスを払うと賞金が負ける。§20.4 の p=63 面ギャザーと同様、
  契約を保ったまま取る手は残っていない。
- **mma を減らす**天井 −28.4% は演算そのもの。GB200 では FP64 TC ピークが
  CUDA core と同じなので、命令形状を変えて屋根は上がらない。
- **`Escale` / 体積平面**は既に double2 で、後者は j+1 プリフェッチ済み。
  隠す変更は `lg_throttle` を悪化させる。
- **xz の占有率 25%→50%** は 128 レジスタ × 512 スレッドで 2 ブロックが
  レジスタファイルに入らない。64 本に落とすとスピルする。
- y は既に 2 ブロック/SM。ストアコンフリクトを消しても 0%。

**契約の中で実装できる候補の天井は、測ったものが全部「差が無い」か
明確な赤字になった。** p=31 `FUSED_TC` の探索を終了する。

他次数への横展開は採用変更が無いので無し。面 2,4 をループ内で評価する
手が p=15 で効いた理由（既読平面の端、フルワープ）は Nq=32 の 2 スラブ
mma 写像では成り立たない、というのが今回の次数をまたぐ負の結果である。

## 19. §18 のあと、残っていた高天井を追加で落とした（2026-08-30）

§18 の終了宣言のあと、面 2,4 の天井 −17.8% と xz 占有率 25% に対して
まだ形の違う実装が残っていたので続けた。カーネルはすべて落として
`9a2b887` に戻した。最速は `CUDAFORTRAN_FUSED_TC` のまま。検証はいずれも
`SCALE_DG_VARYING_COEFF=1`、`Ne=2³`、owned `dqdt` 対 `CUDAFORTRAN_SPLIT` で
max abs 2.665e-15。採否は占有 GPU、12 回交互 A/B（基準バイナリ
`scale-dg_extraction.p31tc`）。

p=127 §11.10 のスウィズル代数簡約は **p=31 では既に入っている**。mma
オペランドは `sw31(colk + 32*kout) ^ (4*ks)` と
`sw31((ti*8+row)+32*colk) + 128*ks` で、畳み込み場が `ks` に依らないことの
恒等変形である。追加の手ではない。

### 19.2 これで閉じたこと

- 面 2,4 は契約内の最大ブロック（−17.8%）だが、実装可能な 4 形
  （ループ内 2 レーン / 先行フル平面 / 体積端+`v`+遅延評価 / 体積端+`v`なし）
  は +25.6% / +25.6% / ±0 / +31.5%。**ゼロより良い点は無い。**
- xz を 2 ブロック/SM にするには 64 レジスタが要る。配列のままではスピル、
  D1D を shared に移すと occupancy 2 のコンパイル上限に当たる、global
  再読では `lg_throttle` が増える。**25% → 50% は取れない。**
- 面 gather のキャッシュヒントは体積とフィールドを共有しているので、
  streaming は体積側を傷つける。

体積平面を `cp.async` で隠す手は天井がアブレーション −4.3% しかなく、
同じ L1 窓に global を足す変更は既に `Escale` 前出しで +2.3%、p=63 では
`Escale` の `cp.async` が +6.9% である。実装しても符号が逆になる側に
載っている。

**契約の中で天井が測定誤差を超える候補は、測った形が全部尽きた。**
カーネルソースは §18 開始時と同じである。

## 20. CUDA-core 融合の最適化（2026-08-30）

親 `9a2b887`、GB200、`make CUDA=1 GPUFLAGS=-gpu=cc100`（nvcc `-arch=sm_100`）、
`conf_perf_p31_fused.conf`（`Ne=8³`、`nstep=200`、graph off）。採否の時間は
Slurm job `69623`（node c390）の 12 回交互 A/B。ncu は job `69607`（改修前）
と `69624`（改修後）、`--set full`、`conf_perf_p31_fused_ncu.conf`。

`CUDAFORTRAN_FUSED` だけを対象にした。`FUSED_TC` / `FUSED_DFMA` の fragment
日程は触っていない。

### 20.1 改修前の律速

ncu（job `69607`）: xz 1077 µs / y 528 µs。L1/TEX **85% / 78%**、DRAM 19% /
16%、SM 40% / 41%、占有率 50%（1024 スレッド、レジスタ 64 / 44）。stall の
支配は **mio_throttle 55% / 52%**（CPIStall: shared の細いロードが MIO を
詰まらせている。ncu の提案は「fewer but wider loads」）。

1 文: **両カーネルは長さ 32 の shared 内積の MIO で律速している。**

### 20.2 採用

交互 A/B 中央値（device fused tendency、597 stage）:

| | Main [ms/step] | device [s] | µs/stage |
|---|---:|---:|---:|
| 改修前（Fortran 移植、1024 スレッド） | 3.234 | 0.59254 | **992.5** |
| 改修後 | 2.415 | 0.42876 | **718.2** |

**−27.6%**（レンジ非重複）。点変化係数の owned `dqdt`（`Ne=2³`）は改修前
CC と**ビット一致**、`CUDAFORTRAN_SPLIT` に対する最大絶対差は 2.66e-15。

効いた変更（1 つずつ、いずれも自然順・長さ `Nq` の内積のまま）:

1. **`__restrict__`**（−0.4%）。p=31 `FUSED_TC` の −4.0% より小さい。CC は
   alias 解析ではなく MIO が支配だから。
2. **スレッドを 512 にして隣接 2 点を `double2` で持つ** + **要素あたり 2
   ブロック（j / k スラブ 16）**。単独の 512 スレッドは占有率 25% で時間は
   動かず、スラブを足して初めて xz −7.4%、続けて y に同じ写像を入れて
   **通算 −19.6%**（0.5937 → 0.4772）。機構: ワープが 16 B の連続 shared /
   global ロードを出し、ncu が要求した wider load になる。面 2/4 はレーン
   `i` が偶数だけなので `__shfl` を `(tid&16)+(j>>1)` と偶奇成分に組み替えた。
3. **xz の次平面 `q,u,w` を内積の前にレジスタへ先読み**（−8.0%、0.4772 →
   0.4389）。j 平面の global ロードが 32 回の inner product の裏に隠れる。
4. **末尾バリアを最終反復で省略**（−0.2%）と **y パネルの二重バッファ**
   （バリア 2 本/面 → 1 本、−0.2%）。小さいがビット一致。
5. **xz パネル `sQU`/`sQW` の二重バッファ**（動的 shared 58880 B、バリア 2 →
   1 本/面、−1.7%、0.4373 → 0.4288）。

改修後の ncu（job `69624`）: xz 847 µs / y 342 µs、命令 122.2 M → 88.5 M と
60.9 M → 41.5 M。L1/TEX は **91% / 91%** に上がり、mio_throttle は 52% /
62% のまま。**律速の種類は変わっていない。速くなったのは同じ MIO 仕事を
16 B ロードと少ないバリアで払うようになったこと。** xz はレジスタ 126 で
1 ブロック/SM（占有率 25%）、y は 64 レジスタで 2 ブロック/SM（46%）。

µs/stage 718.2 は 5.05 TFLOP/s（ピーク 12.6%）、unique DRAM 1.67 TB/s
（21.1%）。最速は `FUSED_TC` 359.7 のまま。論文の主比は **2.00×**。
改修後の CC は iso-schedule DFMA（790.1 µs）より **1.10× 速い**。

> §14 が書いた「TC は CUDA core 融合の 2.66 倍」は当時の 374.8 / 1001.7 である。
> いまの device 時間どうしでは 359.7 / 718.2 = **2.00 倍**。

### 20.4 残りの天井

役割であり、fragment 日程を `FUSED` に持ち込まない。

**契約内で実装できる候補の天井は測った。探索を終了する。**

## 25. y を xz の PDL 従属にする（2026-09-01、採用 −0.76%）

p=31 の `FUSED_TC` は面フラックスを xz カーネルの j ループ外で評価するので
1 stage は **xz → y の 2 グリッド**しかない。したがって p=127 / p=63 の
「面 → xz」の段は該当せず、**y を xz の PDL 従属にする最後の段だけ**が当たる。

コミットは本節を追加したもの、GPU は RIKYU GB200、入力は
`namelists/perf_p31_fused_tc.conf`（`Ne=8³`、`nstep=200`、`WarmupStep=1`、

### 25.1 wait の位置

xz が書く `dqdt` を y が読むのは、エピローグ用 `sDQ` への `cp.async` 先読み
（§19.4 由来の 2 段バッファ）の**最初の 1 本だけ**である。`wait` はその直前に
置いた。`launch_dependents` は xz 側の**面フェーズ直後のバリアの後**、

### 25.3 効いた理由と効き方の上限

§18–19 で確定している律速は xz が `lg_throttle`、y が `mio_throttle` で、
どちらも SM 内の発行資源である。PDL が動かすのはそこではなく
**グリッド境界の隙間とドレイン**で、p=63 §50.3 の nsys が示したのと同じく
「xz の CTA が抜けた SM から y を流し始める」ことだけを買っている。

p=63 で同じ段が −0.2〜−1.5%、p=31 で −0.76% と同じ桁なのは整合的である。
両者とも xz が 1 stage の半分強を占め、y はその後ろにぶら下がっている。
p=127 の y PDL が −2.71% と大きいのは xz が 1024 スレッド × 64 レジスタで
SM を占有し切るため、ドレインの尾がそもそも長いからで、p=31 の xz は
1 ブロック/SM・グリッド 2·Ne = 1024 CTA と細かく、尾が短い。

### 26.1 何を変えたか（§20.4 の範囲外案との違い）

`mod_mesh.f90` の Fmask は面 2 に `(Nq-1) + Nq*fp`、面 4 に `Nq*fp`
（0-based、`fp = j + Nq*k`）を入れる。p=31 の xz カーネルで面 2,4 を作る
スレッドは `pl = (j0+jl) + 32*kk` をすでに持っているので、M 側のノード番号は

ハローなので `VMapP` のまま。**`q`/`u`/`v`/`w` は毎回すべての面点で読む**ので、
`p63_gap_study.md` §20.4 が閉じた「速度を面点ごとに事前計算する」案（呼び出し間で
速度が変わらないという仮定）とは別物である。

`-DDG_CHECK_DIRECT_M24` を付けたビルドで直アドレスと `VMapM[idx]-1` を全面点で
突き合わせ、`Ne=2³` で**不一致 0**。

数値検証: `SCALE_DG_VARYING_COEFF=1`、`namelists/val_p31_split.conf` の
`CUDAFORTRAN_SPLIT` 参照で owned `dqdt` 全点 **max abs 2.66e-15（相対 4.48e-16）**、
変更前バイナリとは**ビット一致**。

ではなくレイテンシで詰まっている」と書いた側面の、逆向きの証拠になっている。

## 29. CUDA graph 再生を p=7 / 15 / 31 で測る（2026-09-01、`GEMM_FUSED`、実測 −1.4〜−3.2%）

本節に p=7 / 15 / 31 の 3 次数分をまとめる（[`p15_gap_study.md`](p15_gap_study.md)
と [`p7_gemm_fused.md`](p7_gemm_fused.md) からここを参照）。

対象は `CUDAFORTRAN_GEMM_FUSED`。親 `c386c85`、GPU は RIKYU GB200 1 枚、
Slurm job `75947`（占有ノード c398）。**カーネルは 1 バイトも変えていない**。
動かしたのは namelist の `UseCudaGraph` だけである。

出所は [`p63_gap_study.md`](p63_gap_study.md) §43–44（p=63 で Main **−1.29%**、
side stream を残して **−1.97%**）。低次数ほどカーネルが短くローンチ比が
大きいので効きやすい側にあたる。§44 以降、graph 時も side stream は
落とさない（`main.f90`）ので、ここで測るのは「side stream 込みの graph」対
「side stream 込みの直接ローンチ」である。

### 29.1 測り方

`Cal_tend` と `CUDA device *` は graph 再生では出ない（ラッパを通らないので
イベントが記録されない）。判定は **`Step loop per stage`** で行う
（`main.f90` の `timer_step_loop`。計測対象ステップの前後を `!$acc wait` で
挟むので stage の取りこぼしが無く、graph 再生でも出る）。`Main per step` も
併記する。

conf は各次数の `namelists/perf_p{7,15,31}_gemm_fused.conf` の `Ne` / `PolyOrder`
/ `dt` を据え置き、`nstep = 200`, `WarmupStep = 1` に揃えたコピーを
graph off / on の 2 本作って使った（`NeX/NeY/NeZ`, `PolyOrder`, `dt` は
両アームで同一。p=7/15 の公開 conf は `nstep=20` = 19 measured step しかなく、
1% 未満を判定できないため両アームとも 200 に揃えた）。graph 経路では
`WarmupStep` は自動で 2 に昇格する（step 1 が直接ローンチ、step 2 が capture）。
12 回交互。

### 29.2 結果

`Step loop per stage`（秒）:

| p | graph off 中央値 | レンジ | graph on 中央値 | レンジ | 差 |
|---|---:|---|---:|---|---:|
| 7 | 1.79704e-3 | 1.79613e-3..1.80062e-3 | **1.77117e-3** | 1.76966e-3..1.77379e-3 | **−1.44%** |
| 15 | 7.32704e-4 | 7.32210e-4..7.33334e-4 | **7.09523e-4** | 7.08513e-4..7.10685e-4 | **−3.16%** |
| 31 | 7.93716e-4 | 7.93252e-4..7.94818e-4 | **7.71301e-4** | 7.70490e-4..7.72210e-4 | **−2.82%** |

（−1.437% / −3.157% / −2.816%）で、p=15 の graph off に 1 点だけ跳ねた
外れ値（2.1976e-3）があるほかはレンジも分かれている。

p=63 の −1.29%（§43、side なし）／−1.97%（§44、side 込み）と並べると、

### 29.3 機構 —— ローンチ本数ではなく「1 ステージの長さ」で決まる

1 ステップは 9 本のローンチで、次数によらず本数は同じである。graph 再生が
消すのはそのホスト側の enqueue コストだから、**得は絶対時間でほぼ一定**で、
率は 1 ステージが短いほど大きくなるはずである。実測の絶対差を並べると:

| p | 1 stage | graph の得（絶対） |
|---|---:|---:|
| 7 | 1797 µs | 25.9 µs |
| 15 | 733 µs | 23.2 µs |
| 31 | 794 µs | 22.4 µs |
| 63（§44 の Main から） | 650 µs | 12.8 µs |

**p=7/15/31 で 22〜26 µs とほぼ一定**で、モデルどおりである
（`overall_summary_report.md` §8.2 がホスト同期を外したあとに残ると測った
50 µs/step = 16.7 µs/stage と同じ桁）。率が p=7 で最小になるのは
得が小さいからではなく、**p=7 の 1 ステージが 1797 µs と 3 次数で最も長い**
（`Ne=32^3` の大きいメッシュを使う公開 conf のため）からである。
p=63 で得が半分になるのは、そこでは elembnd を side stream に出す形が
別で、隠せる隙間が既に減っているためと読める。

### 29.4 数値

graph 再生と直接ローンチは同じカーネルを同じ順で流すので、期待値はビット一致。
`SCALE_DG_VARYING_COEFF=1`、`nstep=4`、`dqdt(:,1:Ne)` 全点:

| p | 点数 | graph vs 直接 | graph vs `CUDAFORTRAN_SPLIT` |

### 29.5 既定 conf は graph off のまま

`namelists/` の既定は変えない。理由は 3 つとも測定に関するもので、性能ではない:

- graph 再生では `Cal_tend` / `Volume derivate + surface lift` /
  `CUDA device *` が**すべて出ない**（`overall_summary_report.md` §8.3）。
  公開表と各 gap study の µs/stage はこれらを分母にしている。
- `nsys` は graph 経路に当てられない（ハングし GPU trace が空になる）。
- `p63_gap_study.md` §43 が同じ理由で既定を off に据え置いており、
  次数間で既定を割るのは比較を壊す。

`UseCudaGraph = .true.` は namelist の 1 行で誰でも on にできる。
**「p=7/15/31 の `GEMM_FUSED` は end-to-end で 1.4〜3.2% 速くできる。ただし
その実行では内訳が測れない」**が本節の結論である。最速カーネルは
p=7 / 15 / 31 とも変わらない。

## 30. ワープ mma タイル拡大とチャンクループ二重バッファ（2026-09-02、採用ゼロ）

`TODO.md` §2.1 の項目。`p63_gap_study.md` §52.3 が明文化した符号則
——「二重バッファが効くかどうかはチャンク数で決まる。p=255 は 16 個で
**−27.7%**（`p255_gap_study.md` §4.1）、p=127 は 2 個で **−4.25%**
（`p127_gap_study.md` §23.3）、p=63 は 1 個で **+2.8〜3.1% で棄却**」——を
p=31 `CUDAFORTRAN_FUSED_TC` に当てた。TODO は `p31_gap_study.md` §18.3 の
「ループが 16 回回る」を根拠に p=31 を 16 チャンク側に置き、**符号則が
最大の勝ちを予測する側**としていた。

**結論を先に: 採用ゼロ。** (a) ワープタイル拡大は単独 **+1.11%**、
(b) 二重バッファは単独 **+1.04%**、**組は +12.05%** で、非加法性は
p=255 / p=127 とは**逆向き**（組が単独の和よりはるかに悪い）に出た。
最速は `CUDAFORTRAN_FUSED_TC` のままで、`reports/README.md` の p=31 行と
主比 B は変わらない。

### 30.1 TODO の前提の訂正 —— p=31 のチャンク数は 16 ではなく 1

符号則の「チャンク」は**縮約 (k) 方向のパネル分割**である
（p=127 の `BKD127`、p=255 の `BK255`、p=63 の `BK63`）。p=31 の xz カーネル
が 16 回回すループは `jl`、すなわち **j 平面のバッチループ**であって、
縮約の分割ではない。Nq=32 の縮約 32 個は 1 枚の shared 平面
（`sFU` / `sFW`、各 1024 double）に丸ごと載っており、`ks` の 8 反復は
その 1 枚の中を歩くだけである。**p=31 の縮約チャンク数は 1 で、符号則が
予測する側は p=63 と同じ「棄却」**だった。

§18.3 の表の「チャンクループ末尾バリアの前送り」も同じ `jl` ループの話で、
そこで +0.58% だったのは本節の (b) が +1.04% であることと整合する。
**符号則そのものは反証されていない。誤っていたのは p=31 のチャンク数の
読み方である。** これで符号則の 4 点目が埋まる:

| 次数 | 縮約チャンク数 | 二重バッファ | 判定 |
|---|---:|---:|---|
| **p=31** | **1**（本節） | **+1.04%** | **棄却** |
| p=63 | 1 | +2.8〜3.1% | 棄却 |
| p=127 | 2 | −4.25%（2×4 タイルと組で） | 採用 |
| p=255 | 16 | −27.7%（4×4 タイルと組で） | 採用 |

### 30.2 何を実装したか

コミットは本節を追加したもの（親 `0c7f39d`）。GPU は RIKYU GB200、ビルドは
`make CUDA=1 GPUFLAGS=-gpu=cc100`（nvcc `-arch=sm_100`）。Slurm ジョブは
時間が `77439`（c384、8 変種同居、12 ラウンド）と `77447`（c384、5 変種、
12 ラウンド）、ncu が `77440`（c384、3 変種同居）。入力は
`namelists/perf_p31_fused_tc.conf`（`Ne=8³`、`PolyOrder=31`、`nstep=200`、
`WarmupStep=1`、graph off）。µs/stage は `CUDA device fused tendency` ÷ 597。

`fused_kernel_geom.h` に p=127 と同じ形のノブを足し、xz / y の両カーネルを
ワープタイルで一般化した:

- `P31_XZ_TM` / `P31_XZ_TN`（`P31_Y_TM` / `P31_Y_TN`）: 1 ワープが持つ
  8×8 mma タイルの数。**ブロックタイルは両カーネルとも 32×32 の出力平面
  そのもの**なので、ワープタイルを広げると warp 数がその分減り、
  スレッド数と占有率が従属して決まる。16 タイル ÷ `TM*TN` がワープ数。
- `P31_XZ_DB` / `P31_Y_DB`: 平面ループを
  `store(jl+1) → mma(jl) → epilogue → barrier` の二重バッファ形にする。
  バリアが平面あたり 2 本から 1 本になる（xz でスラブあたり 33 → 18 本）。
- `P31_XZ_DYN`: shared を静的から動的に切り替える。二重バッファは
  57.5 KB で静的上限 48 KB を超えるので **`DB=1` は `DYN=1` を強制する**。
  これを独立のノブにしたのは §30.4 の理由による。
- `P31_XZ_MINB`: `__launch_bounds__` の第 2 引数（レジスタ予算）。
- `P31_XZ_EARLY`: 最初の平面 global ロードを面バリアの手前に出すか後に
  出すか（§30.5）。

オペランド比は設計どおり動く。1 `ks` ステップあたり、xz は
`TM+TN` 本の shared ロードで `2*TM*TN` 本の mma、y は `TM` 本で `TM*TN` 本:

| xz ワープタイル | ワープ | スレッド | ロード/mma | 蓄積器 [double] |
|---|---:|---:|---:|---:|
| 1×1（現行） | 16 | 512 | 1.00 | 4 |
| 2×1 / 1×2 | 8 | 256 | 0.75 | 8 |
| **2×2** | **4** | **128** | **0.50** | 16 |
| 4×1 / 1×4 | 4 | 128 | 0.625 | 16 |
| 4×4 | 1 | 32 | 0.25 | 64 |

x が i 方向、z が k 方向にオペランドを共有するので、**両方向を同時に
効かせるには i と k の両方を広げるしかない**（i だけ広げると z の
`sFW` ロードが、k だけ広げると x の `sFU` ロードがタイル数ぶん増える）。
これが 2×2 が 2×1 / 1×2 より良い理由であり、`TM*TN=4` が 128 スレッドを
意味する理由でもある。

読み方は 3 つある。

1. **(b) が負ける理由は命令である。** 二重バッファはねらいどおり
   barrier stall を 1.09 → 0.865 に下げ、バリアはスラブあたり 33 → 18 本に
   減っている。ところが**発行命令が 36.91 M → 41.37 M（+12.1%）**増える。
   バッファ添字 `cur` が実行時の値になるため、`sFU`/`sFW` の
   ベースが即値オフセットに畳めなくなり、8 `ks` × 2 本の LDS すべてに
   アドレス演算が付く。p=31 の xz は**バリアで詰まっていない**
   （barrier stall 1.09 は `lg_throttle` 6.26 の 6 分の 1）ので、
   買うものが小さく代金が大きい。§18.3 が「消えるのは 32 本中 1 本」で
   +0.58% だったのと同じ収支が、17 本消しても成り立っている。
2. **(a) は設計どおり効いているのに、効いた資源が律速ではない。**
   shared ld ウェーブフロントは 12.22 M → 5.98 M（**−51.1%**、
   オペランド比 1.00 → 0.50 の予測とぴったり）、命令は −16.2%、
   L1/TEX は 78.6% → 68.8%、`lg_throttle` は 6.26 → 1.62 に落ちる。
   **それでも実時間は +1.11%。** 代金は 2 つで、(i) 占有率が
   24.99% → 11.86% に半減してレイテンシ隠蔽のワープが減ること、
   (ii) **global セクタが 49.46 M → 48.41 M とほぼ動かないのに DRAM read が
   1157 → 1296 MB（+12.0%）に増える**こと。同じ要素の 2 スラブが面 1,3 を
   共有しているが、1 CTA が 128 スレッドになって 4 倍長く走るため、
   その再利用が L2 の寿命から外れる。**L1/TEX を空けても、空いた先に
   DRAM が入ってくる。**
3. **これは `ncu` のクロック固定バイアスの新しい例でもある。** (a) は
   `ncu` の duration で **−1.9%**（350.9 → 344.2 µs）だが、占有 GPU の
   実時間では **+1.11%**（レンジ非重複、12/12）。`AGENTS.md` が書くとおり、
   `ncu` は shared・命令の削減を高く、global の待ちを安く見積もる。
   本節の (a) はまさに「shared と命令を減らして DRAM を増やす」変更で、
   符号が反転する条件を満たしている。`p63_gap_study.md` §19.10 / §20.3 /
   §20.6 の 6 例に 7 例目が加わる。

**(a)+(b) が +12.05% になる理由**も同じ 2 つの合成である。2×2 タイルは
すでに 255 レジスタで、二重バッファのアドレス演算が乗る先のレジスタが
無い。さらに shared が 57.5 KB になって 128 スレッドの CTA が SM あたり
1 個に固定されたまま、命令だけが増える。p=127 では二重バッファが
「広いタイルで失った占有率の穴を埋める」役だったが、p=31 では
**埋める穴が global レイテンシではなく命令発行**なので、同じ道具が効かない。

### 30.5 占有率前提の再検証 —— §19.2 / §27.1 は結論として正しく、理由は違った

§19.2 は「xz を 2 ブロック/SM にするには 64 レジスタが要る。配列のままでは
スピル、D1D を shared に移すと occupancy 2 のコンパイル上限、global 再読では
`lg_throttle` が増える。**25% → 50% は取れない**」と閉じ、§27.1 は
「512 スレッドでは 128 レジスタが天井で、xz の占有率 25% は**動かせない
前提**である」と書いた。`p127_gap_study.md` §23.9 は同じ形の宣言に対して
「**塞がっていたのは占有率であって性能ではなかった**」として、
**占有率を上げる方向ではなく下げる方向に解く**ことで −4.25% を取っている。
`TODO.md` §2.1 はこの逆向きの解法を p=31 に当てることを求めていた。

本節で当てた結果:

- **レジスタ予算は本当に作れる。** 128 スレッド（2×2 タイル）では
  `65536/128 = 512` が予算なので ptxas は上限の **255 レジスタを spill 0 で**
  使う。§27.1 の「128 レジスタ天井」は **512 スレッドという構成の性質**
  であって、p=31 xz というカーネルの性質ではなかった。この意味で
  §23.9 の指摘は p=31 にも当てはまる。
- **占有率は本当に下げられる。** 24.99% → 11.86%。`MINB` を上げて
  戻そうとすると（128 スレッド × `MINB=4`）128 レジスタに切られて
  **672 B スピル**し +58% になる。p=255 §4.1 の「当たりくじではなく
  スピルしない最大の占有率」がここでも成り立つ。
- **しかし性能は付いてこない。** 予算を作り、占有率を下げ、
  オペランド比を 1.00 → 0.50 にし、shared ウェーブフロントを半分にし、
  命令を 16% 減らして、**実時間は +1.11%**。

したがって **§19.2 / §27.1 の結論（xz の占有率は動かせない、25% のままで
良い）は今も正しい**が、**その理由は書かれていたものと違う**。書かれて
いた理由は「レジスタ予算が無い」だった。測ってみると予算は作れる。
本当の理由は **p=31 xz が shared / 命令ではなく global リクエストと
DRAM で詰まっており、ワープを減らすと隠蔽が減るうえに L2 再利用まで
落ちる**ことである。§23.9 の「塞がっていたのは占有率であって性能では
なかった」は p=127 では成り立ち、**p=31 では成り立たない**。
差は律速で、p=127 xz は `long_scoreboard` 11.37 の global 待ちを
二重バッファで隠せたのに対し、p=31 xz の `lg_throttle` 6.26 は
**リクエスト数そのもの**で、隠す相手ではない（§19.1 の
`ld.global.cs` +17.5% がすでに同じことを言っている）。

### 30.7 副産物 1 —— 最初の平面ロードを面バリアの手前に出すと +1.40%

一般化の途中で、改修前と数値も命令ミックスもほぼ同じなのに 1.5% 遅い形が
できた（job `77447`、c384、12 ラウンド交互、0.211912 → 0.214869、
**+1.40%**、レンジ非重複）。原因は**最初の `q,u,w` の `double2` ロードを
面フェーズの `__syncthreads()` の手前に出したこと**だけだった（SASS は
LDG 137 / LDS 26 / DMMA 16 / BAR 3 で改修前と同数、レジスタ 128 → 127）。
戻すと改修前と一致する（§30.3 の 1 行目と 2 行目）。

これは §18.1 の診断（xz は `lg_throttle` で律速、L1/TEX 79%）の直接の帰結
である。面ギャザーがこのカーネルの L1/global 窓を埋めているところに
平面ロードを 3 本足すと、面フェーズがその分だけ延びる。§18.3 の
「xz エピローグの `Escale` を mma の前へ出す **+2.3%**」と同じ形の、
**「このカーネルに global ロードを前送りすると必ず負ける」**という
3 例目である。ノブ `P31_XZ_EARLY` として残し、既定は後ろ（0）。
**ただし符号は構成で変わる**: 2×2 タイル（128 スレッド、LDIT=4）では
前送りの方が速く、§30.3 の (a) はその側で測っている。

二重バッファ形はプロローグで平面 0 を shared に置く必要があるため、
本来この前送りを強いられる。それを避けるためにバリアを 1 本足す形
（スラブあたり 18 本）を採ったので、§30.3 の (b) の数字は
この 1.40% を含んでいない。

### 30.8 副産物 2 —— 静的 shared から動的 shared への変換だけで +1.70%

二重バッファは 57.5 KB で静的上限 48 KB を超えるので動的 shared が要る。
それが (b) の測定に混ざらないよう `P31_XZ_DYN` を独立のノブにして測った:
**PTX 上は同じ仕事で、静的 42.5 KB を動的 42.5 KB に変えるだけで +1.70%**
（0.211967 → 0.215567、レンジ非重複）。動的 shared はベースアドレスが
実行時の値になるので、LDS / STS が即値オフセットに畳めない。

**符号は構成で変わる。** 2×2 タイルでは逆に**動的の方が 1.5% 速い**
（静的 0.217621 対 動的 0.214326）。255 レジスタまで使い切っている
構成では、即値オフセットを畳むためにコンパイラが払うレジスタの方が
高くつく。したがって §30.3 の (a) の代表値には動的の方を採った
（(a) にとって有利な側を採っている）。

### 32.5 §30 との整合 —— これは 8 例目の同じ話である

§30.5 は「p=31 xz が動かない本当の理由は、shared でも命令でもなく

読み方は 3 つ。

1. **時間についていくのは DRAM バイトであって、セクタでも要求でもない。**
   セクタは**ほぼ加法的**に減る（M 側 −3.80 M、P 側 −3.41 M、両方 −7.73 M、
   和 −7.21 M とほぼ一致）のに、時間はまったく加法的でない
   （−4.71% / −2.53% / −17.22%）。DRAM read を見ると理由がそのまま出る:
   **片側だけでは 1156.8 → 1124.0 / 1144.1 MB（−2.8% / −1.1%）しか動かず、
   両方同時に消して初めて 851.2 MB（−26.4%）になる。**
   §30.5 / §32.5 が「p=31 xz は shared でも命令でもなく **global リクエストと
   DRAM** で詰まっている」と書いた、その DRAM の側である。
2. **なぜ片側では動かないか。** 面 2 の M 側は要素 `e` の `i=31` 列であり、
   面 4 の P 側は要素 `e+1` から見た同じ `i=31` 列である（`Fmask` は
   面 2 に `(Nq-1) + Nq*fp`、面 4 に `Nq*fp` を入れる）。
   **launch 全体から見ると、M 側が引くラインの集合と P 側が引くラインの集合は
   同じ**である —— どの要素の `i=0` / `i=31` 列も、自分のブロックからは M 側として、
   x 方向の隣 2 ブロックからは P 側として要求される。片側を coalesce しても、
   同じラインは隣のブロックがもう片側として引き続き要求するので、
   **DRAM から出てくるバイト数は変わらない**。両方を要素内に閉じた
   （`F24=3`）ときに初めて、そのラインが launch から消える。
3. **`lg_throttle` も同じ形で折れる。** §18.1 が xz の律速として挙げた
   `lg_throttle` は片側だけでは 26.25 → 22.25 / 24.91 としか動かず、
   両側で **4.68** に落ちる。律速が動いたのは両側版だけである。
   （`F24=3` / `F24=1` で `long_scoreboard` が 19 に上がるのは、
   `lg_throttle` が退いたあとに露出した global レイテンシで、
   §11.5 / §13.5 が p=7 で見たのと同じ入れ替わりである。）

**これが 5 形すべてに共通する敗因である。** どの形もブロック内で触れるのは
M 側だけであり、M 側の賞金は 4.71%、しかもその 4.71% は
**DRAM を 2.8% しか減らさない**（1156.8 → 1124.0 MB）。
律速資源をほとんど動かさない賞金に対して、5 形はいずれも
**global トラフィックか発行効率をそれ以上に悪くする代金**を払っている。

- **§26 の部分説明で全額説明できるのは 5 形目だけ**である。5 形目は
  そもそも coalesce を狙っていない（stride 32 のまま）ので、賞金はゼロ、
  代金は `VMapM` の MLP、差し引き赤字 —— これで閉じる。
  現行 HEAD の再測は **+1.50%**（§26 の +2.48% と同符号。ノードと commit が
  違うので大きさが違う。§26 の値は当時の測定として残す）。
- **1〜4 形は §26 では説明できない。** これらは実際に coalesce を狙っており、
  §26 の「`VMapM` を消したこと」は代金の一部でしかない。
  本節が足したのは**賞金の側の上限**である: 狙いが完全に成功しても
  **−4.71%**、DRAM で言えば **−2.8%** しか動かない。
  そのうえで 2〜4 形は **coalesced な global トラフィックを新たに足している**。
  §30.7 の「このカーネルに global ロードを前送りすると必ず負ける」
  （3 例）と §18.3 の `Escale` 前出し +2.3% が示すとおり、
  **このカーネルで global を足す変更は例外なく赤字**なので、
  −2.8% の DRAM 削減で +12〜44% の DRAM 増を買う取引が成立する余地は無い。
- 1 形目だけは global を足さないが、代わりに**ワープ効率を 2/32 にする**。
  賞金 4.71% に対して 16 倍の非効率であり、これも桁で負ける。

### 33.5 §30 / §32 との整合

本節は §30.5 / §32.5 の結論の 3 つ目の確認になっている。

- §30 は **命令 +12.1% で遅くなる**側（二重バッファ）を、
  §32 は **命令 −6.3% で速くならない**側（バンクコンフリクト消去）を測った。
  本節は **shared も命令もほとんど動かさずに DRAM だけを 26% 動かすと
  17% 速くなる**側を測った（`F24=3`: 命令 −1.7%、shared wavefront ±0.2%、
  占有率不変、DRAM −26.4%、時間 −17.22%）。
  **3 方向から同じ結論**が出るので、定数オフセットではない。
- §18.2 の「P 側 gather 全部（`iP=iM`）で −5.0%」と本節の
  `F24=3` −17.22% は矛盾しない。§18.2 の `iP=iM` は **P の要求を消すが
  アドレスは M 側のストライドのまま**なので、ラインの集合は変わらない。
  `F24=3` は**両方を要素内の連続アドレスに**しており、そこで初めて
  ラインが消える。§33.3 の 2 番がその差である。
- `ncu` の duration（349.9 → 280.5 µs、−19.8%）は実時間 −17.22% より
  やや大きい。DRAM を減らす変更なので、クロック固定バイアスが
  **global の待ちを安く見積もる**向き（`AGENTS.md`）と一致する。
  採否は §33.2 の実時間で判断している。
