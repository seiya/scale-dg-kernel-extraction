# p=15 (Nq=16) — p=7 と p=255 の間を同一 DOF で埋める

測定環境: RIKYU NVIDIA GB200 1 GPU、`make CUDA=1 GPUFLAGS=-gpu=cc100`。
コミット: 本レポートを追加したコミット（親は `e8e1885`）。
ncu は Slurm job `54662`（`job_ncu_p15.sh`、CUDA core 版）、
`55485`（`job_ncu_p15tc.sh`、Tensor Core 版）、
`55570` / `55602`（`job_ncu_p15face.sh`、生カウンタ、第 10 節の前後）、
`55691`（`job_ncu_occ.sh`、第 11 節の占有率実験）、
`56768`（第 12 節のベクトル化後）。
入力: `conf_perf_p15.conf`（`NeX=NeY=NeZ=16, PolyOrder=15, nstep=20, UseCudaGraph=.false.`）と
`conf_perf_p7.conf` 相当（`NeX=32, PolyOrder=7`、同 `nstep`）。
検証: `input_p15_val.conf` / `input_p15_val_tc.conf` と `NeX=4` 版、
いずれも `SCALE_DG_VARYING_COEFF=1`。

## 1. なぜ p=15 なのか

同一 DOF（16.78 M = 256³）を立方一様メッシュで保つ条件は `NeX * Nq = 256`、
すなわち **Nq が 256 の約数**である。これで候補は 2 冪だけに絞られ、
p = 15, 31, 63, 127 の 4 点しかない。FP64 mma が要求する M,N の 8 倍数・K の 4 倍数は
Nq≥8 の 2 冪なら自動的に満たされるので、**DOF 固定の条件のほうが Tensor Core の
条件より強い**。Nq=12 や 24 のような「TC 的に半端な次数」は検討する前に落ちる。

この 4 点のうち p=15 を最初に取った理由:

- 1 要素の `q` は Nq=8 で 4 KB、**Nq=16 で 32 KB**、Nq=32 で 256 KB。
  227 KB/SM を構造的に超えるのは Nq=32 からなので、**要素まるごとを shared に置く
  設計が通用する最後の点**である。
- 面点率 `6/Nq` が 75% → **37.5%** に落ちる。p=7 の律速だった gather と lift の
  比重が半減する。
- 融合時の理想演算強度 `6*Nq/40` FLOP/B が 1.2 → **2.4** になる。
  GB200 のマシンバランス 5.0 FLOP/B の半分弱。
- `operator_data/p15.dat` が既にある（16 + 256 + 24576 = 24848 値、
  `D1D(1,1) = -60 = -15*16/4`）。p=31 以降と違い LGL 演算子の生成が要らない。

## 2. ホスト側は既に Nq 汎用だった

`main.f90` / `mod_mesh.f90` / `Makefile` / `operator_data/` は**変更不要**。
`OPENACC_ASIS`, `OPENACC_SPLIT`, `CUDAFORTRAN_SPLIT`, `CUDAFORTRAN_GEMM` は
コード変更ゼロで p=15 が走る。`CUDAFORTRAN_FUSED` だけが**独立した 3 層**の
ガードで閉じていた: `mod_advect3d_eq.f90` の設定時チェックと実行時分岐、
および `mod_cuda_dg_kernels.cuf` のラッパ。

p=15 の数値は 4 つの独立実装で一致することを先に確認した
（`CUDAFORTRAN_SPLIT` を基準、`Ne=2³`、点ごと変動係数）:

| 実装 | 基準との相対差 |
|---|---|
| `CUDAFORTRAN_GEMM` | 0（ビット一致） |
| `OPENACC_SPLIT` | 1.26e-15 |
| `OPENACC_ASIS` | 1.26e-15 |

## 3. `tendency_fused_p15_kernel`

p=7 の `tendency_fused_p7_kernel` は**一切変更していない**。
32 レジスタ / 8 ブロック/SM に追い込んだ調整（`tc_paper_survey_2407.09621.md` §8）を
壊す理由がないため、Nq=16 は別カーネルとして書いた。

### shared memory 戦略

p=7 の構成をそのまま Nq=16 にすると
`sFluxX/Y/Z` 3 × 4096 × 8 B = 96 KB + `sflux_bnd` 12 KB + `sD1D` 2 KB + `sLift` 0.75 KB
= **約 111 KB/ブロック**で、48 KB の静的 shared 上限を超え carveout の opt-in が
必須になる。`tc_paper_survey_2407.09621.md` §13.4 が記録した **+31%** の罠がこれである。

採用したのは **Nq³ のスクラッチバッファ 1 本を方向ごとに使い回す**構成:

- 各スレッドは担当ノードの `q` を**レジスタに保持**（要素あたり 1 回だけロード）
- フェーズ X: `u` をロードして `buf = q*u` → 収縮 → `Escale_x` を掛けて累算
- フェーズ Y / Z: `v` / `w` で同じことを同じ `buf` に対して行う
- 面フェーズ: 同じ `buf` の先頭 `6*Nq²` を面流束として使い回す
- epilogue: lift を足して `dqdt` へ

global ロードは `q,u,v,w` 各 1 回ずつで**理論最小のまま**、shared は
`32768 (buf) + 2048 (sD1D) + 768 (sLift)` = **35584 B** で静的 shared に収まる
（実測 `cuobjdump -res-usage` で `SHARED:35584 LOCAL:0`）。
代償は `syncthreads` が 1 回から 7 回に増えることと、3 方向が直列化すること。

### スレッド割り当てとバンクコンフリクト

1 ブロック 1 要素、**1024 スレッド、4 ノード/スレッド**。
スレッド `tid` はノード `tid, tid+1024, tid+2048, tid+3072` を持つ。
これらは `(i,j)` を共有し `k` が 4 プレーンずつ違う。

この割り当てだと**レーンが `i` 方向に並び、収縮添字 `l` は warp 内で一様**になるので、
**swizzle なしで 3 方向とも conflict free** になる:

- x 収縮 `buf(l + (j-1)*16 + (k-1)*256)` は `i` に依存しない → half-warp 全体が
  同一アドレス → ブロードキャスト
- y 収縮 `buf(i + (l-1)*16 + (k-1)*256)` は `i` のみに依存 → 16 連続 double
- z 収縮 `buf(i + (j-1)*16 + (l-1)*256)` も同様に 16 連続 double

`cuda_dg_kernels_tc.cu` の `sw_xy` / `sw_z` が必要だったのは、TC カーネルでは
**レーンが収縮添字に対応する**（mma のフラグメント配置がそう要求する）ためであり、
CUDA core 版では割り当ての自由度でそれを回避できる。

## 4. 検証

すべて `SCALE_DG_VARYING_COEFF=1`（点ごとに変動する `u,v,w,Escale,normal_fn,Fscale`）で、
完全な `dqdt(:,1:Ne)` を比較した。

| ケース | 基準 | 相対差 |
|---|---|---|
| `Ne=2³` | `CUDAFORTRAN_SPLIT` | 2.10e-16 |
| `Ne=4³` | `CUDAFORTRAN_SPLIT` | 4.16e-16 |
| `Ne=4³` | `OPENACC_ASIS` | 1.37e-14 |
| `Ne=2³` 定速度 | `CUDAFORTRAN_SPLIT` | 2.50e-16 |

`OPENACC_ASIS` との差が 2 桁大きいのは総和順序の違いによるもので、
他の実装間の差と同じ性質である。CUDA ビルドと非 CUDA ビルドの両方が通ることも確認した。

## 6. 理論仕事量と達成効率

理論値（1 RK stage あたり、`Nq³*Ne = 16.78 M` DOF）。
体積は 1 ノードあたり `6*Nq + 20` FLOP（3 方向の収縮 `3*2*Nq`、流束積 3、
`Escale` 5、lift 11、最終和 1）、面は 1 面点あたり 21 FLOP。

| | p=7 | p=15 |
|---|---|---|
| 体積 FLOP/ノード | 68 | 116 |
| 面点/要素 | 384 | 1536 |
| 理論 FLOP / call | 1.405e9 | 2.078e9 |
| 理論 DRAM バイト / call | 1.577e9 | 1.326e9 |
| **ncu 実測 DRAM バイト / call** | **1.598e9** | **1.361e9** |

実測が理論の 1.01〜1.03 倍で、**面 gather はほぼ全てキャッシュで吸収されている**。
DRAM トラフィックに無駄はない。

達成効率（ncu ではなく通常実行の device 時間を使用。GB200 のピークは
FP64 CUDA core = FP64 TC = 40.1 TFLOP/s、DRAM 約 7.9 TB/s）:

| | TFLOP/s | ピーク比 | TB/s | ピーク比 |
|---|---|---|---|---|
| p=7 `FUSED_TC` | 5.14 | 12.8% | 5.84 | 74% |
| p=7 `FUSED` | 4.24 | 10.6% | 4.83 | 61% |
| p=15 `FUSED` | 4.79 | 11.9% | 3.14 | **40%** |

**演算強度が倍になった分、p=15 は帯域の壁からは離れた（74% → 40%）。
しかしそれを FLOP レートに変換できておらず、ピーク比は 12% 前後に張り付いたままである。**

## 8. 不採用にした 2 つの調整

**`launch_bounds(1024,2)`**: レジスタは 62 → **32、spill ゼロ**で通った
（`cuobjdump` で `LOCAL:0` を確認）。にもかかわらず device
26.03 → **27.81 ms（+6.8%）**。`Block Limit Shared Mem` が 1 のままなので
ブロック数は増えず、レジスタを削った分だけアドレス再計算が増えただけだった。

**さらに carveout 50% を要求**: device **28.18 ms（+8.2%）**。
`tc_paper_survey_2407.09621.md` §13.4 と同じ結果である。
占有率を上げるにはレジスタと shared の**両方**の制限を同時に外す必要があり、
このカーネルの生きた状態（4 累算器 + 4 個の `q` = 16 レジスタ分）を考えると
32 レジスタで 2 ブロックを成立させる余地は無い。両方とも差し戻した。

## 9. Tensor Core 版 `tendency_fused_p15_tc_kernel`

第 7 節の結果を受けて TC 版を実装した。判断の根拠は天井の比較である。
融合カーネルの DRAM 転送量は理論最小の 1.03 倍なので、カーネルを分割して
占有率を稼ぐ案は必ず転送量を増やす側にしか動かない。3 カーネル分割
（面流束 → xy → z+lift）を見積もると約 2.23 GB/call = 1.64 倍で、
仮に 6.5 TB/s で回っても 343 µs が下限になる。一方 TC 版は転送量を
1.361 GB のまま保てるので、p=7 TC の実績 5.84 TB/s に届けば 233 µs になる。
**分割案の最良値が TC 版の天井に届かない**、というのが優先順位の理由である。

### 設計

shared 戦略は CUDA core 版と同じ「バッファ 1 本を方向ごとに使い回す」を流用した。
これは TC かどうかと直交する話なので、事前調査が TC 移植の最大の障壁と見ていた
「3 本の流束パネルで 96 KB」という問題は、この時点で既に解決済みだった。

m8n8k4 のタイルは 8x8 だが Nq=16 のプレーンは 16x16 なので、
1 プレーンあたり出力タイル 4 枚・k ステップ 4 回になる（p=7 は 1 枚・2 回）。
1 warp が 1 プレーンの j 半分（i は両半分）を持ち、レーンあたりの出力は
`i = tn*8 + 2*colk` とその隣で 4 ノード、CUDA core 版と同じ 4 ノード/スレッドになる。

**フラグメント配列は 3 方向で共用できる**。x は B オペランド `D[i][l]`、
y は A オペランド `D[j_out][j_in]`、z は A オペランド `D[k_out][l]` として読むが、
どの場合もレーンが欲しいのは `D[tile*8 + row][colk + 4*ks]` なので、
`(tile, ks, row, colk)` で引く 1 つの配置で足りる。

**swizzle は 1 本で x と y の両方を賄える**。x はパネルを
`(i = colk + 4*ks, j = tm*8 + row)` で読むので colk がビット 0-1、row がビット 4-5 に入り
ビット 2-3 が死んで 4-way になる。y は `(i = tn*8 + row, j = colk + 4*ks)` で
役割が入れ替わるだけの同じ絵なので、**ノードのビット 4-5 をアドレスのビット 2-3 に
畳む 1 つの関数**で両方直る（`sw_xy15`）。Nq=8 の `sw_xy` を 1 ビット広げた形である。
k ステップのオフセットは x がビット 2-3、y がビット 6-7 で、
どちらも `sw_xy15` が読まないビットなので、swizzle 後のアドレスに対する
単なる XOR のままでよい。

### 検証

| ケース | 基準 | 相対差 |
|---|---|---|
| p=15 TC `Ne=2³` | `CUDAFORTRAN_SPLIT` | 2.10e-16 |
| p=15 TC `Ne=4³` | `CUDAFORTRAN_SPLIT` | 1.30e-14 |
| （対照）p=7 TC `Ne=4³` | `CUDAFORTRAN_SPLIT` | 3.37e-15 |
| （対照）p=7 CUDA core `Ne=4³` | `CUDAFORTRAN_SPLIT` | 0（ビット一致） |

TC 版だけ差が大きいのは mma の 4 項内積が総和順序を変えるためで、
**p=7 でも同じことが起きている**（CUDA core 版はビット一致、TC 版は 3.4e-15）。
収縮長が倍になれば誤差も増えるので Nq=16 で 1.3e-14 は想定内であり、
既存の `OPENACC_ASIS` と `CUDAFORTRAN_SPLIT` の差 1.37e-14 と同じ大きさである。
差の分布も滑らかで（1e-14 超が 262144 点中 12 点、1e-13 超はゼロ）、
局所的な破綻ではない。

### 結果

| | 1 stage | TFLOP/s | ピーク比 | TB/s | ピーク比 |
|---|---|---|---|---|---|
| p=7 `FUSED` | 331.0 µs | 4.24 | 10.6% | 4.83 | 61% |
| p=7 `FUSED_TC` | 273.6 µs | 5.13 | 12.8% | 5.84 | 74% |
| p=15 `FUSED` | 433.9 µs | 4.79 | 11.9% | 3.14 | 40% |
| **p=15 `FUSED_TC`** | **347.7 µs** | **5.98** | **14.9%** | **3.91** | **50%** |

ncu（Slurm job `55485`、クロック固定）:

| メトリクス | p=15 `FUSED` | p=15 `FUSED_TC` |
|---|---|---|
| Duration | 679.4 µs | 543.1 µs |
| **Compute (SM) Throughput** | **36.0%** | **19.8%** |
| Memory Throughput | 74.1% | 67.3% |
| DRAM Throughput | 25.3% | 31.6% |
| Executed IPC | 0.89 | 0.64 |
| Registers / thread | 62 | 64 |
| Achieved Occupancy | 49.2% | 48.9% |

**TC は狙いどおり SM 側の仕事をほぼ半減させた**（36.0% → 19.8%）。
mma はオペランド 1 回の読み出しを 8x8 タイル全体の演算に効かせるので、
CUDA core 版で 1 shared ロードにつき 1 FMA だったものが大幅に減る。
device 時間はその分だけ縮んで **26.04 → 22.22 ms（1.17 倍）**。
第 10 節の swizzle 2 本と第 12 節のベクトル化を入れた最終形は
**20.86 ms（1.249 倍）**である。

**しかし帯域は使い切らなかった**（47%）。残った律速は memory pipe 67% で、
DRAM が 32% しかないこととの差は shared アクセスとキャッシュに載る global
アクセス（特に面 gather）である。占有率は 48.9% のまま動いていない。

### TC の優位は Nq とともに伸びるか

**伸びない。** CUDA core 版に対する TC 版の比は p=7 で 1.21 倍、p=15 で 1.17 倍で、
ほぼ横ばいかむしろわずかに縮んでいる。理由は両方の次数で**演算パイプが律速ではない**
ことにあり、p=15 で SM throughput が 19.8% まで落ちてなお速くならないことがそれを示す。
TC が効くのは演算能力ではなく命令数であり、命令数を削り切った後に出てくるのは
メモリ経路と占有率という別の壁である。

### Nq=16 の融合カーネルは構造的に占有率 50% で頭打ちである

CUDA core 版と TC 版が**どちらも 49% で並んだ**のは偶然ではない。

1. z 収縮が要素全体を要求するので、1 要素 = 1 ブロックで、shared に 32 KB の
   バッファが要る。
2. ブロックあたり最大 1024 スレッドなので、4096 ノードに対し **4 ノード/スレッドが下限**。
3. 4 ノード分の累算器と `q` を持つと 32 レジスタには収まらない
   （実測 62 と 64）。1024 スレッドでの上限である 64 レジスタに TC 版は**ちょうど張り付いており**、
   レジスタの余裕はゼロである。
4. レジスタが 32 を超えると `Block Limit Registers` が 1 になり、
   carveout を広げて shared 側の制限を外しても 2 ブロック目は載らない（第 8 節の実測）。

したがって **Nq=16 では、融合したままで占有率を上げる道は
「レジスタを 32 本に絞り、かつ carveout を広げる」以外に無い**。

> **補足（第 11 節）**: 上の 1〜4 の構造的事実はそのまま正しいが、
> 当初この節はそれを**律速の説明**として書いていた。第 11 節でその条件を
> 実際に満たす版を作って測ったところ、占有率 96.7% を達成したうえで
> **8.0% 遅かった**。つまりこの壁は存在するが、**乗り越える価値が無い**。

## 10. 面 gather の調査と、そこで見つかったバンクコンフリクト

第 9 節末が次の標的に挙げた「memory pipe 67% と DRAM 32% の差」を追った。

### 面 gather はアブレーションで上限を測ってから捨てた

要素の節点順序は `i + 16j + 256k` なので、`i` を固定する面（面 2 と 4、すなわち ±x）は
**本質的に 16 double = 128 B ストライド**になり、1 レーンが 1 キャッシュラインを占める。
p=7 で `tc_paper_survey_2407.09621.md` §13 が M 側を shared に置いて −5.1% を得たのは
この構造に対する対策だった。

Nq=16 で同じ投資に見合うかを、**±x 面の gather アドレスを連続アドレスに差し替える
アブレーション**（数値は壊れるが命令数は不変）で先に測った:

| 版 | device 時間 | 基準比 |
|---|---|---|
| baseline | 22.30 ms | — |
| ±x 面の **M 側**を連続化 | 21.85 ms | **−2.0%** |
| ±x 面の **M と P 両方**を連続化 | 20.08 ms | −9.9% |
| 面フェーズを丸ごと削除 | 14.44 ms | −35.2% |

読み取れることは 3 つ:

1. **p=7 の手法をそのまま持ってきても上限 2.0%**。面点率が 75% → 37.5% に落ちた分だけ
   価値も落ちている（p=7 の実測 −5.1% の半分以下）。しかも Nq=16 では
   1024 スレッド時のレジスタ上限 64 本に張り付いていて、
   `u,v,w` を面用に保持する余地が無い。shared に逃がすには
   `q,u,v,w` で 16 KB 必要で 48 KB の静的枠を超え、`qM` と `VelM` だけに絞っても
   8 KB とバリア 1 回と 3 フェーズにまたがるステージング処理が要る。
   **上限 2.0% に対して割に合わないので不採用**とした。
2. **P 側の方が大きい（差分 7.5%）が、隣接要素のデータなので原理的にステージングできない。**
   面 2 の P 側は +x 隣接要素の `i=0` 面で、そちらも同じくストライドしている。
3. **面フェーズはカーネルの 35%（約 131 µs/stage）を占めるが、外に出すと損をする。**
   同じ仕事を単独カーネルでやる `CUDAFORTRAN_SPLIT` の Element boundary flux は
   p=15 で約 166 µs/stage かかっている。融合カーネルの中では直前に読んだ体積データが
   キャッシュに残っているぶん安く済んでおり、外出しは `flux_bnd` の往復
   （+100 MB/stage）も足して確実に悪化する。

### 代わりに見つかったもの: shared load の 4-way コンフリクト

生カウンタ（job `55570`）を CUDA core 版と並べたところ、狙いとは別のものが出た。

| | p=15 core | p=15 TC |
|---|---|---|
| shared ld 命令 | 31.20 M | **7.34 M** |
| shared ld コンフリクト | 15,465 | **3,212,086** |

**TC 化で shared ロード命令は 4.25 倍減った**（mma がオペランド 1 回の読み出しを
タイル全体に効かせるという狙いは数字で確認できた）。ところが**コンフリクトは 200 倍に増えて
いて**、残った 7.34 M 命令の 44% が衝突していた。CUDA core 版が
レーンを `i` 方向に並べて swizzle 無しで conflict free だったのに対し、
TC 版はレーンが mma のフラグメント配置に縛られるためである。

原因は 2 か所あり、どちらも**書き手と読み手で添字の形が違う**ことによる。

**z 微分の往復**: mma の出力マップで書き、x/y のマップで読む。
書き側は `2*colk` がビット 1-2・出力 `k` がビット 8-10、
読み側は `2*colk` がビット 1-2・`j` がビット 4-6。ビット 0 と 3 が
どちらでも死んでいるので、**書き側のビット 8-9 と読み側のビット 4-5 の両方を
そこへ畳む**と 2 フェーズとも同時に conflict free になる。
各フェーズは相手側のソースビットを warp 内で不変な値としてしか見ないので、
余分な項は定数 XOR になって害が無い。

**面 5/6 の lift 読み出し**: 面 1/3 は `(i,k)`、面 2/4 は `(j,k)`、面 5/6 は `(i,j)` で読む。
warp 内で `k` は不変なので前 2 者はブロードキャストになるが、`(i,j)` 形は
`2*colk` がビット 1-2、`j` がビット 4-7 でビット 0 と 3 が死に、
**epilogue の 8 本のロードが 4-way** になっていた。`j` のビットを死にビットに畳むと
面 5/6 が直り、他の 4 面はそこが warp 不変なのでブロードキャストのまま残る。
書き側は `fp = tid` の 16 連続なので、warp 内不変ビットによる畳み込みは
16 連続の置換のままである。

### 結果

どちらも**レジスタも shared も増やさない**純粋な置換で、
出力は変更前と**ビット一致**（`Ne=4³`、点ごと変動係数）。

| 版 | device 時間 |
|---|---|
| TC ベースライン | 22.25 ms |
| + z 往復の swizzle | 21.98 ms（−1.2%） |
| + 面 5/6 の swizzle | **21.78 ms（累計 −2.1%）** |

ncu（job `55602`、`55570` との比較）:

| メトリクス | 前 | 後 | 変化 |
|---|---|---|---|
| shared ld コンフリクト | 3,212,086 | 202,820 | **−93.7%** |
| stall short_scoreboard | 2.69 | 1.86 | −30.9% |
| stall mio_throttle | 5.93 | 4.48 | −24.5% |
| stall barrier | 7.73 | 6.33 | −18.1% |
| stall long_scoreboard | 22.39 | 20.24 | −9.6% |
| global ld sectors | 62.36 M | 62.36 M | ±0 |

Nq=8 では完全 conflict free の swizzle が**遅かった**（survey §10.3）が、
Nq=16 では素直に速くなる。あちらは 2-way を 1-way にする話で、
こちらは 4-way を 1-way にする話であり、桁が違う。

最終的な p=15 `FUSED_TC` は **363.0 µs/stage、5.72 TFLOP/s（14.3%）、
3.75 TB/s（47%）**、CUDA core 版に対して **1.196 倍**。

## 11. 占有率は律速ではなかった（直接実験）

第 7 節と第 9 節は「どのユニットも飽和しておらず、占有率が 49% だから」という
**状態証拠**だけで占有率を犯人にしていた。第 8 節の 2 つの不採用実験は
`Block Limit Shared Mem` が 1 のままで**占有率が上がっていなかった**ので、
仮説の検証になっていない。そこで占有率が実際に上がる版を作って測った。

2 ブロック/SM を成立させるには 1024 スレッドで**レジスタ 32 本以下**（65536/1024/2）
**かつ** shared 側の制限を外す必要がある。前者は `launch_bounds(1024,2)` で
spill ゼロのまま達成でき、後者は carveout の明示要求で外れる。

| 版 | レジスタ | carveout | 達成占有率 | device 時間 | ncu Duration |
|---|---|---|---|---|---|
| baseline | 62 | 既定 | 49.2% | **26.03 ms** | 679.4 µs |
| `launch_bounds(1024,2)` | 32 | 既定 | 約 49% | 27.81 ms | — |
| 同 + carveout 50% | 32 | 50% | **96.7%** | 28.14 ms | 733.8 µs |
| 同 + carveout 100% | 32 | 100% | — | 39.50 ms | — |

**占有率は狙いどおり 49.2% → 96.7% に倍増し、そのうえで 8.0% 遅かった。**
交絡を分離した内訳は次項のとおりで、**占有率それ自体の価値は約 −0.8%** である。

96.7% 版の ncu を baseline と並べると、何が起きたかがはっきりする:

| メトリクス | baseline (49.2%) | 96.7% 版 |
|---|---|---|
| Duration | 679.4 µs | **733.8 µs** |
| Memory Throughput | 74.1% | **89.4%** |
| Compute (SM) Throughput | 36.0% | 41.2% |
| DRAM Throughput | 25.3% | 34.6% |
| Executed IPC | 0.89 | 0.94 |

warp を倍にすると **memory pipe が 74% → 89% に上がっただけで、
カーネルは短くならなかった**。増えた warp はレイテンシを隠すのではなく、
同じ L1/TEX 経路を奪い合っている（次項で定量化する）。
carveout を 100% まで振ると 39.5 ms（+52%）になるが、
50% までなら +0.4% で済む（下の B）ので、これは shared を欲張りすぎた場合の話である。

### なぜレイテンシ律速なのに warp を増やしても効かないのか

「支配的な stall が long scoreboard = global ロード待ち」なら warp を増やせば
隠れるはずだ、というのが自然な期待である。実測はその期待を明快に否定する。

まず carveout の交絡を分離するため、**占有率を 49% に固定したまま carveout だけ
広げた版**（レジスタ 62 本のままなので `Block Limit Registers` が 1 で占有率は上がらない）
を測った:

| 版 | レジスタ | carveout | 占有率 | device 時間 | baseline 比 |
|---|---|---|---|---|---|
| A baseline | 62 | 既定 | 49.2% | 26.05 ms | — |
| B | 62 | 50% | 49%（据置） | 26.15 ms | **+0.4%**（L1 半減の代償だけ） |
| C | 32 | 既定 | 約 49% | 27.81 ms | **+6.8%**（レジスタ絞りの代償だけ） |
| D | 32 | 50% | **96.7%** | 28.14 ms | +8.0% |

L1 半減はほぼ無料（+0.4%）、レジスタ絞りが +6.8%。
D と C の差 +1.2% から L1 分 +0.4% を引くと、**占有率 49% → 97% それ自体の価値は
約 −0.8%、すなわちゼロかわずかに損**である。

理由は ncu の warp 統計に出ている:

| | A（49%） | D（97%） | 比 |
|---|---|---|---|
| Active Warps Per Scheduler | 7.88 | 15.48 | **1.96×** |
| Warp Cycles Per Issued Instruction | 35.47 | 66.14 | **1.86×** |
| **Issued Warp Per Scheduler** | **0.22** | **0.23** | **1.05×** |
| Eligible Warps Per Scheduler | 0.70 | 1.06 | 1.51× |
| L1/TEX Cache Throughput | 75.9% | 90.7% | |
| L1/TEX Hit Rate | 2.8% | 13.2% | |

**warp を 1.96 倍にしたら、1 命令あたりの stall サイクルが 1.86 倍に伸び、
発行率は 1.05 倍しか動かなかった。** 発行率 = warp 数 / 命令あたりサイクル数は
7.88/35.47 = 0.222 と 15.48/66.14 = 0.234 で、ほぼ保存されている。

これは Little の法則そのものである。**`long scoreboard` は「隠すべき固定レイテンシ」
ではなく、飽和しかけた資源の待ち行列遅延**であって、並列度を上げれば
サービス率が変わらないまま行列が伸びるだけになる。その資源が
L1/TEX であることは、同じ実験で throughput が 75.9% → 90.7% に上がったことに出ている。

言い換えると、baseline の時点で L1/TEX 経路には 1/0.759 = **1.32 倍分の余地しか無く**、
その余地を取りに行くために払うレジスタ絞りの代償が単独で +6.8% なので、
**取りに行った時点で赤字が確定している**。

なお付随して、このカーネルの **L1/TEX ヒット率は 2.8% しかない**。
体積側の `q,u,v,w,Escale` は各 1 回しか読まないストリームなのでヒットしないのが正しく、
これも「L1 を経由する命令の本数」が効いていて「L1 の再利用」は効いていない、
という第 10 節の像と整合する。

### では何が律速なのか

- **占有率ではない**（上の直接実験）。
- **DRAM 帯域ではない**（baseline で 25〜32%、第 6 節のとおり転送量は理論最小の 1.03 倍）。
- **演算パイプではない**（TC 版で SM 19.8%）。
- 支配的な stall は **long scoreboard（global ロードのレイテンシ）で 20〜22**、
  次が barrier 6.3。

残るのは **global ロードの本数と形、すなわち L1/TEX トランザクション**である。
第 10 節のアブレーションが示すとおり、その最大の塊は面フェーズ
（カーネルの 35%）で、うち手が出せない P 側 gather が最大の単一要因である。
warp を増やしても速くならないのは、増えた warp がまさにこの経路を混ませるからで、
第 10 節で shared のコンフリクトを消したときに素直に速くなった（−2.1%）のとは
対照的である。あちらは経路の**混雑を減らす**変更で、
占有率はその混雑を**増やす**変更だった。

## 12. 診断から出た最初の改善: 体積ロードのベクトル化

第 11 節の診断は「効いているのは L1/TEX を通る**命令の本数**であって、
バイト数でも占有率でもない」だった。だとすれば**同じバイトをより少ない命令で運ぶ**のが
直接の打ち手になる。

体積フェーズはスレッドが 1024 飛びの 4 ノードを持ち、`q,u,v,w` をスカラーで
16 本ロードしていた。ノードの持ち方を**隣接 2 ノード × 2 組**（`2*tid` と `2*tid+2048`）
に変えると、4 フィールドがすべて `double2` 1 本で運べる。
どの swizzle もビット 0 を読まず `2*tid` は偶数なので、
**ペアは swizzle を通してもペアのまま**で、shared ストアも 16 B 1 本になる。

ncu（job `56768`）で機構がそのまま確認できる:

| メトリクス | スカラー | double2 | 変化 |
|---|---|---|---|
| **global ld 命令** | 5,681,152 | 4,632,576 | **−18.5%** |
| **global ld sectors** | 62,357,504 | 62,357,504 | **±0** |
| shared st 命令 | 2,076,672 | 1,552,384 | −25.2% |
| shared ld コンフリクト | 202,820 | 761 | −99.6% |
| DRAM read bytes | 1.2327 GB | 1.2325 GB | ±0 |

**セクタ数も DRAM バイト数も 1 つも動いていない**のに device 時間は
**21.75 → 20.86 ms（−4.1%）**、出力は**ビット一致**。
運んだバイトは同じで、運ぶのに使った命令だけが減った。
第 11 節の診断に対する直接の裏取りになっている。

これで p=15 `FUSED_TC` は **347.7 µs/stage、5.98 TFLOP/s（14.9%）、3.91 TB/s（50%）**、
CUDA core 版に対して **1.249 倍**、TC 初版から通算 **−6.2%**。

同じ発想の続きとして、epilogue の lift と z 読み戻しにも隣接ペアの
shared ロードが 10 本ほどあるが、`sw_f15` と `sw_dz15` は**ビット 0 を畳んでいる**ため
ペアの先頭が奇数になり得る。16 B ロードにするにはレーンごとの入れ替えが要るので、
ここは 1-way を保つ現状を優先して見送った。

### 他のパスには使えるか — ほぼ使えない

**p=7 `FUSED_TC`（唯一の有望な候補）: 実装して測ったが 1.8% 遅い**
（16.38 → 16.68 ms、出力はビット一致）。レジスタは 32 本のままで占有率も落ちていない。
効かない理由は前提が成立していないことで、p=7 は **DRAM 72.8% で帯域に張り付いており**、
L1/TEX も 92〜95%（`tc_paper_survey_2407.09621.md` §7）ですでに飽和している。
命令を減らしても運ぶバイトが減らない以上、時間は縮まない。差し戻した。
**「命令数律速で、かつ DRAM が飽和していない」という前提は p=15 固有**である。

**CUDA Fortran のカーネルでは、そもそも書けない。** nvfortran 26.3 は
128 bit の global ロードを出さない。実カーネルの SASS で
`LDG.E.64` が 54 本に対し `LDG.E.128` は **0 本**、
隣接ペアだけの最小テストカーネルでも、`complex(8)`（16 バイト）を使っても
`LDG.E.64` のままだった。したがって前提が成立している
p=15 `FUSED`（DRAM 25%、memory 74%）にすら適用できない。

**残りのパスは前提の側で落ちる**: `volume_flux_kernel` は既に 7.09 TB/s =
ピークの 90%（`overall_summary_report.md` §8.6）、RK 更新カーネルも帯域律速
（DRAM 74.2%、同 §8.8）、p=255 の z GEMM は待ちと演算パイプ支配
（36.6% / 20.4%、`tma_survey.md` §2）である。

### 比較の公平性について

このベクトル化は **C++ 側にしか適用できない**ので、
第 9 節の「CUDA core 版に対する TC 版の優位」を引用するときは注意が要る。
**1.249 倍のうち 4.1% 分は、CUDA core 側に持ち込めない最適化に由来する。**
両者に同じ最適化だけを許した時点の比は **1.196 倍**である
（`reports/README.md` が p=7 で「両者を 100% occupancy で揃えた TC 版の優位は
1.16 倍」と断ったのと同じ趣旨の注記）。

## 13. 結論と次の点

- 同一 DOF での 3 点目が入った。`reports/README.md` の
  「p=7 は帯域・L1 律速、p=255 は演算律速」という対比に対し、
  **p=15 はそのどちらでもなく、占有率律速という第三の状態**にある。
- 演算強度を上げれば帯域の壁からは離れられるが、
  **CUDA core の融合カーネルはそれを演算性能に変換できない**。
  1 スレッドが持つ状態量が `Nq` とともに増え、レジスタが先に尽きるためである。
- **占有率は律速ではなかった**（第 11 節）。96.7% を達成した版は 49% の baseline より
  **8.0% 遅い**。当初この報告が占有率を犯人としていたのは**誤り**で、
  状態証拠だけで断じ、占有率が実際に上がった版を測っていなかったのが原因である。
  実際の律速は **global ロードの L1/TEX トランザクション**で、
  最大の塊は面フェーズ（カーネルの 35%）の、特に手の出せない P 側 gather である。
- **Tensor Core 版は 1.17 倍で、帯域は使い切らなかった**（第 9 節）。
  mma は命令数を削る（SM 36.0% → 19.8%）が、レジスタは減らさない。
  当初の事前予測（「p=15 はまだ帯域側にいるはず」）は**外れ**、
  「TC で帯域を使い切れるはず」という次の予測も**外れた**。
  実際に出てきたのは、**Nq=16 の融合カーネルは占有率 50% で構造的に頭打ち**という壁である。
- **診断は改善に直結した**（第 12 節）。「L1/TEX を通る命令の本数が効く」という
  結論から体積ロードを `double2` 化したところ、**セクタ数も DRAM バイト数も
  1 つも変えずに −4.1%**。有効な手が尽きたわけではなく、
  残っているのはこの種の「同じバイトをより少ない命令で」の積み上げである。
- 面 gather を追ったところ（第 10 節）、**p=7 の M 側ステージングは Nq=16 では上限 2.0%**
  にしかならず不採用。代わりに shared load の 4-way コンフリクトが 2 か所見つかり、
  swizzle 2 本で **−2.1%**（22.25 → 21.78 ms）、コンフリクト **−93.7%**。
  レジスタも shared も増やさず、出力はビット一致。
- 面フェーズはカーネルの 35% を占めるが、その大半は P 側 gather という
  原理的に手の出ない部分と、単独カーネルに出すとかえって高くつく部分である。
- Nq=32 以降は要素が shared に載らないので、この設計は p=15 で打ち止めである。
  p=31 は別の構造（タイル化）を要する。
  **（追記 2026-08-27）その構造を書いて測った（`p31_gap_study.md` §5）。**
  x と z が同じスレッド写像 `(i,k)` を共有し `j` を内側ループにすると累算器が
  スカラで済む、という 2 カーネル分割である。**結果は GEMM に 1.38 倍負けた。**
  なお「要素が shared に載らない」は正しいが、Nq=32 で実際に律速するのは shared ではなく
  **レジスタファイル**だった（縮約 1 回分の平面は 8 KB で載る）。
  そして**この設計が p=15 で打ち止めというのも結果的に正しかった** ——
  融合が GEMM に勝つ次数の上限は p=15 である。
  （**訂正 2026-08-27**: **CUDA core の**融合の上限が p=15 である。Tensor Core の
  融合は p=31 でも `GEMM` に 1.67 倍勝つ —— `p31_gap_study.md` §14.1。）

## 14. 曲線の不連続点としての p=15 —— 律速を測り直した（追記、2026-08-27）

### 14.5 p=63 で使った「面 flux を別カーネルに追い出す」は p=15 では赤字

`p63_gap_study.md` §13.2 は Nq=64 で面 flux を `elembnd_flux_kernel` に追い出した。

**Nq が大きい側だけ**（p=63 で 9.4%、p=15 は 37.5%）という次数依存の判断になる。

### 14.6 残っている 1 つの筋（未着手）

§14.4 の M 側 −7.6% は、**同じ値をもう一度 global から取り直しているために**払っている。
面点の M 側ノードは**その要素自身のノード**であり、カーネルは体積フェーズで
`q,u,v,w` を全ノードぶん既に読んでいる。にもかかわらず面フェーズは
`VMapM` 経由でもう一度 global に行き、**面 2 と 4（(j,k) 平面）では
ストライドが Nq = 128 B になるので 32 レーンが 32 セクタを引く。**

これは `AGENTS.md` の契約を壊さずに直せる可能性がある唯一の項目である
（`VMapM` は使い続け、値の出所を global から既読データに替えるだけで、
配列を代表スカラーに置き換えるわけではない）。障害は、面点の M 側ノードが
**別スレッドのレジスタにある**ことで、shared 経由の再配布が要る。
§14.3 が「shared を 10.3% 増減しても時間は動かない」と測っているので、
その再配布の代金は安い側に倒れる見込みだが、**未実装・未測定である。**

上限は §14.4 の −7.6%（26 µs）で、p=15 を 349 → 323 µs に置く。
§14.1 が指摘した「曲線に乗るなら 250 µs」には**届かない**ことに注意。
面 gather を完全に消しても 284 µs なので、
**p=15 と p=31 の間の不連続の残りは、面点率 37.5% という p=15 の構造そのもの**にある。

## 15. 面フラックスを前に出す —— 同じ gather を体積フェーズの裏に隠す（採用、−5.3%）

コミット: 本節を追加したコミット（親は `e7ae36c`）。GPU は RIKYU GB200 1 枚、
Slurm job `60475` / `60494` / `60503` / `60506`。入力は `conf_perf_p15_tc.conf` の
`nstep` を 200 にしたもの（`Ne=16³`、graph off）。時間はすべて `sbatch` で占有した GPU 上。

§14 が「命令数でも shared でも占有率でもなく global ロード律速、面 gather を
タダにしても上限 −17.5%」と測ったのを受けて、**トランザクションを減らすのではなく
発行位置を変える**ことにした。

### 15.1 結果

| | 変更前 | **採用版** |
|---|---|---|
| **µs/stage** | 345.1 | **326.8（−5.3%）** |
| Main [ms/step] | 1.29838 | **1.24310（−4.3%）** |
| FP64 ピーク比 | 15.1% | **15.9%** |
| 帯域 | 3.94 TB/s (50%) | **4.16 TB/s (53%)** |
| shared | 35584 B | 47872 B |
| レジスタ / spill | 64 / 0 | **64 / 0** |
| 占有率 | 48.8% | 48.7% |

**出力はビット一致**（演算も総和順序も変えていない）。CUDA graph on で 1.21417 ms/step。

### 15.2 変更の中身

面フラックスは**専用の `sflux[1536]`（12288 B）**を持ち、**x パネルを shared に置いた
直後**に評価される。従来は z フェーズの後、`sbuf` が空くのを待ってから評価していた。

`sbuf` を共用していたことが位置を縛っていた、というのがこの節の要点である。
1 枚のバッファを x → y → z → 面と順に使い回す設計は shared を節約するが、
**面 gather を「誰もが最初に待つもの」の位置に固定してしまう。**
12 KB 足して縛りを外すと、gather は x・y・z の 3 フェーズを裏で使って完了できる。
占有率はレジスタ（64 × 1024 = レジスタファイル全体）で決まっているので、
shared を 12 KB 増やしても占有率は動かない —— **この 12 KB は事実上タダである。**

### 15.3 機構の確認 —— 減ったのは待ち時間だけ

ncu（job `60494`、`-s 12 -c 6`）:

| メトリクス | 変更前 | 採用版 |
|---|---|---|
| **long scoreboard** | **47.06%** | **24.46%** |
| global ld requests | 4,632,576 | **4,632,576（同一）** |
| global ld sectors | 62,357,504 | **62,357,504（同一）** |
| L1/TEX | 67.87% | 69.12% |
| MIO throttle | 10.49% | 16.70% |
| barrier | 14.62% | 15.48% |
| 占有率 | 48.76% | 48.74% |

**リクエストもセクタも 1 つも減っていない。** 13.46 セクタ/リクエストという
§14 の悪い数字はそのままである。減ったのは `long scoreboard` だけで、**ちょうど半分**になった。
§14.4 が測った「gather をタダにすれば −17.5%」のうち、**その 3 割を
gather を一切変えずに回収した**ことになる。

§11 が「warp を増やしてもレイテンシは隠れない（待ち行列が伸びるだけ）」と測ったのと
矛盾しない。あちらは**同じ位置の混雑を増やす**変更で、こちらは**混雑の時刻をずらす**
変更である。占有率が動いていない（48.76 → 48.74%）のがその証拠で、
隠したのは並列度ではなく**依存距離**である。

### 15.4 効かなかった 2 つの置き方

| 版 | µs/stage | |

| 変更前 | 345.1 | — |

- **1 段早すぎると損をする。** x パネルの格納より前に置くと最初の mma が遅れ、
  重なりが増えるわけでもないので 1% 悪い。
- **レジスタ退避は spill で相殺される。** 専用バッファを持たずフラックス値 2 個を
  レジスタに抱える版は 20 B の spill を出し（`-Xptxas -v`）、**+2.0% と逆効果**だった。
  ここでも「レジスタ 64 本 × 1024 スレッド = レジスタファイル全体」という
  Nq=16 の構造的な天井が効いている（§11）。

§14.4 の上限（−17.5%）は変更前の 344.4 µs 基準なので、採用版で測り直した

使わない動的 shared を確保しただけの版を測った（静的 47872 B に加算）:

| 追加 shared | 合計 | µs/stage | 対 332.0 |
|---|---|---|---|
| 0 | 47872 B | 332.7 | — |
| +8 KB | 56064 B | 333.0 | +0.1% |
| +16 KB | 64256 B | 333.6 | +0.3% |
| +32 KB | 80640 B | 334.8 | +0.6% |
| +64 KB | 113408 B | 337.4 | +1.4% |
| **+128 KB** | 176 KB | **364.1** | **+9.4%** |

**64 KB までは実質タダで、その先に崖がある。** 占有率はレジスタ
（64 × 1024 = レジスタファイル全部）で 1 ブロック/SM に固定されているので、
shared を増やしても常駐ブロックは減らない。減るのは L1 だけで、
L1 hit が 4.3% しかないこのカーネルでも**崖は実在する**
（P 側 gather のラインが載らなくなる）。`tc_paper_survey_2407.09621.md` §13.4 の
「96 KB は carveout の代金のほうが高い」という Nq=8 での結論は、
**Nq=16 では 64 KB までは成立しない**。

3 パネル化後の 113408 B を起点に測り直すと崖はさらに近い:
+16 KB は 0%、+48 KB で +2.3%、**+64 KB で +12.0%**。

### 16.3 面フェーズを 2 面点/スレッドに（−3.0%）

§15.7 が名指しした律速は MIO throttle と LG throttle、つまり
**メモリ命令の本数**だった。1536 面点を 1024 スレッドが 1〜2 点ずつ持つ形を、
768 スレッドが**連続する 2 点**を持つ形に変えると、面点ごとに coalesced な
4 本（`normal_fn` 3 成分と `Fscale`）と `VMapM`/`VMapP` が
`double2` と `int2` になり、2 点あたり 12 本が 6 本になる。

ncu（job `66079`）: global ld request **4.633 M → 4.043 M（−12.7%）**、
命令数 62.28 M → 60.06 M、LG throttle 5.74 → 2.03。
**ただしセクタは 62.36 M → 70.88 M と 13.7% 増える**: ワープが持つ 64 面点を
偶数半分と奇数半分に割るので、i 方向に連続する 4 面では 1 本のロードが
16 B 飛びの飛び石になる。**命令を減らしてセクタを増やす取引で、
差し引き −3.0% の黒字**という測定である。

### 16.4 3 パネルを同時に shared に置く（−7.0%）

x → y → z と 1 枚の 32 KB バッファを使い回す設計は shared を節約するが、
**使い回しのたびにブロック全体が読み終わるのを待つバリアを要求する**。
3 枚（96 KB）を同時に持つと `__syncthreads` が **8 本から 3 本**に減り、
`u`/`v`/`w` の 6 本の `double2` ロードが**まとめて発行できる**ようになる。
16.2 のカーブどおり +64 KB の代金は 1.4% で、返りは 7.0% である。

ncu（job `66332`）: 命令数 60.06 M → 54.15 M（−9.8%）、shared wavefront
23.25 M → 20.29 M、そして**バンクコンフリクトが ld/st とも 0 になった**
（使い回していたときは 1 枚のバッファに 3 種類の写像が重なっていた）。

**16.3 と 16.4 は足し算より大きい。** 単独では 16.3 が −3.2%、16.4 が −3.7%、
両方で **−9.8%** である。3 パネル化で面フェーズと mma の間からバリアが消えるので、
面フェーズの命令を減らした効果がそこで初めて効く。

### 16.5 `__restrict__`（p=15 で −2.2%、p=63 で −11.6%）

カーネル引数のポインタに `__restrict__` を付けるだけ。`dqdt` と入力配列は
呼び出し側で別々の配列なので別名ではない。**他の次数の TC カーネルにも
そのまま効き、これが本節で最も横に広い変更である**（16.10）。

**例外は p=7 だけ**で、**+3.6% と逆効果**だった。`__launch_bounds__(256, 8)` で
レジスタ 32 本ちょうどに張り付いている設計なので、`__restrict__` が可能にする
ロードの前倒しがレジスタに収まらず、`-Xptxas -v` が
**8 バイトの stack frame**（spill）を出す。レジスタ数は 32 のままなので
占有率は落ちないが、spill のぶんだけ遅い。**p=7 には付けない。**

### 16.6 M 側の i 境界 2 面を shared に常駐させる（−6.1%）

§14.6 が「契約を壊さずに直せる可能性がある唯一の項目」として残し、
§15.7 が「shared が 1280 B しか残っていないので難しくなった」と書いた案である。
16.2 と 16.4 で shared の制約が外れたので実装できた。

要素の節点順序は `i + 16j + 256k` なので、**i を固定する 2 面の面点は
16 double = 128 B 飛び**になり、ワープが 8 セクタで済むところ 32 セクタを引く。
その 2 面（512 点）の M 側ノードは体積フェーズが既に読んでいるので、
**`i` が 0 または 15 の 2 平面ぶんの `q,u,v,w`（2048 double = 16 KB）を
通りがかりに shared へ書き、面フェーズはそこから読む**。

`VMapM` については何も仮定していない: **`VMapM` が返したノード番号**を見て
その平面に載っているかを判定し、載っていなければ従来どおり global へ行く。
仮定しているのは節点順序 `i + 16j + 256k` だけで、これはこのカーネルが
導関数を取るために既に全面的に使っている前提である。

代金は 16 KB（16.2 のカーブで 0%）と、面フェーズをバリアの後ろへ 1 段
移すこと（前は staging より前にあった）。**上限は −4.7%** と測っていたが
（下表）、実測は **−6.1%** で上限を超えた: 上限のアブレーションは 2 面ぶんの
**アドレス形**しか直さないのに対し、実装は他の 4 面の縁に載る点の
global ロードも消しているためである。

| アブレーション（`f304148` + 16.3〜16.5 の 293.2 µs 基準） | µs/stage | |
|---|---|---|
| 対照 | 293.2 | — |
| M 側の i 固定 2 面だけを coalesced に | 279.6 | −4.7% |
| M 側を全面 coalesced に | 266.4 | −9.0% |
| P 側の流れを丸ごと消す | 272.8 | −6.8% |

ncu（job `66392`）: セクタが **70.88 M → 62.49 M** と 16.3 で増えたぶんを
返し、request も 4.043 M → 3.781 M、DRAM 36.7% → 41.1%、
long scoreboard 11.47 → 8.39、LG throttle 2.00 → 0.63。

**6 面すべてを常駐させる案（48 KB）は測って落とした。** 残る j/k 面の上限は
**−3.8%（10.4 µs）**、48 KB 追加の carveout の代金が **+2.6%（7.2 µs）**で、
差し引き 1.2% しか残らない。そこへ 6 平面の帰属を決める分岐が書き込み側と
読み出し側の両方に乗るので、**書く前に赤字が確定している**。
j/k 面の M 側はもともと 16 double 連続 / 256 double 連続で
セクタ効率が悪くない（悪いのは i 固定の 2 面だけ）ことと整合する。

### 16.7 z 往復のバリアを 1 本に（−0.8%）

z の導関数は出力写像が x/y と違うので shared を往復する（§14.3）。
§14.3 は旧カーネルで「往復を消しても 0%」と測っていたが、
**3 パネル化後は往復の値段が −6.2% に上がっている**（往復を消した
アブレーション: 274.6 → 257.6）。他が速くなったぶん、往復に付く
2 本のバリアが相対的に重くなった。

往復そのものは構造的に外せない（m8n8k4 の出力行は x では `i`、z では `k` に
なるので、3 方向のうち 1 つは必ず転置が要る）。外せるのは**バリア 1 本**である:
z の mma でワープ `w` が読む 128 ノードは `ij ∈ [8w, 8w+8)` の全 `k` で、
往復で書く 128 ノードと**集合として一致する**。同じ swizzle で番地を付ければ
書き込みは**そのワープ自身が読んだ番地の中**に落ちるので、
上書きを守るバリアは `__syncwarp()` で足りる。

> **踏んだ落とし穴**: 最初の実装は往復を **x パネル**へ書いたまま
> `__syncwarp()` にしてしまい、**他のワープがまだ x の mma で読んでいる領域を
> 壊すレース**になった。`Ne=4³` の検証は 3 回に 1 回ビット一致してしまい、
> 1 回だけの比較では通過する。**この種の変更の検証は必ず複数回走らせること。**
> 往復を **z パネル**（そのワープが読み終えた場所）へ移すのが正しい形である。

往復に専用の swizzle を与えられなくなるので、読み出し側は 4-way
コンフリクトに戻る（ncu で shared st コンフリクト 0.20 M → 1.24 M）。
bit 0 も畳んで 2-way にする版（`double2` のマージを失う）も測ったが
**273.9 対 273.0 で負け**、`sw_z15` のまま使うのが正しい。

## 23. `CUDAFORTRAN_GEMM_FUSED` を p=15 に開く（2026-08-30）

親 `40fff1a`、GB200、`make CUDA=1 GPUFLAGS=-gpu=cc100`。入力
`namelists/perf_p15_gemm_fused.conf`（`Ne=16³`、`nstep=20`、graph off）。
検証は `SCALE_DG_VARYING_COEFF=1`、`namelists/val_p15_gemm_fused.conf` 対
`val_p15_split.conf`（32,768 点）。

> **2026-08-31 訂正:** §23.3--23.4 の cuBLAS y/z 採用は、現在の経路役割
> （`GEMM_CUTE` と `GEMM_FUSED` は同じ CUTLASS volume-GEMM tile を使い、
> `GEMM_FUSED` の z は fused epilogue とする）に反する。測定値は negative / out-of-scope
> evidence として残すが、現行実装・公開値ではない。役割準拠版への復帰、再検証、
> 再計測は §24。

p=15 の最速は `FUSED_TC`（271.8 µs）のまま。本節は欠測だった GEMM 融合経路を
開き、Nq=16 で融合パッケージが何をするかを測る。

### 23.1 なぜ走らなかったか

y GEMM は `Nq*Ne` 平面を batch にし、CUTLASS
`GemmBatchedIdentityThreadblockSwizzle` が `batch % 65536` を `grid.z` に
載せる。p=15 `Ne=16³` はちょうど 65536 なので **grid.z = 0**（cutlass
status 7）。CUDA の上限 65535 を 1 だけ超える、という説明は半分正しく、
剰余が 0 になることが落ちる理由である。カーネル本体は
`batch_idx += gridDim.z` で複数 batch を踏める。在庫の `GemmBatched` は
65535 件ずつ分割し、自前起動（y scaleadd / z assembly）は `grid.z` を
上限する。Fortran の `Nq*Ne <= 65535` ゲートは外した。

### 23.2 開いた直後の律速（nsys job `70988`、node c387）

login 5-run の device fused **84.87 ms / 57 stage = 1489 µs/stage**。
同一バイナリの `CUDAFORTRAN_GEMM` は **845 µs**。

1 stage あたり（60 instance、warmup 込み）:

| カーネル | µs | 役割 |
|---|---:|---|
| CUTLASS `GemmBatched` ×2 | 571 | y。65535 + 1 の 2 ローンチ。タイル 64×64 対問題 16×16 |
| `GemmBatchedDqdtAssembly` | 503 | 融合 z。タイル 64×32、N=16 は半分が述語 |
| `elembnd_flux` | 175 | GEMM と同じ |
| `volume_flux` | 130 | GEMM と同じ |
| cuBLAS x (`32x64`) | 107 | `Nq<=64` の既存スイッチ |
| 1-batch の 32×32 | 3 | y の余り |

1 文: **この経路は浅い K に合わない CUTLASS タイルで y と z が律速している。**

### 23.3 当時の採用（現在は範囲外）

1. **Nq≤16 の y を cuBLAS strided-batched にする**（`GEMM` / `GEMM_CUTE` と
   同じ呼び出し。`dg_cuda_stream` を毎呼び出し `cublasSetStream`）。
   login GPU 1 で device **1489 → 1126 µs（−24%）**。対 SPLIT max abs
   1.78e-15。y の 571 µs が消える。
2. **Nq≤16 の z を cuBLAS + `separable_lift_assembly` にする**（融合
   epilogue は K=16 で 503 µs あり、GEMM の z+lift より高い。p=31 と同じ
   符号）。点変化係数の owned `dqdt` は SPLIT と**ビット一致**。
3. **Nq≤16 では side stream を切る**（GEMM が Nq<64 で切っているのと同じ。
   重ねる相手が同じ cuBLAS 3 本だと窓より elembnd が大きい）。login GPU 1
   で device **49.80 → 48.58 ms（873 → 852 µs、−2.4%）**。

通算 **1489 → 852 µs/stage（−43%）**、Main 4.66 → 2.78 ms/step。
占有 GPU job `70990`（c178）12 回交互の中央値は device fused **48.545 ms =
851.7 µs/stage**、`GEMM` **48.196 ms = 845.5 µs**（**+0.73%**、レンジ非重複）。
差は融合ドライバの event 区間と、side を切ったあとも残る起動の足場で、
volume カーネルは同じ cuBLAS 3 本 + lift である。

µs/stage 851.7 は 2.44 TFLOP/s（ピーク 6.1%）、unique DRAM 1.56 TB/s
（19.7%）。`FUSED_TC` 271.8 の **3.13 倍**遅い。最速は動かない。

### 23.4 測って落としたこと / 残さないこと

| 候補 | 結果 | 理由 |

| CUTLASS y を 1 ローンチに `grid.z` 上限するだけ | 実装せず | タイル 64×64 が残る。cuBLAS 化のほうが天井が大きい |

TB `64×32` / warp `32×32` を `64×16` / `16×16` にし、未加重 epilogue のまま
`launch_z_gemm_assembly` に戻した（Fortran の Nq≤16 分岐だけ。CUTE の

max abs **1.78e-15**。

占有 GPU job `71057`（c178）12 回交互、device fused 中央値:

レンジは重ならない（cuBLAS-z 48.516–48.573、z16 70.178–70.271）。Main

同一 job の nsys（60 instance、warmup 込み）1 stage あたり:

## 25. Nq=16 に合わせた CUTLASS tile と単一 launch（2026-09-01、採用、−54.6%）

`make CUDA=1 GPUFLAGS=-gpu=cc100`。入力 `namelists/perf_p15_gemm_fused.conf`
（`Ne=16³`、`nstep=20`、graph off）。検証は `SCALE_DG_VARYING_COEFF=1` で
`val_p15_split.conf` 対 `val_p15_gemm_fused.conf`（owned 32,768 点）。
変更は volume GEMM の tile と launch 形だけなので、`GEMM_CUTE` と

### 25.1 出発点

**16×16×16** で tile は 64×64、z（および fused z assembly）は

縮めるだけで −22.6% だった。**他次数で効いて p=15 に未適用**の候補として
最優先で試した。

### 25.8 測って落とした候補

> **2026-09-02 訂正:** 「x を cuBLAS から CUTLASS へ（16×64…16×256 を掃引）、
> 最良で +10%」は掃引した族の外に勝ち形がある。**64×16 / warp 16×16 / K=16 /

| 候補 | 結果 | 機構 |
|---|---:|---|
| x を cuBLAS から CUTLASS へ（16×64…16×256 を掃引） | 最良で **+10%**（41.7 対 37.9 ms） | M=16, N=1,048,576 の wide GEMM では cuBLAS `32×64` が強い。`Nq<=64` の x ライブラリ分岐は据え置き |

## 26. 天井の測定と y epilogue の repad（2026-09-01、採用、−0.63%）

### 26.1 3 本の volume パスの天井（純ストリーミング置換）

> **2026-09-02 訂正:** 本節の「**最も重要なのは x の行である**……約 40 µs の
> 超過は tile 調整の取り残しではなく、16 点の縮約を独立した 1 パスとして回すこと
> そのものの値段」は誤りで、**取り残しだった**。次数専用タイルの CUTLASS x は
> 48.4 µs で、本節が見積もったストリーミング床 50.4 µs とほぼ同じ
> （[`gemm_assignment_and_carrier.md`](gemm_assignment_and_carrier.md) §1）。床 536.7 µs/stage は不変だが、採用形との差は 19% → 14% に縮む。

環境変数 `SCALE_DG_ABL` で x / y / z のカーネルを、**同じバイト数を動かす
だけの単純なストリーミングカーネル**に差し替えた（`dqdt` は当然壊れる。
時間だけを読む）。x と y は `flux → deriv` の 2V コピー、z は 7V
（`flux_z`, `deriv_x`, `deriv_y`, `Ex`, `Ey`, `Ez` 読み + `dqdt` 書き）と
6 面平面の読みを行う。login GPU 3-run、device ms / 57 stage:

| 置換 | device ms | µs/stage | 差 [µs/stage] |
|---|---:|---:|---:|
| 無し（§25 の採用形） | 37.74 | 662.1 | — |
| x → 2V ストリーミング | 35.31 | 619.5 | **−42.6** |
| y → 2V ストリーミング | 35.25 | 618.4 | **−43.7** |
| z → 7V+面 ストリーミング | 35.47 | 622.3 | **−39.7** |
| x, y, z 全部 | 30.59 | **536.7** | **−125.4** |

3 つの差は加算的である（42.6+43.7+39.7 = 126.0 対 同時 125.4）。つまり
**この経路の構造的な床は 536.7 µs/stage**で、採用形との差は 19%。

**最も重要なのは x の行である**。x は cuBLAS の wide GEMM
（M=16, N=1,048,576, K=16）で、我々は tile を一切触っていない。その
ベンダライブラリが、我々の CUTLASS y とほぼ同じ **43 µs** をストリーミング
床の上に残している。したがって 1 パスあたり約 40 µs の超過は
**tile 調整の取り残しではなく、「16 点の縮約を独立した 1 パスとして回すこと」
そのものの値段**である。これを削るには pass を減らす（= `FUSED_TC` の設計、
271.8 µs/stage）しかなく、それは `GEMM_CUTE` と mainloop を共有するという
この経路の役割の外にある。

nsys の内訳（§25.6）の残り 2 本、`volume_flux` 126.2 µs（7V を 7.44 TB/s、
DRAM ピークの 94%）と `elembnd_flux` 138.5 µs は `GEMM` 経路と同一カーネル
なので、この経路として独立に最適化しない。カーネル総和 647 µs に対し
device イベントは 662 µs で、差 **14〜15 µs（2.2%）は launch の隙間**である
（graph off の計測規約による。`UseCudaGraph=.true.` では消える）。

### 26.2 ncu が見つけた最後の 1 つ: y の shared ストアコンフリクト

### 27.1 (B) は既に上限にある

### 27.3 なぜ (A) がほとんど効かないか（ncu、job `75847` / `75855`）

| メトリクス | 改修前 | 2j×4k | 2i×2j×2k |
|---|---:|---:|---:|
| shared wavefront | 47.94 M | 37.34 M（−22%） | 41.90 M（−13%） |
| 発行命令 | 81.81 M | 72.97 M（−11%） | **67.46 M（−17.6%）** |
| L1/TEX | 90.03% | 79.42% | 93.43% |
| long_scoreboard | 7.47 | **10.94** | 10.24 |
| mio_throttle | 8.93 | 7.46 | 13.23 |
| shared LD バンクコンフリクト | 158 k | 55 k | **4,500 k** |
| global sector（LD） | 62.36 M | 63.41 M（+1.7%） | 62.36 M |
| DRAM read / write | 1271 / 124 MB | 1264 / 123 MB | 1321 / **280 MB** |
| ncu duration | 517.9 µs | 518.5 µs | 526.1 µs |

- **2j×4k**: shared wavefront を 22% 減らしても時間は動かない
  （ncu で +0.1%、実時間で +3.07%）。減った分の受け皿が無く、代わりに
  `long_scoreboard` が 7.47 → 10.94 に上がり、global の request/sector が
  +2.0% / +1.7% 増える。**p=15 CC は §21.4 のとおり global 側で詰まっており、
  shared を削っても解放されない。** p=31（§27）で同じ操作が −29.9% を生むのは、
  あちらが shared wavefront 律速で global セクタが 4 形とも同一だからである。
- **2i×2j 1024 スレッド**: (A) としては最も素直な形（レジスタ最小、spill 無し、
  占有率も 50% のまま）なのに **+17.5%** と最も悪い。1 ブロック/SM に戻るので
  §21.2-3 が測った「2 CTA で 2 要素の global を重ねる」効果を失う。
  **p=15 の予算は「占有率 50%」ではなく「2 ブロック/SM」であり、
  それを崩すタイルは (A) の利得を全部食う。**
- **2i×2j×2k**: 命令を 17.6% 減らして −1.72%。ただし z 方向の
  `sbuf[i0 + j*16 + l*256]` が 4 つの j グループで同じ bank 対に落ちるため
  **shared LD コンフリクトが 28 倍**になり、104 B のスピルで DRAM write が
  124 → 280 MB に増えている。それでも勝つのは命令削減が大きいからで、
  ncu の duration は逆に +1.6% を出す（`AGENTS.md` の ncu バイアスどおり、
  shared/レジスタを増やして global を隠す変更を過小評価する）。
  **コンフリクトを潰す padding は打てない**: j ストライドを 17 にすると
  `sbuf` が 34,816 B になり、静的 shared 48 KB と「2 ブロック/SM」の両方を
  壊す。そもそも 32 レーン × 16 B = 512 B は 4 wavefront が下限である。

### 30.2 実装

`cuda_dg_kernels_tc.cu` に `P15_MPLANES` を足した（既定 **2** = §16.6 の製品形、
**6** が本節の候補）。6 のとき shared に常駐する面は

| プレーン | 条件 | shared 添字 |
|---|---|---|
| 0 / 1 | `i == 0` / `i == 15` | `j + 16k` / `256 + j + 16k` |
| 2 / 3 | `j == 0` / `j == 15` | `512 + i + 16k` / `768 + i + 16k` |
| 4 / 5 | `k == 0` / `k == 15` | `1024 + i + 16j` / `1280 + i + 16j` |

`q,u,v,w` 各 1536 double、合計 **48 KB**（2 面のときは 16 KB）。カーネルの動的
shared は **129792 → 162560 B**。書き込みは §16.6 と同じ「体積フェーズの
通りがかり」で、`STAGE_M_PAIR` が 1 スレッドの持つ 4 ノードそれぞれについて
i / j / k の 3 組を判定する。ノード対 `(n, n+1)` は i で隣接するので、
j 法線面と k 法線面は `double2` 1 本で書ける（i 法線面だけが対を割る）。
読み出し `LOAD_M` は **`VMapM` が返したノード番号**から所属プレーンを決め、
どれにも載らなければ従来どおり global へ行く（数値契約どおり `VMapM` は
使い続け、値の出所だけを替えている）。

**検証**: `SCALE_DG_VARYING_COEFF=1`、`Ne=2³`（32,768 点）と `Ne=4³`（262,144 点）で
owned `dqdt(:,1:Ne)` を比較し、改修前 `FUSED_TC` と**全点ビット一致**
（総和順序を変えていない）。`CUDAFORTRAN_SPLIT` 対照は `Ne=2³` で
max abs **1.776e-15**、`Ne=4³` で 1.112e-13（§14.7 / §16 と同じ帯）。
`FUSED_TC` と `FUSED_DFMA` も**ビット一致**（`P15_MPLANES` は `UseTc` を見ない）。
レジスタ 64・spill 0 は 2 面のときと同じ。

2026-08-27 の 1 枚バッファ版の性質で、3 パネル化・M 側 2 面常駐まで来た
現行カーネルではもう成り立たない**（§16.7 が z 往復の値段が 0% → −6.2% に

`P15_MPLANES`（既定 2 = 製品形）と、天井測定用の不正 ablation
`P15_ABL_MCOAL`（既定 0、M 側を coalesced なノード番号で読む。数値は壊れる）は
ソースに残した。`P63_XZ_DB` や `P31_XZ_*` と同じ扱いで、既定はどちらも
改修前の形であり、production dispatch には出ない。

**p=15 `FUSED_TC` の探索終了（§20.4）はそのまま維持する。** 本節は
§20.4 が「§16.6–16.9 のまま」として残していた最後の 1 形を実際に書いて
赤字を確定させたもので、結論を覆さない。最速は `CUDAFORTRAN_FUSED_TC` の
**272.54 µs/stage**（job `78090`）のままである。

## 31. p=15 `FUSED_TC` のチャンク数は 1（2026-09-03、符号則は棄却を予測、測定不要）

`TODO.md` §5 の 3 件目は p=7 について立っているが、p=15 も同じ 1 行で閉じる。
[`p63_gap_study.md`](p63_gap_study.md) §52.3 の符号則——「チャンクループの
二重バッファが効くかは**縮約チャンク数**で決まる。p=31 / p=63 は 1 個で棄却、
p=127 は 2 個で −4.25%、p=255 は 16 個で −27.7%」——を当てるために、
`cuda_dg_kernels_tc.cu` の `tendency_fused_p15_kernel` を読んだ。

### 31.1 事実: 縮約チャンク数は 1（`BK = Nq = 16`）

- 要素 1 個ぶんの 3 方向パネル `sbufX` / `sbufY` / `sbufZ`（各 `NP15 = 4096`
  double）を**同時に**持つ。動的 shared は
  `(3·4096 + 1536 + 256 + 96 + 4·P15_MSTRIDE)·8` = **113,408 B**。
  ptxas はレジスタ **64**、spill 0、`__launch_bounds__(1024, 1)`。
- 縮約は 3 か所の `for (int ks = 0; ks < 4; ++ks)`（x / y / z 各 1 本）で、
  これは `Nq = 16` を `m8n8k4` の k = 4 で割った **mma の k ステップ**である。
  読む相手は**すでに shared に載りきっているパネル**で、
  global → shared のステージングはループの外に 1 回だけある。
- すなわち `BK = Nq = 16` で、**p=63 の `BK63 = NQ63 = 64` と同じ形**。
  縮約チャンク数は **1**。カーネル全体のバリアは
  `__syncthreads` **2 本 + `__syncwarp` 1 本**しかない（§16.4 で 8 本から
  減らしたときの記録）。

符号則は p=31 / p=63 と同じ**棄却**を予測する。

### 31.2 チャンクを作る側にも余地が無い（占有率の数え上げ）

二重バッファを測るにはまず `BK` を下げてチャンクを作る必要がある
（p=63 §52.3 と同じ手順）。その動機は shared を減らしてブロックを増やすことだが、
p=15 では**増えない**。

| 量 | p=15 `FUSED_TC` |
|---|---:|
| スレッド / ブロック | **1,024** |
| レジスタ | 64 |
| レジスタ 1 枚ぶん | `64 · 1024` = **65,536 = レジスタファイル全部** |
| shared / ブロック | 113,408 B（/ 233,472 B） |
| ブロック / SM | **1**（レジスタで決まる） |

**占有率 50% を決めているのはレジスタファイルであって shared ではない。**
`BK` を 8 に落として 3 パネルを半分（48 KB 節約）にしても、ブロックは
1 枚のままである。得られるのはチャンクあたりのバリアだけで、
現在 2 本のバリアが `Nq/BK` に比例して増える。符号は確定して負。

（カーネル本体のこの性質は §16.4 が別の言い方で既に書いている:
「1 バッファを x/y/z で使い回すと shared は減るが、**占有率は
64 レジスタ × 1024 スレッドで 1 ブロック / SM に固定されている**ので
何も買えず、代わりにバリアを払う。3 枚持つ方が 7.0% 速い。」
チャンク分割は、そこで捨てた方向にもう一歩進む変更にあたる。）

### 31.3 判断

**棄却。実装しない。** 6 次数の符号則の表はこれで埋まる:

| 次数 | 縮約チャンク数 | 二重バッファ | 出所 |
|---|---:|---|---|
| p=7 | **1**（ループ自体が無い） | 棄却（数え上げ） | [`tc_paper_survey_2407.09621.md`](tc_paper_survey_2407.09621.md) §21 |
| p=15 | **1**（`BK = Nq = 16`） | 棄却（数え上げ） | 本節 |
| p=31 | 1 | 棄却（実測 +1.04〜+12.05%） | [`p31_gap_study.md`](p31_gap_study.md) §30 |
| p=63 | 1 | 棄却（実測 +2.8〜3.1%） | [`p63_gap_study.md`](p63_gap_study.md) §52.3 |
| p=127 | 2 | 採用 −4.25% | [`p127_gap_study.md`](p127_gap_study.md) §23 |
| p=255 | 16 | 採用 −27.7% | [`p255_gap_study.md`](p255_gap_study.md) §4.1 |

**符号則の閾値はチャンク 2 個である**（1 個は 4 次数とも負、2 個以上は
2 次数とも正）。低次数側で 1 個になる理由も 4 次数で共通で、
`Nq² · 8 B` の平面が 227 KiB の shared に収まってしまうため、
そもそも縮約を切る必要が無い。

**本節で採択したソース変更は無い。**

## 32. p=15 への PDL 適用可否（2026-09-03、適用箇所が無い。天井は graph 再生で実測）

[`p127_gap_study.md`](p127_gap_study.md) §19 →
[`p63_gap_study.md`](p63_gap_study.md) §50 →
[`p31_gap_study.md`](p31_gap_study.md) §25 と横展開されたが p=15 では
一度も言及が無かった。適用条件と実績の整理は
[`tc_paper_survey_2407.09621.md`](tc_paper_survey_2407.09621.md) §22.1 にある。
結論は p=7 と同じで、理由も同じである。

commit は本節を追加したもの（親 `709334a`）、GPU は RIKYU GB200、
入力は `namelists/perf_p15_fused_tc.conf`（`Ne=16³`、`nstep=20`、graph off）、
`nsys` は Slurm job **`78241`**（node `c182`、凍結 exe、`--trace=cuda
--sample=none --resolve-symbols=false`）。graph の A/B は login GPU 5-run 中央値。

### 32.1 事実: tendency は 1 グリッド

`launch_tendency_fused_p15_impl` は
`tendency_fused_p15_kernel<UseTc><<<Ne, P15_THREADS, p15_smem>>>` を
**1 本だけ**起動する（CUDA-core の `tendency_fused_p15_cc_kernel` も 1 本）。
面フラックスも 3 方向の微分もエピローグもこの中にあり、
**PDL の段（面 → xz、xz → y）が 1 つも存在しない。**

nsys が測った 1 stage の全内容:

| グリッド | 生成元 | 中央値 [µs] |
|---|---|---:|
| `main_rk_update_stage_462_gpu`（stage 1 は `_455_`） | OpenACC | 74.35（76.46） |
| `mod_mesh_update_halo_243_gpu` | OpenACC | 5.73 |
| `tendency_fused_p15_kernel<true>` | **CUDA C++** | **263.60** |
| カーネル間の隙間 合計 | — | **9.73** |
| **stage 周期** | | **355.33** |

CUDA C++ グリッドは 1 本だけで、前後の隣は OpenACC 生成のローンチである。
属性 `cudaLaunchAttributeProgrammaticStreamSerialization` を付ける先が無く、
一次側が Fortran では重ならないことは `p127_gap_study.md` §19.2 で実測済み。

### 32.2 隙間の天井を測った: **2.7%、しかも graph 再生で既に取れる**

| | 中央値 [µs/stage] | レンジ | 差 |
|---|---:|---|---:|
| graph off（既定） | **355.75** | 355.70–356.28 | — |
| **graph on** | **345.20** | 344.76–345.63 | **−2.97%（−10.55 µs）** |

login GPU 5-run、レンジ非重複。回収した 10.55 µs は nsys の隙間 9.73 µs の
**108%** で、隙間はホスト側のローンチ待ちそのものである。
PDL が狙える量は全部ここにあり、**`UseCudaGraph = .true.` が全額回収している。
PDL がその上に足せる分は 0。**

CUDA-core 側（`namelists/perf_p15_fused.conf`）も同じである:

| | 中央値 [µs/stage] | レンジ | 差 |
|---|---:|---|---:|
| graph off（既定） | **416.51** | 416.17–418.32 | — |
| graph on | **406.26** | 405.97–408.15 | **−2.46%（−10.25 µs）** |

`FUSED_TC` の −10.55 µs と 3% 以内で一致する。**取れる µs は経路ではなく
1 stage のカーネル本数（3 本）で決まっている。**

なお §28 が測った p=15 `GEMM_FUSED` の graph 利得は **−3.16%** で、
本節の `FUSED_TC` −2.97% と近い。stage の長さがどちらも 350 µs 級で、
消える隙間の µs がカーネル本数で決まるからである
（`GEMM_FUSED` は 6 本前後、`FUSED_TC` は 3 本）。

### 32.3 段を作る側も負け（tail の数え上げ）

PDL が回収するのは先行グリッドの tail である。p=15 は `Ne = 16³ = 4,096`
ブロック、1024 スレッド × 64 レジスタで **1 ブロック / SM**、SM 152 枚なので
**27.0 wave**。tail は最良でもカーネルの `1/27 = 3.7%` で、そのうち
後続の立ち上がりに重なる分だけが賞金になる。p=127 の y PDL が −2.71% と
大きいのは `Ne = 2³` で wave 数が小さいからで、p=15 は逆側である。
分割はさらに、融合が消した global 往復を 1 本ぶん戻す。符号は負。

### 32.4 判断

**適用不能。実装しない。** (a) 段が存在しない、(b) 隣接グリッドが OpenACC 生成、
(c) 狙える隙間の天井 2.74%（9.73 µs/stage）は graph 再生が −2.97% で
全額回収している。**既定 conf は graph off のまま**（graph 再生では
`Cal_tend` / `CUDA device *` が出ず `nsys` も当てられない。§28 と同じ判断）。

**本節で採択したソース変更は無い。**
