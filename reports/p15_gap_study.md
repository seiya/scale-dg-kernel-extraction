# p=15 (Nq=16) — p=7 と p=255 の間を同一 DOF で埋める

測定環境: RIKYU NVIDIA GB200 1 GPU、`make CUDA=1 GPUFLAGS=-gpu=cc100`。
コミット: 本レポートを追加したコミット（親は `e8e1885`）。
ncu は Slurm job `54662`（`job_ncu_p15.sh`、CUDA core 版）、
`55485`（`job_ncu_p15tc.sh`、Tensor Core 版）、
`55570` / `55602`（`job_ncu_p15face.sh`、生カウンタ、第 11 節の前後）。
入力: `conf_perf_p15.conf`（`NeX=NeY=NeZ=16, PolyOrder=15, nstep=20, UseCudaGraph=.false.`）と
`conf_perf_p7.conf` 相当（`NeX=32, PolyOrder=7`、同 `nstep`）。
検証: `input_p15_val.conf` / `input_p15_val_tc.conf` と `NeX=4` 版、
いずれも `SCALE_DG_VARYING_COEFF=1`。

## 1. なぜ p=15 なのか

同一 DOF（16.78 M = 256³）を立方一様メッシュで保つ条件は `NeX * Nq = 256`、
すなわち **Nq が 256 の約数**である。これで候補は 2 冪だけに絞られ、
p = 15, 31, 63, 127 の 4 点しかない。FP64 mma が要求する M,N の 8 倍数・K の 4 倍数は
Nq≥8 の 2 冪なら自動的に満たされるので、**DOF 固定の条件のほうが Tensor Core の
条件より強い**。Nq=12 や 24 のような「TC 的に半端な次数」は検討する前に落ちる。

この 4 点のうち p=15 を最初に取った理由:

- 1 要素の `q` は Nq=8 で 4 KB、**Nq=16 で 32 KB**、Nq=32 で 256 KB。
  227 KB/SM を構造的に超えるのは Nq=32 からなので、**要素まるごとを shared に置く
  設計が通用する最後の点**である。
- 面点率 `6/Nq` が 75% → **37.5%** に落ちる。p=7 の律速だった gather と lift の
  比重が半減する。
- 融合時の理想演算強度 `6*Nq/40` FLOP/B が 1.2 → **2.4** になる。
  GB200 のマシンバランス 5.0 FLOP/B の半分弱。
- `operator_data/p15.dat` が既にある（16 + 256 + 24576 = 24848 値、
  `D1D(1,1) = -60 = -15*16/4`）。p=31 以降と違い LGL 演算子の生成が要らない。

## 2. ホスト側は既に Nq 汎用だった

`main.f90` / `mod_mesh.f90` / `Makefile` / `operator_data/` は**変更不要**。
`OPENACC_ASIS`, `OPENACC_SPLIT`, `CUDAFORTRAN_SPLIT`, `CUDAFORTRAN_GEMM` は
コード変更ゼロで p=15 が走る。`CUDAFORTRAN_FUSED` だけが**独立した 3 層**の
ガードで閉じていた: `mod_advect3d_eq.f90` の設定時チェックと実行時分岐、
および `mod_cuda_dg_kernels.cuf` のラッパ。

p=15 の数値は 4 つの独立実装で一致することを先に確認した
（`CUDAFORTRAN_SPLIT` を基準、`Ne=2³`、点ごと変動係数）:

| 実装 | 基準との相対差 |
|---|---|
| `CUDAFORTRAN_GEMM` | 0（ビット一致） |
| `OPENACC_SPLIT` | 1.26e-15 |
| `OPENACC_ASIS` | 1.26e-15 |

## 3. `tendency_fused_p15_kernel`

p=7 の `tendency_fused_p7_kernel` は**一切変更していない**。
32 レジスタ / 8 ブロック/SM に追い込んだ調整（`execution_times.md` 追記 3）を
壊す理由がないため、Nq=16 は別カーネルとして書いた。

### shared memory 戦略

p=7 の構成をそのまま Nq=16 にすると
`sFluxX/Y/Z` 3 × 4096 × 8 B = 96 KB + `sflux_bnd` 12 KB + `sD1D` 2 KB + `sLift` 0.75 KB
= **約 111 KB/ブロック**で、48 KB の静的 shared 上限を超え carveout の opt-in が
必須になる。`tc_paper_survey_2407.09621.md` §13.4 が記録した **+31%** の罠がこれである。

採用したのは **Nq³ のスクラッチバッファ 1 本を方向ごとに使い回す**構成:

- 各スレッドは担当ノードの `q` を**レジスタに保持**（要素あたり 1 回だけロード）
- フェーズ X: `u` をロードして `buf = q*u` → 収縮 → `Escale_x` を掛けて累算
- フェーズ Y / Z: `v` / `w` で同じことを同じ `buf` に対して行う
- 面フェーズ: 同じ `buf` の先頭 `6*Nq²` を面流束として使い回す
- epilogue: lift を足して `dqdt` へ

global ロードは `q,u,v,w` 各 1 回ずつで**理論最小のまま**、shared は
`32768 (buf) + 2048 (sD1D) + 768 (sLift)` = **35584 B** で静的 shared に収まる
（実測 `cuobjdump -res-usage` で `SHARED:35584 LOCAL:0`）。
代償は `syncthreads` が 1 回から 7 回に増えることと、3 方向が直列化すること。

### スレッド割り当てとバンクコンフリクト

1 ブロック 1 要素、**1024 スレッド、4 ノード/スレッド**。
スレッド `tid` はノード `tid, tid+1024, tid+2048, tid+3072` を持つ。
これらは `(i,j)` を共有し `k` が 4 プレーンずつ違う。

この割り当てだと**レーンが `i` 方向に並び、収縮添字 `l` は warp 内で一様**になるので、
**swizzle なしで 3 方向とも conflict free** になる:

- x 収縮 `buf(l + (j-1)*16 + (k-1)*256)` は `i` に依存しない → half-warp 全体が
  同一アドレス → ブロードキャスト
- y 収縮 `buf(i + (l-1)*16 + (k-1)*256)` は `i` のみに依存 → 16 連続 double
- z 収縮 `buf(i + (j-1)*16 + (l-1)*256)` も同様に 16 連続 double

`cuda_dg_kernels_tc.cu` の `sw_xy` / `sw_z` が必要だったのは、TC カーネルでは
**レーンが収縮添字に対応する**（mma のフラグメント配置がそう要求する）ためであり、
CUDA core 版では割り当ての自由度でそれを回避できる。

## 4. 検証

すべて `SCALE_DG_VARYING_COEFF=1`（点ごとに変動する `u,v,w,Escale,normal_fn,Fscale`）で、
完全な `dqdt(:,1:Ne)` を比較した。

| ケース | 基準 | 相対差 |
|---|---|---|
| `Ne=2³` | `CUDAFORTRAN_SPLIT` | 2.10e-16 |
| `Ne=4³` | `CUDAFORTRAN_SPLIT` | 4.16e-16 |
| `Ne=4³` | `OPENACC_ASIS` | 1.37e-14 |
| `Ne=2³` 定速度 | `CUDAFORTRAN_SPLIT` | 2.50e-16 |

`OPENACC_ASIS` との差が 2 桁大きいのは総和順序の違いによるもので、
他の実装間の差と同じ性質である。CUDA ビルドと非 CUDA ビルドの両方が通ることも確認した。

## 6. 理論仕事量と達成効率

理論値（1 RK stage あたり、`Nq³*Ne = 16.78 M` DOF）。
体積は 1 ノードあたり `6*Nq + 20` FLOP（3 方向の収縮 `3*2*Nq`、流束積 3、
`Escale` 5、lift 11、最終和 1）、面は 1 面点あたり 21 FLOP。

| | p=7 | p=15 |
|---|---|---|
| 体積 FLOP/ノード | 68 | 116 |
| 面点/要素 | 384 | 1536 |
| 理論 FLOP / call | 1.405e9 | 2.078e9 |
| 理論 DRAM バイト / call | 1.577e9 | 1.326e9 |
| **ncu 実測 DRAM バイト / call** | **1.598e9** | **1.361e9** |

実測が理論の 1.01〜1.03 倍で、**面 gather はほぼ全てキャッシュで吸収されている**。
DRAM トラフィックに無駄はない。

達成効率（ncu ではなく通常実行の device 時間を使用。GB200 のピークは
FP64 CUDA core = FP64 TC = 40.1 TFLOP/s、DRAM 約 7.9 TB/s）:

| | TFLOP/s | ピーク比 | TB/s | ピーク比 |
|---|---|---|---|---|
| p=7 `FUSED_TC` | 5.14 | 12.8% | 5.84 | 74% |
| p=7 `FUSED` | 4.24 | 10.6% | 4.83 | 61% |
| p=15 `FUSED` | 4.79 | 11.9% | 3.14 | **40%** |

**演算強度が倍になった分、p=15 は帯域の壁からは離れた（74% → 40%）。
しかしそれを FLOP レートに変換できておらず、ピーク比は 12% 前後に張り付いたままである。**

## 7. ncu による律速の同定（Slurm job `54662`）

ncu はクロックを固定するので絶対時間は通常実行より 1.3 倍長い。比率で読むこと。

| メトリクス | p=7 `FUSED` | p=15 `FUSED` |
|---|---|---|
| Duration | 510.4 µs | 679.4 µs |
| Memory Throughput（メモリ系の最大） | **95.6%** | **74.1%** |
| DRAM Throughput | 39.5% | 25.3% |
| L2 Throughput | 31.2% | 19.1% |
| Compute (SM) Throughput | 41.4% | 36.0% |
| Executed IPC | 1.20 | **0.89** |
| Registers / thread | 32 | **62** |
| Block Limit Registers | 8 | **1** |
| Block Limit Shared Mem | 9 | **1** |
| Block Limit Warps | 8 | 2 |
| Achieved Occupancy | **96.6%** | **49.2%** |

**p=7 と p=15 で律速の性格が変わっている。**
p=7 はメモリ系 95.6% で飽和した「詰まっている」状態だが、
p=15 は**どのユニットも飽和していない**（メモリ 74%、SM 36%）。
実体は **62 レジスタによる 1 ブロック/SM = 占有率 49%** で、
7 回の `syncthreads` のたびに切り替える先の他ブロックが SM 上に存在しない。
IPC が 1.20 から 0.89 に落ちているのがその帰結である。

## 8. 不採用にした 2 つの調整

**`launch_bounds(1024,2)`**: レジスタは 62 → **32、spill ゼロ**で通った
（`cuobjdump` で `LOCAL:0` を確認）。にもかかわらず device
26.03 → **27.81 ms（+6.8%）**。`Block Limit Shared Mem` が 1 のままなので
ブロック数は増えず、レジスタを削った分だけアドレス再計算が増えただけだった。

**さらに carveout 50% を要求**: device **28.18 ms（+8.2%）**。
`tc_paper_survey_2407.09621.md` §13.4 と同じ結果である。
占有率を上げるにはレジスタと shared の**両方**の制限を同時に外す必要があり、
このカーネルの生きた状態（4 累算器 + 4 個の `q` = 16 レジスタ分）を考えると
32 レジスタで 2 ブロックを成立させる余地は無い。両方とも差し戻した。

## 9. Tensor Core 版 `tendency_fused_p15_tc_kernel`

第 7 節の結果を受けて TC 版を実装した。判断の根拠は天井の比較である。
融合カーネルの DRAM 転送量は理論最小の 1.03 倍なので、カーネルを分割して
占有率を稼ぐ案は必ず転送量を増やす側にしか動かない。3 カーネル分割
（面流束 → xy → z+lift）を見積もると約 2.23 GB/call = 1.64 倍で、
仮に 6.5 TB/s で回っても 343 µs が下限になる。一方 TC 版は転送量を
1.361 GB のまま保てるので、p=7 TC の実績 5.84 TB/s に届けば 233 µs になる。
**分割案の最良値が TC 版の天井に届かない**、というのが優先順位の理由である。

### 設計

shared 戦略は CUDA core 版と同じ「バッファ 1 本を方向ごとに使い回す」を流用した。
これは TC かどうかと直交する話なので、事前調査が TC 移植の最大の障壁と見ていた
「3 本の流束パネルで 96 KB」という問題は、この時点で既に解決済みだった。

m8n8k4 のタイルは 8x8 だが Nq=16 のプレーンは 16x16 なので、
1 プレーンあたり出力タイル 4 枚・k ステップ 4 回になる（p=7 は 1 枚・2 回）。
1 warp が 1 プレーンの j 半分（i は両半分）を持ち、レーンあたりの出力は
`i = tn*8 + 2*colk` とその隣で 4 ノード、CUDA core 版と同じ 4 ノード/スレッドになる。

**フラグメント配列は 3 方向で共用できる**。x は B オペランド `D[i][l]`、
y は A オペランド `D[j_out][j_in]`、z は A オペランド `D[k_out][l]` として読むが、
どの場合もレーンが欲しいのは `D[tile*8 + row][colk + 4*ks]` なので、
`(tile, ks, row, colk)` で引く 1 つの配置で足りる。

**swizzle は 1 本で x と y の両方を賄える**。x はパネルを
`(i = colk + 4*ks, j = tm*8 + row)` で読むので colk がビット 0-1、row がビット 4-5 に入り
ビット 2-3 が死んで 4-way になる。y は `(i = tn*8 + row, j = colk + 4*ks)` で
役割が入れ替わるだけの同じ絵なので、**ノードのビット 4-5 をアドレスのビット 2-3 に
畳む 1 つの関数**で両方直る（`sw_xy15`）。Nq=8 の `sw_xy` を 1 ビット広げた形である。
k ステップのオフセットは x がビット 2-3、y がビット 6-7 で、
どちらも `sw_xy15` が読まないビットなので、swizzle 後のアドレスに対する
単なる XOR のままでよい。

### 検証

| ケース | 基準 | 相対差 |
|---|---|---|
| p=15 TC `Ne=2³` | `CUDAFORTRAN_SPLIT` | 2.10e-16 |
| p=15 TC `Ne=4³` | `CUDAFORTRAN_SPLIT` | 1.30e-14 |
| （対照）p=7 TC `Ne=4³` | `CUDAFORTRAN_SPLIT` | 3.37e-15 |
| （対照）p=7 CUDA core `Ne=4³` | `CUDAFORTRAN_SPLIT` | 0（ビット一致） |

TC 版だけ差が大きいのは mma の 4 項内積が総和順序を変えるためで、
**p=7 でも同じことが起きている**（CUDA core 版はビット一致、TC 版は 3.4e-15）。
収縮長が倍になれば誤差も増えるので Nq=16 で 1.3e-14 は想定内であり、
既存の `OPENACC_ASIS` と `CUDAFORTRAN_SPLIT` の差 1.37e-14 と同じ大きさである。
差の分布も滑らかで（1e-14 超が 262144 点中 12 点、1e-13 超はゼロ）、
局所的な破綻ではない。

### 結果

| | 1 stage | TFLOP/s | ピーク比 | TB/s | ピーク比 |
|---|---|---|---|---|---|
| p=7 `FUSED` | 331.0 µs | 4.24 | 10.6% | 4.83 | 61% |
| p=7 `FUSED_TC` | 273.6 µs | 5.13 | 12.8% | 5.84 | 74% |
| p=15 `FUSED` | 433.9 µs | 4.79 | 11.9% | 3.14 | 40% |
| **p=15 `FUSED_TC`** | **363.0 µs** | **5.72** | **14.3%** | **3.75** | **47%** |

ncu（Slurm job `55485`、クロック固定）:

| メトリクス | p=15 `FUSED` | p=15 `FUSED_TC` |
|---|---|---|
| Duration | 679.4 µs | 543.1 µs |
| **Compute (SM) Throughput** | **36.0%** | **19.8%** |
| Memory Throughput | 74.1% | 67.3% |
| DRAM Throughput | 25.3% | 31.6% |
| Executed IPC | 0.89 | 0.64 |
| Registers / thread | 62 | 64 |
| Achieved Occupancy | 49.2% | 48.9% |

**TC は狙いどおり SM 側の仕事をほぼ半減させた**（36.0% → 19.8%）。
mma はオペランド 1 回の読み出しを 8x8 タイル全体の演算に効かせるので、
CUDA core 版で 1 shared ロードにつき 1 FMA だったものが大幅に減る。
device 時間はその分だけ縮んで **26.04 → 22.22 ms（1.17 倍）**。
第 10 節の swizzle 2 本を入れた最終形は **21.78 ms（1.196 倍）**である。

**しかし帯域は使い切らなかった**（47%）。残った律速は memory pipe 67% で、
DRAM が 32% しかないこととの差は shared アクセスとキャッシュに載る global
アクセス（特に面 gather）である。占有率は 48.9% のまま動いていない。

### TC の優位は Nq とともに伸びるか

**伸びない。** CUDA core 版に対する TC 版の比は p=7 で 1.21 倍、p=15 で 1.17 倍で、
ほぼ横ばいかむしろわずかに縮んでいる。理由は両方の次数で**演算パイプが律速ではない**
ことにあり、p=15 で SM throughput が 19.8% まで落ちてなお速くならないことがそれを示す。
TC が効くのは演算能力ではなく命令数であり、命令数を削り切った後に出てくるのは
メモリ経路と占有率という別の壁である。

### Nq=16 の融合カーネルは構造的に占有率 50% で頭打ちである

CUDA core 版と TC 版が**どちらも 49% で並んだ**のは偶然ではない。

1. z 収縮が要素全体を要求するので、1 要素 = 1 ブロックで、shared に 32 KB の
   バッファが要る。
2. ブロックあたり最大 1024 スレッドなので、4096 ノードに対し **4 ノード/スレッドが下限**。
3. 4 ノード分の累算器と `q` を持つと 32 レジスタには収まらない
   （実測 62 と 64）。1024 スレッドでの上限である 64 レジスタに TC 版は**ちょうど張り付いており**、
   レジスタの余裕はゼロである。
4. レジスタが 32 を超えると `Block Limit Registers` が 1 になり、
   carveout を広げて shared 側の制限を外しても 2 ブロック目は載らない（第 8 節の実測）。

したがって **Nq=16 では、融合したままで占有率を上げる道は無い**。
これは第 8 節の 2 つの不採用の一般化であり、占有率を上げたければ
カーネルを分割するしかないが、その場合の下限は上で見た 343 µs で、
TC 版が既に出している 370 µs と大差がない。

## 10. 面 gather の調査と、そこで見つかったバンクコンフリクト

第 9 節末が次の標的に挙げた「memory pipe 67% と DRAM 32% の差」を追った。

### 面 gather はアブレーションで上限を測ってから捨てた

要素の節点順序は `i + 16j + 256k` なので、`i` を固定する面（面 2 と 4、すなわち ±x）は
**本質的に 16 double = 128 B ストライド**になり、1 レーンが 1 キャッシュラインを占める。
p=7 で `tc_paper_survey_2407.09621.md` §13 が M 側を shared に置いて −5.1% を得たのは
この構造に対する対策だった。

Nq=16 で同じ投資に見合うかを、**±x 面の gather アドレスを連続アドレスに差し替える
アブレーション**（数値は壊れるが命令数は不変）で先に測った:

| 版 | device 時間 | 基準比 |
|---|---|---|
| baseline | 22.30 ms | — |
| ±x 面の **M 側**を連続化 | 21.85 ms | **−2.0%** |
| ±x 面の **M と P 両方**を連続化 | 20.08 ms | −9.9% |
| 面フェーズを丸ごと削除 | 14.44 ms | −35.2% |

読み取れることは 3 つ:

1. **p=7 の手法をそのまま持ってきても上限 2.0%**。面点率が 75% → 37.5% に落ちた分だけ
   価値も落ちている（p=7 の実測 −5.1% の半分以下）。しかも Nq=16 では
   1024 スレッド時のレジスタ上限 64 本に張り付いていて、
   `u,v,w` を面用に保持する余地が無い。shared に逃がすには
   `q,u,v,w` で 16 KB 必要で 48 KB の静的枠を超え、`qM` と `VelM` だけに絞っても
   8 KB とバリア 1 回と 3 フェーズにまたがるステージング処理が要る。
   **上限 2.0% に対して割に合わないので不採用**とした。
2. **P 側の方が大きい（差分 7.5%）が、隣接要素のデータなので原理的にステージングできない。**
   面 2 の P 側は +x 隣接要素の `i=0` 面で、そちらも同じくストライドしている。
3. **面フェーズはカーネルの 35%（約 131 µs/stage）を占めるが、外に出すと損をする。**
   同じ仕事を単独カーネルでやる `CUDAFORTRAN_SPLIT` の Element boundary flux は
   p=15 で約 166 µs/stage かかっている。融合カーネルの中では直前に読んだ体積データが
   キャッシュに残っているぶん安く済んでおり、外出しは `flux_bnd` の往復
   （+100 MB/stage）も足して確実に悪化する。

### 代わりに見つかったもの: shared load の 4-way コンフリクト

生カウンタ（job `55570`）を CUDA core 版と並べたところ、狙いとは別のものが出た。

| | p=15 core | p=15 TC |
|---|---|---|
| shared ld 命令 | 31.20 M | **7.34 M** |
| shared ld コンフリクト | 15,465 | **3,212,086** |

**TC 化で shared ロード命令は 4.25 倍減った**（mma がオペランド 1 回の読み出しを
タイル全体に効かせるという狙いは数字で確認できた）。ところが**コンフリクトは 200 倍に増えて
いて**、残った 7.34 M 命令の 44% が衝突していた。CUDA core 版が
レーンを `i` 方向に並べて swizzle 無しで conflict free だったのに対し、
TC 版はレーンが mma のフラグメント配置に縛られるためである。

原因は 2 か所あり、どちらも**書き手と読み手で添字の形が違う**ことによる。

**z 微分の往復**: mma の出力マップで書き、x/y のマップで読む。
書き側は `2*colk` がビット 1-2・出力 `k` がビット 8-10、
読み側は `2*colk` がビット 1-2・`j` がビット 4-6。ビット 0 と 3 が
どちらでも死んでいるので、**書き側のビット 8-9 と読み側のビット 4-5 の両方を
そこへ畳む**と 2 フェーズとも同時に conflict free になる。
各フェーズは相手側のソースビットを warp 内で不変な値としてしか見ないので、
余分な項は定数 XOR になって害が無い。

**面 5/6 の lift 読み出し**: 面 1/3 は `(i,k)`、面 2/4 は `(j,k)`、面 5/6 は `(i,j)` で読む。
warp 内で `k` は不変なので前 2 者はブロードキャストになるが、`(i,j)` 形は
`2*colk` がビット 1-2、`j` がビット 4-7 でビット 0 と 3 が死に、
**epilogue の 8 本のロードが 4-way** になっていた。`j` のビットを死にビットに畳むと
面 5/6 が直り、他の 4 面はそこが warp 不変なのでブロードキャストのまま残る。
書き側は `fp = tid` の 16 連続なので、warp 内不変ビットによる畳み込みは
16 連続の置換のままである。

### 結果

どちらも**レジスタも shared も増やさない**純粋な置換で、
出力は変更前と**ビット一致**（`Ne=4³`、点ごと変動係数）。

| 版 | device 時間 |
|---|---|
| TC ベースライン | 22.25 ms |
| + z 往復の swizzle | 21.98 ms（−1.2%） |
| + 面 5/6 の swizzle | **21.78 ms（累計 −2.1%）** |

ncu（job `55602`、`55570` との比較）:

| メトリクス | 前 | 後 | 変化 |
|---|---|---|---|
| shared ld コンフリクト | 3,212,086 | 202,820 | **−93.7%** |
| stall short_scoreboard | 2.69 | 1.86 | −30.9% |
| stall mio_throttle | 5.93 | 4.48 | −24.5% |
| stall barrier | 7.73 | 6.33 | −18.1% |
| stall long_scoreboard | 22.39 | 20.24 | −9.6% |
| global ld sectors | 62.36 M | 62.36 M | ±0 |

Nq=8 では完全 conflict free の swizzle が**遅かった**（survey §10.3）が、
Nq=16 では素直に速くなる。あちらは 2-way を 1-way にする話で、
こちらは 4-way を 1-way にする話であり、桁が違う。

最終的な p=15 `FUSED_TC` は **363.0 µs/stage、5.72 TFLOP/s（14.3%）、
3.75 TB/s（47%）**、CUDA core 版に対して **1.196 倍**。

## 11. 結論と次の点

- 同一 DOF での 3 点目が入った。`reports/README.md` の
  「p=7 は帯域・L1 律速、p=255 は演算律速」という対比に対し、
  **p=15 はそのどちらでもなく、占有率律速という第三の状態**にある。
- 演算強度を上げれば帯域の壁からは離れられるが、
  **CUDA core の融合カーネルはそれを演算性能に変換できない**。
  1 スレッドが持つ状態量が `Nq` とともに増え、レジスタが先に尽きるためである。
- **Tensor Core 版は 1.17 倍で、帯域は使い切らなかった**（第 9 節）。
  mma は命令数を削る（SM 36.0% → 19.8%）が、レジスタは減らさない。
  当初の事前予測（「p=15 はまだ帯域側にいるはず」）は**外れ**、
  「TC で帯域を使い切れるはず」という次の予測も**外れた**。
  実際に出てきたのは、**Nq=16 の融合カーネルは占有率 50% で構造的に頭打ち**という壁である。
- 面 gather を追ったところ（第 10 節）、**p=7 の M 側ステージングは Nq=16 では上限 2.0%**
  にしかならず不採用。代わりに shared load の 4-way コンフリクトが 2 か所見つかり、
  swizzle 2 本で **−2.1%**（22.25 → 21.78 ms）、コンフリクト **−93.7%**。
  レジスタも shared も増やさず、出力はビット一致。
- 面フェーズはカーネルの 35% を占めるが、その大半は P 側 gather という
  原理的に手の出ない部分と、単独カーネルに出すとかえって高くつく部分である。
- Nq=32 以降は要素が shared に載らないので、この設計は p=15 で打ち止めである。
  p=31 は別の構造（タイル化）を要する。
