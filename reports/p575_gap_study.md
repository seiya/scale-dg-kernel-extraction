# p=575 GEMM / GEMM_FUSED 対応

## 1. 結論

`PolyOrder=575`（`Nq=576`）を `CUDAFORTRAN_GEMM` と
`CUDAFORTRAN_GEMM_FUSED` で実行可能にした。既存の cuBLAS / CUTLASS
カーネルは runtime `Nq` で実装済みであり、必要なコード変更は p=575 を
対応済みの2経路だけに制限する dispatch guard の追加である。

点ごとに変化する `u`, `v`, `w`, `Escale`, `normal_fn`, `Fscale` を使い、
両経路の全 owned `dqdt` 191,102,976 点を比較した。最大絶対差は
`3.5527136788005009e-15`、非有限値は0で、差は浮動小数点丸めの範囲だった。

GB200 の同一入力を3回ずつ実行した中央値では、warm-up 後の device tendency が
GEMM の 20.912 ms/stage に対して GEMM_FUSED は 20.453 ms/stage で、2.20%短い。

## 3. 実装とハードウェア上の成立条件

`Ne=1`, `Nq=576`, `Np=576^3=191102976` で、既存の可変次数 GEMM を使う。

- x: `C(576, 576^2) = D1D(576,576) * flux_x(576,576^2)`
- y: 576 batch の `576 x 576 x 576` GEMM
- z: `C(576^2,576) = flux_z(576^2,576) * D1D_tr(576,576)`

`Nq=576` は 64 の9倍かつ16の36倍なので、既存の CUTLASS tile と FP64 MMA の
端数処理を必要としない。y GEMM の batch 数 `Nq*Ne=576` も CUDA grid.z の
上限65535を十分下回る。64-bit 安全化済みの host-side extent / offset を使い、
device kernel の `Np=191102976` は32-bit signed integer範囲内である。

`CUDAFORTRAN_GEMM` は3方向を cuBLAS で評価し、separable lift と assembly を
行う。`CUDAFORTRAN_GEMM_FUSED` は x/y を CUTLASS、z を custom epilogue 付き
CUTLASS で評価し、z 出力時に x/y 微分、点ごとの `Escale`、全6面の lift を
組み立てて `dqdt` を直接書く。どちらも点ごとの `q*u`, `q*v`, `q*w` と M/P
両側の数値流束を保持している。

p=575、`Ne=1` の主要 device allocation の理論値は次である。小さい演算子、
mapping、runtime allocation は含めない。

| 経路 | 主要配列 | bytes | GiB |
|---|---:|---:|---:|
| `GEMM` | `160*Np` | 30,576,476,160 | 28.48 |
| `GEMM_FUSED` | `144*Np` | 27,518,828,544 | 25.63 |
| 差 | `16*Np` | 3,057,647,616 | 2.85 |

差は GEMM_FUSED が不要とする `deriv_z` と `surface_lift` の2配列である。
`q0` と `dqdt` は owned 領域だけ、`q/u/v/w` は packed halo を含む2要素相当の
領域を確保する現行実装を前提に数えた。

**現行treeでの訂正（2026-08-28、`p1023_gap_study.md`）:** 上表はこの測定時点の
allocationを記録したものである。p=1023対応で通常GEMMも未使用`surface_lift`を
除き、z-GEMM出力を`dqdt`に置いて`deriv_z`を再利用するようになった。現行treeの
通常GEMMはGEMM_FUSEDと同じ`144*Np` = 25.63 GiBである。浮動小数点演算と定常時の
write/read回数は変わらないため、§5の測定表は当時の結果として維持する。

再現用の1ステップ入力として次を追加した。

- `input_p575_val_gemm.conf`
- `input_p575_val_gemm_fused.conf`

## 4. 数値検証

### 4.1 方法

各経路の最初の RK stage が計算した owned `dqdt(:,1:Ne)` を一時ファイルへ出力し、
全191,102,976個の FP64 値を逐次比較した。両実行に
`SCALE_DG_VARYING_COEFF=1` を指定し、点変化する速度・幾何係数・面係数を使用した。
一時 dump と比較プログラムは検証後に削除した。

### 4.2 結果

| 係数 | 比較点数 | exact 不一致 | 非有限値 | 最大絶対差 | 最大相対差 |
|---|---:|---:|---:|---:|---:|
| 点変化 | 191,102,976 | 83,136,618 | 0 | 3.5527136788005009e-15 | 4.1358014856910329e-9 |

最大相対差は値が0に近い点で生じる。最大絶対差は数 ulp の範囲であり、異なる
GEMM 縮約順による丸め差と整合する。全 owned field と全6面を含む比較なので、
定数速度や代表スカラーへの特殊化はない。

通常の benchmark 係数でも追加した両1-step入力が完走し、最終値の min/max は
両経路でそれぞれ `-9.999425159858519E-01` と
`9.999425167637535E-01` だった。

## 5. 性能

### 5.1 入力と測定方法

測定用一時入力は `/tmp/conf_perf_p575_gemm.conf` と
`/tmp/conf_perf_p575_gemm_fused.conf` とし、違いは `DqdtKernel_Type` だけである。

```fortran
NeX = 1; NeY = 1; NeZ = 1
PolyOrder = 575
dt = 1.0D-8
nstep = 50
output_interval = 50
WarmupStep = 5
UseCudaGraph = .false.
MeasureKernelTime = .true.
CublasEmulation = .false.
CutlassMmaShape = "8x8x4"
```

各経路を3回ずつ実行した。各runでは先頭5 stepを実行するが計時から除き、残り
45 step = 135 RK stages を集計した。表は3 runの中央値である。

### 5.2 結果

| 経路 | Main [s] | Main [ms/step] | device tendency [s] | device [ms/stage] |
|---|---:|---:|---:|---:|
| `CUDAFORTRAN_GEMM` | 2.92317 | 64.9594 | 2.82311 | 20.9119 |
| `CUDAFORTRAN_GEMM_FUSED` | 2.86104 | 63.5787 | 2.76111 | 20.4527 |

GEMM_FUSED は device tendency で2.20%、end-to-end Main/stepで2.13%短い。
GEMM_FUSED 内の volume GEMM 区間は中央値2.55809 s、18.9488 ms/stageだった。

各runの device tendency 合計は GEMM が 2.82237 / 2.82329 / 2.82311 s、
GEMM_FUSED が 2.76123 / 2.76111 / 2.76105 s であり、run間変動より経路差が大きい。

この測定では `ncu` を使っていないため、profiler measured FLOP/s や bandwidth は
報告しない。理論 volume work は3方向合計 `6*Nq^4 = 660,451,885,056`
FLOP/stage だが、device tendency には pointwise flux、全6面の numerical flux、
lift、assembly も含まれる。

## 6. 結論と残る課題

- p=575 は現行の generic GEMM 実装、batch上限、32-bit device index の範囲で
  ハードウェア実行可能である。
- 数値的には点変化係数を含む全 owned `dqdt` が丸め誤差範囲で一致した。
- p=575 でも最速は `CUDAFORTRAN_GEMM_FUSED` だが、優位は2.20%である。
- 本結果は p=575、`Ne=1` のもの。p=1023 では `Np=1024^3=2^30` 自体は
  32-bitに収まるが、その倍数となる extent / offset が境界を越える。既知の
  host-side境界は対処済みだが、残る32-bit device添字とメモリ容量を別途検証する必要がある。

上記p=1023の残課題は`p1023_gap_study.md`で解決し、両GEMM経路を実機検証した。

## 11. `GEMM_FUSED` の最適化（2026-09-01）

対象は `CUDAFORTRAN_GEMM_FUSED`、`namelists/perf_p575_gemm_fused.conf`
（`Ne=1`、`nstep=50`、`WarmupStep=5`、graph off）。親 commit `f7788bb`。
ビルド `make CUDA=1 GPUFLAGS=-gpu=cc100 GPUNVCCFLAGS=-arch=sm_100`。
採否は占有 GPU 上の 12 回交互 A/B（中央値、135 measured stages）。
点変化係数の owned `dqdt` 191,102,976 点で検証した。

nsys job `71124`（c178、baseline、`nstep=4`）の 1 stage 中央値:

| カーネル | µs | ピーク比の読み |
|---|---:|---|
| x CUTLASS `64x128` GEMM | 6498 | 220e9 FLOP → 84.5% of 40.1 TFLOP/s |
| y `64x64` batched ScaleAdd | 5776 | 同 FLOP → 95.1% |
| z assembly `64x32` | 6146 | 同 FLOP + epilogue → 89.3% |
| `volume_flux` | 1478 | DRAM 91%（ncu job `71133`） |
| `elembnd_flux` | 105 | x GEMM の裏に隠れている |

device fused 合計は volume GEMM 3 本 + flux で約 19.9 ms。elembnd は隠れる。
login 3-run 中央値は共有 GPU で 20.5 ms 前後まで振れるので、以下は占有 GPU だけを分母にする。

### 11.1 不採用: `flux_y/z` を x GEMM の裏へ（job `73615`、c182）

p=255 では flux 全体が x GEMM より長く隠せない。p=575 では
`flux_yz ≈ 1.0 ms` ≪ `x ≈ 6.5 ms` なので、`flux_x` のあと side2 で y/z を
流すと 4% 近い天井がある。実装はビット一致（191,102,976 点 `cmp`）。

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A 現行 | 2.69924 | 19994 | 2.69871–2.69977 |
| B 重ね | 2.73552 | 20263 | 2.73504–2.73643 |

**B vs A +1.344%、レンジ非重複。** p=63 §26 と同じ機構で、フルグリッドの
DRAM カーネルが x GEMM から SM を奪う。コードは戻した。

### 11.2 採用: Nq≥512 の x を y と同じ `64x64` batched にする（job `73628`、c179）

x が 84.5% なのに対し、同一 FLOP の y が 95% 出ている。p=255 §10.4 の
batched x は +0.7% で負けているので、分岐は `Nq>=512` だけ。
`GEMM_CUTE` の `run_volume_gemm_x` も同じタイルにする（経路の mainloop を
分岐させない）。fused x は `GemmYScale`（`PointwiseScale`）の batched。

点変化 vs `CUDAFORTRAN_GEMM`: max abs **1.78e-15**、非有限 0。

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A `64x128` | 2.70575 | 20043 | 2.70515–2.70678 |
| B batched `64x64` | 2.62627 | 19454 | 2.62560–2.62735 |

**B vs A −2.937%、レンジ非重複。** Main 62.34 → 60.59 ms/step。

nsys job `74701`（c399、B）: x が `GemmBatched` **5890 µs**（6498 から −608 µs）、
y 5758、z 6118、flux 1478。A/B の −589 µs/stage と一致する。

### 11.3 不採用: z を `64x64` にする（job `74705`、c182）

x/y が揃ったあと z が 6118 vs y 5758（+360 µs）で最遅。`Nq>=512` だけ
`GemmZWideSq` を足した。xbatch に対し**ビット一致**。

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A z `64x32` | 2.61968 | 19405 | 2.61910–2.62054 |
| B z `64x64` | 2.63101 | 19489 | 2.62966–2.63190 |

**B vs A +0.433%、レンジ非重複。** コードは戻した。z の 64x32 は
epilogue 付きのまま y のタイルに寄せても得しない。

### 11.4 残る天井

B 採用後の 1 stage は x+y+z+flux ≈ 5.89+5.76+6.12+1.48 = **19.25 ms**
（占有 A/B 19.45 ms に side join と RK 外が乗る）。

- **`volume_flux` 1.48 ms（7.6%）**: DRAM 91%。重ねは §11.1 で赤字、
  `double2` は §11.5 で +0.075%。`q*vel` を GEMM に融合するのは
  p=255 §0.2 で 1.66 倍。契約内の実装ノブは閉じた。
- **z epilogue 対 y +0.36 ms（1.8%）**: 数値契約上の lift / `Escale_z` /
  `dqdt` ストア。p=255 §10 と同じ仕事で、次数が上がると GEMM 本体に埋もれる。
- **elembnd 0.11 ms**: すでに隠れている。
- **CUDA graph**: カーネルが 6 ms 級なので launch の天井は小さい。Main 用ノブ
  として既にある（既定 off）。占有 GPU の Main A/B は未測。

### 11.5 不採用: `volume_flux` の C++ `double2`（job `74712`、c182）

Fortran は `LDG.128` を出さないので、同じ積を `double2` 1 本で運ぶ C++ カーネルに
差し替えた。xbatch に対し**ビット一致**。Slurm stdout（12+12、二重記録なし）:

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A Fortran flux | 2.61987 | 19406 | 2.61927–2.62015 |
| B `double2` | 2.62184 | 19421 | 2.62140–2.62219 |

**B vs A +0.075%、レンジ非重複。** 全 12 対で B が 11–20 µs/stage 遅い。
DRAM 91% では命令数を半分にしてもバイトが減らず、発行の方が高い。コードは戻した。
これで flux 側の契約内ノブは閉じた（重ね §11.1、ベクトル化本節、融合は p=255 §0.2）。

### 11.6 不採用: CUDA graph（job `74724`、c182）

§11.4 で「カーネルが 6 ms 級なのでローンチの天井は小さい」と書いた分を実際に
測った。同じ実行ファイル（`.xbatch`）で `UseCudaGraph` だけを切り替え、占有 GPU
上で 12 回交互。graph 経路は `Cal_tend:` を測らないので分母は `Main per step:`。

| | Main ms/step | レンジ |
|---|---:|---|
| A `UseCudaGraph=.false.` | 60.4209 | 60.4178–60.4284 |
| B `UseCudaGraph=.true.` | 60.4536 | 60.4498–60.4576 |

**B vs A +0.054%、レンジ非重複。** 1 stage あたり 6 ローンチ、1 step で 18。
graph 化で消える host 側のローンチ費用より、replay が side stream の fork/join を
graph edge として持つ分の方がわずかに高い。既定の off のままとする。

### 11.7 不採用: `flux_y/flux_z` の grid を絞って x GEMM の裏へ（job `74740`、c368）

§11.1 は `flux_y/flux_z` をフルグリッドで side2 に流して +1.344% だった。負けた
機構を「フルグリッドの DRAM カーネルが x GEMM から SM を奪う」と書いたので、
**grid を絞れば直る**という仮説を測った。`volume_flux_kernel` を
`volume_flux_x_kernel`（main、q·u だけ）と `volume_flux_yz_kernel`（side2、
grid-stride でブロック数を上限つきに）に分け、side2 の join を x GEMM と
y GEMM の間に入れた（`launch_volume_gemm_xy` をこの分岐だけ 2 本の entry に
割った）。q を 2 度読む分 1.5 GB 増えるが、それは x GEMM の裏に隠れる想定。

191,102,976 点の `dqdt` は `SCALE_DG_VARYING_COEFF=1` で**ビット一致**
（GEMM の順序も引数も変えていない）。占有 GPU で 8 回ずつ交互:

| ブロック上限 | fused s | µs/stage | レンジ | off 比 |
|---|---:|---:|---|---:|
| 0（現行、分割しない） | 2.618860 | 19399 | 2.618740–2.619180 | — |
| 888 | 2.666925 | 19755 | 2.666240–2.669110 | +1.835% |
| 1776 | 2.676555 | 19826 | 2.675980–2.677240 | +2.203% |
| 3552 | 2.673265 | 19802 | 2.672860–2.673580 | +2.077% |

**どの上限でも赤字、レンジは全部非重複。** login node での粗い掃引では
uncapped が +36%、148 ブロックが +13% で、下に凸だが底が現行より上にある。
つまり §11.1 の負けは「grid が大きすぎた」からではない: **grid を絞ると
flux 側が長くなって y GEMM の開始を遅らせ、grid を広げると x GEMM から SM を
奪う**という両側から挟まれた形で、間に得をする窓が無い。コードは戻した。

| B `flux_y/flux_z` を消す | 2.515375 | 18632 | 2.515190–2.515580 |

**天井は 765 µs/stage = 3.943%。** 測定誤差よりはるかに大きいので「小さいから
終わり」ではない。ただし契約内の到達手段（別ストリームで重ねる §11.1 / §11.7、
ベクトル化 §11.5、GEMM への融合 = p=255 §0.2 で 1.66 倍）は全部測って赤字で、
**賞金は残っているが取りに行く道が無い**という状態である。

**3 本の GEMM。** `--set full` を 1 ジョブ内で x / y / z に当てた
（`.xbatch`、`nstep=4`、`-s 9 -c 9`）。時間は ncu のクロック固定込みなので比だけを読む。

| | grid | block | 動的 shared | reg/thread | ブロック/SM | 実効 warp/SM | 占有率 | Compute (SM) | DRAM | L2 hit | 発行命令 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| x `GemmBatched` 64×64 | (9,9,576) | 128 | 65536 | 130 | 3 | 11.91 | 18.6% | **94.77%** | 5.25% | 76.8% | 1.771e9 |
| y `ScaleAdd` 64×64 | (9,9,576) | 128 | 65536 | 168 | 3 | 11.71 | 18.3% | **95.66%** | 7.09% | 72.1% | 1.839e9 |
| z `DqdtAssembly` 64×32 | (9,10368,1) | 64 | 49152 | 254 | 4 | 7.96 | 12.4% | **92.43%** | 6.78% | 80.5% | 2.321e9 |

**3 本とも FP64 パイプ律速で、DRAM は 5〜7% しか使っていない。** 数え合わせ:
1 stage の GEMM は各 2·576⁴ = 220 GFLOP、`DMMA.8x8x4` は 1 warp 命令あたり
512 FLOP なので mma は 4.30e8 warp 命令。スケジューラ数は
`Total SMSP Elapsed / SMSP Active` から約 605、よってスケジューラあたり 711k
命令を 11.92e6 active cycle で発行 = **16.8 cycle に 1 本**。`DMMA.8x8x4` が
スケジューラの 16 FP64 レーンを 256 FMA / 16 = 16 cycle 占めるので、
パイプ占有は 16/16.8 = **95.2%** で、ncu の Compute (SM) 94.77% と一致する。
発行スロット自体は 24〜31% しか埋まっていないので、**命令を減らしても速くならない**
（mma は x で全発行命令の 24.3%、z で 18.5% でしかない）。

MMA 命令形状を大きくする道は [`sm90_mma_shape_survey.md`](sm90_mma_shape_survey.md)
§2 で閉じている: GB200 の ptxas は `mma.sync.m16n8k4/8/16.f64` を
`DMMA.8x8x4` の 2/4/8 命令に展開するので、FP64 パイプの占有サイクルは変わらない。

実時間（nsys job `74701`）に直すと x 5890 / y 5758 / z 6118 µs は
それぞれ 37.4 / 38.2 / 36.0 TFLOP/s = **93.1% / 95.1% / 89.7% of 40.1**。
y に揃えられれば x で 133 µs、z で 361 µs、合わせて 494 µs = 2.5% が上限。
z が一番低いのは、64 スレッド（32×32 warp が 2 本）の CTA でレジスタ 254 本、
実効 7.96 warp/SM しか置けていないためと読める。次節がその検証。

### 11.9 不採用: z の warp タイルを 32×16 にする（job `74822`、c368）

§11.8 の「z だけ 7.96 warp/SM」を直しに行った。threadblock は 64×32 のまま、
warp タイルだけ 32×32 → 32×16 にすると CTA は 2 warp / 64 スレッドから
4 warp / 128 スレッドになり、shared は 48 KB のままなので 4 ブロック/SM ×
4 warp = 16 warp/SM と倍になる。`GemmZWide` の 1 行だけの変更。
191,102,976 点で**ビット一致**。

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A `32x32` warp | 2.621745 | 19420 | 2.620880–2.622320 |
| B `32x16` warp | 2.651300 | 19639 | 2.650750–2.651920 |

**B vs A +1.127%、レンジ非重複。** warp を増やしても速くならないのは §11.8 の
読み（FP64 パイプ 92% で律速、発行スロットは 31% しか埋まっていない）と整合する。
むしろ 32×16 warp は K ステップごとに A 32×K と B 16×K を読むので、
1 CTA あたりの shared フラグメント読み出しが 2×(32+32) から 4×(32+16) に
増え、mma あたりの LDS が増える方が効いた。**z の不足はレジスタでも占有率でも
なく、パイプに入れる命令の質の問題**である。

### 11.10 不採用: z の threadblock タイルを大きくする（job `74827`、c368）

§11.9 で warp を割っても駄目だったので、逆に CTA を大きくして CTA 数を減らす
方向を測った。`GemmZWide` の threadblock だけ替え、warp は 32×32 のまま。
どちらも 191,102,976 点で**ビット一致**。

| threadblock | warp/CTA | shared/CTA | ブロック/SM | fused s | µs/stage | レンジ | A 比 |
|---|---:|---:|---:|---:|---:|---|---:|
| A `64x32`（現行） | 2 | 48 KB | 4 | 2.619480 | 19404 | 2.619090–2.620160 | — |
| B `128x32` | 4 | 80 KB | 2 | 2.723930 | 20177 | 2.723310–2.724490 | +3.987% |
| C `128x64` | 8 | 96 KB | 2 | 2.839890 | 21036 | 2.839440–2.840610 | +8.414% |

**両方とも大差で赤字、レンジ非重複。** これで z のタイル軸は 5 点そろった:

| 変種 | A 比 | 出所 |
|---|---:|---|
| `64x32` / warp `32x32` | 0（現行） | — |
| `64x64` / warp `32x32` | +0.433% | §11.3 |
| `64x32` / warp `32x16` | +1.127% | §11.9 |

| `128x64` / warp `32x32` | +8.414% | 本節 |

CTA を大きくすると shared が増えて 2 ブロック/SM に落ち、8 warp/SM のまま
末尾の波が粗くなる（`Waves Per SM` は 153 → 77 → 38）。z の 89.7% は
タイルでは埋まらない。

### 11.11 天井ゼロ: x と y のオペランド役割の非対称（job `74849`、c368）

§11.8 で x 93.1% / y 95.1%。同じ 64×64 タイル・同じ grid・同じバッチ数なのに
2% 違う。違いは**どちらのオペランドが流れるデータか**である: x は
A = `D1D`（stride 0、crosswise レイアウト）/ B = `flux_x`（congruous）、
y は A = `flux_y` / B = `D1D_tr`。CUTLASS は A と B に別々の shared レイアウトを
使うので、これが 133 µs の出所かどうかを非合法アブレーションで切り分けた:
x の A と B を入れ替えて（`flux_x` を A、`D1D` を B）y と同じ役割にする。
結果は誤りだが、仕事・形状・エピローグは x のまま。

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A 現行 | 2.619650 | 19405 | 2.619080–2.620240 |
| B オペランド入替 | 2.619275 | 19402 | 2.618810–2.619720 |

**B vs A −0.014%、レンジ重複 = 差が無い。** A/B 役割の非対称は 133 µs の
どれ 1 つも説明しない。したがって「x を y の形に転置して書き直す」系の候補は
**天井ゼロ**であり、実装せずに落とす。

### 11.12 不採用: `Escale_x` を y のエピローグへ移す（job `74860`、c368）

§11.11 で x の 2% 不足はオペランド役割ではないと分かったので、残る違いである
**エピローグ**を測った。Nq > 64 では x が `PointwiseScale` で `Escale_x` を
掛けているが、Nq <= 64 の分岐は x をエピローグ無しにして y の
`kMulAddend` 側で `Escale_x` を掛ける。p=575 をその形にした（B）のと、
`Escale_x` をどこにも掛けない非合法アブレーション（C、x のエピローグ費用の天井）
を同じジョブで測った。B は `dqdt` 全点で max abs **1.78e-15**（rel 2.2e-16）。

| | fused s | µs/stage | レンジ | A 比 |
|---|---:|---:|---|---:|
| A 現行（x が `Escale_x`） | 2.621350 | 19417 | 2.620790–2.621660 | — |
| B y 側で `Escale_x` | 2.634425 | 19514 | 2.634180–2.634820 | **+0.499%** |
| C `Escale_x` を消す（非合法） | 2.613220 | 19357 | 2.612610–2.613540 | −0.310% |

**x のエピローグの天井は 60 µs/stage = 0.310% しかなく、それを取りに行く
唯一の契約内の道（y へ移す）は +0.499% で赤字。** y の `kMulAddend` は
`Escale_x` を y のアクセスパターンで読むので、x 側で読むより高い。
これで x 側の候補は尽きた: 役割の非対称は天井 0（§11.11）、エピローグは
天井 0.31% で移設は赤字、タイルは y と同じ最良のものを既に使っている（§11.2）。

### 11.13 採用: Nq≥512 の x / y を 3 段パイプラインにする（job `74862` / `74867` / `74871`、c368）

§11.8 で 3 本とも FP64 パイプ律速と分かったので、タイルではなく
**CUTLASS のソフトウェアパイプライン段数**を動かした。`GemmYScale`
（Nq>64 の x と y が両方使う 64×64 タイル）の段数だけを替える。
2 段は CUTLASS が受け付けない（`MmaMultistage` が 3 段以上を要求、214 エラー）。

| 段数 | shared/CTA | fused s | µs/stage | レンジ | 4 段比 |
|---|---:|---:|---:|---|---:|
| 3 | 48 KB | 2.611925 | 19348 | 2.611700–2.612250 | **−0.399%** |
| 4（従来） | 64 KB | 2.622395 | 19425 | 2.622260–2.622600 | — |
| 5 | 80 KB | 2.656610 | 19679 | 2.656320–2.656940 | +1.305% |

job `74867` で再現（3 段 −0.384%）。z も 3 段にすると 3 段 x/y 単独に対して
**+0.020%（レンジ非重複）**で悪化するので、**z は 4 段のまま**にした。

出荷形は §11.2 と同じく `Nq >= 512` だけの分岐にした（`GemmYScale3`。
`GEMM_CUTE` 側の mainloop を分岐させないため `GemmY3` も同じ段数にして
`run_volume_gemm_x` / `run_volume_gemm_y` の Nq≥512 分岐に入れた）。
`GEMM_FUSED` の 191,102,976 点は**ビット一致**、`CUDAFORTRAN_GEMM` との
点変化係数比較は max abs 1.78e-15。ゲート付きの確認 A/B（job `74871`）:

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A `.xbatch` | 2.622360 | 19425 | 2.622100–2.622570 |
| B `.st3gate` | 2.611890 | **19347** | 2.611740–2.612000 |

**−0.399%、レンジ非重複。** Main 60.42 → 60.17 ms/step。

**なぜ効いたか（ncu job `74911`、同一条件の `74815` と比較）。**
当初の読み「shared が 64→48 KB になって 3→4 ブロック/SM」は**外れ**だった:

| | shared/CTA | Block Limit Shared | Block Limit Reg | 実効 warp/SM | Compute (SM) | 発行命令 |
|---|---:|---:|---:|---:|---:|---:|
| x 4 段 | 65536 | 3 | 3 | 11.91 | 94.77% | 1.7719e9 |
| x 3 段 | 49152 | 3 | 3 | 11.89 | 95.12% | 1.7578e9 |
| y 4 段 | 65536 | 3 | 3 | 11.71 | 95.66% | 1.8388e9 |
| y 3 段 | 49152 | 3 | 3 | 11.71 | 95.95% | 1.8256e9 |

占有率は動いていない（x は reg 130/thread、y は 168/thread で、
`65536/(reg*128)` が 3 ブロットで頭打ちだから shared を削っても増えない）。
動いたのは**発行命令数**で、x −0.79% / y −0.72%。段数が減ると K ループ 1 回
あたりのステージ管理（バッファ添字の回転と `cp.async` のコミット/待ち）が減り、
その分 DMMA と同じ warp で競合する命令が減る。パイプ占有は
94.77 → 95.12% / 95.66 → 95.95% に上がった。**FP64 パイプが 95% で律速して
いるカーネルでは、mainloop の非 mma 命令を削ることだけが効く**——
§11.9 / §11.10 で warp や CTA を増減しても駄目だったことと同じ話の裏側である。

### 11.14 不採用: Nq≥512 の x / y を `TileK = 32` にする（job `74916`、c368）

§11.13 の機構（mainloop の非 mma 命令を減らすと効く）をそのまま延ばして、
K タイルを 16 → 32 にした。K ループが 36 回から 18 回になるので、ステージ管理
命令は半分になるはずである。`GemmYScale3` / `GemmY3` を
`GS<64,64,32>` / warp `GS<32,32,32>`、3 段。`WarpShape::kK / InstShape::kK`
= 8 なので `MmaBase` の制約は満たす。191,102,976 点で**ビット一致**。

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A `TileK=16` 3 段 | 2.614895 | 19370 | 2.611780–2.626610 |
| B `TileK=32` 3 段 | 2.655730 | 19672 | 2.655000–2.659410 |

**B vs A +1.562%、レンジ非重複。** shared が 3 段で 96 KB になり、
1 SM に 2 CTA（8 warp）しか載らない。ループ制御命令の削減より、
プリフェッチ距離が K 32 個ぶんに伸びて 8 warp では隠しきれない方が高い。
§11.13 が 5 段（80 KB）で +1.305% だったのと同じ壁で、
**この 64×64 タイルは 48〜64 KB の shared に収まる範囲でしか動かせない。**

### 11.15 不採用: x / y の warp タイルを `64x32` にする（job `74960`、c368）

§11.13 の機構の残りの延ばし方。64×64 タイルを 32×32 warp 4 本ではなく
64×32 warp 2 本で持つと、K ステップあたりの shared フラグメント読み出しが
4×(32+32) = 256 行から 2×(64+32) = 192 行に減る。**ビット一致**。

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
| A warp `32x32`（4 warp / 128 thread） | 2.609655 | 19331 | 2.609040–2.609850 |
| B warp `64x32`（2 warp / 64 thread） | 2.616250 | 19380 | 2.615860–2.616440 |

**B vs A +0.253%、レンジ非重複。** shared の読み出し行数は減るが、
accumulator が 32 → 64 double/thread になってレジスタが増え、CTA が
64 スレッドになって 1 SM の warp が 12 → 8 に落ちる。z が 64 スレッド CTA で
89.7% しか出ていない（§11.8）のと同じ形に x / y を寄せることになる。
**これで x / y のタイル軸（M/N §11.2・段数 §11.13・K §11.14・warp 本節）は
4 方向とも閉じた。**

### 11.16 横展開: `Nq >= 512` の他の次数（job `74975`、c368）

§11.13 の分岐は `Nq >= 512` なので p=511 / 767 / 1023 にもそのまま載る。
同じ `.xbatch` / `.st3gate` で 8 回ずつ交互に測った

「DRAM 律速のフルグリッドカーネルを、FP64 パイプ 95% の GEMM の裏に
入れる手段が無い」という形で閉じている。新しい機構（GEMM の CTA の中で
flux を分担して計算する等）を思いつけば再開する価値がある。

### 11.18 `feature/cuda` への rebase による訂正（2026-09-01）

本節を `feature/cuda` に rebase する時点で、そのブランチには
[`p511_gap_study.md`](p511_gap_study.md) §12 が既に入っていた。**融合 y GEMM

  3 段になった `GemmY` と同一物なので削除した。

p=575 の `GEMM_FUSED` が起動するカーネルは rebase の前後で同じはずなので
§11.13 の 19347 µs/stage はそのまま有効、という読みを実測で確かめた
（job `75105`、c368、12 回交互）:

| | fused s | µs/stage | レンジ |
|---|---:|---:|---|
