## 1. まとめ（2026-08-26 時点）

> **この節は 2026-08-26（commit `9eed9e5`）時点の記録である（2026-09-11 追記）。
> 現行ツリーでの H100 × GB200 の対の測定は §8（2026-09-05、commit `55bf94c`）
> にあり、そちらが現在の状態を示す。** とくに項目 3 の「GB200 の p=255 の最速は
> `CUDAFORTRAN_GEMM_FUSED`」は、`ba53906`（2026-08-28）以降 GB200 では
> `CUDAFORTRAN_FUSED_TC` に替わっている（§8.1 で GB200 2.8865 / H100 4.5537
> ms/step、どちらも `FUSED_TC` が最速。現行値は
> [`measurement_inventory.md`](measurement_inventory.md) §18.3 で 883.7 対
> `GEMM_FUSED` 943.3 µs/stage）。
>
> 項目 1 と 2 も §8 で一部が覆っている: **項目 2（「p=7 の最速は両機とも
> `FUSED_TC`」）は H100 側で成り立たない**（§8.4。H100 は p=7 で +0.7%、
> p=63 で +0.9% だけ `FUSED` が勝つ。原因は H100 ではなく、この間に CUDA core
> 融合を速くしたこと）。**項目 1（「絶対性能は GB200 が速い」）も全セルでは
> 成り立たない**——`SPLIT` は p=63 で 0.99、p=127 で **0.90** と H100 のほうが
> 速い（§8.1 / §8.5）。項目 4（既定は `8x8x4` 据え置き）は §8.3 と
> [`measurement_inventory.md`](measurement_inventory.md) §18.6 で維持されている。**本節の表と数値は当時の記録として書き換えていない。**


1. **絶対性能は GB200 が速い**（経路により 1.3〜5.4 倍）。ただし p=255 の
   volume GEMM に限れば、命令形状を H100 向けに選ぶと **H100 の方が 3% 速い**
   （741.7 対 765.3 µs/call、§4）。
2. **p=7 の最速は両機とも `CUDAFORTRAN_FUSED_TC`。** ただし CUDA core 版に対する
   優位が違う。GB200 では 1.22 倍、H100 では **1.91 倍**。H100 の FP64 Tensor Core
   ピークが CUDA core の 2 倍あるのに対し、GB200 では同じだからである。
3. **p=255 の最速は機種で入れ替わっていた。** GB200 は `CUDAFORTRAN_GEMM_FUSED`、
   H100 は cuBLAS（`CUDAFORTRAN_GEMM`）。ただしこれは 8x8x4 での話で、
   **`CutlassMmaShape = "16x8x4"` を選ぶと H100 でも `GEMM_FUSED` が最速に戻る**
   （1628.8 対 1652.7 µs/call、§4）。
4. **既定値は変えない。** 既定は GB200 の最速構成（`8x8x4`）のまま。H100 で走らせる
   ときだけ namelist で `16x8x4` を選ぶ（§5）。
5. **達成率の性格が違う。** volume GEMM は GB200 でピークの 84.0%（ほぼ飽和）、
   H100 では 51.9% にとどまる。H100 側にはまだ余地があり、それは cuBLAS との
   1.27 倍の差として見えている（§4.3）。

## 3. 経路横断（job `8500661`、commit `9eed9e5`）

tendency 1 回あたりの GPU 時間。GB200 側は `overall_summary_report.md` §7 の
「現行」列（同じツリー = `63a4234` + ±x 面ステージング = `9eed9e5`）。
どちらも nsys のカーネル時間から算出し、p=255 の GEMM 系では
side stream に隠れる `elembnd_flux_kernel` を除いている。

| 経路 | GB200 [µs/call] | H100 [µs/call] | H100 / GB200 |
|---|---:|---:|---:|
| p7 `OPENACC_ASIS` | 1011.2 | 2278.0 | 2.25 |
| p7 `OPENACC_SPLIT` | 730.6 | 2004.6 | 2.74 |
| p7 `CUDAFORTRAN_SPLIT` | 715.7 | 1979.7 | 2.77 |
| p7 `CUDAFORTRAN_FUSED` | 323.8 | 1731.4 | 5.35 |
| p7 `CUDAFORTRAN_FUSED_TC` | **264.9** | **907.9** | 3.43 |
| p7 `CUDAFORTRAN_GEMM` | 1670.7 | 2904.3 | 1.74 |
| p255 `CUDAFORTRAN_FUSED` | 4978.9 | 6276.8 | 1.26 |
| p255 `CUDAFORTRAN_FUSED_TC` | 4420.9 | 7620.4 | 1.72 |
| p255 `CUDAFORTRAN_GEMM` | 1143.0 | **1602.1** | 1.40 |
| p255 `CUDAFORTRAN_GEMM_CUTE` | 1138.1 | 1990.1 | 1.75 |
| p255 `CUDAFORTRAN_GEMM_FUSED` | **970.7** | 1769.4 | 1.82 |

読み取り:

- **p=7 は両機とも `FUSED_TC` が最速**だが、意味が違う。GB200 では CUDA core 版
  `FUSED`（323.8）に対して 1.22 倍でしかないのに、H100 では 1731.4 → 907.9 の
  **1.91 倍**。§2 のとおり H100 だけ Tensor Core のピークが 2 倍だからで、
  `tc_paper_survey_2407.09621.md` が GB200 で「TC 版の優位は 1.16 倍」と
  結論した理由がここで裏返る。**Tensor Core 版を維持する価値は H100 の方が高い。**
- **p=7 の帯域律速な経路ほど H100 が不利**（`OPENACC_SPLIT` 2.74 倍、
  `CUDAFORTRAN_SPLIT` 2.77 倍）。HBM が約 3.3 分の 1 なので当然である。
- **p=255 では差が小さい**（1.26〜1.82 倍）。演算律速なので、
  FP64 ピークの比（40.1 対 66.9 = 0.60、ただし到達率が違う）が効く。
- この時点では **H100 の p=255 最速は cuBLAS**（1602.1）で、`GEMM_FUSED`（1769.4）が
  負けていた。GB200 とは順位が逆である。§4 でこれが変わる。

## 4. MMA 命令形状（jobs `8502531` / `8502578` / `8502700`、commit `f5794b7`）

CUTLASS 経路の volume GEMM は MMA 命令形状を namelist `CutlassMmaShape` で
選べる（`8x8x4` / `16x8x4` / `16x8x8` / `16x8x16`）。詳細と実装は
[`sm90_mma_shape_survey.md`](sm90_mma_shape_survey.md) にあり、ここでは
H100 側の結論だけを載せる。

### 4.1 GB200 では効かず、H100 では効く

p=255 `Ne=1`、`nstep=1000`、`UseCudaGraph=.false.`。数値はすべて CUDA event の
device 時間を tendency 1 回あたりに直したもの。**4 形状とも参照（cuBLAS）と
一致することを両機で確認済み**（GB200 は `Ne=1` / `Ne=2`、H100 は `Ne=1`）。

volume GEMM のみ [µs/call]:

| 形状 | GB200 | H100 |
|---|---:|---:|
| 8x8x4（既定） | 765.3 | 969.1 |
| **16x8x4** | 765.1 | **741.7** |
| 16x8x8 | 774.7 | 818.8 |
| 16x8x16 | 1323.3 | 1499.1 |

GB200 では 8x8x4 と 16x8x4 が同着（0.03%）。H100 では 16x8x4 が **−23.5%**。
理由は §2 の 4 行目で、GB200 では `mma.sync.m16n8k4/8/16.f64` が
`DMMA.8x8x4` の 2 / 4 / 8 命令に展開されてしまい、命令数が減らないためである。

**16x8x4 の H100 は GB200 より 3.1% 速い**（741.7 対 765.3）。同じコード・同じ
タイルで、H100 の FP64 Tensor Core ピークが 1.67 倍あることがそのまま出ている。

### 4.2 p=255 の順位が GB200 と揃う

tendency 全体 [µs/call]:

| 経路 | GB200 8x8x4 | H100 8x8x4 | H100 16x8x4 |
|---|---:|---:|---:|
| cuBLAS `CUDAFORTRAN_GEMM` | 1174.4 | 1652.7 | 1652.7 |
| `CUDAFORTRAN_GEMM_CUTE` | 1158.6 | 2008.3 | 1781.1 |
| `CUDAFORTRAN_GEMM_FUSED` | **989.0** | 1801.7 | **1628.8** |

8x8x4 では H100 だけ cuBLAS が最速だったが、16x8x4 にすると `GEMM_FUSED` が
cuBLAS を **1.5% 下回り**、GB200 と同じ順位に戻る。

### 4.3 達成効率と、残っている差

volume GEMM の理論仕事量は 1 tendency 呼び出しあたり 25.77 GFLOP
（x/y/z 各 2·M·N·K）。

| | µs/call | 有効 TFLOP/s | 対 FP64 CUDA peak | 対 FP64 Tensor peak |
|---|---:|---:|---:|---:|
| GB200 8x8x4 / 16x8x4 | 765.3 | 33.67 | 84.0% | 84.0%（同じ値） |
| H100 8x8x4 | 969.1 | 26.59 | 79.4% | 39.7% |
| H100 **16x8x4** | 741.7 | **34.74** | **103.7%** | 51.9% |
| H100 16x8x8 | 818.8 | 31.47 | 94.0% | 47.0% |

H100 の 16x8x4 が **CUDA core ピークを超えている**（103.7%）ことが、Tensor Core
経路が実際に効いている直接の証拠である。一方で Tensor ピークに対しては 51.9% で、
**GB200 の 84.0%（ほぼ飽和）と比べて余地が大きい**。その余地は cuBLAS との差として
実在する（volume GEMM 3 本の合計で 43.9 対 34.4 ms = 1.27 倍）。
`sm90_mma_shape_survey.md` §8.5 のとおり、**タイル・warp 数・stage 数・命令まで
揃えても cuBLAS の sm90 カーネルの方が速い**ので、残りは mainloop の実装差である。

### 4.4 H100 固有の落とし穴: x GEMM のレジスタ spill

`16x8x8` は 16x8x4 に負ける。ncu（job `8502700`）によると x GEMM
（tile 64x128x16、warp 32x64x16）でレジスタが 255 本（上限）に張り付き、
**4.46 MB を spill** する。16x8x4 は 248 本で spill ゼロ。occupancy は 3 形状とも
theoretical 12.5% で同じなので、効いているのは spill そのものである。
warp タイルが小さい y / z GEMM では 16x8x8 も溢れない。

x の 16x8x4 も 248 本と上限に近い。**H100 でこのカーネルのタイルや epilogue を
触るときは、レジスタが 255 に達しないか必ず見ること。**

## 5. 既定値の方針

**既定は `8x8x4` のまま**とする。既定値は GB200 の最速構成に合わせるという方針で、
GB200 では 16x8x4 との差が測定ばらつきの範囲（0.03%）だから、既定を動かす利得が
無い。H100 で走らせるときは入力に 1 行足す:

```fortran
  CutlassMmaShape = "16x8x4",
```

対象は `CUDAFORTRAN_GEMM_CUTE` と `CUDAFORTRAN_GEMM_FUSED`。他の経路では無視される。
4 形状ぶんのカーネルは 1 バイナリに実体化してあるので、再ビルドは要らない。

H100 向けビルドは:

```bash
module purge && module load nvhpc
make clean
make CUDA=1 GPUFLAGS=-gpu=cc90 \
  NVCCFLAGS='-O3 -std=c++17 -arch=sm_90 -Ithird_party/cutlass/include --expt-relaxed-constexpr'
```

## 6. H100 で残っている課題

- **cuBLAS との 1.27 倍**（§4.3）。命令形状では埋まらない。次に効くとすれば
  mainloop 側（CUTLASS 3.x / CuTe の pipeline、あるいはタイル選択）。
  H100 では Tensor ピークに対して 51.9% しか出ていないので、GB200（84.0%）より
  伸びしろは大きい。
- **p=7 の Tensor Core 経路。** H100 では CUDA core 版に対して 1.91 倍と、
  GB200（1.22 倍）よりずっと効く。`tc_paper_survey_2407.09621.md` が GB200 で
  「割に合わない」と判断した最適化のいくつかは、H100 では再評価の価値がある。
- **p=255 `FUSED_TC` は H100 で特に悪い**（7620 µs/call、GB200 比 1.72 倍）。
  手書き Tensor Core 経路が CUTLASS / cuBLAS の multistage mainloop に負ける
  という GB200 での結論は、H100 でより顕著である。
- **16x8x16 は両機とも不可。** `MmaBase` が warp あたり 2 回以上の GEMM を要求する
  ため K=32 タイルが必須で、shared が倍・occupancy が半分になる分を命令形状の
  利得では取り返せない。

## 7. 命令形状ノブの実体化（2026-09-04、tree `5e507b8`）

**§1–§6 は commit `9eed9e5` / `f5794b7`（2026-08-26）の記録であり、表は書き換えない。**
以下は、その後 GB200 側でツリーが動いた結果として **H100 を測り直す前に
直さなければならなかった 1 件**と、その修正の検証である。時間の測定は
含まない（TSUBAME 側の再測定はこれから）。

### 7.1 `CutlassMmaShape` は途中から「半分だけ繋がった」ノブになっていた

`§4` の測定当時（`f5794b7`）、x volume GEMM は汎用の
`launch_volume_gemm_x` を通っており、命令形状は x/y/z の 3 本すべてに効いて
いた。**`§4` の数値はその意味でそのまま有効である。**

その後 `51d56a8`（2026-09-02、GEMM ライブラリ割り当てとエピローグ carrier の
測定）で x volume GEMM に**次数別の専用タイル**が入った
（Nq=8→tile 9、16→5、32→7、64→3、128/256→0）。この `XTile` テンプレートは
`GS<8,8,4>` と `Sm80` をハードコードしていたため、`Nq <= 256` では

- `CutlassMmaShape` を変えても **x だけ 8x8x4 のまま**（`GEMM_CUTE` /
  `GEMM_FUSED` の両方で）、
- 融合の x carrier（Nq = 8 / 16 / 32）は `mma_shape != 0` を即座に拒否、
- Nq = 64 の z carrier も採用 package の分岐に形状が無く拒否、

という状態になっていた。低次では `GEMM_CUTE` だけが（x を 8x8x4 に置いたまま）
起動でき、`GEMM_FUSED` は起動できない。**この非対称は AGENTS.md が
`GEMM_CUTE` と `GEMM_FUSED` に禁じている「異なる mainloop / 命令形状」**
そのものなので、この状態の H100 値は公表できない。

### 7.2 実体化した範囲

- `MmaShapeSel<0..3>`（命令形状 → InstructionShape / ArchTag / TileK）を 1 箇所に。
  16x8x16 だけ `TileK = 32` を要求する（`MmaBase` の
  `WarpShape::kK / InstShape::kK >= 2` かつ偶数）ので、タイル専用化のある
  経路では **形状 0〜2 のみ**実体化し、16x8x16 は従来どおり汎用セット限定。
- `XTile` に InstShape / ArchTag をデフォルト引数付きで追加。**既存のタイル別名の
  型は 1 ビットも変わらない**（`static_assert` で担保）。各次数の**採用タイルのみ**を
  形状付きで実体化（`XAdopted8/16/32/64/Hi`）。
- `VolumeGemmSetP7` / `VolumeGemmSetP15` をテンプレート化。従来、非既定形状の
  低次 y/z は汎用 64x64 タイルに落ちており、**タイルと命令の 2 軸が同時に
  動いていた**。これも一軸化された。
- 融合エピローグ: x carrier は Nq = 8（tile 9 / xpkg 5）、16（tile 5 / xpkg 4）、
  32（tile 7 / xpkg 4）の**採用構成のみ**、z carrier は Nq = 64 の **zpkg 5 のみ**を
  形状付きで実体化。`SCALE_DG_XTILE` などの ablation メニュー（weight_mode 4 通り
  × package 8 通り）は 8x8x4 のまま残す。全部を形状ぶん実体化するとビルドが
  倍増し、どの次数も使わない組み合わせのために払うことになる。
- `launch_volume_gemm_x_tiled` に `mma_shape` 引数を追加（Fortran 側の interface と
  呼び出し 2 箇所も）。

### 7.3 検証（GB200、login GPU、`SCALE_DG_VARYING_COEFF=1`、owned `dqdt` 全 16,777,216 点）

p = 7 / 15 / 31 / 63 / 127 / 255 × `GEMM_CUTE` / `GEMM_FUSED` ×
`8x8x4` / `16x8x4` / `16x8x8` の 36 通り。対照は p<=127 が
`CUDAFORTRAN_SPLIT`、p=255 が `CUDAFORTRAN_GEMM`。

| p | `GEMM_CUTE` 3 形状 | `GEMM_FUSED` 3 形状 | 既定形状 変更前バイナリとの比較 |
|---:|---|---|---|
| 7 | max abs 0.000e+00 | rel 2.078e-16 | ビット一致 |
| 15 | 0.000e+00 | 2.078e-16 | ビット一致 |
| 31 | 0.000e+00 | 2.078e-16 | ビット一致 |
| 63 | 0.000e+00 | 4.156e-16 | ビット一致 |
| 127 | 0.000e+00 | 2.078e-16 | ビット一致 |
| 255 | 0.000e+00 | 2.078e-16 | ビット一致 |

**既定（8x8x4）の出力が変更前の実行ファイルとビット一致である**ことが要点で、
型レベルの `static_assert` と合わせて、公表済みの GB200 の値は 1 つも
無効化されない。p >= 511 は `x_mode = 0`（汎用 x）で今回の分岐を通らない。

ビルド確認: cc100（`-gpu=cc100` / `-arch=sm_100`）、**cc90（`-gpu=cc90` /
`-arch=sm_90`、14 分 30 秒）**、非 CUDA（stub）の 3 モードとも成功。
現行ツリーは `NVCCFLAGS` を全指定しなくても `GPUNVCCFLAGS=-arch=sm_90` で
H100 向けにビルドできる（§5 のコマンドはより短く書ける）。

### 7.4 これから測ること

### 8.6.1.1 アブレーションで鎖を閉じる（役割外、採用しない）

### 8.7.1 A: MMA 命令の利得が H100 のほうが小さい（**解決**）

> **2026-09-06 注記（A100 の測定を受けて）。** 以下の測定と「mma は命令数を
> 削って発行律速を外す取引である」という機構は有効だが、**「Tensor ピークが
> 2 倍あることはこの取引に無関係」は 2 台の事情の帰結であって一般則ではない。**
> A100 では TC 飽和に要る強度が 12.5 F/B（H100 は 27.9）で現金化でき、mma を
> 出す経路だけが FP64 CUDA core ピークを超える（p=511 `FUSED_TC` で 132.7%、
> p=575 `GEMM_FUSED` で 129.1%）。GB200 は 2 つの屋根が同じなので原理的に
> 買えず、H100 は帯域で買えないだけだった。`a100_report.md` §4.3 を見ること。
> 以下の表と数値は当時の記録として 1 行も変えていない。

`FUSED_TC ÷ FUSED_DFMA`（同一ソース・同一スケジュール・mma 命令だけを
入れ替える iso-schedule アブレーション。`AGENTS.md` が `FUSED_DFMA` を
置いている理由そのものの軸）:

| p | 7 | 15 | 31 | 63 | 127 | 255 | 511 |
|---|---:|---:|---:|---:|---:|---:|---:|
| GB200 | 0.810 | **0.671** | **0.507** | **0.534** | 0.440 | 0.465 | 0.444 |
| H100 | 0.886 | **0.934** | **0.828** | **0.828** | 0.492 | 0.542 | 0.460 |

**H100 だけ FP64 Tensor Core ピークが CUDA core の 2 倍ある**（§2）。素直に
考えれば mma 命令の利得は H100 のほうが大きいはずで、**全次数で逆**、
p=15〜63 では 2 倍近く小さい。絶対値でも、p=15 で GB200 → H100 の劣化は
DFMA が 1.93 倍なのに TC は 2.68 倍で、**TC 版のほうが H100 で損をしている**。

**レジスタでは説明できない。**`cuda_dg_kernels_tc.cu` を同一 nvcc で
sm_90 / sm_100 にコンパイルして `cuobjdump -res-usage` で比べると、37 本の

ほうが多い**（`tendency_p255_kernel` 176 B 対 56 B、`tendency_fused_p7_tile`
80 B 対 32 B、`tendency_fused_p15` 32 B 対 0 B）。損をしている側が spill の
少ない側である。

3. **降りた先は memory である**: TC の DRAM スループットは 40.4 / 57.7 / 40.8%、
   DFMA は 22.0 / 19.0 / 16.8%（p=15 / 31 / 63）。**mma は「命令律速」を

4. GB200 → H100 は**帯域が 3.30 分の 1、FP64 演算は 1.20 分の 1**（§2）。

5. **順序依存もこれで出る。**食い違いが最大なのは p=31 / 63 で、そこは

   張り付いている**ので、やはり食い違いが小さい（1.095）。

**つまり「H100 は Tensor ピークが 2 倍だから mma が効くはず」という読みが
間違っている。**この問題のこの次数域で mma が買っているのは FLOP/s ではなく
**命令と発行スロット**であり、その代金として帯域への依存が上がる。帯域が
3.3 分の 1 の機械では、その取引のレートが悪くなる。

#### H100 側の ncu が予測を確認した（SGE job `8577233`、node `r21n2`）——A は閉じた

同じ `jobs/mma_axis_ncu.sh` を TSUBAME で走らせた。**予測は「H100 では TC が
HBM の屋根に張り付き、命令数の利得を現金化できない」だった。そのとおりだった。**

| p | | GB200 TC DRAM% | H100 TC DRAM% | GB200 DFMA DRAM% | H100 DFMA DRAM% | GB200 TC/DFMA | H100 TC/DFMA |
|---:|---|---:|---:|---:|---:|---:|---:|
| 15 | | 40.4 | **86.3** | 22.0 | **80.1** | 0.543 | **0.883** |
| 31 | | 57.7 / 46.3 | **89.2 / 87.5** | 19.0 / 16.9 | 69.1 / 60.4 | 0.350 | **0.715** |
| 63 | | 40.8 / 26.2 | **88.7 / 74.7** | 16.8 / 11.0 | 69.6 / 42.2 | 0.415 | **0.674** |
| 255 | | 13.1–15.3 | 52.6–59.3 | 6.0–6.6 | 25.3–28.2 | 0.439 | **0.447** |

**命令数の削減は両機で同じ**（TC÷DFMA の命令数比 GB200 0.434 / 0.199 / 0.271 /
0.297 に対し H100 0.414 / 0.185 / 0.320 / 0.294）。**同じコードなのだから当然で、
これが「削減量は機械の性質ではない」ことの確認になる。**変わるのは
現金化できるかどうかだけである。

- **p=15**: H100 では TC 86.3% / DFMA 80.1% と**両方が屋根**。命令を 2.4 倍
  削っても行き場が無く、TC/DFMA は 0.543 → **0.883** に潰れる。
- **p=31 / 63**: TC だけが屋根（89.2 / 88.7%）で DFMA はまだ余裕がある
  （69.1 / 69.6%）。**罰が TC 側にだけ当たる**ので 0.350 → 0.715、
  0.415 → 0.674。食い違いが最大になるのはここである。
- **p=255**: どちらの機械でもどちらの版も屋根から遠い（H100 でも TC 52.6–59.3%、
  DFMA 25.3–28.2%）。**このとき 2 台は一致する**（0.439 対 0.447）。
  **これが機構を確定させる対照点である**——帯域が効かない次数では、
  同じ命令削減が同じ時間短縮になる。

stall の内訳も同じことを言う。H100 の p=31 TC は `longSB` **93.3**、
`barrier` **38.1**（GB200 は 2.0 / 7.9）で、**メモリ待ちで発行が止まっている**。
SM スループットも H100 の TC は p=15 / 31 で **12.2 / 13.9%** まで落ちる
（GB200 は 25.3 / 38.6%）。**命令を削った結果、H100 では演算器が遊んで
メモリを待つカーネルになる。**

**結論（A、閉じた）**: この問題のこの次数域で f64 mma が買っているのは
FLOP/s ではなく**命令と発行スロット**であり、その代金は**帯域への依存の
上昇**である。H100 は Tensor ピークが CUDA core の 2 倍あるが、**その 2 倍は
この取引には関係が無く**、帯域が 3.30 分の 1 であることだけが効く。
**「H100 では Tensor ピークが 2 倍だから mma の価値が高い」は、この
カーネル・この次数域では成り立たない。**§1 の結論 2 が現行ツリーで
裏返っていた（§8.4）のは、この帰結でもある。

### 8.7.2 B: CUTLASS が cuBLAS に負けるのは H100 だけ（**原因判明**）

> **2026-09-06 注記（A100 の測定を受けて）。この節の結論は 2 台目で裏が取れ、
> 一般化してよいことが確定した。** A100（sm_80 = `cutlass_80_tensorop_d884gemm`

#### 原因は「H100 の CUTLASS が弱い」ではなく「**GB200 の cuBLAS が CUTLASS そのもの**」

`jobs/gemm_library_ncu.sh` を GB200 で走らせ（Slurm job `82208`、node `c393`）、**カーネル名でフィルタせずに** 1 tendency 分の全 launch を

GB200 で走っているのは**その構成を Blackwell 向けにビルドしたもの**である。
どの cubin に入っているかまでは追っていない。）

#### GB200 で `GEMM_CUTE` が勝つ/負ける理由（Slurm job `82209` / `82210`）

縮退しているとはいえ、GB200 の `GEMM_CUTE` 対 `GEMM` は 9 次数とも
6 ラウンドでレンジ非重複の差が出ている（`GEMM_CUTE ÷ GEMM`: 0.913 / 0.799 /
0.979 / **1.005** / **1.013** / 0.991 / **1.006** / 0.999 / **1.005**、

**勝っている側（低次）: 原因は x GEMM のタイル選択である。**

tendency 1 回あたり、span（最初のカーネル開始〜最後の終了）、busy（全ストリームの

**(2) p=127 だけ、同時実行している face flux が伸びる。**カーネル別に分けると:

| p=127、µs/call | `GEMM` | `GEMM_CUTE` | 差 |

`GEMM_CUTE` 側で 18% 長くかかる。**これは face flux が side stream で
volume GEMM と**同時に走っている**からで、同居する相手の SM 占有が変われば
伸びる。実際 ncu の占有率は cuBLAS の 3 本が 12.14 / 12.15 / 12.15% で
揃っているのに対し、`GEMM_CUTE` は 18.33 / 12.17 / 18.33%（grid 4096 /

**結論**: GB200 で `GEMM_CUTE` が p=63 / 127 で負ける 0.5〜1.3% は、
**GEMM カーネルの速度差ではない**。半分から全部が CUTLASS のホスト側
launch コスト（一定 3 µs/call）で、p=127 の残りは**同居する face flux が
GEMM の占有率上昇で押される分**である。**どちらも「どちらの GEMM 実装が
速いか」とは別の軸**であり、ライブラリ／mainloop の比較としてこの
0.5〜1.3% を引くことはできない。

カーネル自体が負けているのは **p=511 の +0.34% だけ**で、そこは cuBLAS が
3 本とも 64x128 タイル（212 レジスタ、命令 892 M）を使うのに対し、
`GEMM_CUTE` の z が 64x32・**block 64**・156 レジスタ・命令 1350 M で
6.92 ms（他 2 本は 6.80 ms）という違いがある。**cuBLAS の構成に寄せる
余地があるのはこの 1 点。**

**この報告と論文への含意**: `AGENTS.md` は GEMM 系を「論文のライブラリ
ベースライン」と位置づけている。**GB200 上ではそのベースラインは
CUTLASS であって、独立したベースラインではない。**GB200 の
`GEMM` 対 `GEMM_CUTE` の比を「cuBLAS に勝った / 並んだ」と読むことは
できない。H100 の数字だけがその主張を支えられる。

#### 8.7.2.1 その 16.198 ms は「固定クロックの直列和」である —— 引き算を確定させた（SGE job `8602523`、node `r21n9`、commit `9d1dfd9`）

上の 16.198 ms（および 9.993 / 8.521 ms）は **`ncu` 既定の `--clock-control base`
で測った、直列化された 1 stage の和**である。同じツリーのキャンペーン
（job `8567869`）の `CUTE volume GEMM only` は @8x8x4 13.516 ms/stage、
@16x8x4 9.072 ms/stage なので、**周辺カーネルが一致しているのに CUTLASS 側だけ
19.8% / 10.2% 大きい**という食い違いが残っていた（`volume_flux` は
3.404 ms で 0.03% 一致）。この状態で到達率を出すと、引き算の仕方で
**0.96 とも 1.12 とも**書けてしまう。1.12 は物理的にあり得ない値である。

同じ向きに効く機構が 2 つあり、周辺カーネルの一致はどちらも否定できない:

1. **`ncu` のクロック固定。** @8x8x4 は発行律速なので base/boost 比をそのまま
   食らう。`volume_flux` は DRAM 律速（90.6%）でクロックにほぼ不感なので、
   **周辺カーネルが 0.03% で一致することは GEMM について何も証明しない。**
2. **`CUTE volume GEMM only` は sum ではなく span。**
   `mod_advect3d_eq.f90` が読む `timer_volume_flux` は `dg_ev_harvest` の
   `ms(2)`、すなわち `SCALE_DG_CUTEPAR` の fork/join をまたぐ主ストリーム上の
   CUDA event 区間で、3 本重ねの重なりが入った elapsed である。`ncu` は
   直列化して duration の和を返す。

**そこで 2 項を別々に測った。**入力は `namelists/perf_p511_gemm.conf`
（`nstep=20`、`WarmupStep=2` ＝ 18 step ＝ 54 stage）そのままで、
PART A はプロファイラ無し・本番クロック、PART B は job `8577463` と同じ
12 launch ウィンドウ（`-s 14 -c 12`、`nstep=4`）。

##### PART A: 3 本重ねの得は p=511 では実質ゼロ（機構 2 は棄却）

`SCALE_DG_CUTEPAR` 2（既定＝3 本重ね）対 0（直列）、4 ラウンド交互、
volume GEMM span [µs/stage] の中央値:

|---|---:|---:|---:|---|
| 8x8x4 | 13465.8 | 13478.7 | **0.10%** | 13411.8–13519.2 / 13439.1–13546.5（**重複＝差が無い**） |
| 16x8x4 | 8940.5 | 8952.7 | **0.14%** | 8936.6–8943.1 / 8949.2–8954.1（非重複） |

**19.8% を説明できる重なりは存在しない。**p=511 の 1 本は grid 32768 /
65536 ブロックで 132 SM を単独で埋めるので、3 本を並べても時分割になるだけ
である。GB200 の `gemm_assignment_and_carrier.md` §13.6 が p=511 で

実質的に直列和であり、duration の和と直接比べてよい。**

（0.9982 / 0.9979）。すなわち **13〜20% はクロック固定が全額**であり、
これらのカーネルは純粋に発行律速で、`sm__throughput` もクロック不変である
（両クロックで 0.2 ポイント以内）。

**cuBLAS だけは追随しない**（時間比 1.168 対クロック比 1.221 ＝ 0.957）。
カーネル単位に割ると出どころは 1 本に絞れる: x（grid (8,8,512)）は

`none` にすると `dram__throughput` が 75.3 → 84.5% に上がり `sm__throughput` は
87.9 → 80.7% に下がる。**`a100_report.md` §12.2 の「`elapsed` にストール時間が
入るので SM 側の利用率はクロック不変ではない」がここでも出ている**わけで、
同時に **「クロック不変」は DRAM 成分を持たないカーネルに限った性質**である
ことを示す対照になっている。**`none` のクロック自体も構成で違う**
（1.976 / 1.859 / 1.952 GHz）ので、公称 boost 1980 MHz を一律に当てることも
できない。

**残差**: `ncu`(`none`) は本番（PART A par=0）より **2.3% / 3.5% 速い**
（0.977 / 0.965）。プロファイラは隣接カーネルも側ストリームも無い状態で
1 本ずつ回すぶん、連続実行より有利になる（16x8x4 のほうが残差が大きく、
`none` で維持できたクロックも低いことと向きが揃う）。**到達率は本番側の
数字から出す。**

##### 到達率（確定）

volume GEMM の理論仕事量は 1 stage あたり 3·2·512⁴ = **412.32 GFLOP**。
H100 の屋根は FP64 Tensor Core 66.9 TFLOP/s（この経路は DMMA を出すので
`AGENTS.md` の機種別規則によりこちら）、FP64 CUDA core 33.5 TFLOP/s:

| p=511 volume GEMM 3 本 | 直列時間 [ms/stage] | 有効 TFLOP/s | 対 TC 屋根 | 対 CC 屋根 | 発行屋根（`sm__throughput` @none） |
|---|---:|---:|---:|---:|---|
| `GEMM_CUTE` @8x8x4 | 13.479（PART A par=0） | 30.59 | **45.7%** | 91.3% | **94.7 / 94.7 / 92.7%** |
| `GEMM_CUTE` @16x8x4 | 8.953（PART A par=0） | 46.06 | **68.8%** | 137.5% | 81.7 / 81.7 / 67.1% |
| cuBLAS | 7.293（`ncu` `none` のみ） | 56.54 | **84.5%** | 168.8% | 90.9 / 80.7 / 90.1% |

（cuBLAS 経路には GEMM だけの event タイマが無い——
`mod_advect3d_eq.f90` は `CUDA device GEMM tendency` しか出さない——ので
PART A の対応する行が無い。残差の向きからすると本番はこれより 2〜3% 遅い、
すなわち 84.5% は上限として読む。）

**@8x8x4 の到達率は 0.95（発行屋根）であって 1.12 ではない。**1.12 は、
固定クロックの `elapsed` に対して定義された `sm__throughput` を、より短い
本番時間へ手で引き伸ばして得た値である（0.947 × 1.198 ≒ 1.13）。
`AGENTS.md` が「固定クロックの `pct_of_peak_sustained_elapsed` は簡単な規則で
boost に持ち越せない」と書いているのはまさにこの操作のことで、正しい手続きは
**`--clock-control none` で取り直してそのまま読む**である。0.96 という別の
引き算も、値としては近いが理由が違う（重なりを差し引いたのではなく、
`ncu` 固定クロックの時間をそのまま使ったにすぎない）。

**§8.7.2 の表と 16.198 ms は記録として残す。**あれは固定クロック
（1.602 GHz）での直列和であり、命令数の比較——この節の主題——には
そのまま使える。使えないのは、本番クロックの時間や到達率としての引用である。

`GEMM_CUTE` と `GEMM_FUSED` に volume mainloop・タイル・段数・swizzle・
バッチ分割・**GEMM ごとのライブラリ割り当て**を同一にすることを要求しており、
p=511 では実際に両経路とも 3 本すべて CUTLASS で grid も
(8,8,512)×2 ＋ (8,8192,1) で一致する。したがって既定形について
**未測定なのはエピローグの取り分だけ**になった——融合担い手（z）が背負う
重み付け＋surface lift と、`Nq>=64` で `xy_weighted` が x / y に前送りする
ぶんである。

**残る穴（2026-09-08、SGE `8602846` で埋まった。`measured_dram_and_roofs.md`
§6.5）**: 既定形の `GEMM_FUSED` は **13.629 ms/stage ＝ 屋根の 45.2%**
（`ncu` `none`）で、到達率比 `GEMM_FUSED ÷ FUSED_TC` は **1.149**
（GB200 1.160 から −0.9%、A100 1.125 は −3.0%）。**§6.4 の +34.1% は形状の
産物だった。**本節の `GEMM_CUTE@8x8x4`（13.170 ms、46.8%）との差
＝ **エピローグの取り分は +3.5%** で、内訳は担い手 z が +8.4%（`sm%`
92.7 → 86.8）、`xy_weighted` を背負う x / y が +0.7% ずつ。下の外挿 1.02 は
**実測 1.149 に置き換わった**（外挿が外したのは、エピローグ係数を
16x8x4 から借りたこと——mainloop が発行で飽和している 8x8x4 では
エピローグが影に隠れて ×1.035 にしかならない）。以下は経緯として残す。

`measured_dram_and_roofs.md` §6.4 が
必要としているのは **`GEMM_FUSED`（分子）と `FUSED_TC`（分母）の既定形での
到達率比**で、H100 の同節の行は `SHAPE=16x8x4` で採ったもの（1.556）しかない。
上のエピローグ係数を別ジョブから借りて外挿すると @8x8x4 で 15.4 ms/stage
＝ 屋根の 40.1%、比 1.02 になるが、**その係数は別ジョブ・別コミットをまたぐ**

±10% の不確かさが乗る。**外挿値 1.02 は本文書の主張ではない。**
必要な測定は **同一ジョブ・同一ノード・`none` で `GEMM_FUSED`・`GEMM_CUTE`・
`FUSED_TC` を両形状ぶん採ること**で、`jobs/tsubame_p511_fusion_roof.sh`
（`jobs/roof_bytes_ncu.sh` を `ORDERS=511`・`PATHS_511`・両 `SHAPE` で 2 回
呼ぶだけなので、集計規則は §6.4 と同一）がそれである。**`GEMM_CUTE` を
同じジョブに入れてあるので、エピローグの取り分はジョブをまたがない差になり、
本節の 13.17 ms（`ncu` `none`）の別ノードでの再現性も同時に見える。**

### 8.7.3 C: `SPLIT` 逆転の残差（**解決。残差はアーキテクチャ差ではない**）

§8.6.1.1 はレジスタ数で 58〜83% を説明し、残差 4.6 / 10.7 / 16.8%
（p=15 / 63 / 127）に spill が混ざっていると書いた。**切り分けたところ、
残差はアーキテクチャ差ではなく、GB200 向けコード生成そのものだった。**

#### 4 点で占有率と spill を分ける（Slurm job `82454`、node `c265`、8 ラウンド交互）

sm_100 のコード生成はこのカーネルに 56 レジスタを要求し、**上限を下げると
必ず spill が出る**。ただし占有率はレジスタ数の階段関数（256 スレッド/ブロック、
64 K レジスタ/SM）なので、4 点で 2 つの効果を分けられる:

| レジスタ | ブロック/SM | 理論占有率 | spill | p=15 | p=63 | p=127 |
|---:|---:|---:|---:|---:|---:|---:|
| 56（既定） | 4 | 50.0% | 0 B | — | — | — |
| **52** | 4 | **50.0%** | 24 B | **−20.03%** | **−15.83%** | **−13.39%** |
| **48** | 5 | **62.5%** | 40 B | **−30.50%** | **−29.43%** | **−26.72%** |
| 44 | 5 | 62.5% | 64 B | −17.79% | −18.78% | −16.86% |

（`volume_deriv_kernel` の device 時間、8 ラウンドの中央値、既定比。
4 点とも既定とレンジ非重複。）

**52 は占有率が既定と同じで、しかも spill を背負っているのに 13〜20% 速い。**
占有率でも spill でも説明できない。**上限を掛けること自体がコード生成を
変えている。**そして 44 は 48 と占有率が同じなのに 10〜13 ポイント遅く、
**spill はやはり高くつく**。§8.6.1.1 の −17〜19% は、この 3 つの効果
（コード生成の改善・占有率の利得・spill の損失）の差引だった。

#### ncu が何が変わったかを言う（Slurm job `82455`、node `c265`、p=127）

| ビルド | dur | 占有 | **L1%** | L1 hit | 命令 | IPC | local LD / ST（sector） | **longSB** |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| reg56（既定） | 8.85 ms | 49.6% | **55.5** | 52.4 | 1731 M | 0.30 | 0 / 0 | **20.4** |
| cap52 | 6.92 ms | 49.5% | **71.5** | 51.4 | 1835 M | 0.40 | 0 / 10 M | 12.4 |
| **cap48** | **6.68 ms** | 62.0% | **93.4** | 59.4 | 1971 M | 0.44 | 268 M / 289 M | 13.4 |
| cap44 | 8.70 ms | 61.9% | 92.7 | 66.2 | 2174 M | 0.38 | **805 M / 633 M** | 16.4 |

（p=63 も同形: L1% は 52.3 / 68.0 / 92.1 / 91.5。）

読み取り:

- **52 の spill はバイナリにはあるが、実行されていない**（local LD 0 sector、
  ST 10 M）。つまり 52 対 56 は**実質どちらも spill 無しの比較**で、それでも
  L1 スループットが **55.5% → 71.5%**、`longSB` が **20.4 → 12.4**、IPC が
  0.30 → 0.40 に動く。**既定の 56 レジスタのコードは、単に質が悪い。**
  命令数はむしろ既定のほうが少ない（1731 M 対 1835 M）のに遅い。
- **48 は L1 を 93.4% まで押す**（ほぼ飽和）。spill は実際に実行されるが
  （268 M / 289 M sector）、占有率の利得が上回る。
- **44 は spill が 3 倍**（805 M / 633 M）で、稼いだ L1 帯域を spill 自身が
  食い、48 より 30% 遅い。

**このカーネルは L1 スループット律速**という §8.6.1 の診断はそのままで、
**GB200 の既定ビルドはその L1 を半分しか使えていない**というのが残差の正体
である。H100 の 44 レジスタ・spill 無しのコードは L1 を 79.0% まで押す
（§8.6.1）。**GB200 は上限 48 で 93.4%、H100 より高いところまで行く。**

#### 残差は消える

上のアブレーション係数を production の実測（§8.6.1 の表）に当てると:

| p | GB200 既定 | **GB200 @48** | H100 | 48 対 H100 |
|---:|---:|---:|---:|---|
| 15 | 1196.1 µs | **831.3** | 935.0 | **GB200 が 11.1% 速い** |
| 63 | 3492.9 | **2464.7** | 2563.4 | **GB200 が 3.9% 速い** |
| 127 | 6443.9 | **4722.1** | 4585.0 | H100 が 2.9% 速い |

**`SPLIT` の逆転（H100/GB200 が 0.99 と 0.90）はアーキテクチャの性質では
なく、GB200 向けビルドのレジスタ配分が悪いことの帰結である。**同じ占有率を
H100 が自然に得ているところを GB200 は上限指定でしか得られず、既定では
得ていない。上限を 48 にすると逆転は p=15 と p=63 で消え、p=127 でも
2.9% まで縮む。

**この節を `SPLIT` の最適化に使ってはいけない。**`CUDAFORTRAN_SPLIT` は
control 経路（`AGENTS.md`）であり、`maxregcount` は実行ファイル中の
すべての CUDA Fortran カーネルに掛かる。ここで確定したのは機構だけである。
#### 一般化するか調べた（Slurm job `82456`、node `c156`）——しない

「sm_100 のレジスタ配分がこのカーネルで 27〜30% 損をしている」が
`volume_deriv_kernel` 固有なのか、production にも同じ余地があるのかを
screening した。`-gpu=maxregcount` は **CUDA Fortran のカーネルにしか
掛からない**（`.cu` は nvcc 管轄）ので、経路が対照付きで割れる:
`GEMM` / `GEMM_FUSED` は周辺カーネル（`volume_flux`、`elembnd_flux`、
`separable_lift_assembly`）が CUDA Fortran なので**動きうる**、
`FUSED` / `FUSED_TC` は tendency カーネルが `.cu` なので**動いてはいけない**。

`Main` ms/step 中央値、6 ラウンド交互、既定（56）比:

**結果は否定的である。** production で実在の利得が出たのは `GEMM` の

どの次数でも動かない（`separable_lift_assembly` を融合して走らせないので、

production の CUDA Fortran カーネルはレジスタが 24〜32 本・占有率 80〜98% で、
配分の良し悪しが効く領域にそもそも居ない。**`maxregcount` を production に
入れる根拠は無い**（0.4% を得るために実行ファイル全体に粗い上限を掛ける
形になり、数値検証もやり直しになる）。

### 8.7.4 説明が付いた: p=7 だけ `volume_deriv` が逆転しない

p=7 の SPLIT は**別のカーネル**を launch する（`volume_deriv_p7_kernel`、
1 要素 1 ブロック、shared 14 KB）。同一コンパイラで両アーキテクチャの

| カーネル | sm_90 | sm_100 |
|---|---:|---:|

| `volume_deriv_p7_kernel`（p=7 が使う） | 32 | 32 |
| `surface_lift_kernel` | 30 | 32 |
| `dqdt_assembly_kernel` | 24 | 22 |
| 他 12 本 | 差は 2 以内 | |

**逆転するカーネルだけがレジスタ数で 12 本違い、p=7 が使うほうは同じ。**
§8.6.1 の説明はこれで閉じる（p=7 の比 1.96 は他のカーネルと同じ側）。

なお `volume_flux_deriv_p7_kernel` と
`volume_flux_deriv_lift_assembly_p7_kernel` は**定義だけあって launch 箇所が
無い**（デッドコード）。測定には影響しない。

### 8.7.5 説明が付いた: `surface_lift` の比が p=127 で 3.24 に跳ぶ

`surface_lift` の H100/GB200 は p=15 / 31 / 63 で 1.19〜1.25 なのに p=127 で
**3.24** になる。§8.6.1 の ncu にすでに答えがある: GB200 の `surface_lift` の
DRAM スループットは p=15 / 63 で **8.8 / 7.2%** だが p=127 では **62.4%** で、
そこで初めて DRAM 律速になる。**DRAM 律速になった瞬間に HBM ピーク比 3.30 が
効く**というだけで、`volume_deriv` の逆転とは無関係である。

### 8.8.6 z タイル 64x64 を実装して測った——**不採用**（Slurm `82569` / `82586`、node `c389`）

§8.8.4 / §8.8.5 の手掛かり（cuBLAS の 64x64 は平の z で両機とも速い）を、
規則どおり **`VolumeGemmSet` の `GemmZ` / `GemmZScale` / `GemmZWide` を
同時に 64x32 → 64x64 に替えて**実装し、変更前バイナリと交互に測った。
warp タイル `GS<32,32,TileK>` は据え置きなので、ブロックは 2 warp（64
スレッド）から 4 warp（128 スレッド）になり、**エピローグの 1 スレッド
あたりフラグメントは 32 doubles のまま不変**（64·32/64 = 64·64/128）。
「フラグメントが増えないなら担い手も耐えるはず」というのが採用の見込みだった。

**数値は全次数で正しい**（p=63 / 127 / 255 / 511、点変化係数、owned `dqdt`
全点、`GEMM` 対照。`GEMM_CUTE` は 4 次数ともビット一致、`GEMM_FUSED` は
2.078e-16〜4.156e-16）。

**時間**（`Main` ms/step 中央値、8 ラウンド交互、p=575 / 767 は 4）:

| p | `GEMM_CUTE` | `GEMM_FUSED` | `GEMM`（対照） |
|---:|---:|---:|---:|
| 63 | **−1.20%** ※ | **+8.58%** ※ | +0.04%（重複） |
| 127 | **−0.97%** ※ | **+4.29%** ※ | −0.04%（重複） |
| 255 | **−0.73%** ※ | **+2.89%** ※ | +0.03%（重複） |
| 511 | −0.39% ※ | +0.41% ※ | −0.01%（重複） |
| 575 | −0.40% ※ | +0.36% ※ | +0.00%（重複） |
| 767 | −0.33% ※ | +0.36% ※ | −0.00%（重複） |

※ = レンジ非重複。**cuBLAS 経路はこの変更の影響を受けないはずで、実際に
6 次数とも ±0.04% でレンジ重複**——対照が働いており、測定は信頼できる。

**平の z は速くなり、担い手は遅くなる。**`AGENTS.md` は z タイルを
`GEMM_CUTE` と `GEMM_FUSED` で共有すると定めているので、
**`GEMM_CUTE` だけの −1.2% では採用できない**。しかも `GEMM_FUSED` は
p>=511 の最速経路であり、p=63 の +8.58% は論外である。**不採用とし、
ソースは revert した**（revert 後のバイナリは変更前と `cuobjdump -res-usage`
で 805 カーネル全一致、p=63 `GEMM_FUSED` の交互実行もレンジ重複）。

**機構**（担い手カーネルの ncu、Slurm `82586`）:

| p=127 担い手 | dur | regs | grid | block | 占有 | SM% | local LD / ST | 命令 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 64x32（現行） | **310.4 µs** | 254 | 8192 | 64 | 12.15% | **71.0** | **0 / 0** | 68.6 M |
| 64x64 | 373.6 µs | 254 | 4096 | 128 | 12.17% | 59.2 | **5.77 M / 4.46 M** | 63.9 M |

| p=63 担い手 | dur | regs | grid | block | 占有 | SM% | local | 命令 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 64x32（現行） | **234.9 µs** | **238** | 8192 | 64 | 12.09% | **50.9** | 0 / 0 | 57.5 M |
| 64x64 | 292.3 µs | **254** | 4096 | 128 | 12.17% | 40.7 | 0 / 0 | 49.7 M |

- **占有率は動かない**（12.1%）。64 スレッド × 4 ブロックと 128 スレッド ×
  2 ブロックは warp 数が同じで、**これは占有率の話ではない。**
- **CTA が半分になり（8192 → 4096）、SM スループットが 71.0 → 59.2%
  （p=127）、50.9 → 40.7%（p=63）に落ちる。**命令数はむしろ減っている
  （68.6 → 63.9 M）のに遅い。**担い手はレイテンシ律速で、少なく大きい CTA
  では隠す相手が足りない。**
- p=127 では **担い手が spill を始める**（local LD 5.77 M sector）。p=63 では
  レジスタが 238 → 254 と上限に迫る。

**事前の見立て（フラグメントが不変だから安全）は不十分だった。**担い手の
エピローグは他 2 本の微分と面データも読むので、**フラグメント量が同じでも
CTA 数の半減と 254 レジスタが効く**。**平の z（軽いエピローグ）は広いタイルを
好み、担い手は好まない。**同じ mainloop を共有する規則がある以上、
この 2 つは両立しない。

**残る可能性**（未測定）: `GEMM_CUTE` と `GEMM_FUSED` の両方で z を 64x64 に
しつつ、**担い手だけ warp タイルや stage 数で埋め合わせる**道はまだ
塞がっていない（`AGENTS.md` が共有を求めるのは mainloop のタイル・warp 数・
stage 数・swizzle であり、そこを揃えたまま担い手の spill を消す自由度は
エピローグ側にしか無いので、見込みは薄い）。

## 8.11 実装の質と機械を切り分けた —— **H100 の到達率の差は機械の性質ではない**（2026-09-09、SGE `8611480` / `8611482`、node `r7n8`）

### 8.11.1 なぜ —— これは C3 の一般命題に直接あたる

### 8.11.4 **答え: 機械ではない。命令数である**

**同じ機械・同じ問題・同じ演算量で、次の 3 つが揃っている:**

- **DRAM バイトは 4 セルとも同一**（2.1335〜2.1349 GB、**幅 0.07%**）。
  **メモリトラフィックの差ではない。**
- **占有率も同一**（12.41〜12.47%）。**並列度の差でもない。**
- **理論演算量は定義上同一。**

**違うのは発行する命令数である。自前 CUTLASS は同じ算術に対して
cuBLAS の 2.31〜2.44 倍の命令を発行する**（命令/FLOP が 0.1255 対
0.2892 / 0.3065）。L1 バイトも **1.372 倍**動かす。

したがって **A.5.3 の落差は機械の性質ではない。**同一機械・同一問題で
到達率が **46.8% から 84.6% まで動く**のは、**mainloop が同じ算術を
何命令・何 L1 バイトで実行するか**の違いだけによる。

> **2026-09-09 注記: この 46.8%〜84.6% は §8.11.3 の表と同じ `ncu`(`none`) 基準である。**
> §8.7.2.1 の手続きで本番側に直すと **45.7% 〜 高々 84.5%** になる。散らばりの幅は
> ほぼ変わらず、**「実装で散る」という結論は不変**である。

### 8.11.5 形状ノブが何を買っているか —— 命令ではなく math パイプ

`16x8x4` は自前 CUTLASS の時間を **13.180 → 8.678 ms（−34.2%）**にするが、
**命令数は 3.950e9 → 3.726e9（−5.7%）しか減らない**。買っているのは
命令の総数ではなく **math パイプの圧力**である: `DMMA.16x8x4` が単一命令に
なるので mma 発行が半分になり、**math stall が 2.37 → 0.94** に落ちる。
その結果**律速資源が移る**:

- `8x8x4`: `SM%` **92.69**、`L1%` 53.57 —— SM パイプ律速
- `16x8x4`: `SM%` 67.15、`L1%` **80.21** —— **L1 律速に変わる**

**形状ノブは命令ギャップを閉じない**（2.44 倍 → 2.31 倍）。
**閉じるには mainloop がレジスタでもっと再利用する必要がある**——
cuBLAS は 246 レジスタで L1 を 40% に抑え、自前は 156〜168 レジスタで
L1 を 54〜80% まで使う。**これは register blocking の差である。**

### 8.11.6 本文で何が書き換わるか

- **`draft_appendix_a5.md` A.5.3 の「切り分ける対照は取っていない」は消せる。**
  対照は本節で、答えは「実装の質」である。
- **`draft_architecture_mechanism.md` §7.6 の C3 の一般命題は弱める必要がある。**
  「到達率は (カーネル, 機械) の属性」は、**同一機械・同一カーネル種・
  同一 DRAM トラフィック・同一占有率でも実装で 46.8〜84.6% に散る**という
  本節の測定と両立しない。C3 が言えるのは
  **「到達率は移植しない」**までであって、**その値が機械の属性だ**とは
  言えない。
- **`draft_order_mechanism.md` §6.5(b) の守る線「H100 の CUTLASS が弱いとは
  書かない」は、もう守れない。**本節は**弱いことを機構つきで測っている**。
  §7 側を弱めた 2026-09-08 の処置と合わせ、**両方を測定に基づいて
  書き直すべきである**（A.5.3 と §7.6 が同じ測定を引く形になる）。

### 8.11.7 測っていないこと

- **なぜ cuBLAS の mainloop が 2.3 倍少ない命令で済むか。**SASS は見ていない。
  レジスタ数（246 対 156〜168）と L1 バイト（1.372 倍）から
  register blocking の差だと**読める**が、**分解はしていない**。
- **`GEMM_FUSED` 側では取っていない。**本節は一軸を保つため `GEMM_CUTE`
  だけである。A.5.3 の 45.2% / 61.2% は `GEMM_FUSED` の stage 量なので、
  **本節の 46.8% / 71.0%（体積 GEMM 3 本のみ）と同じ量ではない。**
  順序と桁は一致するが、**数値を差し替えてはならない。**
- **GB200 / A100 で同じ分解を取っていない。**本節は H100 のみ。
  GB200 では cuBLAS が CUTLASS 生成カーネルを出すので軸が縮退しており
  （§8.7.2）、**同じ対照はそもそも取れない。**
