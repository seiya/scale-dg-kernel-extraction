## 1. なぜ 3 台目が A100 なのか

2 台では 2 つの軸が交絡している。A100 はその空白セルである。

| | FP64 CUDA core | FP64 Tensor Core | HBM | B/FLOP（対 CC） | TC 飽和に要る強度 | f64 MMA 形状 |
|---|---:|---:|---:|---:|---:|---|
| GB200 (cc 10.0) | 40.1 TF | 40.1 TF（**1.0x**） | 7.9 TB/s | 0.197 | 5.1 F/B | `8x8x4` のみ |
| H100 (cc 9.0) | 33.5 TF | 66.9 TF（2.0x） | 2.396 TB/s | 0.072 | **27.9 F/B** | `8x8x4` / `16x8x4` / `16x8x8` / `16x8x16` |
| **A100 (cc 8.0)** | **9.7 TF** | **19.5 TF（2.0x）** | **1.555 TB/s** | **0.160** | **12.5 F/B** | **`8x8x4` のみ** |

- **TC/CC 比 2 倍**という点では H100 と同じ側、**f64 MMA が `8x8x4` しかない**
  という点では GB200 と同じ側。§8.3（`16x8x4` が H100 高次で 18〜22%）と
  §8.7.1（mma が買うのは命令数）を、この 2 つを分離した状態で検証できる。
- B/FLOP は GB200 に近く（0.160 対 0.197）、H100（0.072）から遠い。
  §8.2 のルーフライン説明が正しければ、**A100 の達成率カーブは GB200 のそれに
  重なり、時間だけ約 4〜5 倍になる**はずである。

## 2. 予測に使ったモデル

各次数・各経路について、時間が**演算分と帯域分の和**（重なりなし）に分かれると
置く。係数 `a`, `b` は機種非依存と仮定する。

```
t_m = a * (W_flop / peak_flop_m) + b * (W_bytes / peak_bw_m)
```

GB200 を基準に `A = a*W_flop/40.1T`, `B = b*W_bytes/7.9T` と置くと、
2 台の実測から `A`, `B` が**一意に決まる**（未知数 2、方程式 2）。

```
t_GB200 = A + B
t_H100  = (40.1/33.5) A + (7.9/2.396) B = 1.1970 A + 3.2972 B
t_A100  = (40.1/9.7)  A + (7.9/1.555) B = 4.1340 A + 5.0804 B   <- 予測
```

このモデルの性質:

- **A100/GB200 比は構造的に 4.134〜5.080 の間に入る。** 演算律速の極限で 4.134
  （FP64 CC ピーク比）、帯域律速の極限で 5.080（HBM ピーク比）。
  H100/GB200 が 3.10 → 1.11 と 3 倍近く動いたのに対し、**A100/GB200 は
  5.08 → 4.13 の狭い帯にしか動かない**。これがこの機械を足す一番の帰結である。
- 演算ピークは **CUDA core 側（9.7 TF）を全経路の分母に使う**。`FUSED_TC` にも
  TC ピーク 19.5 TF は使わない。§8.7.1 が「mma が買うのは命令数であって
  FLOP/s ではない」と結論しており、§8.2 も H100 の TC 経路に 33.5 TF を
  当てているので、それに揃える。
- **モデルに入っていないもの**: 命令発行率、レジスタ割り当て、占有率、
  launch オーバーヘッド、ライブラリのカーネル選択。これらが効く行は外れる。
  **外れること自体が情報**なので、下の §5 に「外れたら何が言えるか」を書く。

### 予測 2: A100 では mma の利得が**現金化できる**（H100 の逆転は起きない）

§8.7.1 は、H100 で mma の利得が小さいのは「TC が HBM の 86〜89% に張り付いて
命令削減を現金化できない」からだと結論した。A100 は TC 飽和に要る演算強度が
**12.5 F/B と H100 の 27.9 の半分以下**なので、この説明が正しければ A100 では
GB200 に近い挙動になるはずである。

`FUSED_TC ÷ FUSED`:

| | p=7 | p=15 | p=31 | p=63 | p=127 | p=255 |
|---|---:|---:|---:|---:|---:|---:|
| GB200 実測 | 0.897 | 0.956 | 0.871 | 0.895 | 0.746 | 0.638 |
| H100 実測 | **1.007** | 0.938 | 0.982 | **1.009** | 0.790 | 0.519 |
| **A100 予測** | **0.926** | 0.951 | 0.896 | 0.919 | 0.754 | 0.615 |

**全 6 次数で TC が勝つ（GB200 と同じ）。H100 で起きた p=7 / p=63 の逆転
（1.007 / 1.009）は A100 では起きない。** ここが外れたら §8.7.1 (A) の説明は
間違いで、TC の不利は帯域ではなく別の要因ということになる。

### 予測 3: `GEMM` と `GEMM_CUTE` は A100 で**縮退する**

§8.7.2 は、GB200 の cuBLAS が FP64 volume GEMM に
`cutlass_80_tensorop_d884gemm`——**sm_80 向けの CUTLASS 生成カーネル**——を
出していることを突き止め、そのために GB200 ではライブラリ軸が測定になって
いないと結論した。A100 はそのカーネルの母国機であり、我々の既定
`MmaSet_884` も `cutlass::arch::Sm80` タグ（`cuda_cutlass_gemm_fused.cu:261`）
である。

**この予測の検証は時間ではなく `nsys` のカーネル名で行う**（時間による検証は
§3 の当てはめが H100 の本物のライブラリ差を吸ってしまうので弱い）。

- **予測**: A100 の cuBLAS も `cutlass_80_tensorop_d884gemm` 系を出し、
  `GEMM` と `GEMM_CUTE` は GB200 と同様に縮退する（`Main` で数 % 以内）。
- **これが出れば**: 「GB200 でライブラリ軸が死んでいるのは cuBLAS が
  CUTLASS を呼んでいるからで、Blackwell に FP64 GEMM が無いこと固有の事情
  ではない」が確定する。§8.7.2 (B) の結論が 2 台で立つ。
- **これが外れ、A100 の cuBLAS が手書きカーネルを出したら**: GB200 の縮退は
  Blackwell 固有（`56c3154`「cuBLAS は Blackwell の FP64 GEMM を持たず
  エミュレーションだけ」）の帰結であり、§8.7.2 の一般化は取り下げる。

## 5. 外れたら何が言えるか（モデルの反証条件）

| 外れ方 | 含意 |
|---|---|
| A100/GB200 が **5.08 を超える** | HBM ピーク比より悪い。加法モデルの外——A100 の実効帯域が 1.555 TB/s に届いていない（HBM2e の実効効率、または L2 の差）。 |
| A100/GB200 が **4.13 を下回る** | FP64 CC ピーク比より速い。A100 が TC ピーク 19.5 TF を実際に使えている（＝演算の分母を 19.5 TF に取り直すべき）ことを意味し、§8.7.1 の「mma は FLOP/s を買わない」に対する反例になる。 |
| 低次（p=7〜31）だけ大きく外れる | launch オーバーヘッドと Ice Lake ホストの寄与。§8.5 が `SPLIT` について立てて棄却した仮説が、今度は本当だったことになる。3 種類のホスト（Grace / TSUBAME x86 / Ice Lake）が揃うので分離できる。 |
| 高次（p=511 / 575）だけ大きく外れる | 40 GiB では L2 / HBM の作業集合の乗り方が違う。ここは payload が 23〜33 GiB で容量の 6〜8 割を占めるので、他 2 台と条件が揃わない可能性がある。 |
| `FUSED_DFMA` だけ外れる | iso-schedule 対照が sm_80 で成立していない（レジスタ割り当ての差）。§8.7.3 と同じ機構。 |

## 7. sm_80 への移植で必要だった変更（2026-09-05、GB200 上でクロスビルド）

**「既定が `arch::Sm80` タグだからほぼ素通り」は誤りだった。** cc80 ビルドを
実際に通したところ 2 件の sm_90 依存が出た。どちらも sm_90 / sm_100 の挙動は
変えない形で外してある。

### 7.1 `cuda_dg_kernels_tc.cu` の PDL が sm_90 専用（**ビルドが通らない**）

`FUSED_TC` / `FUSED_DFMA` の実体は Programmatic Dependent Launch を使っており、
`-arch=sm_80` では ptxas が拒否する:

```
ptxas ... error : Instruction 'griddepcontrol' requires .target sm_90 or higher
ptxas ... error : Modifier '.launch_dependents' requires .target sm_90 or higher
```

- デバイス側 `griddepcontrol.launch_dependents` / `.wait` が 9 箇所
  （p=31 / p=63 / p=127 の融合カーネル）、ホスト側
  `cudaLaunchAttributeProgrammaticStreamSerialization` が 7 箇所。
- **これを外さないと A100 では `FUSED_TC` と `FUSED_DFMA` がビルドできず、
  §4 の予測 2（mma の利得の現金化）は検証すらできない。**
- 対処: デバイス側は `dg_pdl_launch_dependents()` / `dg_pdl_wait()` に包み、
  `__CUDA_ARCH__ >= 900` の内側だけで asm を出す。ホスト側は
  `numAttrs = dg_pdl_num_attrs()` とし、PDL の無いビルドでは属性を 0 個にする。
  sm_80 では PDL ヒントが消えて**通常のストリーム順**に落ちるだけで、
  生産者 → 消費者の依存はより保守的に保たれる。
- **注意**: これは A100 で `FUSED_TC` が PDL 分だけ不利になることを意味する。
  §3 の予測は PDL 込みの GB200 / H100 実測から外挿しているので、
  **A100 の `FUSED_TC` / `FUSED_DFMA` が予測より遅く出たら、まずこの PDL 欠落を
  疑う**こと。切り分けは GB200 で `P63_PDL_STAGE=0` 等をビルド時に落とした
  アブレーションで取れる（未実施）。

### 7.2 `CutlassMmaShape` 1〜3 が sm_80 では**デバイストラップになる**

`-arch=sm_80` での `cuda_cutlass_gemm_fused.cu` のコンパイルは
**エラーも警告も無く通る**（exit 0、17 MB のオブジェクト）。しかし
`third_party/cutlass/include/cutlass/arch/mma_sm90.h` は
`mma.sync.aligned.m16n8k4.f64` の asm を `__CUDA_ARCH__ >= 900` の内側に置き、
それ以外では `CUTLASS_NOT_IMPLEMENTED()` に落とす。その定義は
`cutlass/detail/helper_macros.hpp:92` の **`asm volatile("brkpt;")` /
`assert(0)`** である。

つまり A100 で `CutlassMmaShape = "16x8x4"` を選ぶと、namelist のエラーではなく
**カーネル内のデバイストラップ**になる。`cuda_cutlass_has_sm90_f64_mma()` を
追加し、`cuda_cutlass_set_mma_shape` で `error stop` に変えた。

判定はビルドターゲット（`__CUDA_ARCH_LIST__`、nvcc はホストパスでも定義する）と
実行時のデバイス CC の両方を見る。ホスト側判定の実測:
`sm_80 -> 0`、`sm_90 -> 1`、`sm_100 -> 1`、`-gencode` で 80+90 -> 1
（最後のケースがあるので実行時確認も要る）。

### 7.3 検証（GB200、login GPU、commit は本ファイルと同じ）

- **cc80 フルビルド成功**（`make CUDA=1 GPUFLAGS=-gpu=cc80
  GPUNVCCFLAGS=-arch=sm_80`、21.7 MB、エラー 0）。実行は sm_100 の
  GB200 では不可なので、A100 上で行う。
