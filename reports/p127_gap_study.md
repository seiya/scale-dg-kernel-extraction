# p=127 (Nq=128) — 同一 DOF ギャップの 5 点目、マシンバランスを越える最初の点

測定環境: RIKYU NVIDIA GB200 1 GPU、`make CUDA=1 GPUFLAGS=-gpu=cc100`。
コミット: 本レポートを追加したコミット（親は `760e96e`）。
実行ファイルは `scale-dg_extraction.p127` に凍結し、実測・nsys・ncu すべてで同じものを使った。
nsys は Slurm job `58383`（`job_nsys_p127.sh`）、ncu は Slurm job `58384`
（`job_ncu_p127.sh`、`--set full`）。いずれも p=63 と p=255 を**同一実行ファイル**で並べて取っている。
入力: `conf_perf_p127*.conf`（`NeX=NeY=NeZ=2, PolyOrder=127, UseCudaGraph=.false.`）。
検証: `input_p127_val*.conf`（`Ne=2³`、`nstep=1`、`SCALE_DG_VARYING_COEFF=1`）。

## 1. なぜ p=127 か —— 検証すべき 3 つの予測

`p63_gap_study.md` §9 が次の点として名指ししていた:

> **次にマシンバランスを越えるのは p=127 のはずである。** GEMM 経路の転送量 ≒ 151 B/ノードを
> Nq 非依存として、`6*Nq + 20 = 5.0 * 151` を解くと **Nq ≒ 123**。

同一 DOF（16.78 M = 256³）を立方一様メッシュで保つ条件 `NeX*Nq = 256` から埋められるのは
p = 15, 31, 63, 127 の 2 冪だけで（`p15_gap_study.md` §1）、p=127 は `NeX=NeY=NeZ=2`、`Ne=8`、
`Nq=128`。1 要素の `q` は **16 MB** で、要素を shared に載せる話は Nq=32 で既に終わっている。

作業前に立てた予測は 3 つである。

1. **演算強度がマシンバランス（GB200 で 40.1 TFLOP/s ÷ 7.92 TB/s = 5.06 FLOP/B）を越える。**
   体積 FLOP/ノードは `6*Nq+20 = 788`、転送量が Nq 非依存の ≒151 B/ノードなら 5.2 FLOP/B。
2. **FP64 ピーク比は p=63 の 28.7% と p=255 の 65.8% の間、45% 前後に乗る。**
3. **x GEMM をどちらのライブラリに渡すべきか変わりうる。** 現行の分岐は `Nq <= 64` で cuBLAS
   （`mod_cuda_dg_kernels.cuf:1068`）。根拠は mainloop の深さで、`TileK=16` に対し
   p=63 は 4 反復（cuBLAS が 1.59 倍速い）、p=255 は 16 反復（互角）。
   **p=127 は 8 反復でちょうど中間**にあり、外挿できない。

融合カーネルは書いていない。`p63_gap_study.md` §8 の判断（Nq≥64 では手書き融合が GEMM に
勝つ条件が厳しすぎる）が p=127 ではさらに厳しくなる —— §6 のとおり必要な達成効率は
25.2% 超から **46.5% 超**に上がった。

## 2. ホスト側で必要になった変更 —— **無し**

**p=127 はコードを 1 行も足さずに 5 経路すべてで走った。** これは p=63 の作業
（`p63_gap_study.md` §2）で入れた一般化がそのまま効いたということである。確認した点:

- `mod_mesh.f90:271` は `operator_data/p127.dat` が無いので `generate_lgl_operators(p,...)` に
  落ちる。生成は 1 秒未満で、数値は §3 のとおり基準実装と一致する。
- `mod_mesh.f90:279` の `dense_lift = (Nq <= 128)` は Nq=128 を**含むように書かれていた**
  （コメントが「100 MB at Nq=128」と名指ししている）。`Lift_mat(128,128,128,6)` = 100.7 MB が
  実体化されるので、`OPENACC_SPLIT` と `CUDAFORTRAN_SPLIT` を基準実装として使える。
- `mod_dg_optr_kernel.f90` の 4 か所の `select case(Nq-1)` は `case default` で
  `*_general` に落ちる。
- `cuda_cutlass_gemm_fused.cu` / `cuda_cublas_gemm.cu` / `cutlass_z_gemm_assembly.h` は
  `Nq` が実行時 `int` で完全に汎用。
- `Nq*Ne = 128*8 = 1024` は CUTLASS の `grid.z` batch 上限 65535 に対し余裕がある。
- `Nq >= 64` なので `cuda_cal_dqdt_gemm` の側ストリームは既定で on（§8 で正しいと確認）。

使えるのは `CUDAFORTRAN_GEMM` / `GEMM_FUSED` / `GEMM_CUTE` / `CUDAFORTRAN_SPLIT` /
`OPENACC_SPLIT` の 5 つ。`CUDAFORTRAN_FUSED` と `FUSED_TC` は p=7/15/255 専用のままである
（`mod_advect3d_eq.f90:142,:153`）。

メモリは 1 フィールド 134 MB、work を含めて約 1.6 GB。

## 3. 検証

すべて `SCALE_DG_VARYING_COEFF=1`（点ごとに変動する `u,v,w,Escale,normal_fn,Fscale`）で、
`SCALE_DG_DUMP_DQDT` により完全な `dqdt(:,1:Ne)`（16,777,216 値）を落として比較した。
基準は `input_p127_val_ref.conf`（`DGOptrKernel_OptType="GENERAL"` + `OPENACC_SPLIT`）で、
`max|ref| = 8.548236`。

| ケース | 基準 | 最大絶対差 | 相対差 |
|---|---|---|---|
| p=127 `CUDAFORTRAN_SPLIT`, `Ne=2³` | `OPENACC_SPLIT`(GENERAL) | 0 | **0（完全一致）** |
| p=127 `CUDAFORTRAN_GEMM`, `Ne=2³` | 同 | 0 | **0（完全一致）** |
| p=127 `CUDAFORTRAN_GEMM_CUTE`, `Ne=2³` | 同 | 0 | **0（完全一致）** |
| p=127 `CUDAFORTRAN_GEMM_FUSED`, `Ne=2³` | 同 | 3.553e-15 | **4.156e-16** |

`GEMM_FUSED` だけ差が出るのは z epilogue が lift を面から直接評価して総和順序を変えるためで、
p=63 / p=255 で記録されている 4.16e-16 と同値である。**次数を変えても同じ値になる**のは
この差が丸め 1 回分であることの傍証になっている。

コード変更が無いので既存次数の回帰試験は不要（§8 のノブ掃引はすべて一時ビルドで行い、
採用したものは無い）。

## 6. 理論仕事量と達成効率 —— 予測 1 と 2 の答え

体積は 1 ノードあたり `6*Nq + 20` FLOP、面は 1 面点あたり 21 FLOP。
DRAM バイトは ncu の実測（Memory Throughput × Duration の、tendency 5 カーネル分の合計）で、
`p63_gap_study.md` §6 と同じ取り方である（同じ手順で p=63 は 2.669e9、p=255 は 2.531e9 と
公表値 2.666e9 / 2.532e9 を再現した）。

| | p=7 | p=15 | p=63 | **p=127** | p=255 |
|---|---|---|---|---|---|
| `Ne` | 32³ | 16³ | 4³ | **2³** | 1 |
| 体積 FLOP/ノード | 68 | 116 | 404 | **788** | 1556 |
| 理論 FLOP / stage | 1.405e9 | 2.078e9 | 6.811e9 | **1.324e10** | 2.611e10 |
| DRAM バイト / stage | 1.598e9 | 1.361e9 | 2.669e9 | **2.480e9** | 2.531e9 |
| バイト/ノード | — | — | 159.1 | **147.8** | 150.9 |
| **演算強度 [FLOP/B]** | 0.88 | 1.53 | 2.55 | **5.34** | 10.32 |
| 実装 | `FUSED_TC` | `FUSED_TC` | `GEMM_FUSED` | **`GEMM_FUSED`** | `GEMM_FUSED` |
| Main [ms/step] | 1.0715 | 1.3054 | 2.0459 | **2.3941** | 3.2364 |
| 1 stage [µs] | 269.5 | 346.3 | 592.8 | **710.3** | 990.0 |
| TFLOP/s（ピーク比） | 5.21 (13.0%) | 6.00 (15.0%) | 11.49 (28.7%) | **18.63 (46.5%)** | 26.38 (65.8%) |
| TB/s（ピーク比） | 5.93 (75%) | 3.93 (50%) | 4.50 (57%) | **3.49 (44%)** | 2.56 (32%) |

（p=7 / p=15 / p=63 / p=255 の値も本コミットの実行ファイルで測り直した。
`p63_gap_study.md` §10 末尾の 4 点表と µs 単位で一致する。）

**予測 1 は当たった。** p=127 の演算強度は **5.34 FLOP/B** で、マシンバランス
**5.06 FLOP/B**（40.1 TFLOP/s ÷ 7.92 TB/s）の**向こう側にある**。5 点で初めてである。
予測の根拠だった「転送量が Nq 非依存」も実測 147.8 B/ノードで裏づけられた
（p=63 の 159.1、p=255 の 150.9 との差は面フェーズだけで説明できる）。

**予測 2 も当たった。** FP64 ピーク比は **46.5%** で、事前に置いた「45% 前後」の通り。
同一 DOF の 5 点で **13.0 → 15.0 → 28.7 → 46.5 → 65.8%** と単調に上がる。
帯域側は逆に 75 → 50 → 57 → 44 → 32% と下がる。p=63 が「帯域 57% / 演算 29% で
どちらの天井にも当たっていない」点だったのに対し、**p=127 は演算側に軸足を移した点**である。

## 7. ncu による律速の同定（Slurm job `58384`、`--set full`）

ncu はクロックを固定しキャッシュを掃除するので絶対時間は nsys と一致しない。比率で読むこと。

p=127 `GEMM_FUSED`:

| カーネル | Duration | Compute (SM) | DRAM | L1/TEX | 占有率 | レジスタ | 実行命令数 |
|---|---|---|---|---|---|---|---|
| z GEMM + assembly | 411.3 µs | 54.6% | 28.7% | 54.4% | 12.2% | **254** | 98.70 M |
| y GEMM | 258.3 µs | **79.0%** | 11.0% | 52.6% | 18.3% | 130 | 44.84 M |
| x GEMM | 251.1 µs | **81.5%** | 11.1% | 40.8% | 12.1% | 212 | 35.98 M |
| `volume_flux_kernel` | 133.6 µs | 43.2% | **84.4%** | 69.5% | 80.2% | 24 | 18.35 M |
| `elembnd_flux_kernel` | 42.8 µs | 9.7% | **60.4%** | 46.2% | 85.6% | 32 | 1.67 M |

同一実行ファイルの p=63 / p=255（比較用）:

| カーネル | p=63 SM / DRAM | p=255 SM / DRAM |
|---|---|---|
| z GEMM + assembly | 37.8% / 36.5% | 73.1% / 20.2% |
| y GEMM | 67.1% / 18.0% | 89.3% / 6.3% |
| x GEMM | 68.7% / 18.5%（cuBLAS） | 87.9% / 10.1% |
| `volume_flux_kernel` | 43.2% / 84.5% | 43.2% / 84.2% |
| `elembnd_flux_kernel` | 11.4% / 75.0% | 9.0% / 57.5% |

**p=127 の性格は p=63 と p=255 の間を素直に埋めている**が、内訳の重みが変わった:

1. x GEMM と y GEMM は **SM 発行律速**（81.5% / 79.0%）で、p=63 の 68.7 / 67.1% から
   p=255 の 87.9 / 89.3% へ向かう途中にある。占有率 12–18% はレジスタ 212 / 130 本の
   代償として意図的に取っているものである。
2. `volume_flux_kernel` と `elembnd_flux_kernel` は **DRAM の屋根**（84.4%、60.4%）。
   合わせて直列時間の 18.8%（面は側ストリームで隠れる）。**3 次数で 43.2% / 84% と
   1 桁まで同じ**で、削り代は無い。
3. z GEMM + assembly は依然として最大のカーネル（直列の 37.4%）で、SM 54.6% / DRAM 28.7% と
   **どちらでもない**。レジスタ 254 本・占有率 12.2% は 3 次数とも同じで、p=255 で
   `tma_survey.md` §2 が記録した構造と同じである。ただし SM は p=63 の 37.8% から
   54.6% に上がっており、**次数とともに演算側に寄っている**。

### 占有率を決めているもの —— レジスタと shared が**同時に**律速している

ncu の occupancy limiter を 3 本とも並べると、**`Block Limit Registers` と
`Block Limit Shared Mem` が完全に一致している**:

| カーネル | Block Size | レジスタ/thread | shared/block | Reg 上限 | Shared 上限 | 理論占有率 |
|---|---|---|---|---|---|---|
| z GEMM + assembly | 64 | 254 | 49,152 B | **4** | **4** | 12.50% |
| x GEMM | 128 | 212 | 73,728 B | **2** | **2** | 12.50% |
| y GEMM | 128 | 130 | 65,536 B | **3** | **3** | 18.75% |

CUTLASS の stage 段数は、この 2 つがちょうど釣り合うところに設定されている。
**したがって片方だけを削っても常駐ブロックは 1 つも増えない。**
これが「z のタイル・段数を振っても動かない」（§8.4、p=63 §11.2、p=255 `tma_survey.md` §2）
という 3 次数で共通の観測に対する、一段深い説明である。占有率を上げたければ
レジスタと shared を**同時に**削る必要があり、`GemmZ` の 5 stage 版が
（shared を増やす方向なので）+5% で終わるのもこれで説明がつく。
なお `Waves Per SM` は 13.5 / 6.7 / 9.0 で、CTA の数が足りないわけではない。

### K が深くなることの効き

`TileK=16` に対する mainloop の反復回数は `Nq/16` = 4 / 8 / 16 である。
命令あたりの仕事はそれに従って増える:

| | mainloop 反復 | x GEMM FLOP/命令 | y GEMM FLOP/命令 | z GEMM FLOP/命令 † |
|---|---|---|---|---|
| p=63 | 4 | 101.1（cuBLAS） | 73.8 | 26.9 |
| **p=127** | **8** | **119.4** | **95.8** | **43.5** |
| p=255 | 16 | 135.0 | 112.6 | 63.0 |

† z は epilogue に lift と assembly が入るので GEMM 分だけの分子で割った下限値である。

同じ 16.78 M DOF に対し方向あたりの GEMM は p=63 で 2.147 GFLOP、p=127 で 4.295 GFLOP、
p=255 で 8.590 GFLOP と倍々になるが、命令数はそれより緩やかにしか増えない。
これが §6 の達成効率が単調に上がる直接の理由である。

### ncu と nsys で x と y の順序が入れ替わる

nsys では x 163.8 / y 137.9 µs だが、ncu では x 251.1 / y 258.3 µs と逆転する。
y GEMM は同じ 128×128 の `D1D_tr` を 1024 個の batch すべてで読むので実運用では L2 に
載っているが、ncu は既定でカーネル間にキャッシュを掃除するためその再利用が消える、
というのが最も素直な説明である。**時間の帰属は nsys、律速の判定は ncu** という
これまでの使い分けを変える必要は無い。

## 8. 次数依存ノブの掃引 —— 予測 3 の答え

すべて `nstep=400`、tendency の µs/stage。

### 8.1 x GEMM のバックエンド —— **変更せず**（予測 3 は外れ）

`mod_cuda_dg_kernels.cuf:1068` の `if (Nq <= 64)` を `Nq <= 128` にした一時ビルドと比較した
（3 回ずつ交互に実行）:

| | 実測 [µs/stage] | 中央値 |
|---|---|---|
| x = CUTLASS（現行） | 710.0 / 709.6 / 709.1 | **709.6** |
| x = cuBLAS | 706.8 / 707.5 / 712.5 | 707.5 |

**差 0.3%、ばらつきの中である。** p=63 で 1.59 倍あった cuBLAS の優位は、
**p=255 を待たず p=127 で既に消えている**。§7 のとおり mainloop 8 反復で CUTLASS 2.x の
prologue / epilogue は十分に薄まる。`Nq <= 64` の閾値は現行のままで正しい。

**予測 3 は「変わりうる」としていたが、実際には変えるべき理由が無かった。**
なお nsys の x GEMM は p=127 で 163.8 µs、y は 137.9 µs で比は 1.19。
p=63 の CUTLASS x は y の 2.04 倍だったので、**x GEMM の弱さそのものが K の深さで解消している**。

### 8.2 `CutlassMmaShape`

| shape | `GEMM_FUSED` [µs/stage] |
|---|---|
| **`8x8x4`（既定）** | **710.6** |
| `16x8x4` | 706.7 |
| `16x8x8` | 720.6 |
| `16x8x16` | **1911.8** |

p=63 と同じ形である。`16x8x4` の 0.5% は測定のばらつきと同じ大きさなので既定を維持した
（H100 では `16x8x4` が効くが、GB200 では 3 次数とも効かない）。

`16x8x16` が 2.7 倍遅い理由は p=63 では「`TileK=32` で mainloop が 2 反復しか残らない」と
説明していたが、**p=127 では 4 反復あるのに依然として遅い**。切り分けのため
`8x8x4` のまま `TileK` だけ 16→32 にしたビルドを測ると **942.8 µs（+33%）**だった。
つまり `16x8x16` の損の**一部（+33%）は TileK=32 そのもの**（CTA あたり shared が倍になり
占有率が下がる）で、**残りは命令形状と ArchTag 側**である。反復回数だけの問題ではない。

### 8.3 境界流束の側ストリーム —— 現行どおり on が正しい

`cuda_cal_dqdt_gemm`（`CUDAFORTRAN_GEMM`）で `use_side = .false.` にした一時ビルドと比較:

| | Main [ms/step] | tendency [µs/stage] |
|---|---|---|
| 側ストリーム off | 2.7961 / 2.7998 | 844.1 / 844.7 |
| 側ストリーム on（現行） | 2.7710 / 2.7700 | 835.6 / 835.7 |

Main −1.0%、device −1.05%。面点率が `6/Nq` = 4.7% とさらに下がっても重ねる価値は残る。
`Nq >= 64` の条件はそのままでよい。`GEMM_FUSED` / `GEMM_CUTE` は元から無条件に重ねている。

### 8.4 `GemmZ` のタイルと stage 段数 —— 効かない

z GEMM + assembly は直列の 37.4% を占める最大のカーネルで、SM は p=63 の 37.8% から
54.6% に上がっている。それでも形は動かない（この掃引だけ別セッションで取ったため
baseline が 716.1 µs と 0.8% 高い。相対値で読むこと）:

| `GemmZ` | µs/stage |
|---|---|
| **`<64,32>` / warp `<32,32>` / 4 stages（現行）** | **716.1** |
| `<64,32>` / warp `<32,32>` / 3 stages | 716.6 |
| `<64,32>` / warp `<32,32>` / 5 stages | 752.9 |
| `<64,64>` / warp `<32,32>` / 4 stages | 730.2 |
| `<32,32>` / warp `<32,32>` / 4 stages | 728.1 |

p=63（`p63_gap_study.md` §11.2）でも p=255（`tma_survey.md` §2、
`overall_summary_report.md` §8.9）でも同じで、**このカーネルは 3 次数とも調整を受け付けない**。

### 8.5 `GemmX` / `GemmY` のタイル形状 —— 効かない（追記）

`GemmX` のスレッドブロックタイルはどの次数でも振られたことが無く、`GemmY` は p=63 で
ワープ形状と段数だけが振られていた。**p=127 は x GEMM の `M = Nq = 128` がタイル M と
一致させられる唯一の次数**（p=63 は M=64 で既に 1 タイル、p=255 は M=256 で 4 タイル）
なので、`M` を 1 タイルで覆えば `flux_x` の読み出しが 2 回から 1 回に減る（−134 MB/stage）。
これを含めて 5 通り測った（`nstep=400` を 2 回、空き GPU に固定）:

| 変種 | µs/stage |
|---|---|
| **`GemmX <64,128>` warp `<32,64>` 3 stages / `GemmY <64,64>` warp `<32,32>` 4 stages（現行）** | **709.7 / 708.6** |
| `GemmX <128,128>` warp `<64,32>` 3 stages（M を 1 タイルで覆う） | 711.5 / 712.0 |
| `GemmX <128,64>` warp `<64,32>` 3 stages（同上、N タイル半分） | 710.5 / 710.3 |
| `GemmX <64,128>` warp `<32,64>` 4 stages | 713.3 / 714.3 |
| `GemmY <128,64>` warp `<64,32>` 4 stages | 708.5 / 708.7 |
| `GemmY <128,128>` warp `<64,32>` 4 stages | 723.2 / 722.2 |

**`M` を 1 タイルで覆っても速くならない。** x GEMM は DRAM 11.1% の SM 発行律速なので、
転送量を 5% 削っても時間には出ない、という §7 の診断とそのまま整合する。
`GemmY <128,64>` は最初 −0.4% に見えたが、baseline と交互に 3 回ずつ測り直すと
707.8 / 708.6 / 708.3 対 708.5 / 708.7 / 708.5 で**差は無い**。
これで CUTLASS 側のタイル・ワープ・段数・`TileK`・命令形状のノブは 5 種すべて掃引済みで、
**採用すべきものはひとつも無かった**。

**測定衛生（再掲）**: この掃引の 1 回目はログインノードの GPU 0 に他人のプロセスが
載っている間に取ってしまい、同じ baseline が 710 → 884 → 968 µs と流れて全部無意味だった。
`p63_gap_study.md` §11.4 と同じ失敗である。`nvidia-smi --query-compute-apps` で確認し、
`CUDA_VISIBLE_DEVICES` で空いている GPU に固定してから測り直している。
また**冷えた GPU での 1 本目は捨てること**（アイドル時 120 MHz からの立ち上がりで 801 µs に出た）。

## 9. 結論

- 同一 DOF の 5 点目が入った。p=127 の最速は **`CUDAFORTRAN_GEMM_FUSED`**、
  Main **2.3941 ms/step** / **710.3 µs/stage**（graph on で 2.3383 ms、−2.3%）。
  `CUDAFORTRAN_GEMM` の 1.16 倍、`CUDAFORTRAN_SPLIT` の 8.8 倍速い。
- **コードは 1 行も要らなかった。** p=63 の作業で入れた LGL 演算子の生成・
  `case default` フォールバック・CUTLASS の batch 上限検査が、そのまま p=127 を通した。
  ノブも 4 種類掃引して**採用すべき変更は無かった**。
- **予測 1（マシンバランス越え）は当たった。** 演算強度 **5.34 FLOP/B** >
  マシンバランス **5.06 FLOP/B**。5 点で初めてである。
- **予測 2（ピーク比 45% 前後）は当たった。** **46.5%**。同一 DOF 5 点の FP64 ピーク比は
  **13.0 → 15.0 → 28.7 → 46.5 → 65.8%** と単調である。
- **予測 3（x GEMM のバックエンドが変わりうる）は外れた。** cuBLAS と CUTLASS は
  p=127 で既に互角（差 0.3%）で、`Nq <= 64` の閾値は正しいままだった。
  p=63 で観測された CUTLASS x GEMM の弱さは `K=64` に固有のものである。
- **「GEMM 経路の転送量は Nq に依存しない」が 3 点目でも成り立った**（147.8 B/ノード）。
  `volume_flux_kernel` が 3 次数で 128.9 / 129.0 / 129.3 µs、実行命令数まで
  18,350,080 で同一というのが直接の証拠である。
- **融合カーネルを書く条件はさらに厳しくなった。** 融合の理想転送量は 40 B/ノード =
  671 MB/stage で、帯域だけなら 85 µs/stage が下限になる。しかし 1.324e10 FLOP を
  710 µs 未満で回すには FP64 ピークの **46.5% 超**が要る。手書き融合がこれまで出した
  ピーク比は p=7 で 13.0%、p=15 で 15.0% である。

## 10. 次の点

- **p=31 (Nq=32, `Ne=8³`) が唯一の未着手**である。`Nq*Ne = 262144` なので CUTLASS 経路は
  使えず（`p63_gap_study.md` §2.3）、`CUDAFORTRAN_GEMM` か新規の融合カーネルになる。
  Nq=32 では 1 要素の `q` が 256 KB で 227 KB/SM をわずかに超えるので、p=15 の
  「要素まるごとを shared に置く」形は使えずタイル化が要る（`p15_gap_study.md` §9）。
  **融合が勝つ p≤15 と GEMM が勝つ p≥63 の交差点がそこに挟まっている**ので、
  この 5 点からは外挿できない。
- p=127 の GEMM 経路に残っているのは「DRAM の屋根に張り付いた `volume_flux`（18.8%）」と
  「調整を受け付けない z epilogue（37.4%）」で、p=63 §11 で当たった 3 つの案
  （`volume_flux` を mainloop に畳む / `GemmZ` のタイル / `GemmY` のワープ形状）は
  次数を変えても結論が変わらないことが本作業で確認できた。

### p=127 に残っている手（棚卸し）

**GEMM 経路の中には、もう手が無い。** §8 で 5 種類のノブを掃引して採用ゼロ、
§7 で占有率がレジスタと shared に**同時に**張り付いていることが分かった以上、
CUTLASS の形をいじる方向は閉じている。残っているのは枠組みの外にある 3 つで、
いずれも本作業のスコープ（既存経路を p=127 に開いて測る）を超える。

1. **`volume_flux` を GEMM の mainloop に畳む —— 依然として不採用。**
   p=63 §11.1 が挙げた 3 つの理由のうち 1 つは p=127 で消える（あちらは
   「x を CUTLASS に戻す −68 µs を先に払う」必要があったが、p=127 の x は元から CUTLASS）。
   しかし残る 2 つは消えないどころか**悪化する**: 残存実装
   （`mma_multistage_operand_mul.h:314`）は global→shared を レジスタ経由に置き換えて
   `cp.async`（LDGSTS）を捨てるので、p=255 の 1.66 倍という損は次数に依存しない。
   加えて再利用の勘定が p=63 と逆になる: x GEMM の M タイルは p=63 では `M/64 = 1` で
   B タイルの再利用がそもそも無かったが、**p=127 は `M/64 = 2` で再利用が生まれている**。
   materialize した flux を 2 回読むのをやめて 2 回作り直すことになるので、
   p=63 より条件が悪い。
2. **RK 更新カーネルを tendency に畳む —— 効果は大きいが、抽出インタフェースを変える。**
   tendency の外側では `main_rk_update_stage_*` が 1 step あたり 225.3 µs
   （74.3 + 74.3 + 76.7）で、**Main の 9.4%** を占める。DRAM 71.6% で 1 回あたり
   0.50 GB、1 step で 1.5 GB（tendency 全体の 7.44 GB に対して 17%）。
   z epilogue が `dqdt` を書き、直後に RK 更新がそれを読み直しているので、
   畳めば 1 stage あたり 268 MB（`dqdt` の書きと読みの往復）が消える。
   ただしこれは `dqdt` を実体化しないということであり、
   **AGENTS.md の「配列ベースのインタフェースより特殊化した問題を解いてはいけない」に
   触れる**。やるなら別途スコープを切る話である。なお 3 次数で 74.4 / 74.3 / 74.2 µs と
   完全に次数非依存なので、p=127 固有の話ではない。
3. **タイル型の融合カーネル —— 条件は p=63 のときよりさらに厳しい。**
   融合の理想転送量 40 B/ノード = 671 MB/stage は帯域下限 85 µs/stage を与えるが、
   1.324e10 FLOP を 710 µs 未満で回すには FP64 ピークの **46.5% 超**が要る
   （p=63 の時点では 25.2% 超だった）。手書き融合の実績は p=7 で 13.0%、p=15 で 15.0%。
   GB200 では FP64 Tensor Core ピークが CUDA core ピークと同じなので、
   TC に書き換えても天井は上がらない。

**実運用として今日できること**は 1 つだけある: `UseCudaGraph = .true.` で
Main 2.3941 → **2.3383 ms/step（−2.3%）**。カーネルも順序もデータも変わらない。
