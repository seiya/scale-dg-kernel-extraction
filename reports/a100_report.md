（`ab99614`、その §4 の予測表は以降 1 行も変えていない）。本ファイルはその答え
合わせで、**予測 1 は外れ、予測 2 と 3 は当たった**。

## 1. まとめ

1. **予測 1 は外れた。** A100/GB200 比は 4.99（p=7）から **2.52（p=511）**まで
   落ち、予測した「4.13〜5.08 の狭い帯」を p=15 以降ずっと下回った。
2. **外れ方は `a100_prediction.md` §5 が名指しした反証条件そのもの**である:
   「4.13 を下回る → A100 が TC ピーク 19.5 TF を実際に使えている」。
   **実際に使えていた。**
3. **A100 は FP64 CUDA core ピークを超える。** mma を出す経路は高次で
   **9.7 TF を超え**（p=511 `FUSED_TC` で **132.7%**、p=575 `GEMM_FUSED` で
   **129.1%**）、TC 屋根 19.5 TF に対して 52〜66% に達する。CUDA core 経路
   （`FUSED` / `FUSED_DFMA`）は**一度も超えない**（最大 55.4%）。
4. **モデルの欠陥は 1 つのパラメータだった。** 演算の屋根を mma 経路だけ
   9.7 → 19.5 TF に取り替えると、誤差は **−0.2〜−43.1%（幅 43 ポイント）から
   +1.5〜+13.2%（幅 12 ポイント）**に縮み、符号も揃う（§3）。
5. **予測 2 は当たった。** `FUSED_TC ÷ FUSED` は 6 次数とも 1 未満
   （0.993〜0.523）。H100 の p=7 / p=63 の逆転は**起きなかった**。
6. **`h100_report.md` §8.7.1 は機種条件付きの主張に格下げが要る**（§4）。
   「mma が買うのは命令数であって FLOP/s ではない」は GB200（2 つの屋根が同じ
   なので買いようがない）と H100（2 倍はあるが帯域で現金化できない）で測った
   結論で、**A100 では mma が FLOP/s を買っている**。
7. **順位が 1 次数動いた。** p=511 の最速は GB200 では `GEMM_FUSED` だが、
   A100 では **`FUSED_TC`**（96.71 対 102.98、6.1% 速い）。
8. **予測 3 は当たった（§7）。** A100 の cuBLAS も
   `cutlass_80_tensorop_d884gemm_*` を出す。**p=63 では 3 つの volume GEMM
   すべてでスレッドブロックタイルが我々の CUTLASS と一致する。**
   `h100_report.md` §8.7.2 の結論は Blackwell 固有ではなく、**ライブラリ軸は
   3 台中 2 台で縮退している**。

買わない**という §8.7.1 の描像がそのまま出ている。

### 4.3 `h100_report.md` §8.7.1 への注記

§8.7.1 の結論は「**mma が買うのは命令数であって FLOP/s ではない**」だった。
これは 2 台で測ったもので、その 2 台は:

- **GB200**: TC 屋根 = CC 屋根なので、mma は原理的に FLOP/s を買えない。
- **H100**: 2 倍はあるが TC が HBM の 86〜89% に張り付いて現金化できない
  （TC 飽和に 27.9 F/B が要る）。

**A100 は 3 つ目の場合であり、そこでは mma が FLOP/s を買う。** TC 飽和に要る
強度が 12.5 F/B と H100 の半分以下なので現金化でき、実際に CUDA core 屋根を
32.7% 超えた（p=511 `FUSED_TC`）。**§8.7.1 は「命令数の取引である」という機構の
記述としては正しいが、「FLOP/s は買わない」の部分は 2 台の事情の帰結であって
一般則ではない。** §8.7.1 は測定の記録として残し、本ファイルを参照する注記を
足す。

## 5. `a100_prediction.md` §5 の反証条件との対応

| §5 が予め書いた外れ方 | 起きたか | 実際 |
|---|---|---|
| 比が 5.08 を超える | いいえ | 最大 4.99（p=7） |
| **比が 4.13 を下回る → TC ピークを使えている、§8.7.1 への反例** | **はい** | **p=15 以降ずっと。p=511 で 2.52。§3.2 と §4.3 のとおり** |
| 低次だけ大きく外れる → launch とホストの寄与 | いいえ | 低次ほど当たっている（p=7 で −0.2%） |
| 高次だけ大きく外れる → 40 GiB の作業集合 | 部分的 | 外れは高次で大きいが、原因は容量ではなく屋根（§3.3 で説明が付く） |
| `FUSED_DFMA` だけ外れる | いいえ | 他と同じ傾向 |

**予測を先に書いておいたことが機能した。** 外れ方が事前に列挙した 5 通りの
どれかに落ち、そこから機構が一意に決まった。

## 6. 残っていること

- **p=127 の PDL の税は §8 で測った**（`FUSED_TC` +3.20%、`FUSED_DFMA` +3.43%）。
- **修正モデルの残差は §9 で切り分け、§10 と §11 で追い切った。** GB200 の CC 経路は
  L1 律速だが **A100 は違い**（DRAM または FP64）、**§10.3 の機構は撤回**。
  結論は「**律速資源は (カーネル, 機種) の組の性質**であり、機種非依存の 2 係数
  モデルは原理的に成り立たない」（§11.3）。残る交絡は `ncu` の不均等な
  クロック固定（§11.4、GB200 0.53× / A100 0.77×）で、`--clock-control none`
  での取り直しが未実施。
- **p=511 の順位逆転**（`FUSED_TC` が `GEMM_FUSED` を 6.1% 抜く）は A100 固有で、
  TC 屋根が 2 倍あることの帰結と見られるが、**アブレーションで確かめていない。**
- **コンパイラは 3 台で揃っていない**（26.3 / 26.1 / **25.9**）。同一機械での
  感度（A100 で p=63 だけ `nvidia/23.3`）は未取得。

## 9. 修正モデルの残差はどこから来るか（3 台での解析、測定なし）

§3.3 の修正モデル（mma 経路の演算屋根を 19.5 TF にする）は A100 で
+1.5〜+13.2% の残差を残した。3 台そろったので、**2 台で当てはめて 3 台目を
予測する**のではなく、**3 台を同時に見て**残差の構造を調べた。以下は既存
測定の再解析であり、新しい測定ではない。

### 9.1 2 パラメータの加法モデルは 3 台には合わない

`t_m = a·(W_flop/peak_m) + b·(W_bytes/BW_m)` を 3 台で最小二乗当てはめすると
（演算屋根は経路が出す命令で選ぶ: mma 経路は TC、それ以外は CC）、
**44 組の残差 RMS は 18.0%** で、しかも符号が機種で揃う（GB200 が負に大きく、
A100 が小さく正）。一部の組では演算係数 `a` が負になり、**物理的に解釈できない
当てはめ**になる。

**2 方程式 2 未知数だった 2 台の当てはめは構造的に厳密**で、モデルの妥当性を
検証していなかった。3 台目が初めてそれを検証し、**落ちた**。

### 9.2 残差は経路の種類で分かれる

| 経路の種類 | GB200 残差 | A100 残差 |
|---|---:|---:|
| mma 経路（`FUSED_TC` / GEMM 3 種）、低次 | −0.4 〜 −6.6% | +0.1 〜 +1.2% |
| mma 経路、高次（p>=255） | −12.5 〜 −16.9% | +3.0 〜 +5.0% |
| **CUDA core 経路（`FUSED` / `FUSED_DFMA`）** | **−17.0 〜 −45.3%** | +0.5 〜 +5.0% |

**壊れているのは主に CUDA core 経路である。** mma 経路は低次で数 % に収まる。

### 9.3 CC 経路を無理に合わせると、H100 の「実効演算」が公称の半分になる

GB200 と A100 の 2 点で `a`, `b` を解き、H100 の実測時間から実効演算
スループットを逆算すると:

| 経路の種類 | H100 実効演算 | 公称 | 比 |
|---|---:|---:|---:|
| **CUDA core（11 組、p=7〜511）** | **13.9 〜 16.8 TF（中央 15.8）** | 33.5 TF | **42〜50%** |
| mma（ばらつき大、逆問題が悪条件） | 34 〜 2316 TF | 66.9 TF | 51%〜（発散） |

**CC 側の 15.8 TF は 11 組・7 次数で 42〜50% に収まっており、ばらつきが小さい。**
mma 側は分母がほぼ 0 になる組があって発散するので、**この逆算が意味を持つのは
CC 経路だけ**である。

これは「H100 の FP64 演算器が公称の半分」という意味ではない。**CC 経路の律速が
FP64 パイプではないので、FP64 屋根で当てはめると係数がそれを吸ってしまう**、と
読むべきである。`h100_report.md` §8.7.3 は `volume_deriv_kernel` について
まさにそれを見つけている——**DRAM を使わず L1 レイテンシ律速**で、占有率を
揃えるだけで 13〜20% 動いた。

### 9.4 次にやること

**モデルには第 3 項が要る。** 演算と DRAM のほかに、L1/shared スループット
（SM 数 × クロックに比例し、FP64 FLOP には比例しない）の項を置いて 3 台で
当てはめ直す。それには各機の L1/shared 実効帯域が要るので、
**`ncu` の Memory Workload Analysis（`--set full`、または
`l1tex__throughput`）を 3 台で取る**のが次の一手である。GB200 では
`AGENTS.md` の規則どおり Slurm 経由で、A100 では `pjsub` 経由で。

それまでは、**加法 2 項モデルは mma 経路の低次でのみ数 % の精度がある**、
という限定つきで使うのが正しい。

### 10.4 できなかったこと（ネガティブな結果）

**`ncu` の 2 指標から L1 の絶対ピーク（B/clk/SM）は逆算できなかった。**
`l1tex__t_bytes.sum / gpu__time_duration.sum` を
`l1tex__throughput.avg.pct_of_peak_sustained_elapsed` で割ってピークを求めると、
20 カーネルで **9.5〜54.3 B/clk/SM** とばらつき、定数にならない。
`l1tex__throughput` の百分率は複数の L1 サブパイプ（wavefronts / sectors /
data pipe）の最大値であって `t_bytes` を分母にした値ではないので、この割り算に
意味がない。**§10.3 の「SM × クロック」は依然として仮定である。**

**正しい検証は絶対値の逆算ではなく、同じカーネルが各機で自分の L1 屋根の
何割にいるかを比べることである。**（**実施した: §11。結果は否定。**） GB200 の CC カーネルは自機の L1 の
74.9〜94.3% にいる。**A100 でも同じ範囲に入れば、両機とも L1 の屋根に張り付いて
いることになり、時間比 = L1 屋根比というモデルが成り立つ。** これは
`jobs/wisteria_l1_roof_ncu.sh` を投げれば決まる（`share-short`、2.5 時間、
`-g` を埋めるだけ）。**§10.3 はそれまで暫定である。**

### 10.5 ついでに出たもの

- **p=15 `FUSED` は 254 レジスタで占有率 12.2%**、IPC 0.20。`h100_report.md`
  §8.7.3 がレジスタ割り当てを問題にしたのと同じ形が、CC 融合カーネルの
  最低次にも出ている。ただし L1 が 86% なので、占有率を上げても L1 が先に
  頭打ちになる可能性が高い。**未検証。**
- **`pdl_elembnd_flux_kernel` は DRAM 律速**（`dram%` 75.9、`l1%` 46.8、
  占有率 89%）。面流束のギャザーなので素直な結果である。

### 11.3 本当の結論: 律速資源はカーネルの性質ではない

§9 の問い（なぜ機種非依存の 2 係数が合わないのか）への答えはこれである。
**律速資源は (カーネル, 機種) の組の性質であって、カーネルの性質ではない。**
`tendency_y_p255_cc_kernel` は GB200 で L1 87%、A100 で FP64 65%。
`tendency_fused_p15_cc_kernel` は GB200 で L1 86%、A100 で DRAM 84%。
同じ SASS ではないにせよ同じソース・同じ形状のカーネルが、機械を替えると
別の屋根に当たる。

**したがって「機種非依存の係数 (a,b) と経路ごとに 1 つの屋根」というモデルは
原理的に成り立たない。** 当てはめの良し悪しの問題ではない。必要なのは、
各機の屋根をすべて持ち、カーネルごとの各階層のトラフィックから
`max`（または和）を取る形である。`ncu` は階層ごとのトラフィックを出せるので
測定は可能だが、**それはもはや 2 パラメータのモデルではない。**

### 11.4 交絡: `ncu` のクロック固定は 2 台で不均等

**この比較自体にバイアスがある。** 実測 SM クロック（`sm__cycles_elapsed`）は
GB200 **1.084 GHz**、A100 **1.078 GHz** とほぼ同じだが、**boost に対する比が
違う**:

| | boost | `ncu` 固定 | 比 |
|---|---:|---:|---:|
| GB200 | 2062 MHz | 1084 MHz | **0.53** |
| A100 | 1410 MHz | 1078 MHz | **0.77** |

SM 側の屋根（L1、FP64、SM スループット）はクロックに比例して下がるので
百分率はあまり動かないが、**DRAM のピークはクロックに依らない**。つまり
`ncu` 下では **DRAM の逼迫が過小に出て、その度合いは GB200 のほうが大きい**。

**§11.1 で「GB200 は L1 律速、A100 は DRAM 律速」と見えた差の一部は、
この不均等な固定の産物である可能性がある。** 本番クロックでは GB200 も
DRAM 寄りに動くはずである。`AGENTS.md` が「`ncu` はグローバルメモリ待ちを
安く見積もる」と書いているのは、まさにこの効果である。

**§11.1 の「一致は 16 本中 7 本」は上限ではなく下限としても読めない**——
バイアスの向きは分かるが大きさは測っていない。**これを分離するには
`ncu --clock-control none` で両機を取り直す**（実行ごとのばらつきと引き換えに
boost クロックの姿が見える）。それは未実施である。

### 11.5 いま言えること / 言えないこと

**言える:**
- 加法 2 項・機種非依存係数のモデルは 3 台では成り立たない（§9、RMS 18.0%）。
- CC 経路の実効演算比は GB200/A100 で **2.45（四分位 2.21〜2.65）**、公称の
  FP64 比 4.134 ではない。これは屋根の同定に依らない当てはめ量である。
- GB200 の CC カーネルは `ncu` 下で L1 が 74.9〜94.3% と支配的（§10.1）。
- A100 の CC カーネルは `ncu` 下で L1 40.3〜87.0% にとどまり、DRAM または
  FP64 が上に来る（§11.1）。

**言えない:**
- 「第 3 項は L1 である」（§10.3 の機構）。**取り下げ。**
- 本番クロックでどの資源が律速か。`ncu` の不均等な固定を外していない。
- 2 台で律速が違うことの、バイアスを除いた真の大きさ。
