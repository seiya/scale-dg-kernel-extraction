# GEMM 経路のライブラリ割り当てとエピローグ担い手（2026-09-02）

`CUDAFORTRAN_GEMM_FUSED` / `CUDAFORTRAN_GEMM_CUTE` の 2 つのノブを、
文書が固定していたのをやめて測り直した記録。**p=7 −15.2%、p=15 −9.1%、
p=31 −23.0%、p=63 −1.2%**（いずれも `GEMM_FUSED` の `CUDA device` µs/stage）。
p=7 / 15 / 31 は担い手が z から x に替わり、p=31 は 708.0 → 545.4 µs/stage。

対象は次の 2 つで、どちらも「性能で負けていたから採らなかった」のではなく
**`AGENTS.md` が測定を先回りして禁止していた**ものである。

1. **volume GEMM ごとのライブラリ割り当て。** 旧規則は「y または z を cuBLAS
   にするのは defect」「`Nq<=64` の x を cuBLAS にするのが唯一の例外」。
2. **融合エピローグの担い手。** 旧定義は「z の epilogue に融合すること」と、
   z を名指ししていた。

`AGENTS.md` の commit `cbc6cea` でどちらも測定事項になった。担い手が cuBLAS に
なれないこと（cuBLAS は epilogue を持てない）と、割り当てが `GEMM_CUTE` と
`GEMM_FUSED` で一致することだけが固定点である。

## 測定条件

- GB200 1 GPU（login node）、`make CUDA=1 GPUFLAGS=-gpu=cc100`、nvhpc/26.3。
- ツリーは `cbc6cea` + 本作業の差分。`UseCudaGraph = .false.`。
- 数値の基準は `CUDAFORTRAN_SPLIT`。ただし **p=255 に `SPLIT` は無い**ので
  （`AGENTS.md` の対応パス一覧）、そこは `CUDAFORTRAN_FUSED` を基準にした。
- namelist は `namelists/perf_p{7,15,31}_gemm_fused.conf`。`GEMM_CUTE` と p=63 は
  `DqdtKernel_Type` だけを差し替えたスクラッチ複製（`namelists/` には入れていない）。
  `NeX/NeY/NeZ`・`PolyOrder`・`dt`・`nstep` は一切変えていない。
- 数値: `SCALE_DG_VARYING_COEFF=1`（`u,v,w,Escale,normal_fn,Fscale` すべて点変化）、
  `Ne=2³`、`nstep=1`、owned `dqdt(:,1:Ne)` 全点を `CUDAFORTRAN_SPLIT` と比較。
- 時間: 凍結バイナリ 1 本 + env 切り替えで **12 対の交互 A/B**、中央値とレンジ。
  レンジが重なる場合は「差なし」と読む。profiler は使っていない（`ncu` / `nsys`
  は `sbatch` が要るうえ、機構はカーネル単体を落とすアブレーションで分離できた）。

### 機構: 汎用タイルの N 述語化

x GEMM は `M=Nq, N=(Np/Nq)*Ne, K=Nq` だが、**C が column-major なので
`cutlass::device::Gemm` は転置問題を解く**。したがって threadblock の M が長軸に、
**N が Nq に当たる**。汎用 `GemmX` タイルは 64×128 なので、N 128 列のうち
`(128−Nq)/128` が述語で捨てられていた。

x カーネル単体の代金（x を落とすアブレーション `SCALE_DG_XCUTLASS=3` の差分、
`GEMM_CUTE`、µs/stage）:

| 次数 | 述語で捨てる N の割合 | cuBLAS x | CUTLASS x | 差 |
|---|---:|---:|---:|---:|
| p=7 | 93.8% | 189.4 | 97.1 | **−48.7%** |
| p=15 | 87.5% | 102.0 | 56.7 | **−44.4%** |
| p=31 | 75.0% | 76.7 | 65.8 | −14.2% |
| p=63 | 50.0% | 89.4 | 87.5 | −2.1% |

符号と順序は述語化の読みどおりだが、**減衰は `1−Nq/128` より速く、Nq=16 と 32 の
間で崩れる**。cuBLAS x は N=Nq のタイルを与えた後は**どの次数でも勝たない**。
Nq≤64 に交叉は存在せず、Nq=64 で測定限界に消えるだけである。

つまり `Nq<=64` の cuBLAS-x 分岐は、**x に次数専用タイルを与えていなかったことの
症状**であって、cuBLAS がこの形状で構造的に強いという証拠ではなかった。

### 採用タイル

`XTile<TbM,TbN,WM,WN,TileK,Stages>`、mma 8×8×4。

| 次数 | タイル | 形 |
|---|---|---|
| Nq=8 | 9 | 64×16×16 / warp 16×16×16 / 3 stage |
| Nq=16 | 5 | 64×16×16 / warp 16×16×16 / 3 stage |
| Nq=32 | 7 | 32×32×16 / warp 16×16×16 / 3 stage |
| Nq=64 | 3 | 128×64×16 / warp 64×32×16 / 3 stage |

各次数 12 候補を掃引した。上位 3 形は互いに誤差内で、次数をまたいで一貫する
負け方が 3 つある: **`TileK=32` は全次数で負け**（+0.7 / +0.4 / +2.2%）、
**stage を深くすると負けるか無効**、**threadblock の N を Nq より広げると即負け**
（Nq=16 で得の 2/3 を返す、Nq=64 で +9.6%）。

ビルド不成立は p=7 の N=8 のみ（FP64 multistage の B iterator が
contiguous iteration 0 で static assert）。Nq≥16 では N=Nq が使えるので起きない。

y カーネル単体（`SCALE_DG_YCUBLAS=2` のアブレーション、p=7、`GEMM_CUTE`）:
**960.9 → 807.2 µs/stage（−16.0%）**。ステージの改善はまるごと y から来ており、
他カーネルへの副作用はない。

機構は x と同種だが別の軸である。CUTLASS の FP64 multistage は**最小 2 warp**を
要求するので（`cuda_cutlass_gemm_fused.cu` の該当注記）、Nq=8 の 8×8 出力に対して
使える最小タイルが 32×64 になり、**出力の 31/32 と K の半分**が捨てられる。
どちらのライブラリも屋根には遠く（807 µs で 333 GB/s = HBM の 4%、
333 GFLOP/s = 40.1 TFLOP/s の 0.8%）、小問題のオーバーヘッド差でしかない。

**これは「低次数ほど cuBLAS」という単調則ではない。** Nq=16 では cuBLAS y は
2.27 倍遅い。交叉は Nq=8 と 16 の間にあり、勝つのは Nq=8 だけである。
`p31_gap_study.md` §22 が p=31 で「調整後の CUTLASS y が cuBLAS y に勝つ」と
測ったのとも矛盾しない。**タイルが埋まるかどうかで符号が決まる。**

x を CUTLASS にした後も y の割り当ては反転しない（上表は新しい x の下での再測定）。

## 3. エピローグの担い手（Nq=32 では x、他は z）

`GEMM_FUSED` の必須要件は「3 本の volume GEMM のうち**最後のもの**が最終の体積
重み付けと面 lift/assembly を epilogue に融合すること」であって、それが z である
必要はない。3 本の deriv はどれも同じ線形インデックスの要素ごと読みなので、
どれでも最後に走れば担える。3 候補すべてを測った。

### 採用と却下

| 次数 | 採用担い手 | µs/stage | 却下した担い手 |
|---|---|---:|---|
| **p=7 (Nq=8)** | **x** | **1482.0** | z 1504.7、**y +179.8%** |
| **p=15 (Nq=16)** | **x** | **597.9** | z 613.2、y +24.8% |
| **p=31 (Nq=32)** | **x** | **545.4** | y +11.3%、z +28.5% |
| p=63 (Nq=64) | z | 564.3 | x +17.7%（天井、後述 §3 の item 2） |

**担い手の採否は epilogue の命令パッケージに依存する**（後述「16 B epilogue」）。
狭い epilogue の下では x 担い手は p=7 / p=15 で +4.0% の負けだったが、
16 B epilogue を入れると両方でひっくり返る。したがって下の「x +4.0%」等の
記述は**狭い epilogue の下でのみ正しい**。

`GEMM_CUTE` はどの次数でも時間・数値とも不変（ライブラリ割り当てと mainloop
タイルは両パス同一のまま、変わったのは `GEMM_FUSED` 側の epilogue だけ）。
`run_x_gemm_assembly` に `GemmXWide` と `GemmX` の `Mma` 型が同一であることの
`static_assert` を置いたので、**mainloop 共有の規約はコンパイル時に機械検査される**。

### p=31 の採用形

| 構成 | µs/stage | 対 | 対 |
|---|---:|---:|---|
| z 担い手（本作業前） | 702.6 | +18.9% | 0/12 |
| y 担い手 + `Escale_x` 前送り + cuBLAS z + z‖x | 609.5 | — | — |
| x 担い手、前送りなし | 608.1 | −0.16% | 11/12 |
| x 担い手 + `Escale_y`、直列 | 597.6 | −1.88% | 12/12 |
| **x 担い手 + `Escale_y` + cuBLAS z + y‖z** | **591.0** | **−3.03%** | **12/12** |
| x 担い手 + 両前送り + CUTLASS z | 667.6 | +9.6% | 0/12 |

`Main per step` 2097.6 → 2044.1 µs、`Step loop per stage` 697.8 → 679.7 µs。
スケジュールは面フラックスを volume flux より前に side stream へ（`p31_early_face`）、
y を `dg_side2_stream` で z と並行、join 後に x 担い手。

担い手カーネル単体（`SCALE_DG_CSKIP` の差分）は **x 215.8 対 y 223.9 µs**。
勝ちの主因は epilogue 本体である（担い手が解放する平 GEMM は y 側 39.4 µs の方が
x 側 21.8 µs より高いので、そちらは逆風）。

### 機構（1）: タイル適合は必要条件だが十分条件ではない

x は転置後の問題の N が厳密に Nq で、採用タイルの `TbN` が Nq=16/32/64 とぴったり
一致する（Nq=8 だけは N=8 が CUTLASS の static assert で作れないため 16 で半述語）。
z は Nq=32 で行の半分、y は Nq=16 で列の半分を捨てる。**それでも x は 3 次数で負ける。**

| | タイル | 問題 (m,n) | 無駄 |
|---|---|---|---|
| p=15 y | 16×32 | (16,16) | 列の半分が述語、CTA は z の 4 倍 |
| p=15 z | 16×64 | (256,16) | ぴったり |
| p=31 y | 32×32 | (32,32) | ぴったり |
| p=31 z | 64×32 | (1024,32) | 行の半分が述語 |
| p=7 y | 32×64 | (8,8) | **出力の 31/32 と K の半分**、レジスタ 255 でスピル |
| x（全次数） | `TbN`=Nq | (Nq²·Ne, Nq) | ぴったり（Nq=8 のみ半分） |

タイル適合で説明できるのは棄却の側だけである。採否を決めていた軸は他に 2 つあった。

**最も強い反例は `Nq>64` にある。** そこでは y 担い手のタイルが**完全に適合する**
（64×64 が 128² / 256² の batch に対して述語化ゼロ。Nq=32 で y に担い手を取らせた
のと同じ適合）のに、3 候補で**最下位**（p=127 +7.09%、p=255 +7.62%）。
適合は必要条件ですらなく、単に棄却の側をよく説明する指標である。

**担い手が残す平 GEMM の値段。** 担い手選択は「どのカーネルに epilogue を載せるか」
であると同時に「どのカーネルを平の GEMM として残すか」の選択でもある。p=15 で
x 担い手が負けた理由はこれで、x 担い手の epilogue 自体は z より**安い**
（174.6 対 184.8 µs）のに、残される平 z が 78.2 µs、平 x が 47.9 µs と 30 µs 高い。

**Nq=64 ではレジスタ。** x 担い手だけが唯一レジスタが効く担い手で、128×64 タイルで
254 regs・スピル 136/272 B。前送りでテンソルを減らすとスピルが 8 B まで落ち、
p=63 の x 担い手は +119.9% から +18.2% まで縮むが、それでも届かない。
**「レジスタは制約ではなかった」（本作業の前半の結論）は Nq≤32 の性質であって、
次数の一般則ではない。**

### 機構（2）: 面ロード 4 対 2 は担い手を決めない — 予測の反証

y 担い手は batch が `k + Nq*elem` で **k がタイル内で定数**なので、`lx`(j,k) が
行不変、`ly`(i,k) が列不変になり、要素ごとに残るのは `lz` の 2 ロードだけである。
z と x はそれぞれ `lz` / `lx` の 1 対だけが分離でき、要素ごと 4 ロード残る。
**この構造から「y が有利」と予測したが、それは誤りだった。**

p=31 は両者ともタイルにぴったり乗り、読む体積テンソル数も等しいという、
この軸だけを比べられる条件である。そこで **4 ロードの x（215.8 µs）が
2 ロードの y（223.9 µs）に勝つ**。面ロードの半減は担い手選択の決定項ではない。

（`p31_gap_study.md` §22 の y 担い手が epilogue 単体で z の 218.1 → 159.2 µs
（−27%）だったのは事実だが、その −27% は面ロード半減**だけ**ではなく、
z タイル 64×32 の行半述語の解消を含んでいた。両者を分離できていなかった。）

### 機構（3）: 行索引の整数除算 —— 採否がコード生成の一点で反転した

x 担い手の「行」はパック索引 `c = j + Nq*k + Nq²*elem` そのものなので、行反復ごとに
整数除算が 2 回要る。z（行 = k）や y（行 = j、k は batch 固定）にはこれが無い。
しかも x の行は長軸なので、この前計算は安い列側ではなく多い行側で払われる。

Nq が 2 冪であることを使ってシフト / マスクに置き換えた A/B（同一バイナリ、
`SCALE_DG_XFWD` bit 2 で除算版を強制）:

| 次数 | シフト版 | 除算版 | 差 | 対 |
|---|---:|---:|---:|---|
| p=15 | 638.6 | 659.0 | +3.19% | 0/10 |
| p=31 | 590.9 | 606.6 | +2.66% | 0/10 |

さらにこの書き換えは ptxas のレジスタ配分ごと変え（130 → 96 regs、Nq=64 の
スピル 104/208 → 64/128 B）、**ステージ全体では p=31 で 667.6 → 590.7 µs（−11.5%）、
p=63 で 908.8 → 673.8 µs（−25.8%）**を生んだ。命令として測れるのは 2.7〜3.2% で、
残りはレジスタ圧の緩和である。

**この修正が無ければ x 担い手は p=31 でも 9.7% 負けていた。** 担い手の採否が
アルゴリズムではなくコード生成の一点で反転した例として記録する。

### p=7（Nq=8）の y 担い手 — 測れた。+179.8%

「y は cuBLAS だから担い手になれない」は誤りで、y を CUTLASS に戻せば測定できる。
CUTLASS の static assert には当たらず、ビルドは通る。

| 構成 | µs/stage | 対現行 | 対 |
|---|---:|---:|---|
| z 担い手・cuBLAS y（現行） | **1505.5** | — | — |
| z 担い手・CUTLASS y（前提条件のみ） | 1658.0 | +10.13% | 0/12 |
| y 担い手 + `Escale_x` + z‖x | 3872.2 | +157.2% | 0/12 |
| y 担い手 | 4213.1 | +179.8% | 0/12 |

**分解**: 超過 2367 µs のうち前提条件（y を cuBLAS → CUTLASS）が 152.5 µs（6.4%）、
残り 2214 µs（93.6%）が担い手 epilogue。同じ mainloop の平 CUTLASS y が 956.0 µs
なのに対し担い手は 3354.4 µs で、**epilogue を付けるだけで 3.5 倍**になる。
レジスタは 255・スピル 16/20 B で、Nq=16/32 の y 担い手（134/128、スピル 0）とは
別の領域にいる。面ロード 4 → 2 の効果は完全に埋没している。

これはタイル適合の読みを**裏づける** 3 点目のデータである（p=15 で +250%、
p=7 でさらに一桁大きい）。

### 機構（4）: 16 B epilogue —— 担い手の採否を左右する命令パッケージ

`p7_gemm_fused.md` §13 が `Nq>64` から p=7 に開いた 3 つ（クランプ集約、16 B lift、
16 B epilogue）を、x 担い手の上で 8 通り全部測り直した。`p31_gap_study.md` §28 が
p=31 で +69.1% として棄却したのは z 担い手の 254 レジスタ・16.3 M スピルが理由で、
**その壁は z タイル 64×32 の性質だった**（現行 x 担い手は 32×32 で 96 regs・スピル 0）。

p=31、8 通り（12 対ずつ、**基準は pkg0 = 590.0**。下の差はすべて pkg0 比であって、
採用形 pkg4 を基準にすると別の値になる —— 後述の再測定を参照）:

| pkg | 内容 | µs/stage | 差 | 対 |
|---|---|---:|---:|---|
| 0 | なし | 590.0 | — | — |
| 1 | クランプ集約 | 598.2 | +1.39% | 0/12 |
| 2 | 16 B lift | 594.5 | +0.76% | 0/12 |
| 3 | 1+2 | 595.5 | +0.93% | 0/12 |

### pkg4 を基準にした再測定 —— 16 B lift は次数で符号を変えない

上の表は pkg0 基準なので、採用形の上で各成分がいくらかは別に測る必要がある。
占有ノード（Slurm job 77091）で pkg4 を基準に 12 対:

| pkg4 に足す | p=7 | p=15 | p=31 | p=63 |
|---|---:|---:|---:|---:|
| クランプ集約 | **−0.24%**（11/12） | −0.06%（8/12） | +0.05%（2/12） | **−0.12%**（11/12） |
| （後日 HEAD で再測定） | −0.15%（12/12） | −0.06%（10/12） | −0.02%（6/12） | **−0.30%**（11/12） |
| 16 B lift | +2.78%（0/12） | +3.24%（0/12） | +2.44%（0/12） | +2.09%（0/12） |
| 両方 | +4.57% | +5.68% | +4.89% | +0.31% |

**16 B lift は次数で符号を変えない。4 次数すべてで 2.1〜3.2% 負ける。**
`p7_gemm_fused.md` §13 の「p=7 では勝つ」は **z 担い手の下での測定**で、
担い手が x に移った時点で成立しなくなっていた。機構は意図どおり働いており
（global load request −27〜34%、命令 −10〜15%）、代金はレジスタ 124 → 154 で、
Nq≤32 では SM あたり 1 CTA を失い（理論占有率 25% → 18.75%）、Nq=64 では
z 担い手の 238 → 254 で占有率は 12.5% に張り付いたまま依存鎖が伸びて負ける
（`math_pipe_throttle` 0.56 → 0.90、`stall wait` 1.51 → 1.62）。
**1 つの符号に 2 つの異なる代金が対応している。**

**クランプ集約の振れ幅は ±0.25% であって ±1.4% ではない。** 上表の +1.39% は
pkg0 基準の値である。レジスタ 124 → 126 で達成占有率は不変（x 担い手の 3 次数で
24.1%）、命令 −4.7%（Nq≤32）/ −1.6%（Nq=64）、**global load request は完全に不変**。
代金は**レイテンシ被覆**で、消す `min()` 鎖が面 gather の発行と使用の間に立って
いたため `stall_long_scoreboard_per_issue_active` が全次数で上がる
（p=7 1.92 → 2.20、p=15 2.77 → 3.00、p=31 2.53 → 2.83、p=63 0.86 → 0.88）。

**どの次数でこの取引が引き合うかは閉じていない。** 勝つ 2 つ（p=7、p=63）は
baseline の long-scoreboard が最も低い（1.92、0.86 対 2.53、2.77）ので向きは
合うが、p=31（2.53）が負けて p=15（2.77）が引き分けなので単調ではない。
同一に動いて除外できたもの: レジスタ、達成占有率、命令数、global load request、
バンクコンフリクト。±0.25% では残りを ptxas のスケジューリングから分離できない。

**非加法性は次数ではなく担い手に従う。** 16 B lift の上にクランプを足すと
Nq≤32（x 担い手）では 1.8〜2.5% **悪化**し、Nq=64（z 担い手）では 1.8% **改善**する。

**`ncu` のクロック固定バイアスの教科書的な例が 1 つ増えた。** クランプ集約を
`ncu` は −1.4 / −0.7 / +0.15 / +0.7% と採点するが、実時間は
−0.24 / −0.06 / +0.05 / −0.12%。命令削減を過大評価し、増えた global 待ちを
過小評価し、**p=63 では符号を間違える**。採否は実時間のみで決めた。

### 16 B epilogue は `Escale` 前送りの符号を反転させる

p=31 で `Escale_y` の y への前送りは、狭い epilogue では勝ち、**16 B epilogue の下では
負ける**（`xfwd=0` が `xfwd=1` に −0.32%、12/12）。アブレーションで内訳が取れる:
前送りは y GEMM に 10.3 µs 払い、担い手から 8.5 µs 取り返す。狭い epilogue では
同じ体積テンソル 1 本が担い手に 27.6 µs かかっていたので 17.3 µs の勝ちだった。
**16 B epilogue は体積テンソル 1 本の限界費用を 3.2 倍安くし、それが取引を裏返す。**

したがって現行の p=31 採用形に `Escale_y` 前送りは入っていない。

### 他次数への波及 —— p=7 と p=15 で担い手が裏返る

- **p=15**: x 担い手・前送りなし・pkg4・y‖z で **597.9**（z 担い手 613.2 に −2.51%、12/12）。
  非加法性が強く、**両 `Escale` を前送りすると pkg4 は +8.58%**、前送りなしなら −2.56%。
  pkg0（16 B epilogue 無し）は +5.21% で、§3 冒頭に記録した x 担い手 +4.0% を再現する。

  355.9 → 278.8 µs（−21.7%）。126 regs、スピル 0。y は cuBLAS のまま（CUTLASS y は +9.22%）。
- **p=63**（担い手は z のまま）: 8 通り測り直して **zpkg5（16 B epilogue + クランプ、

  形に対する値で、zpkg4 に対しては −0.12%）。254 regs・スピル 8 B が

  記録したのは 16 B lift が同時に on だったときの値で、**off にすると符号が変わる**。
  2 つは相互作用しており、どちらも単独の判定ではない。

### item 2: p=63 の x 担い手の天井 —— 却下

> **後日の再測定（HEAD）:** 基準の z 担い手は 570.3 ではなく **564.4** µs/stage、

### item 3: p=15 の平 z タイル —— 動かせるものは無い

`GemmZ` は Nq=16 で 16×64 / warp 16×32 / K=16 / 3 stage。転置後の問題が (16, 256) で
`TbM` が既に Nq、`TbN` が長軸を切る形になっており、x の勝ち形の鏡像で**もともと正しい**。
12 候補を掃引して、名目上でも勝つのは `ztile4`（warp 16×16）の −0.01% / −0.05% だけで
**レンジ完全重複＝差なし**。負け方は x の掃引と同じ 3 方向（`TileK=32` +7.72%、
4 stage +1.23%、5 stage +3.05%、`TbM` を Nq より広げると +4.02%）。

なお平 z の値段は新スケジュールでは **54.8 µs**（z 担い手の直列スケジュールでの
78.2 µs ではない）。cuBLAS z は x 担い手の下で +3.12%（z 担い手の下では +5.4%）で却下。
この項目の前提（平 z を安くすれば担い手が裏返る）は、担い手が別の理由で
裏返ったため消滅した。

### item 4: p=15 の y タイル 16×16 —— 構築不能

3 つの static assert に当たる:

- `default_mma_core_sm80.h:481` — `WarpCount::kCount > 1, "This specialization requires at least two warps."`
- `regular_tile_access_iterator_tensor_op_sm80.h:90` と `:454` — `ThreadMap::kThreads / 32 > 1`

さらに **16×16 を 2 warp に分割する方法も無い**: warp `8×16` は
`mma_tensor_op_tile_iterator_sm80.h:854` の `"Divisibility."`、warp `16×8` は同 `:99`。
この CUTLASS では FP64 TensorOp の 16×16 タイルは warp 分割によらず到達不能。

## 6. 未解決だったもの —— すべて解けた

`SCALE_DG_CSKIP` を `GEMM_CUTE` の `separable_lift_assembly_kernel` にも効くよう
拡張して、両パスを同じアブレーションで値付けした（µs/stage）:

| | p=7 | p=15 | p=31 |
|---|---:|---:|---:|
| 担い手カーネル（FUSED − CSKIP） | **279.5** | 176.2 | 184.3 |
| `separable_lift_assembly`（CUTE − CSKIP） | 168.5 | 166.3 | 159.8 |
| 平 x GEMM | 97.4 | 56.4 | 65.5 |
| 分離した場合の合計 | 265.9 | 222.7 | 225.3 |
| **融合の得** | **−13.6** | +46.5 | +41.0 |
| スケジュール差 | −10.7 | −10.9 | −16.3 |
| 予測 FUSED − CUTE | **+2.9** | −57.4 | −57.3 |
| 実測 FUSED − CUTE | **+2.9** | −57.4 | −57.3 |

**恒等式は全次数で 0.1 µs まで閉じる。** 担い手の中の epilogue は
**p=7 で 182.1 µs、p=15 で 119.8、p=31 で 118.8** — 同じ 16.78 M 出力点に対して
Nq=8 だけ 52% 高い。融合が節約する DRAM も見積もりを実測で置き換えた:
分離 1254.6 MB 対 融合 1031 MB で **223.6 MB**（見積もりの 268.4 MB ではない。
`deriv_x` の書き出しの一部は吸収される）、価値は **46.5 µs**（見積もり 34 µs ではない）。

**原因は `TbN`=16 の半述語化で、Nq=8 だけに起きる。** N=8 は CUTLASS の FP64
multistage B iterator が contiguous iteration 0 で static assert するので構築できず、
**Nq=8 は担い手タイルの N が問題の N の 2 倍になる唯一の次数**である（他は Nq に
厳密一致）。`ncu`（job 77076、2 次数を 1 ジョブ）で、p=7 と p=15 は**同一タイル**
（64×16 / warp 16×16 / K=16 / 3 stage / 128 スレッド）なのに:

| | Nq=8 | Nq=16 | 比 |
|---|---:|---:|---:|
| CTA 数 | 32,768 | 16,384 | **2.00** |
| 実行命令 | 169.3 M | 88.9 M | **1.90** |
| DRAM バイト | 1031 MB | 981 MB | 1.05 |
| l1tex セクタ | 55.0 M | 54.0 M | 1.02 |
| レジスタ / 達成占有率 | 126 / 24.10% | 124 / 24.05% | 1.00 |
| `thread_inst/inst` | 32.0 | 32.0 | 1.00 |

メモリ仕事は同じで命令が 2 倍。`thread_inst/inst = 32` は**レーン述語化が
起きていない**ことを意味する — 各 CTA は 64×16 タイルを丸ごと計算して lift し、
`OutputTileIterator` の境界マスクが store 時に死んだ半分を捨てるだけである。
差分は epilogue の **+62.3 µs** で、融合が節約する 46.5 µs の 1.34 倍。

除外した仮説: 担い手の占有率（次数によらず 24%。`separable_lift_assembly` は
30 regs・**91%** だがこれも全次数同じで、p=7 だけの説明にならない）、面 gather の
L2 挙動（l1tex 55.0 対 54.0 M、lts 50.6 対 48.8 M セクタで差なし）、y‖z の重ねに
よる歪み（スケジュール差は −10.7 µs で**融合に有利な側**。担い手は join の後に
単独で走り、ステージの 18.9% を占める＝律速経路上にある）。

**対処は無い。** 死んだスレッドの早期脱出は実装・ビット一致検証・測定して
**却下**（命令が 170.5 → 171.0 M と増え、占有ノード 12 対で 3/12、レンジ重複）。
死んだ列は同じ warp のレーンなので、ガードは分岐ではなく SASS の述語になり
発行スロットを節約しない。担い手専用の狭いタイルは `GEMM_CUTE` との共有義務が
あり、`run_x_gemm_assembly` の `static_assert` が機械検査している。
**Nq=8 の構造的限界として記録する。**

### 解けた: `Nq>64` の担い手 —— z が守った

12 対交互、占有ノード（Slurm job 77137）、`CUDA device` µs/stage、全行レンジ非重複:

| 担い手 | p=127 (Nq=128) | p=255 (Nq=256) |
|---|---|---|
| **z（採用）** | **639.6** | **943.0** |
| x（tile 18、`Escale_y` 前送り、pkg5） | 680.7（**+6.43%**、0/12） | 977.1（**+3.63%**、0/12） |
| y（`Escale_x` 前送り） | 685.2（+7.09%、0/12） | 1014.4（+7.62%、0/12） |

**x は「担い手として」負けた。「未調整だから」ではない。** 共有 64×128 タイルの
初手は +59% だったが、両パス 20 タイルの掃引で **+6.4%** まで詰まった。**タイルが
52 ポイント、残る 6 が担い手そのもの**である。機構は epilogue フラグメントの大きさ
（`TbM*TbN/threads`）で、x 担い手はこれを 5 本持つ（accumulator、Dy、Dz、Ex、lift）。
64×128 / 128 スレッドでは 1 本 64 double ＝ **255 regs・スピル 304 B**。勝ち形は
32 double の tile 18（64×64 / warp 32×32 / 4 stage）と tile 5（同 3 stage）で
**230 regs・スピル 0** —— z 担い手の 64×32 タイルと同じフラグメント幅である。
**同占有率（2 CTA/SM、理論 12.5%）・両者スピル 0** の条件でも担い手カーネルは
**231.4 対 191.6 µs**（p=127）、**318.0 対 287.6**（p=255）。レジスタを減らした
tile 12（64×32、148 regs、3 CTA/SM）は**むしろ遅い**ので、レジスタ数は軸ではない。

**掃引したタイルは共有相手にタダではない。** 汎用 64×128（tile 0）が両次数とも
`GEMM_CUTE` 上で最速で、担い手の勝ち形は CUTE 上では tile 5 +1.16%/+0.74%、
tile 18 +1.23%/+1.35% の負けである。

**x が構造的に持てないもの。** `deriv_x` を y に畳む（`Nq>64` の融合パッケージの
本体、p=127 で z カーネルの 15.7 µs）には x が y より前に走る必要があり、担い手は
最後なので**原理的に不可能**。x 担い手の epilogue は体積テンソルを 3 本読み、
z 担い手は 2 本で済む。`Escale_y` 前送りは x 担い手でも生きる（−0.60% / −0.65%）が、
`Escale_z` は引き合わない（+0.75% / −0.34%）。

アブレーションの内訳は両次数とも 0.0 µs まで閉じる（p=127: 担い手 +39.8、
残り +1.1、予測 +40.9 対 実測 +40.85。p=255: +30.4 / +3.4、予測 +33.8 対 実測 +33.79）。

**`p127_gap_study.md` §18–20 と `p255_gap_study.md` §10・§15–22 の長い z-epilogue
最適化は、これで追認された。** 担い手を替えてもあれには勝てない。

### 副産物: `GEMM_CUTE` の x にあった食い違いを 1 つ消した

`Nq=128/256` では `GEMM_FUSED` の x が `run_gemm_nn_scaled_repad`（accumulator の
staging pad 付き）を通るのに、`GEMM_CUTE` の x はそれを通っていなかった。mainloop
タイルは同一（64×128）なので規約違反ではないが、意図しない差である。`GEMM_CUTE` を
同じ tiled launcher（tile 0）に通して揃えると **−0.25%（p=127）/ −0.23%（p=255）**、
12/12、レンジ非重複、3 台目のノードで再確認（job 77163）。

### 行索引のシフト化は次数とともに**減衰**する —— 予測の反証

§6 で「x の行索引の整数除算は次数が上がるほど行が長くなるので効き方が変わる」と
書き、暗に**大きくなる**と見ていた。逆だった: `Nq<=64` の 2.7〜3.2% に対し、
`Nq>64` では **0.8〜1.3%** しかない。

### 解けた: クランプ集約の符号 —— 水準ではなく増分の比で決まる

測定した 6 つのカーネルすべてで、次の恒等式が **0.4 ポイント以内**で成立する:

```
duration = K · instructions · (発行命令あたりの warp レイテンシ) / (スケジューラあたり常駐 warp)
```

したがってクランプ集約は、**消す命令が失うレイテンシ被覆を上回るときに勝つ**。
HEAD で pkg4 → pkg5 を測り直した（`*` は役割外アブレーション、env のみ、dispatch 外）:

| 担い手 | 基準 issue% | Δ命令 | Δレイテンシ | Δカーネル（ncu） | Δステージ（実時間） | 対 |
|---|---:|---:|---:|---:|---:|---|
| x Nq=8 | 61.3 | −4.72 | +3.26 | −1.57 | **−0.15%** | 12/12 |
| x Nq=16 | 56.7 | −4.72 | +4.15 | −1.12 | −0.06% | 10/12 |
| x Nq=32 | 54.0 | −4.67 | +4.29 | +0.26 | −0.02% | 6/12 |
| z Nq=64 | 39.8 | −1.59 | +1.64 | −0.14 | **−0.30%** | 11/12 |
| z Nq=16 `*` | 40.8 | −1.35 | +9.93 | +7.27 | +2.70% | 0/12 |
| x Nq=64 `*` | 18.4 | −14.66 | +1.82 | −12.97 | −5.70% | 12/12 |

- **予測は立てた範囲で当たった。** p=7 の担い手は 3 つの x 担い手の中で最も
  発行律速（issue-active 61.3 > 56.7 > 54.0）で、命令削減を最もよく取り込む。
  x 担い手族の中では Δ命令が −4.7% で一定なので、順序はレイテンシ項だけで決まり、
  それは単調である（3.26 < 4.15 < 4.29）。
- **前回の試みが失敗した理由も分かった。** 見ていたのが `long_scoreboard` の
  **水準**だったからで、費用は水準ではなく**増分**である。
- **4 つの採用次数が 1 つの指標に並ばないのには理由がある。** Nq=64 だけ別の
  カーネル（z 担い手）で、そこではクランプが消す命令も失う被覆もどちらも
  1.6% しかなく、僅差で勝ち側に落ちる。
- **担い手と次数の両方が符号を変えるので、どちらも軸ではない。** 役割外の 2×2
  交差がそれを示す: z は Nq=16 で +2.70% 負けるが Nq=64 で勝ち、x は Nq=32 で
  引き分けだが Nq=64 で 5.70% 勝つ。
- 前回同様に除外: レジスタ（124 → 126）、達成占有率、global load request、
  バンクコンフリクト。
- **`ncu` のバイアスを再確認。** カーネル水準の Δ を担い手のステージ占有率で
  薄めると大きい 2 つはよく当たる（p=63 x −4.7 対 実測 −5.70、p=15 z +2.1 対
  +2.70）が、**p=63 の z では符号を間違える**（+0.38 対 実時間 −0.30%）。

### 解けた: p=63 の x 担い手に `Ey*Dy` を畳む —— 却下、ただし律速が変わった

`GemmBatchedScaleAdd` を `GemmZScale`（平の z と同一 mainloop、`static_assert` 済み）
に載せ、x epilogue に `kFold` を足した。`SCALE_DG_XFWD` bit 3、既定 off、Nq=64 のみ。

| p=63、12 対、占有ノード | µs/stage | 対 z 担い手 |
|---|---:|---:|
| z 担い手（採用） | **564.4** | — |
| 畳み込みなしの最良 x 担い手（LB2） | 670.5 | +18.80% |
| **畳み込みありの最良（クランプ + LB2）** | **664.1** | **+17.66%** |

**106.1 µs の差のうち 6.4 µs（6%）しか閉じない。** アブレーションは 0.0 µs まで
閉じる（担い手から −27.9 µs 出て、z GEMM に +11.2 µs 払う）。

**しかし律速は変わった。** 意図どおりに働いていて、なお負ける:
担い手の DRAM は 667 → **527 MB**（z 担い手の 526 と同じ）、命令は 60.2 → **51.5 M**
で **z 担い手の 58.9 M を下回る** —— それでもカーネルは 336.8 対 237.6 µs。
残差は全部レイテンシ被覆である（発行命令あたり warp レイテンシ **8.10 対 4.97**、
`long_scoreboard` **2.98 対 0.88**、どちらも 2 CTA/SM、達成占有率 11.96% 対 12.02%）。
レジスタ 254 → 252、スピルは両者 0。3 CTA には ≤170 が要るので、この方向で
占有率上限を買い戻すことはできない。

**`Nq=64` の x 担い手はもはや命令でもトラフィックでもなく、レイテンシ被覆の
問題である。** これが天井の正体で、契約内で動かす手は残っていない。

### 副産物: 実際の欠陥を 1 つ見つけて直した

`SCALE_DG_XPKG` bit 1（16 B lift）はホスト側が書く**面レイアウトも切り替える**が、
Nq=64 の launch-bounds インスタンス化は平のレイアウトを読んでいた。したがって
bit 1 と bit 3–4 を**同時に立てた組み合わせは静かに誤った値**を出していた
（相対 4.7e-13、丸め誤差ではない）。`dg_gemm_plan` で禁止した。公表済みの数値で
この組み合わせを使ったものは無い（本節の天井は pkg 9）ので、無効になる結果は無い。

## 8. 再現

```bash
module load nvhpc
make clean && make CUDA=1 GPUFLAGS=-gpu=cc100

# 数値検証
SCALE_DG_VARYING_COEFF=1 SCALE_DG_DUMP_DQDT=<out> \
  ./scale-dg_extraction <val_pN_{split,gemm_fused,gemm_cute}.conf>

# A/B（12 対交互、凍結バイナリ 1 本 + env 切り替え）
#   x:       SCALE_DG_XCUTLASS=0 (cuBLAS) / 1 (CUTLASS) / 2 (+Escale_x) / 3,4 (skip)
#            SCALE_DG_XTILE=<n>   -1 で測定済み既定

#   ablation: SCALE_DG_{Z,C,F,V}SKIP
```

env を 1 つも設定しなければ本文書の採用構成になる。
