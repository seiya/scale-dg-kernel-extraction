# GEMM 経路のライブラリ割り当てとエピローグ担い手（2026-09-02）

`CUDAFORTRAN_GEMM_FUSED` / `CUDAFORTRAN_GEMM_CUTE` の 2 つのノブを、
文書が固定していたのをやめて測り直した記録。**p=7 −15.2%、p=15 −9.1%、
p=31 −23.0%、p=63 −1.2%**（いずれも `GEMM_FUSED` の `CUDA device` µs/stage）。
p=7 / 15 / 31 は担い手が z から x に替わり、p=31 は 708.0 → 545.4 µs/stage。

対象は次の 2 つで、どちらも「性能で負けていたから採らなかった」のではなく
**`AGENTS.md` が測定を先回りして禁止していた**ものである。

1. **volume GEMM ごとのライブラリ割り当て。** 旧規則は「y または z を cuBLAS
   にするのは defect」「`Nq<=64` の x を cuBLAS にするのが唯一の例外」。
2. **融合エピローグの担い手。** 旧定義は「z の epilogue に融合すること」と、
   z を名指ししていた。

`AGENTS.md` の commit `cbc6cea` でどちらも測定事項になった。担い手が cuBLAS に
なれないこと（cuBLAS は epilogue を持てない）と、割り当てが `GEMM_CUTE` と
`GEMM_FUSED` で一致することだけが固定点である。

## 測定条件

- GB200 1 GPU（login node）、`make CUDA=1 GPUFLAGS=-gpu=cc100`、nvhpc/26.3。
- ツリーは `cbc6cea` + 本作業の差分。`UseCudaGraph = .false.`。
- 数値の基準は `CUDAFORTRAN_SPLIT`。ただし **p=255 に `SPLIT` は無い**ので
  （`AGENTS.md` の対応パス一覧）、そこは `CUDAFORTRAN_FUSED` を基準にした。
- namelist は `namelists/perf_p{7,15,31}_gemm_fused.conf`。`GEMM_CUTE` と p=63 は
  `DqdtKernel_Type` だけを差し替えたスクラッチ複製（`namelists/` には入れていない）。
  `NeX/NeY/NeZ`・`PolyOrder`・`dt`・`nstep` は一切変えていない。
- 数値: `SCALE_DG_VARYING_COEFF=1`（`u,v,w,Escale,normal_fn,Fscale` すべて点変化）、
  `Ne=2³`、`nstep=1`、owned `dqdt(:,1:Ne)` 全点を `CUDAFORTRAN_SPLIT` と比較。
- 時間: 凍結バイナリ 1 本 + env 切り替えで **12 対の交互 A/B**、中央値とレンジ。
  レンジが重なる場合は「差なし」と読む。profiler は使っていない（`ncu` / `nsys`
  は `sbatch` が要るうえ、機構はカーネル単体を落とすアブレーションで分離できた）。

### 機構: 汎用タイルの N 述語化

x GEMM は `M=Nq, N=(Np/Nq)*Ne, K=Nq` だが、**C が column-major なので
`cutlass::device::Gemm` は転置問題を解く**。したがって threadblock の M が長軸に、
**N が Nq に当たる**。汎用 `GemmX` タイルは 64×128 なので、N 128 列のうち
`(128−Nq)/128` が述語で捨てられていた。

x カーネル単体の代金（x を落とすアブレーション `SCALE_DG_XCUTLASS=3` の差分、
`GEMM_CUTE`、µs/stage）:

| 次数 | 述語で捨てる N の割合 | cuBLAS x | CUTLASS x | 差 |
|---|---:|---:|---:|---:|
| p=7 | 93.8% | 189.4 | 97.1 | **−48.7%** |
| p=15 | 87.5% | 102.0 | 56.7 | **−44.4%** |
| p=31 | 75.0% | 76.7 | 65.8 | −14.2% |
| p=63 | 50.0% | 89.4 | 87.5 | −2.1% |

符号と順序は述語化の読みどおりだが、**減衰は `1−Nq/128` より速く、Nq=16 と 32 の
間で崩れる**。cuBLAS x は N=Nq のタイルを与えた後は**どの次数でも勝たない**。
Nq≤64 に交叉は存在せず、Nq=64 で測定限界に消えるだけである。

つまり `Nq<=64` の cuBLAS-x 分岐は、**x に次数専用タイルを与えていなかったことの
症状**であって、cuBLAS がこの形状で構造的に強いという証拠ではなかった。

### 採用タイル

`XTile<TbM,TbN,WM,WN,TileK,Stages>`、mma 8×8×4。

| 次数 | タイル | 形 |
|---|---|---|
| Nq=8 | 9 | 64×16×16 / warp 16×16×16 / 3 stage |
| Nq=16 | 5 | 64×16×16 / warp 16×16×16 / 3 stage |
| Nq=32 | 7 | 32×32×16 / warp 16×16×16 / 3 stage |
| Nq=64 | 3 | 128×64×16 / warp 64×32×16 / 3 stage |

各次数 12 候補を掃引した。上位 3 形は互いに誤差内で、次数をまたいで一貫する
負け方が 3 つある: **`TileK=32` は全次数で負け**（+0.7 / +0.4 / +2.2%）、
**stage を深くすると負けるか無効**、**threadblock の N を Nq より広げると即負け**
（Nq=16 で得の 2/3 を返す、Nq=64 で +9.6%）。

ビルド不成立は p=7 の N=8 のみ（FP64 multistage の B iterator が
contiguous iteration 0 で static assert）。Nq≥16 では N=Nq が使えるので起きない。

y カーネル単体（`SCALE_DG_YCUBLAS=2` のアブレーション、p=7、`GEMM_CUTE`）:
**960.9 → 807.2 µs/stage（−16.0%）**。ステージの改善はまるごと y から来ており、
他カーネルへの副作用はない。

機構は x と同種だが別の軸である。CUTLASS の FP64 multistage は**最小 2 warp**を
要求するので（`cuda_cutlass_gemm_fused.cu` の該当注記）、Nq=8 の 8×8 出力に対して
使える最小タイルが 32×64 になり、**出力の 31/32 と K の半分**が捨てられる。
どちらのライブラリも屋根には遠く（807 µs で 333 GB/s = HBM の 4%、
333 GFLOP/s = 40.1 TFLOP/s の 0.8%）、小問題のオーバーヘッド差でしかない。

**これは「低次数ほど cuBLAS」という単調則ではない。** Nq=16 では cuBLAS y は
2.27 倍遅い。交叉は Nq=8 と 16 の間にあり、勝つのは Nq=8 だけである。
`p31_gap_study.md` §22 が p=31 で「調整後の CUTLASS y が cuBLAS y に勝つ」と
測ったのとも矛盾しない。**タイルが埋まるかどうかで符号が決まる。**

x を CUTLASS にした後も y の割り当ては反転しない（上表は新しい x の下での再測定）。

## 3. エピローグの担い手（Nq=32 では x、他は z）

`GEMM_FUSED` の必須要件は「3 本の volume GEMM のうち**最後のもの**が最終の体積
重み付けと面 lift/assembly を epilogue に融合すること」であって、それが z である
必要はない。3 本の deriv はどれも同じ線形インデックスの要素ごと読みなので、
どれでも最後に走れば担える。3 候補すべてを測った。

### 採用と却下

| 次数 | 採用担い手 | µs/stage | 却下した担い手 |
|---|---|---:|---|
| **p=7 (Nq=8)** | **x** | **1482.0** | z 1504.7、**y +179.8%** |
| **p=15 (Nq=16)** | **x** | **597.9** | z 613.2、y +24.8% |
| **p=31 (Nq=32)** | **x** | **545.4** | y +11.3%、z +28.5% |
| p=63 (Nq=64) | z | 564.3 | x +17.7%（天井、後述 §3 の item 2） |

**担い手の採否は epilogue の命令パッケージに依存する**（後述「16 B epilogue」）。
狭い epilogue の下では x 担い手は p=7 / p=15 で +4.0% の負けだったが、
16 B epilogue を入れると両方でひっくり返る。したがって下の「x +4.0%」等の
記述は**狭い epilogue の下でのみ正しい**。

`GEMM_CUTE` はどの次数でも時間・数値とも不変（ライブラリ割り当てと mainloop
タイルは両パス同一のまま、変わったのは `GEMM_FUSED` 側の epilogue だけ）。
`run_x_gemm_assembly` に `GemmXWide` と `GemmX` の `Mma` 型が同一であることの
`static_assert` を置いたので、**mainloop 共有の規約はコンパイル時に機械検査される**。

### p=31 の採用形

| 構成 | µs/stage | 対 | 対 |
|---|---:|---:|---|
| z 担い手（本作業前） | 702.6 | +18.9% | 0/12 |
| y 担い手 + `Escale_x` 前送り + cuBLAS z + z‖x | 609.5 | — | — |
| x 担い手、前送りなし | 608.1 | −0.16% | 11/12 |
| x 担い手 + `Escale_y`、直列 | 597.6 | −1.88% | 12/12 |
| **x 担い手 + `Escale_y` + cuBLAS z + y‖z** | **591.0** | **−3.03%** | **12/12** |
| x 担い手 + 両前送り + CUTLASS z | 667.6 | +9.6% | 0/12 |

`Main per step` 2097.6 → 2044.1 µs、`Step loop per stage` 697.8 → 679.7 µs。
スケジュールは面フラックスを volume flux より前に side stream へ（`p31_early_face`）、
y を `dg_side2_stream` で z と並行、join 後に x 担い手。

担い手カーネル単体（`SCALE_DG_CSKIP` の差分）は **x 215.8 対 y 223.9 µs**。
勝ちの主因は epilogue 本体である（担い手が解放する平 GEMM は y 側 39.4 µs の方が
x 側 21.8 µs より高いので、そちらは逆風）。

### 機構（1）: タイル適合は必要条件だが十分条件ではない

x は転置後の問題の N が厳密に Nq で、採用タイルの `TbN` が Nq=16/32/64 とぴったり
一致する（Nq=8 だけは N=8 が CUTLASS の static assert で作れないため 16 で半述語）。
z は Nq=32 で行の半分、y は Nq=16 で列の半分を捨てる。**それでも x は 3 次数で負ける。**

| | タイル | 問題 (m,n) | 無駄 |
|---|---|---|---|
| p=15 y | 16×32 | (16,16) | 列の半分が述語、CTA は z の 4 倍 |
| p=15 z | 16×64 | (256,16) | ぴったり |
| p=31 y | 32×32 | (32,32) | ぴったり |
| p=31 z | 64×32 | (1024,32) | 行の半分が述語 |
| p=7 y | 32×64 | (8,8) | **出力の 31/32 と K の半分**、レジスタ 255 でスピル |
| x（全次数） | `TbN`=Nq | (Nq²·Ne, Nq) | ぴったり（Nq=8 のみ半分） |

タイル適合で説明できるのは棄却の側だけである。採否を決めていた軸は他に 2 つあった。

**最も強い反例は `Nq>64` にある。** そこでは y 担い手のタイルが**完全に適合する**
（64×64 が 128² / 256² の batch に対して述語化ゼロ。Nq=32 で y に担い手を取らせた
のと同じ適合）のに、3 候補で**最下位**（p=127 +7.09%、p=255 +7.62%）。
適合は必要条件ですらなく、単に棄却の側をよく説明する指標である。

**担い手が残す平 GEMM の値段。** 担い手選択は「どのカーネルに epilogue を載せるか」
であると同時に「どのカーネルを平の GEMM として残すか」の選択でもある。p=15 で
x 担い手が負けた理由はこれで、x 担い手の epilogue 自体は z より**安い**
（174.6 対 184.8 µs）のに、残される平 z が 78.2 µs、平 x が 47.9 µs と 30 µs 高い。

**Nq=64 ではレジスタ。** x 担い手だけが唯一レジスタが効く担い手で、128×64 タイルで
254 regs・スピル 136/272 B。前送りでテンソルを減らすとスピルが 8 B まで落ち、
p=63 の x 担い手は +119.9% から +18.2% まで縮むが、それでも届かない。
**「レジスタは制約ではなかった」（本作業の前半の結論）は Nq≤32 の性質であって、
次数の一般則ではない。**

### 機構（2）: 面ロード 4 対 2 は担い手を決めない — 予測の反証

y 担い手は batch が `k + Nq*elem` で **k がタイル内で定数**なので、`lx`(j,k) が
行不変、`ly`(i,k) が列不変になり、要素ごとに残るのは `lz` の 2 ロードだけである。
z と x はそれぞれ `lz` / `lx` の 1 対だけが分離でき、要素ごと 4 ロード残る。
**この構造から「y が有利」と予測したが、それは誤りだった。**

p=31 は両者ともタイルにぴったり乗り、読む体積テンソル数も等しいという、
この軸だけを比べられる条件である。そこで **4 ロードの x（215.8 µs）が
2 ロードの y（223.9 µs）に勝つ**。面ロードの半減は担い手選択の決定項ではない。

（`p31_gap_study.md` §22 の y 担い手が epilogue 単体で z の 218.1 → 159.2 µs
（−27%）だったのは事実だが、その −27% は面ロード半減**だけ**ではなく、
z タイル 64×32 の行半述語の解消を含んでいた。両者を分離できていなかった。）

### 機構（3）: 行索引の整数除算 —— 採否がコード生成の一点で反転した

x 担い手の「行」はパック索引 `c = j + Nq*k + Nq²*elem` そのものなので、行反復ごとに
整数除算が 2 回要る。z（行 = k）や y（行 = j、k は batch 固定）にはこれが無い。
しかも x の行は長軸なので、この前計算は安い列側ではなく多い行側で払われる。

Nq が 2 冪であることを使ってシフト / マスクに置き換えた A/B（同一バイナリ、
`SCALE_DG_XFWD` bit 2 で除算版を強制）:

| 次数 | シフト版 | 除算版 | 差 | 対 |
|---|---:|---:|---:|---|
| p=15 | 638.6 | 659.0 | +3.19% | 0/10 |
| p=31 | 590.9 | 606.6 | +2.66% | 0/10 |

さらにこの書き換えは ptxas のレジスタ配分ごと変え（130 → 96 regs、Nq=64 の
スピル 104/208 → 64/128 B）、**ステージ全体では p=31 で 667.6 → 590.7 µs（−11.5%）、
p=63 で 908.8 → 673.8 µs（−25.8%）**を生んだ。命令として測れるのは 2.7〜3.2% で、
残りはレジスタ圧の緩和である。

**この修正が無ければ x 担い手は p=31 でも 9.7% 負けていた。** 担い手の採否が
アルゴリズムではなくコード生成の一点で反転した例として記録する。

### p=7（Nq=8）の y 担い手 — 測れた。+179.8%

「y は cuBLAS だから担い手になれない」は誤りで、y を CUTLASS に戻せば測定できる。
CUTLASS の static assert には当たらず、ビルドは通る。

| 構成 | µs/stage | 対現行 | 対 |
|---|---:|---:|---|
| z 担い手・cuBLAS y（現行） | **1505.5** | — | — |
| z 担い手・CUTLASS y（前提条件のみ） | 1658.0 | +10.13% | 0/12 |
| y 担い手 + `Escale_x` + z‖x | 3872.2 | +157.2% | 0/12 |
| y 担い手 | 4213.1 | +179.8% | 0/12 |

**分解**: 超過 2367 µs のうち前提条件（y を cuBLAS → CUTLASS）が 152.5 µs（6.4%）、
残り 2214 µs（93.6%）が担い手 epilogue。同じ mainloop の平 CUTLASS y が 956.0 µs
なのに対し担い手は 3354.4 µs で、**epilogue を付けるだけで 3.5 倍**になる。
レジスタは 255・スピル 16/20 B で、Nq=16/32 の y 担い手（134/128、スピル 0）とは
別の領域にいる。面ロード 4 → 2 の効果は完全に埋没している。

これはタイル適合の読みを**裏づける** 3 点目のデータである（p=15 で +250%、
p=7 でさらに一桁大きい）。

### 機構（4）: 16 B epilogue —— 担い手の採否を左右する命令パッケージ

`p7_gemm_fused.md` §13 が `Nq>64` から p=7 に開いた 3 つ（クランプ集約、16 B lift、
16 B epilogue）を、x 担い手の上で 8 通り全部測り直した。`p31_gap_study.md` §28 が
p=31 で +69.1% として棄却したのは z 担い手の 254 レジスタ・16.3 M スピルが理由で、
**その壁は z タイル 64×32 の性質だった**（現行 x 担い手は 32×32 で 96 regs・スピル 0）。

p=31、8 通り（12 対ずつ、**基準は pkg0 = 590.0**。下の差はすべて pkg0 比であって、
採用形 pkg4 を基準にすると別の値になる —— 後述の再測定を参照）:

| pkg | 内容 | µs/stage | 差 | 対 |
|---|---|---:|---:|---|
| 0 | なし | 590.0 | — | — |
| 1 | クランプ集約 | 598.2 | +1.39% | 0/12 |
| 2 | 16 B lift | 594.5 | +0.76% | 0/12 |
| 3 | 1+2 | 595.5 | +0.93% | 0/12 |

### pkg4 を基準にした再測定 —— 16 B lift は次数で符号を変えない

上の表は pkg0 基準なので、採用形の上で各成分がいくらかは別に測る必要がある。
占有ノード（Slurm job 77091）で pkg4 を基準に 12 対:

| pkg4 に足す | p=7 | p=15 | p=31 | p=63 |
|---|---:|---:|---:|---:|
| クランプ集約 | **−0.24%**（11/12） | −0.06%（8/12） | +0.05%（2/12） | **−0.12%**（11/12） |
| （後日 HEAD で再測定） | −0.15%（12/12） | −0.06%（10/12） | −0.02%（6/12） | **−0.30%**（11/12） |
| 16 B lift | +2.78%（0/12） | +3.24%（0/12） | +2.44%（0/12） | +2.09%（0/12） |
| 両方 | +4.57% | +5.68% | +4.89% | +0.31% |

**16 B lift は次数で符号を変えない。4 次数すべてで 2.1〜3.2% 負ける。**
`p7_gemm_fused.md` §13 の「p=7 では勝つ」は **z 担い手の下での測定**で、
担い手が x に移った時点で成立しなくなっていた。機構は意図どおり働いており
（global load request −27〜34%、命令 −10〜15%）、代金はレジスタ 124 → 154 で、
Nq≤32 では SM あたり 1 CTA を失い（理論占有率 25% → 18.75%）、Nq=64 では
z 担い手の 238 → 254 で占有率は 12.5% に張り付いたまま依存鎖が伸びて負ける
（`math_pipe_throttle` 0.56 → 0.90、`stall wait` 1.51 → 1.62）。
**1 つの符号に 2 つの異なる代金が対応している。**

**クランプ集約の振れ幅は ±0.25% であって ±1.4% ではない。** 上表の +1.39% は
pkg0 基準の値である。レジスタ 124 → 126 で達成占有率は不変（x 担い手の 3 次数で
24.1%）、命令 −4.7%（Nq≤32）/ −1.6%（Nq=64）、**global load request は完全に不変**。
代金は**レイテンシ被覆**で、消す `min()` 鎖が面 gather の発行と使用の間に立って
いたため `stall_long_scoreboard_per_issue_active` が全次数で上がる
（p=7 1.92 → 2.20、p=15 2.77 → 3.00、p=31 2.53 → 2.83、p=63 0.86 → 0.88）。

**どの次数でこの取引が引き合うかは閉じていない。** 勝つ 2 つ（p=7、p=63）は
baseline の long-scoreboard が最も低い（1.92、0.86 対 2.53、2.77）ので向きは
合うが、p=31（2.53）が負けて p=15（2.77）が引き分けなので単調ではない。
同一に動いて除外できたもの: レジスタ、達成占有率、命令数、global load request、
バンクコンフリクト。±0.25% では残りを ptxas のスケジューリングから分離できない。

**非加法性は次数ではなく担い手に従う。** 16 B lift の上にクランプを足すと
Nq≤32（x 担い手）では 1.8〜2.5% **悪化**し、Nq=64（z 担い手）では 1.8% **改善**する。

**`ncu` のクロック固定バイアスの教科書的な例が 1 つ増えた。** クランプ集約を
`ncu` は −1.4 / −0.7 / +0.15 / +0.7% と採点するが、実時間は
−0.24 / −0.06 / +0.05 / −0.12%。命令削減を過大評価し、増えた global 待ちを
過小評価し、**p=63 では符号を間違える**。採否は実時間のみで決めた。

### 16 B epilogue は `Escale` 前送りの符号を反転させる

p=31 で `Escale_y` の y への前送りは、狭い epilogue では勝ち、**16 B epilogue の下では
負ける**（`xfwd=0` が `xfwd=1` に −0.32%、12/12）。アブレーションで内訳が取れる:
前送りは y GEMM に 10.3 µs 払い、担い手から 8.5 µs 取り返す。狭い epilogue では
同じ体積テンソル 1 本が担い手に 27.6 µs かかっていたので 17.3 µs の勝ちだった。
**16 B epilogue は体積テンソル 1 本の限界費用を 3.2 倍安くし、それが取引を裏返す。**

したがって現行の p=31 採用形に `Escale_y` 前送りは入っていない。

### 他次数への波及 —— p=7 と p=15 で担い手が裏返る

- **p=15**: x 担い手・前送りなし・pkg4・y‖z で **597.9**（z 担い手 613.2 に −2.51%、12/12）。
  非加法性が強く、**両 `Escale` を前送りすると pkg4 は +8.58%**、前送りなしなら −2.56%。
  pkg0（16 B epilogue 無し）は +5.21% で、§3 冒頭に記録した x 担い手 +4.0% を再現する。

  355.9 → 278.8 µs（−21.7%）。126 regs、スピル 0。y は cuBLAS のまま（CUTLASS y は +9.22%）。
- **p=63**（担い手は z のまま）: 8 通り測り直して **zpkg5（16 B epilogue + クランプ、

  形に対する値で、zpkg4 に対しては −0.12%）。254 regs・スピル 8 B が

  記録したのは 16 B lift が同時に on だったときの値で、**off にすると符号が変わる**。
  2 つは相互作用しており、どちらも単独の判定ではない。

### item 2: p=63 の x 担い手の天井 —— 却下

> **後日の再測定（HEAD）:** 基準の z 担い手は 570.3 ではなく **564.4** µs/stage、

### item 3: p=15 の平 z タイル —— 動かせるものは無い

`GemmZ` は Nq=16 で 16×64 / warp 16×32 / K=16 / 3 stage。転置後の問題が (16, 256) で
`TbM` が既に Nq、`TbN` が長軸を切る形になっており、x の勝ち形の鏡像で**もともと正しい**。
12 候補を掃引して、名目上でも勝つのは `ztile4`（warp 16×16）の −0.01% / −0.05% だけで
**レンジ完全重複＝差なし**。負け方は x の掃引と同じ 3 方向（`TileK=32` +7.72%、
4 stage +1.23%、5 stage +3.05%、`TbM` を Nq より広げると +4.02%）。

なお平 z の値段は新スケジュールでは **54.8 µs**（z 担い手の直列スケジュールでの
78.2 µs ではない）。cuBLAS z は x 担い手の下で +3.12%（z 担い手の下では +5.4%）で却下。
この項目の前提（平 z を安くすれば担い手が裏返る）は、担い手が別の理由で
裏返ったため消滅した。

### item 4: p=15 の y タイル 16×16 —— 構築不能

3 つの static assert に当たる:

- `default_mma_core_sm80.h:481` — `WarpCount::kCount > 1, "This specialization requires at least two warps."`
- `regular_tile_access_iterator_tensor_op_sm80.h:90` と `:454` — `ThreadMap::kThreads / 32 > 1`

さらに **16×16 を 2 warp に分割する方法も無い**: warp `8×16` は
`mma_tensor_op_tile_iterator_sm80.h:854` の `"Divisibility."`、warp `16×8` は同 `:99`。
この CUTLASS では FP64 TensorOp の 16×16 タイルは warp 分割によらず到達不能。

## 6. 未解決だったもの —— すべて解けた

`SCALE_DG_CSKIP` を `GEMM_CUTE` の `separable_lift_assembly_kernel` にも効くよう
拡張して、両パスを同じアブレーションで値付けした（µs/stage）:

| | p=7 | p=15 | p=31 |
|---|---:|---:|---:|
| 担い手カーネル（FUSED − CSKIP） | **279.5** | 176.2 | 184.3 |
| `separable_lift_assembly`（CUTE − CSKIP） | 168.5 | 166.3 | 159.8 |
| 平 x GEMM | 97.4 | 56.4 | 65.5 |
| 分離した場合の合計 | 265.9 | 222.7 | 225.3 |
| **融合の得** | **−13.6** | +46.5 | +41.0 |
| スケジュール差 | −10.7 | −10.9 | −16.3 |
| 予測 FUSED − CUTE | **+2.9** | −57.4 | −57.3 |
| 実測 FUSED − CUTE | **+2.9** | −57.4 | −57.3 |

**恒等式は全次数で 0.1 µs まで閉じる。** 担い手の中の epilogue は
**p=7 で 182.1 µs、p=15 で 119.8、p=31 で 118.8** — 同じ 16.78 M 出力点に対して
Nq=8 だけ 52% 高い。融合が節約する DRAM も見積もりを実測で置き換えた:
分離 1254.6 MB 対 融合 1031 MB で **223.6 MB**（見積もりの 268.4 MB ではない。
`deriv_x` の書き出しの一部は吸収される）、価値は **46.5 µs**（見積もり 34 µs ではない）。

**原因は `TbN`=16 の半述語化で、Nq=8 だけに起きる。** N=8 は CUTLASS の FP64
multistage B iterator が contiguous iteration 0 で static assert するので構築できず、
**Nq=8 は担い手タイルの N が問題の N の 2 倍になる唯一の次数**である（他は Nq に
厳密一致）。`ncu`（job 77076、2 次数を 1 ジョブ）で、p=7 と p=15 は**同一タイル**
（64×16 / warp 16×16 / K=16 / 3 stage / 128 スレッド）なのに:

| | Nq=8 | Nq=16 | 比 |
|---|---:|---:|---:|
| CTA 数 | 32,768 | 16,384 | **2.00** |
| 実行命令 | 169.3 M | 88.9 M | **1.90** |
| DRAM バイト | 1031 MB | 981 MB | 1.05 |
| l1tex セクタ | 55.0 M | 54.0 M | 1.02 |
| レジスタ / 達成占有率 | 126 / 24.10% | 124 / 24.05% | 1.00 |
| `thread_inst/inst` | 32.0 | 32.0 | 1.00 |

メモリ仕事は同じで命令が 2 倍。`thread_inst/inst = 32` は**レーン述語化が
起きていない**ことを意味する — 各 CTA は 64×16 タイルを丸ごと計算して lift し、
`OutputTileIterator` の境界マスクが store 時に死んだ半分を捨てるだけである。
差分は epilogue の **+62.3 µs** で、融合が節約する 46.5 µs の 1.34 倍。

除外した仮説: 担い手の占有率（次数によらず 24%。`separable_lift_assembly` は
30 regs・**91%** だがこれも全次数同じで、p=7 だけの説明にならない）、面 gather の
L2 挙動（l1tex 55.0 対 54.0 M、lts 50.6 対 48.8 M セクタで差なし）、y‖z の重ねに
よる歪み（スケジュール差は −10.7 µs で**融合に有利な側**。担い手は join の後に
単独で走り、ステージの 18.9% を占める＝律速経路上にある）。

**対処は無い。** 死んだスレッドの早期脱出は実装・ビット一致検証・測定して
**却下**（命令が 170.5 → 171.0 M と増え、占有ノード 12 対で 3/12、レンジ重複）。
死んだ列は同じ warp のレーンなので、ガードは分岐ではなく SASS の述語になり
発行スロットを節約しない。担い手専用の狭いタイルは `GEMM_CUTE` との共有義務が
あり、`run_x_gemm_assembly` の `static_assert` が機械検査している。
**Nq=8 の構造的限界として記録する。**

### 解けた: `Nq>64` の担い手 —— z が守った

12 対交互、占有ノード（Slurm job 77137）、`CUDA device` µs/stage、全行レンジ非重複:

| 担い手 | p=127 (Nq=128) | p=255 (Nq=256) |
|---|---|---|
| **z（採用）** | **639.6** | **943.0** |
| x（tile 18、`Escale_y` 前送り、pkg5） | 680.7（**+6.43%**、0/12） | 977.1（**+3.63%**、0/12） |
| y（`Escale_x` 前送り） | 685.2（+7.09%、0/12） | 1014.4（+7.62%、0/12） |

**x は「担い手として」負けた。「未調整だから」ではない。** 共有 64×128 タイルの
初手は +59% だったが、両パス 20 タイルの掃引で **+6.4%** まで詰まった。**タイルが
52 ポイント、残る 6 が担い手そのもの**である。機構は epilogue フラグメントの大きさ
（`TbM*TbN/threads`）で、x 担い手はこれを 5 本持つ（accumulator、Dy、Dz、Ex、lift）。
64×128 / 128 スレッドでは 1 本 64 double ＝ **255 regs・スピル 304 B**。勝ち形は
32 double の tile 18（64×64 / warp 32×32 / 4 stage）と tile 5（同 3 stage）で
**230 regs・スピル 0** —— z 担い手の 64×32 タイルと同じフラグメント幅である。
**同占有率（2 CTA/SM、理論 12.5%）・両者スピル 0** の条件でも担い手カーネルは
**231.4 対 191.6 µs**（p=127）、**318.0 対 287.6**（p=255）。レジスタを減らした
tile 12（64×32、148 regs、3 CTA/SM）は**むしろ遅い**ので、レジスタ数は軸ではない。

**掃引したタイルは共有相手にタダではない。** 汎用 64×128（tile 0）が両次数とも
`GEMM_CUTE` 上で最速で、担い手の勝ち形は CUTE 上では tile 5 +1.16%/+0.74%、
tile 18 +1.23%/+1.35% の負けである。

**x が構造的に持てないもの。** `deriv_x` を y に畳む（`Nq>64` の融合パッケージの
本体、p=127 で z カーネルの 15.7 µs）には x が y より前に走る必要があり、担い手は
最後なので**原理的に不可能**。x 担い手の epilogue は体積テンソルを 3 本読み、
z 担い手は 2 本で済む。`Escale_y` 前送りは x 担い手でも生きる（−0.60% / −0.65%）が、
`Escale_z` は引き合わない（+0.75% / −0.34%）。

アブレーションの内訳は両次数とも 0.0 µs まで閉じる（p=127: 担い手 +39.8、
残り +1.1、予測 +40.9 対 実測 +40.85。p=255: +30.4 / +3.4、予測 +33.8 対 実測 +33.79）。

**`p127_gap_study.md` §18–20 と `p255_gap_study.md` §10・§15–22 の長い z-epilogue
最適化は、これで追認された。** 担い手を替えてもあれには勝てない。

### 副産物: `GEMM_CUTE` の x にあった食い違いを 1 つ消した

`Nq=128/256` では `GEMM_FUSED` の x が `run_gemm_nn_scaled_repad`（accumulator の
staging pad 付き）を通るのに、`GEMM_CUTE` の x はそれを通っていなかった。mainloop
タイルは同一（64×128）なので規約違反ではないが、意図しない差である。`GEMM_CUTE` を
同じ tiled launcher（tile 0）に通して揃えると **−0.25%（p=127）/ −0.23%（p=255）**、
12/12、レンジ非重複、3 台目のノードで再確認（job 77163）。

### 行索引のシフト化は次数とともに**減衰**する —— 予測の反証

§6 で「x の行索引の整数除算は次数が上がるほど行が長くなるので効き方が変わる」と
書き、暗に**大きくなる**と見ていた。逆だった: `Nq<=64` の 2.7〜3.2% に対し、
`Nq>64` では **0.8〜1.3%** しかない。

### 解けた: クランプ集約の符号 —— 水準ではなく増分の比で決まる

測定した 6 つのカーネルすべてで、次の恒等式が **0.4 ポイント以内**で成立する:

```
duration = K · instructions · (発行命令あたりの warp レイテンシ) / (スケジューラあたり常駐 warp)
```

したがってクランプ集約は、**消す命令が失うレイテンシ被覆を上回るときに勝つ**。
HEAD で pkg4 → pkg5 を測り直した（`*` は役割外アブレーション、env のみ、dispatch 外）:

| 担い手 | 基準 issue% | Δ命令 | Δレイテンシ | Δカーネル（ncu） | Δステージ（実時間） | 対 |
|---|---:|---:|---:|---:|---:|---|
| x Nq=8 | 61.3 | −4.72 | +3.26 | −1.57 | **−0.15%** | 12/12 |
| x Nq=16 | 56.7 | −4.72 | +4.15 | −1.12 | −0.06% | 10/12 |
| x Nq=32 | 54.0 | −4.67 | +4.29 | +0.26 | −0.02% | 6/12 |
| z Nq=64 | 39.8 | −1.59 | +1.64 | −0.14 | **−0.30%** | 11/12 |
| z Nq=16 `*` | 40.8 | −1.35 | +9.93 | +7.27 | +2.70% | 0/12 |
| x Nq=64 `*` | 18.4 | −14.66 | +1.82 | −12.97 | −5.70% | 12/12 |

- **予測は立てた範囲で当たった。** p=7 の担い手は 3 つの x 担い手の中で最も
  発行律速（issue-active 61.3 > 56.7 > 54.0）で、命令削減を最もよく取り込む。
  x 担い手族の中では Δ命令が −4.7% で一定なので、順序はレイテンシ項だけで決まり、
  それは単調である（3.26 < 4.15 < 4.29）。
- **前回の試みが失敗した理由も分かった。** 見ていたのが `long_scoreboard` の
  **水準**だったからで、費用は水準ではなく**増分**である。
- **4 つの採用次数が 1 つの指標に並ばないのには理由がある。** Nq=64 だけ別の
  カーネル（z 担い手）で、そこではクランプが消す命令も失う被覆もどちらも
  1.6% しかなく、僅差で勝ち側に落ちる。
- **担い手と次数の両方が符号を変えるので、どちらも軸ではない。** 役割外の 2×2
  交差がそれを示す: z は Nq=16 で +2.70% 負けるが Nq=64 で勝ち、x は Nq=32 で
  引き分けだが Nq=64 で 5.70% 勝つ。
- 前回同様に除外: レジスタ（124 → 126）、達成占有率、global load request、
  バンクコンフリクト。
- **`ncu` のバイアスを再確認。** カーネル水準の Δ を担い手のステージ占有率で
  薄めると大きい 2 つはよく当たる（p=63 x −4.7 対 実測 −5.70、p=15 z +2.1 対
  +2.70）が、**p=63 の z では符号を間違える**（+0.38 対 実時間 −0.30%）。

### 解けた: p=63 の x 担い手に `Ey*Dy` を畳む —— 却下、ただし律速が変わった

`GemmBatchedScaleAdd` を `GemmZScale`（平の z と同一 mainloop、`static_assert` 済み）
に載せ、x epilogue に `kFold` を足した。`SCALE_DG_XFWD` bit 3、既定 off、Nq=64 のみ。

| p=63、12 対、占有ノード | µs/stage | 対 z 担い手 |
|---|---:|---:|
| z 担い手（採用） | **564.4** | — |
| 畳み込みなしの最良 x 担い手（LB2） | 670.5 | +18.80% |
| **畳み込みありの最良（クランプ + LB2）** | **664.1** | **+17.66%** |

**106.1 µs の差のうち 6.4 µs（6%）しか閉じない。** アブレーションは 0.0 µs まで
閉じる（担い手から −27.9 µs 出て、z GEMM に +11.2 µs 払う）。

**しかし律速は変わった。** 意図どおりに働いていて、なお負ける:
担い手の DRAM は 667 → **527 MB**（z 担い手の 526 と同じ）、命令は 60.2 → **51.5 M**
で **z 担い手の 58.9 M を下回る** —— それでもカーネルは 336.8 対 237.6 µs。
残差は全部レイテンシ被覆である（発行命令あたり warp レイテンシ **8.10 対 4.97**、
`long_scoreboard` **2.98 対 0.88**、どちらも 2 CTA/SM、達成占有率 11.96% 対 12.02%）。
レジスタ 254 → 252、スピルは両者 0。3 CTA には ≤170 が要るので、この方向で
占有率上限を買い戻すことはできない。

**`Nq=64` の x 担い手はもはや命令でもトラフィックでもなく、レイテンシ被覆の
問題である。** これが天井の正体で、契約内で動かす手は残っていない。

### 副産物: 実際の欠陥を 1 つ見つけて直した

`SCALE_DG_XPKG` bit 1（16 B lift）はホスト側が書く**面レイアウトも切り替える**が、
Nq=64 の launch-bounds インスタンス化は平のレイアウトを読んでいた。したがって
bit 1 と bit 3–4 を**同時に立てた組み合わせは静かに誤った値**を出していた
（相対 4.7e-13、丸め誤差ではない）。`dg_gemm_plan` で禁止した。公表済みの数値で
この組み合わせを使ったものは無い（本節の天井は pkg 9）ので、無効になる結果は無い。

### 実装

`flux_all_kernel`（`mod_cuda_dg_kernels.cuf`）を新設した。スレッドを
`npoint + nface` 本並べ、前半が `volume_flux_kernel` の本体を、後半が
`elembnd_flux_kernel` の本体を**そのまま**実行する。式・丸め・出力レイアウト
（`pair_nq2` の face→(group,slot) 再配置を含む）は 1 文字も変えていない。

起動は**共有ヘルパ `launch_flux_all` 1 か所**からだけで、
`cuda_cal_dqdt_gemm_unfused`（`GEMM` / `OZAKI1` / `OZAKI2`）と
`cuda_cal_dqdt_gemm_cutlass`（`GEMM_CUTE` / `GEMM_FUSED`）の両ドライバが
そこを通る。`AGENTS.md` の「周辺カーネルの最適化は共有 launch ヘルパを通し、
GEMM 系 5 経路全部に同時に入れる」に文字どおり従っている
（`launch_volume_flux` と同じ扱い）。

ノブ `SCALE_DG_FLUXFUSE`:

| 値 | 意味 |
|---|---|
| 0 | 従来（2 本別カーネル）。2026-09-03 以前の全測定はこれ |
| **1（既定）** | **face flux が dg_stream 上で volume flux と直列になる場合にだけ融合する** |
| 2 | face flux が side stream に載っている場合も融合する（その重ねを捨てる） |

**モード 1 が「5 経路のどこで発火するか」は経路ごとの schedule が決めており、
規則そのものは 5 経路で 1 つである。** 具体的には
`GEMM` / `OZAKI1` / `OZAKI2` / `GEMM_CUTE` の Nq<64 で発火し、
`GEMM_FUSED` の Nq≤32（`p31_early_face` で face を side stream に出している）と
全経路の Nq≥64（`use_side`）では発火しない。**発火しない側は「別の規則」では
なく「同じ規則が偽になる」だけ**で、経路間の実装差ではない。

## 9.2 p≥511 への横展開 —— (b) 経路間差は**存在しなかった**（`static_assert` で機械検査化）

`TODO.md` §7 の 3 行目 (b)。**先に片付けよという指示どおり最初に見たが、
p≥511 には直すべき食い違いが無かった。** 理由は、同じ食い違いが
**2026-09-01 に既に別経路から直っていた**からである。

- `Nq=128/256` で見つかった食い違い（§6「副産物」）は「`GEMM_FUSED` の x は
  `run_gemm_nn_scaled_repad` を通るのに `GEMM_CUTE` の x は素の epilogue だった」。
- `Nq≥512` では x は**単発 GEMM ではなく batched GEMM**になっており

  `GEMM_CUTE` は `run_gemm_batched_nn` を通る。**この 2 本はどちらも
  `RepadEpilogue<…, 8>` を張った capped 版**である

```cpp

                  typename Set::GemmY::GemmKernel::Mma,
                  typename Set::GemmYScaleShallow::GemmKernel::Mma>::value,

```

を置いた。`run_x_gemm_assembly` の `GemmXWide`/`GemmX` の `static_assert`

## 9.4 採用: `GEMM` パスの volume GEMM 3 本を別ストリームに（全 7 次数で勝ち）

### 実装

`gemm_volume_xyz` に `gvol_par` を足した。ノブは `SCALE_DG_GVOLPAR`:

| 0 | 3 本とも `dg_stream`（2026-09-03 以前の全測定） |

### 9.7.3 原因 —— §9.5 の 2 つの数字は別のノブで測られていた

§9.5 の表は本文に書いてあるとおり **`SCALE_DG_GVOLPAR=0`（直列）** で採った。

**§9.5 の占有ノード値 12 561 は gp0 の 12 596 と 0.3% 以内、
login 値 14 327 は gp2 の 14 330 と 0.02% 以内。** 両方とも再現した。
`GEMM` 側が login と占有で一致して見えたのは、**native が gp0/gp2 で
0.27% しか動かないので、schedule が違うことを隠していた**からである。

**ノード仮説はクロスチェックで棄却できる。** 占有 GPU（job `78530` PART B、
node `c187`）で 4 通りを 3 ラウンド回すと:

|---|---:|---:|---:|---:|

| login | 13 337 | **12 596（0.945×）** | 13 300 | **14 330（1.077×）** |

**同じノードの中で両方の符号が出る。** 差の担い手はノードではなくノブである。

### 9.7.4 なぜ並列 schedule で emulation だけが 13.8% 遅くなるのか

`cuda_cublas_gemm.cu` は **cuBLAS ハンドルを 1 本 (`g_handle`) しか持たず、
FP64 emulation 用に 8 GiB の作業領域 (`g_workspace`) を 1 つだけ**確保して
`cublasSetWorkspace` で貼っている（cuBLAS が fixed-point emulation の最大所要と
文書化している量）。`gemm_volume_xyz` は 3 本の volume GEMM を
`dg_set_cuda_stream` で別ストリームに載せ替えるだけなので、
**並列にしても同じハンドルと同じ 8 GiB scratch を共有する**。
表の gp1 が gp2 と同じ 14 330 に張り付いていることが決め手で、
**2 本目が飛んだ瞬間に全額（+13.8%）が発生し、3 本目はもう何も足さない**。
これは「帯域が足りない」形ではなく「共有 scratch を 2 者で使えない」形である。
native DGEMM は emulation ほど作業領域を使わないので gp0/gp2 で 0.27% しか動かない。

**§9.4 が `OZAKI1` / `OZAKI2` にこのノブを与えなかったのと同じ理由が
`CublasEmulation` にも当てはまっていた。** §9.4 は Ozaki の launcher が
1 本のデバイス作業領域を共有することを理由に `par = 0` に落としているが、
**emulation も同じ性質を持つのに落としていなかった。**

### 9.7.5 副産物 —— これは性能問題ではなく**破壊バグ**だった

p=7 `Ne=2³`、`SCALE_DG_VARYING_COEFF=1`、owned `dqdt(:,1:Ne)` 全 4096 点を
`CUDAFORTRAN_SPLIT` と比較する（`SCALE_DG_DUMP_DQDT`）:

| schedule | 非有限点 | 対 `SPLIT` 最大絶対差 |
|---|---:|---:|
| `SCALE_DG_GVOLPAR=0` | 0 | 8.88e-15 |
| `SCALE_DG_GVOLPAR=1` | 0 | 8.88e-15 |
| **`SCALE_DG_GVOLPAR=2`（既定）** | **16 / 4096 が ±Inf** | **inf** |

3 回繰り返して 3 回とも同じ 16 点。**既定 schedule と
`CublasEmulation = .true.` の組み合わせは、2026-09-03 の §9.4 が既定を 2 に
した時点から owned `dqdt` を壊していた。** §9.5 の表は `SCALE_DG_GVOLPAR=0`
で採ったので、**§9.5 の数値そのものは汚染されていない**。

`mod_cuda_dg_kernels.cuf` に `gemm_emulation_on` を持たせ

**emulation はノブに依らず 12.6 ms/stage に落ち着く。** native gp2 13 300.0 に対して

## 9.8 未解明 2 の機構 —— §8 は DYNAMIC を、§9.5 は FIXED を測っている（2026-09-03）

### 9.8.1 §8 の測定条件を突き止める

- §8 は commit **`38952e4`** と書いているが、**そのコミットには p≥511 の
  Ozaki ゲートが無い**。ゲートを開けたのは次の commit
  **`dd3c4a7`「Allow Ozaki GEMM paths at p>=511 and record per-p measurements」**
  で、`git show --stat dd3c4a7` のとおり **§8 の本文を追加したのもこの commit**
  である。したがって §8 が測ったツリーは `38952e4` ではなく **`dd3c4a7`**。
  §8 の commit 表記は親を書いた誤りである（測定値の解釈は変わらない）。
- 入力・物差し・パラメータは §8 の記載どおり `Ne=1`、`nstep=20`、
  `WarmupStep=2`、`OzakiSliceCount=8`、`OzakiModuliCount=14`、login GPU。
  §8 の表は **1 step の device 合計**（同節の訂正注記のとおり）。

### 9.8.2 `dd3c4a7` から現行ツリーまでの Ozaki 差分は 2 件しかない

`git log dd3c4a7..44b02a6 -- 'cuda_ozaki*'` は 2 件:

| commit | 内容 | 速度への影響 |
|---|---|---|
| `a1cdb57` | Ozaki-I `scale_a` の作業領域を `Nq²×Ne` に right-size | メモリのみ。数値も演算も不変 |
| **`fd091fc`** | **FP64 emulation の既定を FIXED 55 bit に。「同じ制御が Ozaki-I の early-exit と Ozaki-II の追加 A pack も決める」** | **これが全部** |

`fd091fc` が Ozaki に入れたのは 2 つ:

- **Ozaki-I**: `decompose_a_tn` / `decompose_b_nn` の残差 early-exit
  (`scales_need_next_slice`) を **`if (!g_state.fixed && ...)` で囲った**。
  既定が FIXED になったので **early-exit が既定で無効**になり、
  常に `slice_count` 枚すべてを作る。`run_slice_pairs` はスライス対を回すので
  仕事は **枚数の 2 乗**で効く。既定の `kDefaultSlices` も 8 → 7 に変わった。
- **Ozaki-II**: A 側の追加パック（最大 4 スライス）を
  `const int max_a_slices = g_state.fixed ? 1 : kMaxASlices;` で **FIXED では 1 枚**に。
  既定の `kDefaultModuli` も 14 → 7 に変わった。

**つまり `fd091fc` は Ozaki-I を重く、Ozaki-II を軽くする。順位が逆になる向きが
これで説明できる。**

### 9.8.3 §8 を現行ツリーで再現した

`namelists/perf_p511_gemm.conf` の `DqdtKernel_Type` と Ozaki パラメータだけを
替えた複製（`jobs/perf_p511_gemm_ozaki{1,2}_{FIXED,ADP}.conf`、
`OzakiSliceCount = 8`、`OzakiModuliCount = 14`、`EmulationMantissaControl` で
FIXED / ADP を切り替え）を、**ツリー `44b02a6`、login GPU、`SCALE_DG_GVOLPAR=0`**
（§9.4 のとおり Ozaki は元々このノブを取らないが、native も直列に揃えた）で走らせる。
物差しは `CUDA device Ozaki-I/II GEMM` ÷54。

| 経路 | 制御 | µs/stage | native（gp0 13 336.6）比 | §8 の記録 |
|---|---|---:|---:|---:|
| `OZAKI1` | **ADP（= §8 の既定）** | **15 205** | **1.140×** | **1.14×** ✔ |
| `OZAKI1` | FIXED（= 現行既定） | 220 857 | 16.6× | — |
| `OZAKI2` | **ADP（= §8 の既定）** | **41 534** | **3.114×** | **3.1×** ✔ |
| `OZAKI2` | FIXED（= 現行既定） | 31 573 | 2.37× | — |

**§8 の 1.14× と 3.1× は、現行ツリーで ADP に戻すと 2 桁とも一致する。**
`OZAKI1` FIXED 220 857 と `OZAKI2` FIXED 31 573 は §9.5 の 221 056 / 31 569 と

変わったのは既定の精度設定だけである。**

### 9.8.4 仕事量で裏を取る（`SCALE_DG_OZAKI1_SLICE_STATS`）

`OZAKI1` は実際に使ったスライス数を出せる。p=511、8 スライス指定、18 step / 162 GEMM 呼び出し:

| 制御 | s_a / 呼 | s_b / 呼 | s_a·s_b / 呼 | **s_a·s_b 合計 / step（INT8 GEMM の代理）** | device |
|---|---:|---:|---:|---:|---:|
| FIXED | 8.00 | 8.00 | 64.0 | **576** | 11.926 s |
| ADP | min1 max2 mean **1.33** | mean **1.33** | 1.67 | **15** | 0.841 s |

**INT8 GEMM 本数の比は 38.4×、device 時間の比は 14.5×。** 比例しないのは
分解・パック・CRT など枚数に比例しない固定費があり、ADP 側の小さな GEMM は
スループットではなく発行レイテンシで律速されるからである。
**向きと桁は完全に一致し、「早期打ち切りが効いていた／いなくなった」以外の
説明を必要としない。**

### 9.8.5 精度を揃えた比較（依頼の必須項目）—— **§8 の 1.14× は無効な設定の速度**

p=7 `Ne=2³`、`SCALE_DG_VARYING_COEFF=1`、owned `dqdt(:,1:Ne)` 全 4096 点、
対 `CUDAFORTRAN_SPLIT` の最大絶対差:

| 経路 | 枚数 | FIXED | ADP |
|---|---:|---:|---:|
| **`OZAKI1`** | 7 slices | **3.55e-15** ✔ | **3.04e-01** ✘ |
| **`OZAKI1`** | 8 slices | **3.55e-15** ✔ | **3.04e-01** ✘ |
| `OZAKI2` | 7 moduli | 2.97e-01 ✘ | 1.86e-01 ✘ |
| `OZAKI2` | 14 moduli | 2.97e-01 ✘ | 1.86e-01 ✘ |

読めること:

- **ADP の `OZAKI1` は数値が合わない。** §9.8.4 の統計どおり実効 1.33 枚
  ≒ 10 bit 級しか作らないので、`scales_need_next_slice` が DG の
  `D1D` × flux に対して早く打ち切りすぎている。
  **`p511_gap_study.md` §8 の「Scheme I が native の 1.14× まで縮む」は、
  DG の要求精度を満たさない設定の速度である。**
- **DG の要求精度を満たす Ozaki は `OZAKI1` FIXED だけ**（3.55e-15）。
  その p=511 の速度は **220 857 µs/stage ＝ native の 16.6×**。
- **`OZAKI2` は FIXED でも ADP でも、7 moduli でも 14 moduli でも合わない**
  （1.9e-01〜3.0e-01）。**moduli を増やしても改善しない**ので、
  §9.5 が「moduli 数が足りていない」と書いた読みは訂正する:
  効いていないのは moduli 数ではなく **A 側の int8 表現**である
  （FIXED は A を 1 パックしか作らず、ADP でも
  `matrix_needs_second_slice` が p=7 では 2 枚目を要求していない）。
  **`OZAKI2` の性能値は 7 次数すべて「その精度での速度」であって、
  DG に使える設定の速度ではない。**

### 9.8.6 したがって未解明 2 はこう閉じる

- **機構**: `fd091fc`（2026-08-29）が `EmulationMantissaControl` の既定を
  DYNAMIC から FIXED に変え、その制御が Ozaki-I の残差 early-exit と
  Ozaki-II の追加 A パックを同時に決めている。§8（2026-08-28）は DYNAMIC を、
  §9.5（2026-09-03）は FIXED を測った。**両方とも正しい測定であり、
  違うものを測っている。** 実装の演算そのものは §8 以降変わっていない
  （§9.8.3 で 2 桁一致を確認）。
- **順位が逆になる理由**: FIXED 化は Ozaki-I を 14.5× 重くし
  （スライス対 15 → 576）、Ozaki-II を 1.32× 軽くする（A パック 4 → 1）。
  **符号が逆なので順位が入れ替わる。**
- **精度を揃えた結論**: DG の要求精度で比較できるのは `OZAKI1` FIXED だけで、
  p=511 で native の **16.6×**。**Ozaki は精度を揃えると native に一段と負ける。**
  §9.5 の「Ozaki は 7 次数すべて native に負ける」は強まりこそすれ弱まらない。
- `p511_gap_study.md` §8 の表は**書き換えない**。当時の DYNAMIC 既定での
  測定として残し、§8 に訂正注記を足した。

# 10. ライブラリ軸（`GEMM` 対 `GEMM_CUTE`）の符号反転と、p=7 の融合の値段（2026-09-03）

`reports/measurement_inventory.md` §7.6 / §7.7 が job `78678` の副産物として立てた
2 つの未解明を閉じる。**性能を動かすことは目的ではない。**目的は機構の同定で、
本節ではソースを 1 バイトも変更していない（測定はすべて既存の `SCALE_DG_*`
ノブと既存 namelist で行った）。

結論を先に 3 つ:

1. **`GEMM` 対 `GEMM_CUTE` は一軸比較になっていない。** 既定では `GEMM` だけが
   3 本の volume GEMM を別ストリームへ分散する（`SCALE_DG_GVOLPAR` 既定 2、§9.4）
   のに対し、`GEMM_CUTE` は `dg_stream` 上で 3 本を直列に走らせる。
   §7.6 の 10 点にはライブラリ軸とスケジュール軸が混ざっている。**欠陥である**
   （判断の根拠は §10.7）。
2. **一軸に揃えても符号反転は残るが、位置と大きさが変わる。** `GVOLPAR=0` で
   揃えると `Nq<=32` の CUTLASS 勝ちはむしろ大きくなり、負けは Nq=64 の
   **+1.51%** が最大で、**Nq=256 では符号が戻って CUTLASS が 1.33% 勝つ**。
3. **符号を決めているのは 3 本のうち z ただ 1 本**である。同一ドライバ上で
   1 本ずつライブラリを差し替えると効果は 6 次数すべてで**加法的**で、
   `Nq<=32` の勝ちは x と y と z のタイル適合、`Nq>=64` の負けは
   **CUTLASS の z が 64 スレッド（2 ワープ）CTA を 8192 個並べる**ことに閉じる。
4. **§7.7（p=7 の融合）は未解明ではなかった。** 機構は**本レポート §6 に
   すでに書かれていた**（`SCALE_DG_CSKIP` による同じ分解、原因は `TbN`=16 の
   半述語化）。§10.8 はそれを別ツリー・別ノードで再現し、素の x と担い手 x の
   レジスタ差とカーネル本数を足しただけである。**棚卸しの帳簿の欠陥である。**

## 10.6 「固定費が償却される」型の説明は立つか —— 半分だけ立つ

§7.6 は「負け幅が次数とともにゼロへ戻る」ことに「小さい行列ほどライブラリの
オーバヘッドが相対的に重い」という読みを付けていた。測った範囲では**その形の
説明は tail については立たず、CTA 内の仕事量については立つ。**

- **tail は次数で減衰しない。** conf は次数が上がるほど `Ne` を落として
  問題規模を揃えているので、**grid と waves/SM は p=63 と p=127 で完全に同一**
  （x 2048 / 6.74、y 4096 / 8.98、z 8192 / 13.47）。tail 損は両次数で同じ 3.9% で、
  次数の関数ではない。**「tail が償却される」という説明は反証された。**
- **減衰しているのは Δz の絶対値のほう**で、−12.4（p=63、ステージの 2.0%）→
  −4.9（p=127、0.7%）→ −5.2（p=255、0.5%）→ −65.0（p=511、0.51%）。
  grid が同じで K = Nq だけが伸びるので、**CTA あたりの mainloop が長くなり、
  CTA 固定費（prologue、パイプライン充填、epilogue、最終波の空き）の
  相対比重が下がる**という形になる。ncu の SM throughput もその向きで動く
  （z は 64.0% → 80.2%、cuBLAS 側との差は 3.4 → 1.7 ポイント）。
- **prologue と tail を切り分けるアブレーションは走らせていない**ので、
  「CTA 固定費」の内訳までは特定できていない。ここは未解明として残す。
- `Nq<=32` 側の減衰は別の量で説明が付く。述語で捨てられる割合 `1 − Nq/TbN` は
  Nq とともに単調に減り、§1 の x カーネル単体（−48.7 / −44.4 / −14.2 / −2.1%）
  がその減衰を直接測っている。**こちらは「固定費の償却」ではなく
  「無駄なタイル面積の消失」である。**

## 10.7 §10.1 は `AGENTS.md` の一軸性要件に照らして欠陥か —— 欠陥である

**判断: 欠陥である。ただし「経路役割の defect」ではなく「比較設計の defect」である。**

根拠。

- `AGENTS.md` は `GEMM` について「Surrounding kernels … are shared with

N が `Nq*Nq` を覆い、grid = `(ceil(Nq/64), Nq*Nq/32, Ne)`。conf が次数とともに
`Ne` を落とすので、**3 次数とも CTA 数がちょうど 8192 になる**:

| p | Nq | Ne | grid | CTAs | block | K/BK | **nsys z 時間** |
|---:|---:|---:|---|---:|---:|---:|---:|
| 63 | 64 | 64 | (1, 128, 64) | **8192** | 64 | 4 | **98.52 µs** |
| 127 | 128 | 8 | (2, 512, 8) | **8192** | 64 | 8 | **141.23 µs** |
| 255 | 256 | 1 | (4, 2048, 1) | **8192** | 64 | 16 | **251.84 µs** |

述語で捨てられる面は 3 次数ともゼロである（`Nq` は 64 の倍数、`Nq*Nq` は 32 の
倍数）。したがって **grid・block・タイル・段数を固定したまま K = Nq だけが
4 倍になる 3 点**が、conf を 1 つも書き換えずに手に入る。

`T = a + b·(K/16)` の 3 点最小二乗:

| | 値 |
|---|---:|
| 切片 a（K 非依存分） | **43.21 µs** |
| 傾き b | 12.927 µs / BK ステップ |
| a が z カーネルに占める割合 | **p=63 43.9% / p=127 30.6% / p=255 17.2%** |

**これが §10.6 の「K が伸びて CTA 固定費の相対比重が下がる」の数値化**である。
ただし**この 3 点は直線に乗っていない**: 隣接 2 点から出る傾きは
`Nq 64→128` で 10.677、`128→256` で 13.826 µs/step、切片はそれぞれ 55.81 と
30.62 µs である（3 点 LSQ の rms は 3.89 µs）。理由は測れている ——
`ncu` の SM throughput が p=63 で **63.7%**、p=255 で **87.9%** と、
**同じカーネルが低次数ではレイテンシ律速、高次数ではスループット律速に
変わる**ためで、1 本の直線の傾きに意味が無い。
**したがって「切片 43 µs が固定費である」とは書けない。** 言えるのは
**固定費は 31〜56 µs の幅にあり、その相対比重が 44% → 17% と落ちる**ことまでで、
内訳はこの回帰からは出ない。以下の 2 つの直接測定で分ける。

### 10.10.2 tail —— 波の階段を直接測る（`Ne` 掃引、**機構同定専用**）

**この掃引は性能比較ではない。** `AGENTS.md` は「カーネル比較で `Ne` を変えるな」
と定めており、ここで `Ne` を振るのは **z の CTA 数 128·`Ne` を波の境界を
またいで動かすため**だけである。**下の数字を `perf_*` の表と並べてはならない。**
`namelists/` には何も足していない（`jobs/conf/mech_p63_cute_ne*.conf`、
`jobs/` は gitignore）。p=63、`GEMM_CUTE`、`nstep=6`、`NeX=Ne, NeY=NeZ=1`、
`Ne` を 4〜76 の 29 点。数値は正しい（ただの別問題サイズ）。

z カーネル時間は **きれいな階段**になった。段の境目は CTA 数
1152→1280、1792→1920、2432→2560、2944→3072、3584→3840 のあいだにあり、
**すべて 608 の倍数（1216 / 1824 / 2432 / 3040 / 3648）を挟む**。

> **波の量子 Q = 608 CTA。** `ncu` はこの z を
> `Block Limit Shared Mem = 4`（動的共有 49 152 B/CTA）、
> `Waves Per SM = 13.47` と報告する。8192 / 13.47 / 4 = **152.06 → SM 数 152、
> SM あたり 4 CTA**。**掃引が独立に出した 608 と、`ncu` の 13.47 が一致する。**

29 点全部を波数で回帰すると:

| モデル | 当てはめ | R² | rms |
|---|---|---:|---:|
| T = a + b·**W**（W = CTA/608、端数を許す） | 4.888 + 6.913·W | 0.99779 | 1.186 µs |
| **T = a + b·⌈W⌉（波は丸ごと消費される）** | **1.522 + 6.976·⌈W⌉** | **0.99845** | **0.994 µs** |

**⌈W⌉ のほうが当てはまる。** 波量子化＝tail が実在することの直接証拠である。
検算として、**波がちょうど埋まる `Ne`** では端数線との差が消えるはずで、
実際そうなる:

| Ne | CTAs | W | 実測 [µs] | 端数線 a+b·W | 差 | 差 / 実測 |
|---:|---:|---:|---:|---:|---:|---:|
| 19 | 2432 | **4.000** | 30.814 | 29.425 | +1.39 | +4.5% |
| 57 | 7296 | **12.000** | 86.242 | 85.231 | +1.01 | +1.2% |
| 76 | 9728 | **16.000** | 113.742 | 113.134 | +0.61 | +0.5% |
| **64（本番）** | **8192** | **13.474** | **98.517** | 95.511 | **+3.01** | **+3.05%** |

波がちょうど埋まる 3 点では差が波数とともに 4.5%→0.5% と縮む（残っているのは
grid の launch/drain 1.52 µs の相対比重）。**本番の `Ne=64` だけが、
波数が大きいのに +3.01 µs＝+3.05% と浮いている。** 波モデルの上限は
`b·(14 − 13.474) = 3.67 µs = 3.73%`。よって:

- **tail（最終波の充填不足）= 3.01〜3.67 µs ＝ z カーネルの 3.05〜3.73%。**
  §10.5 が waves の小数部から見積もった 3.9% と一致する。
  実測が上限より小さいのは、47% しか埋まらない最終波が満杯の波より少し速く
  終わるからで、**最終波は「丸ごと 1 波ぶん」までは損をしていない。**
- **grid 全体の launch / drain = a = 1.52 µs ＝ z の 1.55%（p=63）。**
  これは絶対値なので p=127 では 1.1%、p=255 では 0.6% に薄まる。
- **tail は次数の関数ではない。** grid は 3 次数とも 8192 CTA、`ncu` の
  `Waves Per SM` も 3 次数とも 13.47 なので、**tail は 3 次数とも
  z カーネルの 3.0〜3.7%** である。**§10.6 の「tail は償却されない」は、
  これで係数付きで確定した。**

### 10.10.3 したがって §10.5 の負け幅のうち tail はどれだけか

§10.3 の per-GEMM 掃引で `Nq>=64` の Δz は
−12.4（p=63）/ −4.9（p=127）/ −5.2（p=255）µs/stage だった。
tail の絶対値は z カーネルの 3.0〜3.7% なので
**3.0〜3.7（p=63）/ 4.2〜5.2（p=127）/ 7.6〜9.4（p=255）µs/stage** に当たる。

- **p=63 では Δz 12.4 µs のうち tail は 3.0〜3.7 µs（24〜30%）**にすぎない。
  残りの 7〜9 µs は CTA あたりの並列度（2 ワープ CTA、実占有率 12.0%）である。
- **p=127 / p=255 では tail だけで Δz を超える。** つまりこの 2 次数では
  「tail を除けば CUTLASS の z は cuBLAS より速い」ことになる。
  ただし **cuBLAS 側の tail は同じ方法で測れていない**（cuBLAS のタイル選択は
  制御できないので `Ne` 掃引が同じ意味を持たない）ので、
  **差し引きの符号はここでは断定しない。**

### 10.10.4 prologue —— アブレーション用ノブ（**既定オフ、production dispatch 外**）

多段パイプラインの充填ぶんを分けるため、既存の `SCALE_DG_ZTILE`
（これまで `Nq==16` にしか通っていなかった）を `Nq>=32` にも通した。
`cuda_cutlass_gemm_fused.cu` に `ZG0`〜`ZG8` の候補を足し、
`launch_volume_gemm_z` に `tile >= 0` の分岐を 1 本増やしただけである。

- **既定は `z_tile = -1`（`dg_gemm_defaults` は全次数でそのまま）なので、
  production dispatch はこれらに一切到達しない。** `GEMM_CUTE` と
  `GEMM_FUSED` は従来どおり同じ mainloop を共有する。
- `ZG0` は既定タイルと同一形（64x32 / warp 32x32 / BK16 / Stages 4）で、
  **`SCALE_DG_ZTILE=0` は既定と同じ時間になることを確認した**
  （§10.10.5 の表で +0.03 / −0.01 / +0.02%）。
- **9 タイルすべて、点ごとに変化する `u/v/w/Escale/normal_fn/Fscale`
  （`SCALE_DG_VARYING_COEFF=1`）で、`dqdt` 全 16 777 216 点が既定と
  ビット一致**する（p=63、`jobs/ztile_validate.sh`）。タイル形はどれも
  出力要素あたりの K 累積順序を変えないので当然である。

| index | 形 | 変えているもの |
|---|---|---|
| 0 | 64x32 / w32x32 / BK16 / **S4** | **＝既定**（対照） |

| 5 | **64x64** / w32x32 / S4 | CTA 数を半分に |
| 6 | **128x32** / w32x32 / S4 | （p=63 では M=64<128 で半分が述語落ち） |
| 7 | 64x32 / **w16x32** / S4 | CTA 数そのまま、ワープ数 2→4 |
| 8 | 64x32 / w32x32 / **BK32** / S4 | mainloop 反復数を半分に |

`Stages = 2` は作れない（CUTLASS が 2 段パイプライン版の `MmaCore` に
回すが、FP64 TensorOp ではその部分特殊化が曖昧になる）。

**段数だけを動かして波数を固定するつまみは存在しない。**
本作業の範囲では **prologue の時間ぶんは分離できない。**

### 10.10.6 prologue の**命令数**は正確に測れる

時間は分けられないが、命令数は分けられる。`ncu` の `Executed Instructions`:

| p | S4 | S3 | 差 | 差 / CTA | **差 / ワープ命令** |
|---:|---:|---:|---:|---:|---:|
| 63 | 36 241 408 | 34 652 160 | **1 589 248** (−4.39%) | 194.0 | **97.0** |
| 255 | 93 061 120 | 91 471 872 | **1 589 248** (−1.71%) | 194.0 | **97.0** |

**2 次数で差が 1 命令も違わない。** grid が同じ 8192 CTA なので、これは
**CTA あたりの固定量＝まさに固定費**であることの直接の証拠である。
中身も合う: 1 段は A タイル 64×16 と B タイル 16×32 を global→shared に運ぶ。
64 スレッド（2 ワープ）CTA なら A が 1024 要素 ⇒ LDG 32 + STS 32 ワープ命令、
B が 512 要素 ⇒ 16 + 16、合計 **96 ワープ命令**で、実測 97.0 と一致する。

したがって **prologue（`Stages−1` = 3 段の充填）= 291 ワープ命令/CTA
= grid 全体で 4 767 744 命令 = p=63 では全命令の 13.2%、p=255 では 5.1%**。
**「固定費の相対比重が K とともに下がる」が、命令の勘定でも 2.6 倍の
減衰として出ている**（43.9%→17.2% の回帰と同じ向き、同じ桁）。

### 10.10.7 まとめ —— どこまで言えて、どこから言えないか

**言えること（z カーネルに対する割合、p=63 の本番構成）:**

| 項目 | 値 | 出所 |
|---|---:|---|
| **tail（最終波の充填不足）** | **3.05〜3.73%** | `Ne` 掃引 29 点、⌈W⌉ 回帰 R²=0.99845 |
| **grid の launch / drain** | **1.55%** | 同回帰の切片 1.52 µs |
| **prologue（命令数ベース）** | **13.2%（p=255 で 5.1%）** | `ncu`、S4−S3 の差が 2 次数で完全に一致 |
| K 非依存分の合計（時間） | 31〜56 µs ＝ **31〜57%** | 固定 grid の K 回帰。**3 点が直線に乗らないので幅で書く** |
| tail の次数依存 | **無し**（3 次数とも waves/SM 13.47） | `ncu` ＋ grid の恒等式 |

**言えないこと（推測で埋めない）:**

- **prologue の時間ぶん。** §10.10.5 のとおり `Stages` は共有メモリ経由で
  波数と占有率を同時に動かすので、時間としては分離できない。
  分離するには「共有メモリ総量を変えずに段数だけ変える」実装が要る
  （たとえば段ごとのタイルを小さくして総量を保つ）が、**実装していない。**
- **K 回帰の切片 43 µs を固定費と読むこと。** 3 点は直線に乗らない
  （SM throughput が 63.7%→87.9% と律速が変わる）。
- **cuBLAS 側の tail。** `Ne` 掃引と同じ手が使えない（タイル選択を制御できない）。
  §10.10.3 の「p=127 / 255 では tail だけで Δz を超える」は
  **CUTLASS 側だけの勘定**であって、差し引きの符号を決めるものではない。
- **`ZG2`(S5) が p=63 でだけ既定とほぼ同じになる理由。** S5 の共有は 60 KB で
  Block Limit は 3 のはずだが、その構成の `ncu` は取っていない。
- **`ZG6`(128x32) が p=63 で +12.16%、p=255 で −0.09% と符号が変わる理由。**
  p=63 では `Nq=64 < TbM=128` で M の半分が述語落ちする（§1 と同型）が、
  p=255 では落ちない、という読みは形から言えるだけで、**`ncu` で確かめていない。**
- **`GEMM_FUSED` 側の担い手 z（`run_z_gemm_assembly`）**。本節は
  `launch_volume_gemm_z` が出す**平の z** だけを測っている。

### 10.10.8 `ZG1`(S3) が速いことを採否と読んではならない

p=63 で −1.42%、p=255 で −0.20%（8 ラウンド交互、レンジ非重複）は
**本節では機構の証拠**としてだけ使っている。採否にしない理由は 2 つある。

1. **役割。** `AGENTS.md` は `GEMM_CUTE` を「独立に速度最適化しない対照」と
   定め、volume mainloop のタイル・段数・swizzle を `GEMM_FUSED` と
   **同一に保て**と要求している。`launch_volume_gemm_z` は両経路が通る共有
   ヘルパなので既定を動かせば両方に入るが、**それは「対照の再チューニング」
   ではなく「共有 mainloop の変更」という別の判断**であり、
   `GEMM_FUSED` の担い手 z（`run_z_gemm_assembly` は集合自身の `GemmZ` を
   使う）まで含めた設計と測定が要る。本作業はそれをしていない。
2. **測定。** 上の −1.42% は 8 ラウンド交互で取っており信頼できるが、
   `GEMM_FUSED` 側では測っていないし、p=7 / 15 / 31（z が cuBLAS だったり
   別タイルだったりする次数）でも測っていない。
   **`TODO.md` に候補として立てるのが正しい扱いである。**

### 11.5 依存関係の事実 —— **融合は重ね合わせの機会を 3 から 2 へ減らす**

**§10.7 が案 A に付けた「融合軸のほうが汚れる」という評価は、依存の向きを
取り違えていた。** ソースで確認できることは 3 つある。

1. **未融合なら 3 本の volume GEMM は互いに独立である。**
   `cuda_cal_dqdt_gemm_cutlass` の `.not. fuse_epilogue` 分岐は x → `deriv_x`、
   y → `deriv_y`、z → `dqdt` と別々の配列に書き、3 本のあとで
   `separable_lift_assembly_kernel` が 3 出力をまとめて読む。
   **3 本のあいだにデータ依存は無い。** これは
   `mod_cuda_dg_kernels.cuf` の `SCALE_DG_GVOLPAR` のコメント
   （「the three volume GEMMs are independent, so they can be spread over
   streams」）がすでに書いていた事実で、未融合 cuBLAS ドライバはそれを
   実際に使っている。
2. **融合すると担い手は他の 2 本に依存する。** 担い手の launch は
   `launch_x_gemm_assembly` / `launch_y_gemm_assembly` / `launch_z_gemm_assembly`
   の 3 つで、**どれも引数に `deriv_x, deriv_y`（＝他の 2 本の微分）を取る**。
   エピローグが同じ節点インデックスでそれらを要素ごとに読むからで、
   これは `AGENTS.md` が担い手の定義として書いていることそのものである
   （「the epilogue reads the other two derivatives elementwise at the same
   node index」）。**担い手が x / y / z のどれであっても成り立つ**ので、
   担い手の選択で話は変わらない。
3. **したがって、融合したときに同時に走れるのは非担い手 2 本だけである。**
   実装もそうなっている: `overlap_y`（z 担い手、y を side2 へ）、
   `overlap_z`（y 担い手、z を side2 へ）、`overlap_xy`（x 担い手、y を side2 へ）
   はいずれも「非担い手 2 本のうち片方を側ストリームに出す」形で、
   担い手は必ず join のあとに走る。

**帰結**: 融合は重ね合わせの機会を **3 → 2 に減らす**。`overlap_y` が
`fuse_epilogue .and. ...` で条件付けられている（2921 行）のは**実装上の選択**で
あって、融合が重ね合わせを可能にしているからではない。

**現状の配置は次のようになっている。**

| 経路 | 重ねている volume GEMM の本数 | 根拠 |
|---|---:|---|
| `GEMM`（既定 `GVOLPAR=2`） | **3**（side が空いていれば） | `gemm_volume_xyz` |
| `GEMM_CUTE`（出荷形） | **0** | 未融合分岐は直列 |
| `GEMM_FUSED` | **2**（Nq=8 / 16 / 32 のみ。Nq>=64 は 0） | `overlap_xy`（担い手 x、`ysched=1`）。Nq>=64 は担い手 z で `overlap_y` が `Nq<64` 条件により偽 |

**未融合側が 0 本、融合側が 2 本なので、「融合すると重ね合わせが 1 本減る」という
代金が融合軸に計上されていないどころか、Nq<=32 では融合側にだけ重ね合わせの得が
乗っている。** これが §11.6 で数値になる。

§11.6 は、`Nq >= 64` では `GEMM_FUSED` が重ねを 1 本も使っていないので
「`GEMM_CUTE` にだけ重ねを与えた 0.9122 / 0.8851 / 0.9045 / 0.9293 は
like-for-like ではなく融合軸の**下限**であり、真の一軸値は出荷形の比と
CUTE 重ね版の比のあいだにある」と書き、**`GEMM_FUSED` の非担い手 2 本を
Nq>=64 で重ねたらどうなるかは測っていない**（§11.8 の 1 件目）としていた。

**本節がそれを測った。** ソース上、`Nq > 64` の `GEMM_FUSED` が重ねを持てる
唯一の道は畳み込みを捨てることである（畳み込むと y が `deriv_x` を読むので
x と重ねられない）。その取引の値段が上の表であり、

- **重ねで買えるのは Nq=128 で 0.92%、Nq=256 で 0.89%、Nq>=512 ではゼロ。**
- **畳み込みを手放す代金は +48.10 〜 +5.90%。**

したがって **`GEMM_FUSED` は Nq >= 128 において、すでに自分に許された
いちばん速い形になっている。** これで §11.6 の未解決は次のように閉じる:

1. **「下限」という位置づけはそのまま維持される。** CUTE に重ねを与えた比は
   依然として融合に最も不利な側の値である。
2. **同時に、その下限が事実上 like-for-like の値になった。** 「両経路とも
   自分に可能な最良のスケジュールで走らせる」を like-for-like と定義するなら、
   `GEMM_CUTE` は 2 本重ね、`GEMM_FUSED` は畳み込み＋直列がそれぞれの最良なので、
   **§11.6 の「CUTE 重ね」列（Nq=128 で 0.8851、256 で 0.9045、512 で 0.9293）が
   その定義での正しい融合軸**である。区間は下端で閉じた。
3. **「`GEMM_FUSED` が重ねを使っていないのは実装上の手抜きではない」**ことが
   数字で示された。§11.6 は「融合の帰結（担い手依存）と畳み込みの帰結の
   両方による」と書いていたが、**どちらの寄与が支配的かまでは言えていなかった**。
   本節の答えは**畳み込みの側が 6〜50 倍大きい**である。
4. §11.6 の読みどころ 4「融合軸の汚れは 0→2 の側から来ている」も変わらない。

## 12.2 (2) 共有 z メインループ `Stages` 4 → 3 —— Nq = 64 / 128 / 256 で採用

### 12.2.2 採用の範囲と、なぜ次数で切るのか

**採用は Nq = 64 / 128 / 256 の 3 次数に限り、両経路に同時に入れた。**
`AGENTS.md` は「多項式次数による特殊化は、共有 CUTLASS mainloop / launch 構成

一方で **`GEMM_FUSED` が Nq=512 で +0.09%、Nq=1024 で +0.05% 負ける
（どちらもレンジ非重複＝実在する差）**。差はどちらも 0.1% 以下だが、
**本番経路を測定で遅くする変更を、対照側の 0.1% と引き換えに入れる理由が無い。**
Nq = 576 / 768 は `GEMM_FUSED` がレンジ重複＝差なしなので、
**`GEMM_FUSED` が得をする次数はひとつも上に無い。**

### 12.2.3 機構 —— 段数 ⇒ 共有メモリ ⇒ Block Limit ⇒ waves/SM

§10.10.5 / §10.10.6 が p=63 で測った鎖がそのまま効いている:

- 1 段は `(TbM+TbN)·BK·8 = 12 288 B` を食う。S4→S3 で 49 152 → 36 864 B、
  `Block Limit Shared Mem` 4 → 6、**waves/SM 13.47 → 8.98**。⌈8.98⌉=9 なので
  **tail（最終波の充填不足）が 3.7% → 0.2% へほぼ消える**（§10.10.2 で
  `Ne` 掃引 29 点が独立に出した波量子 Q = 608 CTA と一致）。
- prologue（`Stages−1` 段の充填）は **CTA あたり 291 ワープ命令＝ grid 全体で
  1 589 248 命令**で、これは **p=63 と p=255 で 1 命令も違わない**（§10.10.6）。
  つまり**絶対量が固定**であり、**K = Nq とともに相対比重だけが落ちる**
  （全命令の 13.2% → 5.1%）。

**次数依存はこの 2 つの合成として説明が付く。** 得は「tail が消えるぶん＋
prologue が浅くなるぶん」で、**tail は 3 次数（Nq=64/128/256）とも grid が

急速に薄まり、Nq >= 512 では 0.1% 台に沈む。** §10.10.5 の nsys が同じことを
z カーネル単体で見せている（S4→S3 で p=63 98.7→89.1 µs ＝ −9.8%、

## 13.1 利用者の決定（2026-09-03）―― §10.7 の案 A を採用

> `GEMM_CUTE` は 3 本重ねる。これで `GEMM` と正当な比較になる。`GEMM_FUSED` は、
> もともと 3 本重ねられるのを、epilogue を融合することで 2 本しか重ねられなく
> なった。**これはそのメリットとデメリットを両方含んでさらに勝てるかどうかと
> いうのが `GEMM_FUSED` の評価**である。なのでどちらも正当な評価。

要点は、**融合が課すスケジュールの制約は融合の代金であり、融合軸に計上される
べきもの**だという一点である。§11.5 が測った依存関係の事実（未融合の 3 本は
独立、融合すると担い手が他の 2 本を要素ごとに読む）を、軸の設計として引き受け
たことになる。したがって:

- **ライブラリ軸**（`GEMM` 対 `GEMM_CUTE`）は 3 本対 3 本で読む。
- **融合軸**（`GEMM_CUTE` 対 `GEMM_FUSED`）は「重ねられるだけ重ねた未融合」対
  「融合が課す制約のもとで重ねられるだけ重ねた融合」で読む。融合側が
  Nq<=32 で 2 本・Nq>=64 で 0 本なのは**欠陥ではなく融合の代金**である。

§10.7 の推奨（(D) 主・(C) 従）は採らなかった。(D)（per-GEMM 掃引）は軸として
残るが、経路そのものの数字ではないという §10.7 の但し書きは変わらない。

## 13.2 実装 ―― `SCALE_DG_CUTEPAR` の既定を 0 から 2 へ

§11.4 で入れたノブの**位置づけだけ**が変わった。コードパスは §11.4 のものと

## 追記（2026-09-05）: GB200 上の「cuBLAS」は CUTLASS 生成カーネルである

本稿の per-GEMM ライブラリ割り当ての測定（§ 各所の「cuBLAS x/y/z 対 CUTLASS
x/y/z」）は、**GB200 上では「NVIDIA のライブラリ実装対我々の実装」ではない。**

`reports/h100_report.md` §8.7.2（Slurm job `82208`、node `c393`、ncu で
カーネル名をフィルタせずに採取）のとおり、**GB200 の cuBLAS はこの
ベンチマークが呼ぶ FP64 volume GEMM に CUTLASS 生成の sm_80 カーネル
`cutlass_80_tensorop_d884gemm_{64x128_16x3, 64x64_16x4, 64x32_16x4}_nn_align1`
を出す**（p=255 で 3 種、p=511 は 64x128_16x3 の 1 種）。タイル族は
`GEMM_CUTE` が組むものと同じで、x GEMM はレジスタ 212 本・grid 2048・
block 128 まで一致する。

**したがって本稿の測定の位置づけはこうなる。**

- **有効なまま**: どのタイル・どの段数・どの命令形状が速いかという
  **構成の比較**。cuBLAS 側は「CUTLASS 3.x が sm_80 向けに生成した構成」で、
  我々の側は「CUTLASS 2.x multistage で組んだ構成」であり、両者の比較は
  構成の比較として意味を持つ。採用した割り当てもそのまま有効である。
- **読み替えが要る**: 「cuBLAS に勝った / 並んだ」という言い方。GB200 では
  **相手もCUTLASS** なので、ライブラリ実装の優劣を示す証拠にはならない。
  本物のライブラリ軸は H100 側にしかなく、そこでは cuBLAS は sm_90 専用の
  手書き xmma（`tensor16x8x8`）で、`GEMM_CUTE` に 1.20〜1.45 倍勝つ。

**本稿の測定値は 1 つも書き換えていない。**変わったのは、それが何の差を
測っていたかである。
