# 時間積分後の精度検証

- 日付: 2026-09-06
- GPU: NVIDIA GB200 1 GPU（RIKYU ログインノード）
- ビルド: commit `48eb7da` + 本コミット、`make CUDA=1 GPUFLAGS=-gpu=cc100 GPUNVCCFLAGS=-arch=sm_100`
- 入力: `namelists/acc_p{7,63,255}_gemm.conf`（`DqdtKernel_Type` のみ差し替え）
- 実行: `SCALE_DG_ACCURACY=1 ./scale-dg_extraction namelists/acc_p7_gemm.conf`

## 0. 何を埋める検証か

`AGENTS.md` の数値契約が要求するのは、**点変化係数での owned `dqdt` 全点比較**、
すなわち**テンデンシ 1 回**の検証である。それは通っている（16,777,216 点、
`GEMM_CUTE` はビット一致、`GEMM_FUSED` は 2.1e-16〜4.2e-16）。
しかし**時間積分を nstep 回まわした後の解の精度**は、これまで測っていなかった。
カーネル出力が一致することと、積分後の解が正しいことは別の主張である。

定数速度・周期領域なら厳密解がある。初期条件
`q(x,0) = sin(2πx) sin(2πy) sin(2πz)` に対して
`∂q/∂t + ∇·(qu) = 0` の解は任意の t で
`q(x,t) = sin(2π(x−u_x t)) sin(2π(y−u_y t)) sin(2π(z−u_z t))` であり、
LGL 重み `w1D` で積分すれば L2 誤差も総質量も出る。
実装は `main.f90` の `report_accuracy_if_requested`（環境変数
`SCALE_DG_ACCURACY=1` でのみ動き、タイマー停止後に走る）と、
`mod_mesh.f90` に追加した `w1D`（`w_i = 2/(p(p+1)P_p(x_i)²)`）と `ElemSize`。
`SCALE_DG_VARYING_COEFF=1` は速度が点変化して閉じた解を持たないので、
その組み合わせでは**誤った誤差を出す代わりに何も出さない**。

## 1. 時間積分は 3 次精度である（p=7、`FUSED_TC`、t_end = 0.01 固定）

| dt | nstep | 相対 L2 誤差 | 前の行との比 |
|---:|---:|---:|---:|
| 1.0e-4 | 100 | 2.6309e-11 | — |
| 5.0e-5 | 200 | 3.2943e-12 | **7.99** |
| 2.5e-5 | 400 | 4.2359e-13 | **7.78** |
| 1.0e-5 | 1000 | 7.5838e-14 | 5.59（2.5³ = 15.6） |

**dt を半分にすると誤差が 8 分の 1 になる。**SSP-RK3 の 3 次精度が
そのまま出ている。最後の行だけ比が落ちるのは**丸め誤差の床**に当たったため
で、これが次節の絶対値がどれも 1e-13 付近に張り付く理由である。
すなわちベンチマークの dt では**空間離散化誤差も時間離散化誤差も丸め誤差以下**
であり、次節が比べているのは実装どうしの一致である。

## 2. 全経路が、厳密解に対しても互いに対しても一致する

`dt` × `nstep`）。厳密解に対する相対 L2、L∞ 絶対誤差、質量ドリフト。
質量の厳密値は 0（`sin` の 1 周期積分）なので、ドリフト欄はそのまま

- **同じ次数の経路どうしの誤差の差は最大 2.8e-18**（p=63、`GEMM_CUTE` 対
  `GEMM_FUSED`）で、**誤差そのものの 5e-6 倍**しかない。7 つの実装は、
  積分後の解として区別できない。
- **`FUSED` / `FUSED_TC` / `FUSED_DFMA` は 3 次数とも互いに完全一致**
  （表示 16 桁で同一）。iso-schedule の 2 つは mma 命令だけの違いなので
  当然だが、CUDA core 融合まで一致するのは丸め順序が同じだからである。
- **質量ドリフトは 1e-18 台**。厳密値 0 に対して、丸め誤差の水準で保存している。
- **絶対値そのものは §1 のとおり丸め誤差の床**である。これは実装の精度が
  良いという主張であって、DG の収束次数を測ったものではない（空間精度を
  見るには粗い格子が要る。本リポジトリの対象外）。

### 2.1 診断が離散化誤差を見ていることの確認（粗い格子）

上の表がすべて 1e-13 台なのは実装が悪くないからではなく、**この格子が
`sin` を過剰に解いている**からである。診断そのものが離散化誤差を
見られることは、粗い設定で確認した（非 CUDA ビルド、`OPENACC_SPLIT`、
p=3、`Ne=4³`、dt=1e-5、`nstep=100`、t=0.001）:

| 量 | 値 |
|---|---:|
| 相対 L2 誤差 | **1.9374e-04** |
| L∞ 誤差 | 4.6502e-04 |
| 質量ドリフト | 5.204e-18 |

**同じ診断が、解像度を落とすと 9 桁大きい誤差を返す。**上の表の 1e-13 は
測れていないのではなく、その設定では本当にそこにいる。
（この実行は CPU / OpenMP ビルドで、`AGENTS.md` が要求する
非 CUDA ビルドの確認も兼ねている。）

## 3. 制約と、やっていないこと

- **定数速度でしか動かない。**点変化係数（`SCALE_DG_VARYING_COEFF=1`）には
  閉じた解が無く、その場合この診断は何も出さない。点変化係数の検証は
  従来どおり `dqdt` 全点比較のほうが担う。**2 つは相補的で、どちらも要る。**
- 診断は既定 off（`SCALE_DG_ACCURACY=1` のときだけ動く）で、タイマー停止後に
  実行される。**性能測定には 1 命令も乗らない。**
- `acc_*` の `nstep` は 1 周期ではない。ベンチマークの `dt` で 1 周期は
  p=7 で 10 万ステップ、p=255 では 1000 万ステップになるので、
  **厳密解を任意の t で評価する**ことで代えている（数学的には同じ検証で、
  1 周期に特別な意味は無い）。p=7 の 1 周期（`nstep=100000`、t=1.0）だけは
  実際に走らせた: §4。

## 4. 1 周期（p=7、`FUSED_TC`、`nstep=100000`、t = 1.0）

| 量 | 値 |
|---|---:|
| 終了時刻 | 1.0（＝ ちょうど 1 周期、`vel = 1`、領域 1） |
| 絶対 L2 誤差 | 2.6762e-12 |
| 相対 L2 誤差 | 7.5696e-12 |
| L∞ 誤差 | 6.4727e-12 |
| 質量ドリフト | −4.609e-18 |

**t=0.01（1000 ステップ）の 7.5838e-14 のちょうど 100 倍**である。
ステップ数を 100 倍にして誤差も 100 倍——**誤差はステップ数に比例して
線形に積み上がっており、これは §1 の「丸め誤差の床」の性格そのもの**
（離散化誤差なら dt を変えずステップ数を増やせば別の増え方をする）。
1 周期まわしても解は初期条件に相対 7.6e-12 で戻り、質量は 1e-18 台を保つ。

## 5. 再現手順

```bash
make CUDA=1 GPUFLAGS=-gpu=cc100 GPUNVCCFLAGS=-arch=sm_100
# 1 経路
SCALE_DG_ACCURACY=1 ./scale-dg_extraction namelists/acc_p63_gemm.conf
# 全経路（DqdtKernel_Type だけ差し替える）
for path in CUDAFORTRAN_SPLIT CUDAFORTRAN_FUSED CUDAFORTRAN_FUSED_TC \
            CUDAFORTRAN_FUSED_DFMA CUDAFORTRAN_GEMM CUDAFORTRAN_GEMM_CUTE \
            CUDAFORTRAN_GEMM_FUSED; do
  sed "s/DqdtKernel_Type = \"CUDAFORTRAN_GEMM\"/DqdtKernel_Type = \"$path\"/" \
      namelists/acc_p63_gemm.conf > /tmp/acc.conf
  SCALE_DG_ACCURACY=1 ./scale-dg_extraction /tmp/acc.conf | grep -A6 '^Accuracy'
done
```

§1 の dt 収束は `namelists/acc_p7_gemm.conf` の `dt` と `nstep` を
（1.0e-4, 100）/（5.0e-5, 200）/（2.5e-5, 400）/（1.0e-5, 1000）に替えたもの。
§4 は同じファイルで `nstep = 100000`。
