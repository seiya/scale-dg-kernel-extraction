### 2.3 分解 —— どちらの前提が壊れたか

`1/Nq` の法則は 2 つを同時に仮定している。

- **(a) 分子**（担い手の追加読みの費用）が体積点数 `P` に比例する。
- **(b) 分母**（stage 全体）が `P × Nq` に比例する = 縮約が支配的で効率一定。

| Nq | 分子/点 [ns/Mpoint] | 分母/(点·Nq) [µs] | GEMM 以外の割合 |
|---:|---:|---:|---:|
| 128 | 18.649 | 0.34763 | 34.6% |
| 256 | 18.637 | 0.23745 | 23.4% |
| 512 | 14.918 | 0.18735 | 13.5% |
| 576 | 14.065 | 0.18288 | 12.2% |
| 768 | 13.720 | 0.17425 | 9.5% |
| 1024 | 9.802 | 0.16837 | 7.3% |

区間ごとの比（1.000 なら前提が成り立っている）:

| 区間 | `Nq` 比 | 実測（ksum） | (a) 分子/点 | (b) 分母/(点·Nq) | **外れた前提** |
|---|---:|---:|---:|---:|---|
| 128→256 | 2.000 | **1.367** | **0.999** ✔ | **0.683** ✘✘ | **分母** |
| 256→512 | 2.000 | 1.971 | 0.800 ✘ | 0.789 ✘ | **両方（相殺）** |
| 512→576 | 1.125 | 1.165 | 0.943 | 0.976 | 小 |
| 576→768 | 1.333 | 1.302 | 0.975 | 0.953 | 小 |
| 768→1024 | 1.333 | **1.803** | **0.714** ✘✘ | **0.966** ✔ | **分子** |

（恒等式 `実測 = Nq比 × (b) ÷ (a)` は 5 区間とも 0.002 以内で閉じる。）

**両端は逆の理由で外れている。**

- **128→256 は分母が伸びない。** 点数が一定（16.78 M）のまま `Nq` だけが
  倍になる区間なので、**点あたり O(1) のカーネル（`volume_flux` 129.3、
  `rk_update` 75.4、`elembnd_flux` 47.7、`update_halo` 6.2）は 1 µs も
  伸びない**。それが Nq=128 の stage の **34.6%** を占めている。
  加えて GEMM 自体も 488.0 → 781.2 µs、すなわち **2.00 倍ではなく 1.60 倍**
  しか伸びない（`GEMM/(点·Nq)` が 0.22724 → 0.18188、比 **0.800**）——
  これは §6.3 / §10.10.1 の「CTA 固定費の相対比重が K とともに落ちる」が
  同じ向きに効いているもので、**畳み込みの得を分母側から削っている**。
  2 つの寄与は 0.800（メインループ効率）× 0.854（周辺カーネルの希釈）
  ＝ 0.683 と分かれる。
- **768→1024 は分子が伸びない。** 点数は 2.370 倍になるのに、担い手の
  追加費用は 1.693 倍しか増えない（点あたり 13.720 → 9.802 ns/Mpoint、
  **−28.6%**）。分母のほうは 3.054 倍で、`P × Nq` の 3.160 倍に対して
  3.4% 外れているだけである。
- **256→512 が `Nq` 比に合うのは、2 つの違反がほぼ同じ大きさで
  逆向きに相殺するからである**（分子 0.800、分母 0.789）。
  **中央 3 区間の一致を「両方の前提が成り立っている証拠」と読んではならない。**
  §12.1.2 と `draft_order_mechanism.md` §6.2 の *closely follows* は
  結果として正しいが、理由はこれである。

|---:|---:|---:|---:|---:|

**追加読みは帯域律速ではない**（どの次数でも屋根の 1/3 未満）。

## 3. (ii) 融合の上りの枝 —— 賞金は `volume_flux` の除去ではない

### 3.1 前提が違っていた

`draft_order_mechanism.md` §6.2 は融合の賞金を「除去される `volume_flux`」
として説明している。**`Nq ≤ 32` ではそれが起きていない。**

nsys が示すのは:

- **`GEMM_CUTE` は `Nq ≤ 32` で `flux_all` を 1 本走らせる**
  （体積フラックスと要素境界フラックスを 1 カーネルで計算する）。
- **`GEMM_FUSED` はそれを `volume_flux` ＋ `elembnd_flux` の 2 本に割る。**

したがってこの次数帯では、**融合はフラックス側で得をしていない。損をしている**:

| Nq | `CUTE` の `flux_all` | `FUSED` の `volume_flux` + `elembnd_flux` | 差 |
|---:|---:|---|---:|
| 8 | 296.13 | 136.45 + 171.89 = 308.34 | **+12.21** |
| 16 | 266.27 | 137.78 + 142.00 = 279.78 | **+13.51** |
| 32 | 240.01 | 141.89 + 114.09 = 255.98 | **+15.97** |

`Nq ≥ 64` では両経路とも `volume_flux` を別に持ち、差は `elembnd_flux` の
−2.96（Nq=64）／−9.28（Nq=128）だけになる。

### 3.2 賞金の内訳（`ksum`、µs/stage）

| Nq | 吸収される `separable_lift_assembly` | 体積 GEMM 側の割増 | フラックス側 | 合計 |
|---:|---:|---:|---:|---:|
| 8 | −163.95 | **+180.76** | +12.21 | **+29.03**（融合が負ける） |
| 16 | −161.54 | **+120.00** | +13.51 | −28.04 |
| 32 | −157.90 | **+117.58** | +15.97 | −29.05 |
| 64 | −155.73 | **+96.08** | −3.09 | −62.38 |
| 128 | −154.88 | **+34.82** | −9.53 | −129.09 |

`Nq = 32` はさらに x（cuBLAS）が −4.48、y が −0.75 動いており、
合計はそれを含む。「体積 GEMM 側の割増」は、`Nq ≤ 32` では平の z GEMM が担い手
`GemmDqdtAssemblyX` に置き換わる差（92.14 → 272.90 など）、
`Nq ≥ 64` では畳み込みが入るので x/y/z の 3 本ぶんの差である。

**読めること:**

- **除去される仕事は次数によらずほぼ一定である。**
  `separable_lift_assembly` は 163.95 → 154.88 µs/stage、すなわち
  `Nq` が 16 倍になっても **5.5% しか減らない**。点あたり O(1) の
  カーネルを点数一定で測っているので、当然そうなる。
  **賞金が増えているのは「除去される仕事が増えるから」ではない。**
- **増えているのは、担い手が払う割増が縮むからである。**
  **180.76 → 120.00 → 117.58 → 96.08 → 34.82 µs/stage** と単調に落ちる。
  融合エピローグの費用は、メインループが長くなるほど覆われる ——
  §2.4 と同じ機構が、同じ担い手について、逆向きの符号で効いている。
- **`Nq = 8` で融合が負けるのは、割増（180.76）が吸収する lift（163.95）を
  上回るからである。** 差 16.81 にフラックス側の 12.21 が乗って +29.03。
  **これが公表値 `F ÷ C = 1.0127` の中身である。**
- **`Nq = 32 → 64` で賞金が動かない理由。** ここは構造が 2 か所同時に
  変わる区間である（`flux_all` が消え、畳み込みが入る）。割増は
  117.58 → 96.08 と 21.5 縮むが、フラックス側が +15.97 → −3.09 と
  19.1 だけ有利に振れる一方で、`ksum` ベースの賞金は 29.05 → 62.38 と
  倍増している。**device 物差しでこれが平ら（8.26% → 8.25%）に見えるのは
  重なりの差である**（§3.3）。

### 3.3 重なりの寄与

同じトレースから、窓内の `span`（重なりを 1 回だけ数える）を取ると:

| Nq | `ksum` 差 | `span` 差 | 公表 device 差（§13.8） |
|---:|---:|---:|---:|
| 8 | −1.92% | **−1.18%** | −1.27% |
| 16 | +3.96% | **+5.69%** | +7.16% |
| 32 | +4.32% | **+6.81%** | +8.26% |
| 64 | +8.48% | **+7.30%** | +8.25% |
| 128 | +14.74% | **+11.18%** | +12.05% |

`span` は公表 device 系列を**符号・順序・山の位置ともに再現**する
（残差は nsys のオーバヘッドと別ジョブ差）。**`ksum` と `span` の差が
重なりの寄与**であり、経路ごとの重なり率は

| Nq | `GEMM_CUTE` | `GEMM_FUSED` |
|---:|---:|---:|
| 8 | 0.66% | 1.13% |
| 16 | 1.10% | 2.90% |
| 32 | 1.60% | 4.15% |
| 64 | 8.83% | 8.03% |
| 128 | 9.40% | 5.96% |

**`Nq ≤ 32` では `GEMM_FUSED` のほうがよく重なり**（賞金を 1.7〜2.5 ポイント
押し上げる）、**`Nq ≥ 64` では `GEMM_CUTE` のほうがよく重なる**
（賞金を 1.2〜3.6 ポイント押し下げる）。後者は
`AGENTS.md` が「融合の代金」と呼んでいるもの ——
担い手が他の 2 本を読むので 3 本の重なりが取れない —— そのものである。

**したがって上りの枝は 2 つの単調な量の和である**: 縮み続ける担い手の割増
（180.8 → 34.8）と、`Nq = 64` を境に符号が変わる重なりの差。
**`32 → 64` の平坦は、前者が縮むぶんを後者が食う 1 点だけの現象**であって、
畳み込みとは関係がない（`draft_order_mechanism.md` §6.5(c) が
「畳み込みが入る場所で増えていない」と書いた観察は正しく、
**その理由は畳み込みの不在ではなく重なりの反転である**）。

## 5. 測っていないこと

- **`GemmDqdtAssemblyX`（`Nq ≤ 32` の担い手）と
  `GemmBatchedDqdtAssembly`（`Nq ≥ 64`）は別の型である。**
  §3.2 の割増系列はその 2 つをまたいでおり、
  **同一カーネルの `Nq` 依存として読んではならない。**
- **`flux_all` と `volume_flux + elembnd_flux` の使い分けがどの条件で
  切り替わるか**はソースを追っていない。測ったのは「切り替わっている」
  ことと、その費用である。
- **Nq=1024 で L2 ヒット率が落ちる理由。**要求は点あたり一定（116.5 B）
  なのに DRAM ÷ L2 が 0.19 → 0.233 に上がることは測ったが、
  **何が何を追い出しているかは測っていない**（候補: 追加ストリームが
  オペランドタイルを L2 から追い出す）。分子の結論には効かない ——
  バイトが増えてなお速くなっているので、向きは変わらない。
- **他機（H100 / A100）で同じ分解を取っていない。**本報告は GB200 のみ。
- **重なり率は `span` から逆算した量**であって、ストリーム単位の
  タイムラインを読んだものではない。

## 6. 再現

```bash
module load nvhpc
make CUDA=1 GPUFLAGS=-gpu=cc100 GPUNVCCFLAGS=-arch=sm_100

sbatch jobs/nsys_invnq_departures.sh   # Nq = 128/256/768/1024 の畳み込み、
                                       # Nq = 8..128 の融合軸、カーネル別
sbatch jobs/nsys_invnq_mid.sh          # Nq = 512/576 を足し、同じ A/B を
                                       # プロファイラ無しの device 物差しで
sbatch jobs/ncu_fold_carrier2.sh       # 担い手の ncu、畳み込み on/off を 1 ジョブで
```

`ncu` の名前フィルタは使わないこと。`--kernel-name regex:DqdtAssembly` は
既定の name base ではテンプレート引数が落ちて 3 本とも `cutlass::Kernel` に
なり、`--kernel-name-base demangled` にしても担い手は先頭 8 launch に
入らないので、**job `88643` / `88644` は 8 本とも 0 行で終わった**。
`jobs/roof_bytes_ncu.sh` の形（フィルタ無し、tendency 呼び出し単位のスキップ、
担い手はレジスタ数 254/255 で同定）が動く形である。

どちらのジョブも凍結した実行ファイルのコピーをプロファイルし、
`export DEBUGINFOD_URLS=` と `--resolve-symbols=false` を使い、
各プロファイラ起動を `timeout` で囲む（`AGENTS.md`）。
