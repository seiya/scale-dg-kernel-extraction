# Ozaki Scheme II（arXiv:2504.08009v3）適用調査

作成日: 2026-08-27
対象リポジトリ: `scale-dg-kernel-extraction`
ブランチ / HEAD: `feature/cuda` / `c66bfca`
対象GPU: NVIDIA GB200 (RIKYU) 1 GPU、compute capability 10.0、host `c000`
build: NVIDIA HPC SDK 26.3、`nvcc -O3 -arch=sm_100 -lcublas`、cuBLAS 13.2.1
測定コード: `bench_ozaki2/`（`ozaki2_floor.cu`, `int8_peak.cu`, `pscan.cu`）
実行形態: ログインノード上で直接実行（プロファイラは使っていないので Slurm 不要）

本レポートは本体コードを一行も変えていない。cuBLAS のマイクロベンチだけで
採否を決めた記録である。前提となる cuBLAS 組み込みエミュレーションの実測は
`cublas_emulation_survey.md` にある。

**結論: 不採用。** ただし「遅かった」ではなく、**この論文が成立する条件は
K = Nq ≳ 600、すなわち p ≳ 500-650 であり、本リポジトリの p=7 / p=255 は
どちらもその手前にある**という定量的な線が引けた。

| 判定項目 | 結果 |
|---|---|
| p=7（K=8） | 論外。`cublas_emulation_survey.md` の実測で native 比 130.6 倍遅い |
| p=255（K=256） | INT8 GEMM の**演算だけ**で native DGEMM の 95-103%。パックも CRT 再構成もする前に負けている |
| 融合実装で逃げられるか | 不可。s 組の INT32 アキュムレータがレジスタに入らない（§5） |
| 成立する p | s=14 で **p ≈ 500-650**、確実に勝つのは p ≳ 1000（§6） |

---

## 1. 論文の内容

arXiv:2504.08009v3 "Ozaki Scheme II: A GEMM-oriented emulation of
floating-point matrix multiplication using an integer modular technique"。

対角スケーリングで入力を整数化し、互いに素な `s` 個の法での積を INT8 Tensor
Core（INT32 集積）で並列に求め、中国剰余定理で厳密な積を再構成して逆スケール
する。従来の Ozaki scheme が `k` スライスに対し `k(k+1)/2` 本の GEMM を要した
のに対し、本手法はちょうど `s` 本で済む。

報告値は GH200 で 80.2 TFLOP/s（s=14）対 native DGEMM 60.9 TFLOP/s = **1.32×**、
n = 8000-16384 の正方 GEMM である。

## 2. 本リポジトリでの対象と形状

`cuda_cal_dqdt_gemm`（`mod_cuda_dg_kernels.cuf`）の volume GEMM。Nq = p+1、
Ne = 1 として

| GEMM | 形状 | 現行 µs/call | 有効 TFLOP/s | 対 40.1 |
|---|---|---:|---:|---:|
| x | `M=256, N=65536, K=256` | 254.2 | 33.80 | 84.3% |
| y | `256x256x256` batched × 256 | 242.9 | 35.37 | 88.2% |
| z | `<64,32,16>`（assembly + lift epilogue 込み） | 338.6 | 26.23 | 65.4% |

（`overall_summary_report.md` §12 の値。x+y で 493 µs、tendency 988 µs/call の
ちょうど半分。z は epilogue を融合済みでライブラリ GEMM に戻せないので、
エミュレーションの対象になり得るのは x と y だけである。）

x/y は既に FP64 ピークの 84-88% に達しており、native 側に伸びしろは無い。
本リポジトリで唯一 compute bound な場所なので、候補としては正しい。

## 3. 実測: エミュレーションの下限

`ozaki2_floor.cu` は x / y の形状そのままで次を測る。

- `native` : `cublasDgemm`（倒すべき相手）
- `int8 x s, 1 C` : s 本の INT8 GEMM を**同一の** INT32 C に書く。パックも
  再構成も無し、つまり**演算だけの下限**
- `int8 x s, s C` : s 個の別々の INT32 C に書く（部分積の書き出しトラフィック込み）
- `reconstruct` : s 個の INT32 を読んで FP64 C を 1 本書く 1 パス（CRT のトラフィック）

事前に「`int8 x s, 1 C` だけで native を超えたら打ち切り」と決めて測った。

### 3.1 s = 14（FP64 相当に必要な moduli 数）

```
x GEMM  M=256 N=65536 K=256   (C = 134.2 MB fp64 / 67.1 MB int32)
native  DGEMM             : 256.4 us   33.50 TFLOP/s
int8 x 14, 1 C            : 242.8 us   (17.3 us each)      <- 演算だけの下限
int8 x 14, 14 C           : 265.1 us
reconstruct               : 219.5 us   4.89 TB/s (1074 MB)
--------------------------------------------------------
14 C + reconstruct        : 484.5 us   -> native の 1.89 倍遅い
1 C  + reconstruct        : 462.2 us   -> native の 1.80 倍遅い

native  DGEMM   y batched : 255.3 us   33.65 TFLOP/s
int8 x 14,      y batched : 240.9 us   (17.2 us each)      -> 0.94x
```

**打ち切り条件に該当。** 演算だけで native の 95%（y は 94%）を使い切っており、
パックも再構成も一切していない。run 間変動はあり、`int8 x 14, 1 C` は別 run で
264.7 µs（native の 103%）も出たが、結論は動かない。

### 3.2 moduli 数 s の依存性

```
 s    INT8 のみ   再構成    合計    native 比
 6     108.8      118.2    227.0     0.89x
 8     150.5      128.7    279.3     1.09x
10     189.8      167.8    357.7     1.40x
14     264.7      221.0    485.7     1.90x
18     310.6      268.1    578.8     2.25x
```

損益分岐は **s ≈ 7**。論文が FP64 相当に用いるのは s=14 で、そこでは 1.9 倍遅い。
s=6 なら 0.89 倍だが、それは単精度強の精度であって `AGENTS.md` の
「丸め誤差レベルで一致」という数値契約を満たさない。しかも 0.89× は x GEMM 単体の
話で、tendency 988 µs/call のうち x+y は 493 µs だから全体では **−5%** にしかならない。

## 4. なぜ負けるか: INT8 側は正常で、K が浅い

INT8 の実力不足ではない。`int8_peak.cu` で M=256, N=65536 を固定して K を振ると:

```
   K      us     TOP/s   C書き出し TB/s
  128    23.3    184.1       3.24
  256    23.9    358.9       3.50   <- p=255 の位置
  512    25.8    665.3       3.90
 1024    34.2   1004.4       3.92
 2048    46.4   1481.0       4.34
 4096    69.5   1977.4       4.83
 8192   117.6   2338.0       5.14
16384   204.3   2691.1       5.58

大正方 INT8（演算の天井）
  4096^3    52.3 us   2630.1 TOP/s
  8192^3   264.8 us   4151.7 TOP/s
 16384^3  1861.9 us   4724.4 TOP/s
```

この GPU の INT8 天井は **4724 TOP/s**、FP64 40.1 TFLOP/s の **118 倍**で、
論文の前提は満たしている。しかし K=256 では **1 本の INT8 GEMM が INT32 の C
（67 MB）を書き出す帯域で律速**しており（3.5 TB/s）、Tensor Core は天井の
**7.6%** しか使えていない。`1 C` と `s C` の差がほとんど出ない（242.8 対 265.1 µs）
のも同じ理由である。

論文が 1.32× を出したのは n=8000-16384、つまり K が 30-60 倍深い領域である。

Ozaki II が従来 Ozaki に対して減らすのは GEMM の**本数**（`k(k+1)/2 → s`）＝
演算項であって、ここで支配的な `O(s·M·N)` の INT32 トラフィック項ではない。
`cublas_emulation_survey.md` で cuBLAS 組み込みエミュレーションが p=255 で
8.8 倍遅かったのと同じ壁であり、実装を自前にしても越えられない。

## 5. 融合実装で逃げられない理由

s 組の INT32 アキュムレータを 1 カーネルに保持すれば、再構成の 1 GB は消せる。
しかし CUTLASS の INT8 mainloop で 128×128 タイルを取ると、

```
14 組 × 128 × 128 × 4 B = 917,504 B / CTA
```

に対し SM のレジスタファイルは 64K レジスタ × 4 B = **256 KB**。2 桁足りない。
s を減らせば精度を、タイルを小さくすれば効率を失う。s を外側ループにすれば
§3 の `s C` 版そのもの（既に native と同等以上）になる。逃げ道は無い。

## 6. どの p なら成立するか

`pscan.cu` による外挿。決め手になる比

```
有効演算 / INT32 出力バイト = 2·M·N·K / (4·M·N) = K/2 = Nq/2
```

が N に依らないので、N=65536 に切り詰めた形状で `R_fp64(Nq)` と `R_int8(Nq)` を
実測し、本来の `N = Nq^2` へ外挿できる。

```
t_native = 2·Nq^4 / R_fp64
t_emu    = s·2·Nq^4 / R_int8  +  (4s+8)·Nq^3 / BW
```

`BW` は再構成パスの実測帯域（この測定では 4.12 TB/s）。

モデルの検算: Nq=256 で `t_native` 予測 0.255 ms 対直接実測 0.256 ms（一致）、
`t_emu` 予測 0.599 ms 対直接実測 0.486 ms（モデルが約 2 割悲観。再構成帯域が
この測定で 4.12 TB/s、§3 の直接測定で 4.89 TB/s だったため）。したがって
交点はモデル上の値よりやや低い側に出る。

**交点 Nq ≈ 620（p ≈ 620）、2 割の悲観を補正すると実勢 p ≈ 550。幅を取って
p ≈ 500-650。** s=10 まで落とせるなら p ≈ 480。確実に勝つのは p ≳ 1000（1.7×）で、
そこは論文が想定する n=8000-16384 の領域に近づいたときである。

### 6.2 交点を決めているもの

`R_fp64` は Nq=256 で既にピークの 84% に達し、以後 39 TFLOP/s で頭打ち。
動いているのは INT8 側だけで、FP64 比は

- Nq=256 → 10.5×
- Nq=640 → 29×
- Nq=4096 → 111×

s=14 本ぶん払って勝つには FP64 比 14× 以上、さらに再構成トラフィックぶんが要る。
**FP64 比 20-30× に届く Nq ≈ 600 前後**が分岐点になる。

なお全体利得はこの表より**良い**方向に働く。GEMM は Nq^4、それ以外のカーネル
（`volume_flux_kernel` など）は Nq^3 なので、p=255 で 85% だった volume GEMM の
比率は Nq=640 では 97% になり、x/y GEMM の利得がほぼそのまま tendency の利得になる。

### 6.3 x/y/z をまとめても交点はほとんど動かない

`combined.cu` による実測。まず**何が構造的に可能か**が先に決まる。

`dqdt_assembly_kernel`（`mod_cuda_dg_kernels.cuf:1874-1878`）は

```fortran
dqdt = -( Escale_x*deriv_x + Escale_y*deriv_y + Escale_z*deriv_z + lift )
```

で、`Escale` は点ごと・方向ごとの場である（`AGENTS.md` の数値契約）。重み付けは
FP64 の再構成**後**に起きるので、**3 方向が INT32 のアキュムレータを共有することは
できない**。「3 方向を 1 本のモジュラ GEMM にまとめて再構成を 1/3 にする」という
最も効く道は塞がっている。残る統合は 2 つだけ。

- **(A) N 方向の連結**: moduli ごとに `N=Nq^2` の GEMM 3 本ではなく `N=3Nq^2` を 1 本
- **(B) 再構成の融合**: `3s` 組の INT32 を 1 パスで読み、`Escale` を掛け、lift を
  足して `dqdt` を 1 回書く（3 回の再構成 + `dqdt_assembly_kernel` を置換）

```
Nq=256, Ne=1, s=14
native  x  DGEMM          :  255.0 us  (33.68 TFLOP/s)
native  y  DGEMM batched  :  254.4 us  (33.77 TFLOP/s)
native  z  DGEMM          :  254.7 us  (33.73 TFLOP/s)
native  assembly kernel   :  155.6 us  ( 6.90 TB/s)
native  x+y+z+assembly    :  919.7 us

(A) int8 14x3, N=Nq^2 each   :  729.8 us  (494.3 TOP/s)
(A) int8 14x1, N=3*Nq^2      :  626.6 us  (575.8 TOP/s)   -14.1%
(B) reconstruct x3 + assembly:  950.4 us  (4.52 TB/s, 4.29 GB)
(B) 融合 reconstruct+assembly:  874.1 us  (3.99 TB/s, 3.49 GB)   -8.0%

  すべて別々   : 1680.2 us  ->  1.83x
  (A)+(B) 両方 : 1500.7 us  ->  1.63x
```

native の assembly が 155.6 us / 6.90 TB/s なのは `overall_summary_report.md` の
152.8 us / DRAM 92% と一致する。なお現行ツリーは lift と assembly を z epilogue に
融合済みで volume 3 本は 835.7 us なので、**実際の相手に対しては 1.80x** である。

**効かない理由は 1 行で出る。融合再構成パスだけで 874.1 us、native の
volume GEMM + assembly 全体 919.7 us の 95%。** INT8 GEMM が仮に無料でも
ようやくトントンで、3 方向がアキュムレータを共有できない以上、`3s` 組の
INT32（2.8 GB）を読む義務は消えない。

(A) の -14.1% もタダではない。INT8 レートが 494 -> 576 TOP/s に上がるのは M=256 で
128 幅のタイル行が 2 本しかなく、N を 3 倍にして初めて wave が埋まるからだが、
**連結には `flux_y` / `flux_z` が縮約軸を先頭にしたレイアウトである必要がある**。
y は中間軸、z は最終軸を縮約するので現状そうなっていない。`volume_flux_kernel` で
shared memory 経由の転置書き出しにすれば追加トラフィックなしで作れる見込みはあるが、
103 us のために 90% 帯域で回っているカーネルを触ることになる。

(A)+(B) を §6.1 の外挿に織り込むと:

```
   p     Nq   native[ms]  別々[ms]  まとめ[ms]  別々  まとめ  分岐点 s
 255    256       0.921     2.090      1.746   2.27   1.90       6.7
 511    512      12.272    15.310     12.758   1.25   1.04      13.4
 575    576      19.666    22.457     18.732   1.14   0.95      14.8
 639    640      29.197    29.705     24.750   1.02   0.85      16.8
 767    768      59.408    50.207     41.801   0.85   0.70      20.6
1023   1024     180.824   117.017     97.370   0.65   0.54      27.5
```

**交点は Nq ~ 620 -> 560（p ~ 620 -> 560）**、2 割の悲観を補正した実勢では
p ~ 550 -> 500。一段下がるだけで、p=255 が交点の半分という状況は変わらない。
統合の利得は「再構成とライブラリ境界の付随コストを削る」ことであって、
本質の `K = Nq = 256` は動かない。

### 6.4 将来ハードウェアの成立条件（FLOP/byte）

`balance.py`。native は compute bound、エミュレーションは §4 のとおり DRAM bound
なので、閉じた形で書ける。

```
t_nat = W / P_fp64            W = 2*Nq^4
t_emu = T / B                 T = (9s + 8) * Nq^3
```

`T` はライブラリ GEMM 構造で避けられないトラフィックである（s 本の INT8 GEMM が
INT32 C を書く `4s*Nq^3` と INT8 B を読む `s*Nq^3`、再構成が INT32 を読む `4s*Nq^3` と
FP64 を書く `8*Nq^3`）。Nq=256, s=14 で **T = 2.25 GB、native の 268 MB の 8.4 倍**。

条件は 2 つに分かれる。

**条件 1（演算）: `P_int8 / P_fp64 > s = 14`。**
GB200 の実測天井は 4724 TOP/s / 40.1 TFLOP/s = **117.8 倍**で、**8.4 倍の余裕で
すでに満たされている**。INT8 がこれ以上速くなっても p=255 では 1 us も縮まない。

**条件 2（バランス）: `P_fp64 / B < 2*Nq / (9s+8)`。** s=14 なら **`Nq/67` FLOP/byte**。

```
    p      Nq   必要な FLOP/B          実機のバランス
    7       8         0.12      H100  FP64 TC   peak : 20.00  (5.2x 不足)
  127     128         1.91      H100  FP64 CUDA peak : 10.15  (2.7x)
  255     256       * 3.82      GB200           peak :  5.08  (1.33x)
  511     512         7.64      GB200 実効 7.09 TB/s :  4.75  (1.24x)
 1023    1024        15.28
```

同じことを固定ハードで書くと:

```
                 必要な B (P=40.1 TF)   |  必要な P_fp64 (B=7.9 TB/s)
  break-even  :   10.5 TB/s             |   30.2 TFLOP/s
  1.5x 勝つ   :   15.7 TB/s             |   20.1 TFLOP/s
  2x 勝つ     :   21.0 TB/s             |   15.1 TFLOP/s
  GB200 現状  :    7.9 TB/s             |   40.1 TFLOP/s
```

**足りないのは 1.33 倍（実効ベースで 1.24 倍）だけである。** また s 依存は
`512/(9s+8)` で、s=10 の要求 5.22 FLOP/B は GB200 の 5.08 とほぼ一致する
（§3.2 で直接測った分岐 s ~ 7 との差は、エミュレーションが実際には 4.63 TB/s、
ピークの 59% しか出せていないぶんである）。

**帰結: この手法が現実味を帯びるのは「INT8 が速くなったとき」ではなく、
「FP64 が遅くなったとき」または「帯域が伸びたとき」である。** GB200 が H100 より
条件に近いのは、帯域が 2.4 倍になった一方で FP64 をあえて伸ばさなかった
（Hopper の FP64 Tensor Core 2 倍優位を捨てた、`AGENTS.md` 記載の事実）からで、
それだけで条件 2 が 4 倍改善している。次世代で帯域が 13 TB/s 級に伸びて FP64 が
据え置きなら、break-even 10.5 TB/s を越えて p=255 でも 1.3-1.5 倍になる。

**この純トラフィック限界（p ~ 340）と §6.1 の実測外挿（p ~ 620）は矛盾しない。**
前者は「INT8 演算が無料で、全トラフィックがピーク帯域で流れる」理想の下限、
後者は INT8 GEMM の実測レート（K=256 で天井の 7.6%）と再構成の実測帯域を
そのまま使った現実である。差の 1.8 倍はタイル形状・プロローグ・ライブラリ境界で
落ちるぶん。**将来ハードの議論には 3.82 FLOP/B を、実装可能性の議論には
p ~ 620 を使うこと。**

なお条件 2 は「INT32 が必ず DRAM を往復する」というライブラリ GEMM 構造の帰結で、
§5 のとおりこれは仮定ではなく制約である。レジスタファイルが 1 桁増えて s 組の
INT32 アキュムレータが載る日が来れば、条件 2 自体が消える。

## 7. p ≈ 600 が実際には届かない理由

1. **メモリは律速ではない。** Nq=640, Ne=1 で 1 要素 2.62 億点、FP64 場 1 本
   2.10 GB。`q/q0/dqdt/u/v/w` に flux と deriv を足して約 25 GB、エミュレーションの
   INT32 バッファ 14 本で 14.7 GB。189 GB には十分入る。
2. **実装が p=255 決め打ち。** `CUDA_P255_NQ = 256` はコンパイル時定数で、
   `mod_cuda_dg_kernels.cuf` の 4 箇所が `Nq /= CUDA_P255_NQ` で弾いている。
   `mod_mesh.f90` の `generate_lgl_operators_p255` も degree=255 決め打ちで、
   255 次の LGL 節点は既に独自の反復（上限 100 回）を要している。600 次では
   節点生成そのものが FP64 で厳しい。
3. **物理。** p=620 の 1 要素は DG というより擬スペクトル法である。CFL が
   1/p^2 で効くので dt は p=255 比で約 1/6 になり、time-to-solution では
   GEMM 側の 1.1× 程度は消える。

## 8. 再現方法

```bash
module load nvhpc-hpcx
cd bench_ozaki2
nvcc -O3 -arch=sm_100 -o ozaki2_floor ozaki2_floor.cu -lcublas
nvcc -O3 -arch=sm_100 -o int8_peak    int8_peak.cu    -lcublas
nvcc -O3 -arch=sm_100 -o pscan        pscan.cu        -lcublas
nvcc -O3 -arch=sm_100 -o combined     combined.cu     -lcublas

./ozaki2_floor 14 1      # §3.1（引数は s と Ne）
for s in 6 8 10 14 18; do ./ozaki2_floor $s 1; done   # §3.2
./int8_peak              # §4
./pscan 14               # §6.1（引数は s）
./combined 14            # §6.3
python3 balance.py       # §6.4
```

`bench_ozaki2/` のソースは本レポートの表を再現するためだけのもので、本体のビルドには
関与しない（`Makefile` から参照されない独立のマイクロベンチである）。ユーザの明示的な
指示によりレポートと合わせてコミットしてある。実行ファイルは `.gitignore` 済み。

## 9. まとめ

- INT8 Tensor Core の天井（4724 TOP/s = FP64 の 118 倍）は十分高く、
  論文の前提は GB200 でも満たされている。
- 効かないのは `K = Nq` が浅いから。K=256 では INT8 GEMM が INT32 出力の
  書き出し帯域で律速し、天井の 7.6% しか出ない。
- s=14 のエミュレーションは**演算だけ**で native DGEMM の 95-103% を消費する。
  パック・再構成を足すと 1.9 倍遅い。融合してもレジスタ容量で不可能。
- 成立するのは p ≳ 500-650。本リポジトリの p=255 は交点の半分の Nq しかない。
- x/y/z をまとめても 1.83x → 1.63x、交点 p ~ 620 → 560 で、桁は変わらない。
  3 方向は `Escale` の点ごと重み付けのため INT32 アキュムレータを共有できず、
  融合再構成パスだけで native の volume GEMM 全体の 95% を使う（§6.3）。
- ハードウェア側の条件は **`P_fp64 / B < 2*Nq/(9s+8)` = 3.82 FLOP/byte**（p=255, s=14）。
  GB200 は 5.08 で **1.33 倍足りないだけ**。INT8 の演算条件（`P_int8/P_fp64 > s`）は
  117.8 倍で既に満たされているので、鍵は INT8 の速さではなく **FP64 に対する帯域**
  である（§6.4）。
- したがって**不採用**。将来 p を大幅に上げる話が出たとき、あるいは FP64 あたりの
  帯域が 1.3 倍以上潤沢な世代が出たときに §6 の表を見直せばよい。
