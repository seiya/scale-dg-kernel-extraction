# `FUSED_DFMA` のレジスタ予算 —— iso-schedule が DFMA に払わせている代金（2026-09-03）

`AGENTS.md` は `CUDAFORTRAN_FUSED_DFMA` を「`FUSED_TC` と同一ソースの
`UseTc=false`、MMA 命令だけの iso-schedule アブレーション」と定義している。
`__launch_bounds__` は `UseTc` を見ない —— それが iso-schedule の条件そのもの
—— ので、**DFMA 対照は TC のレジスタ予算を強制的に共有させられている**。
本レポートはその代金を 6 次数すべてで測り、機構比 A を 2 通りの分母で引く。

**本レポートは経路定義を変えない。** `DFMA_OWN_BPSM` は既定 0 のコンパイル時
ノブで、production dispatch には入っていない。既定ビルドの SASS は改修前と
バイト一致である（§7）。定義を変えるかどうかは利用者の判断で、本レポートは
判断材料だけを揃える。

前史: p=7 の 1 例目は
[`tc_paper_survey_2407.09621.md`](tc_paper_survey_2407.09621.md) §19.9
（当時の `P7_TC_KP=1` 形で −6.13%）、p=255 の spill の存在は
[`p255_gap_study.md`](p255_gap_study.md) §26.9 の「副産物 2（未評価）」。
本レポートは両方を 6 次数に広げ、時間まで測って閉じる。

**2026-09-03 追記。** §0〜§7 は job `78408`（node `c190`）の記録である。
その後 job `78612`（node `c186`）で `ncu` を当て、§4 が「測れていない」と
明記した 3 点 ——(a) spill 命令がホットループの内か外か、(b) 消えた stall の
種別、(c) p=127 xz の残存 112 B の時間寄与 —— を **§10 で測定値に
置き換えた**。§8 は「4 択と推奨」から**採用した方針とその根拠**に
書き直してある（採用: **2 列。`AGENTS.md` の定義は変えない**）。

## 1. レジスタ予算の地図（ptxas、時間を測る前に）

`__launch_bounds__(threads, minBlocks)` の `minBlocks` がレジスタ上限を決める。
DFMA 側だけ動かす掃引の全結果（TC 側はどの行でも production のまま、
レジスタも spill も動かない）。**spill は cumulative stack size**。

### p=7（`tendency_fused_p7_tile_kernel`、`P7_THREADS=128`）

| `P7_BPSM_DFMA` | DFMA reg | DFMA spill | blocks/SM |
|---:|---:|---:|---:|
| **6（production）** | 80 | **32 B** | 6 |
| **5** | 96 | **0** | 5 |
| 4 | 128 | 0 | 4 |
| 3 / 2 / 1 | 150 | 0 | 3 |

TC 側は全行 80 reg / spill 0 / 6 blocks。`=3` 以下は 150 レジスタで飽和する。

### p=15（`tendency_fused_p15_kernel`、1024 スレッド）

| `P15_MINB_DFMA` | DFMA reg | DFMA spill | blocks/SM |
|---:|---:|---:|---:|
| **1（production）** | 64 | **0** | 1 |
| 2 | 32 | 720 B | (2) |
| 3 | 64 | 8 B | 1 |

**この次数に「単体最適形」は存在しない。** 1024 スレッドでは 65536/1024 = 64
がレジスタ数の物理上限で、production はすでに `minBlocks=1`（＝上限）かつ
spill 0 である。予算を動かせる方向は 1 つしかなく、そちらは spill を生む。

### p=31（`P31_XZ_THREADS = P31_Y_THREADS = 512`）

| `P31_*_MINB_DFMA` | xz reg / spill | y reg / spill | blocks/SM |
|---:|---:|---:|---:|
| **1（production）** | 126 / **0** | 90 / **0** | 1 / 1 |
| 2 | 64 / 216 B | 64 / 0 | 2 |
| 3 | 40 / 456 B | 40 / 112 B | (3) |

TC 側は xz 128 / y 64、いずれも spill 0。**p=15 と同じく単体最適形は存在しない**:
512 スレッドの上限 128 に対し DFMA は xz 126 / y 90 で、`minBlocks=1` のもとで
すでに欲しいだけ取れている。

### p=63（`P63_THREADS = P63Y_THREADS = 512`）

| 設定 | xz reg / spill | y reg / spill | y blocks/SM |
|---|---:|---:|---:|
| **production（`P63_BPSM=1`, `P63Y_BPSM=2`）** | 128 / 0 | 64 / **16 B** | 2 |
| `P63Y_BPSM_DFMA=1` | 128 / 0 | 96 / **0** | 1 |
| （参考）両方 2 | 64 / 272 B | 64 / 16 B | 2 |

xz は production ですでに `minBlocks=1` で spill 0。動かせるのは y だけ。

### p=127（`P127_XZ_THREADS = P127_Y_THREADS = 512`）

| 設定 | xz reg / spill | y reg / spill | y blocks/SM |
|---|---:|---:|---:|
| **production（`XZ_MINB=1`, `Y_BPSM=2`）** | 128 / **112 B** | 64 / **104 B** | 2 |
| `P127_Y_BPSM_DFMA=1` | 128 / **112 B** | 124 / **0** | 1 |
| （参考）両方 2 | 64 / 656 B | 64 / 104 B | 2 |

**xz の 112 B は launch bounds では除去できない。** `P127_XZ_MINB` は
production ですでに 1（最小）で、512 スレッドのレジスタ上限 128 をすでに
使い切っている。**「単体最適形」を作ってもこの代金は残る。**

### p=255（`tendency_p255_kernel`、`TH255=128`、4 インスタンス）

| `MINB255_DFMA` | DFMA reg | DFMA spill（4 本） | blocks/SM |

| 1 | 224 / 254 | 0 | 2 |

TC 側は 4 本とも 168 reg / spill 0 / 3 blocks。`=1` は `=2` と同一コード。

### まとめ

| p | production で DFMA だけが払う spill | launch bounds で消せるか |

## 4. 機構: spill 命令の本数と、それが買う占有率の 1 段

**`ncu` は本レポートでは当てていない**（利用者の指示でこれ以上のジョブ投入を
行わなかった）。したがって「どの stall が動いたか」は**測れていない**。
代わりに、コンパイル時に確定する 2 つの量だけで説明を試み、それが実測と
どこまで整合するかを示す。この節の主張は `ncu` によるものではない。

`cuobjdump -sass` で DFMA インスタンス（`ILb0`）のローカルメモリ命令を数えた
（iso ＝ production 設定、opt ＝ §2 の単体最適設定。**TC 側はどちらでも
`LDL`/`STL` ともに 0**）:

| カーネル（DFMA 側） | iso `LDL` / `STL` | opt `LDL` / `STL` |
|---|---:|---:|
| `p7_tile` | 4 / 4 | **0 / 0** |
| `p15` | 0 / 0 | 0 / 0 |
| `p31_xz` / `p31_y` | 0 / 0 | 0 / 0 |
| `p63_xz` | 0 / 0 | 0 / 0 |
| `p63_y` | 3 / 3 | **0 / 0** |
| `p127_xz` | **14 / 26** | **14 / 26（不変）** |
| `p127_y` | 52 / 35 | **0 / 0** |
| `p255` `DIR=0` (F24 off) | 14 / 14 | **0 / 0** |
| `p255` `DIR=1` | 29 / 29 | **0 / 0** |
| `p255` `DIR=2` | 29 / 29 | **0 / 0** |
| `p255` `DIR=0` (F24 on) | 14 / 14 | **0 / 0** |

**取引はどの次数でも同じ形をしている。** 予算を上げると spill 命令が消える
（賞金）が、占有率が 1 段落ちる（代金）。実測の符号は、その 2 つの大きさで
そのまま説明できる:

| p | 消える `LDL+STL` | 占有率の変化 | 実測 |
|---:|---:|---|---:|
| 7 | 8 | 6 → 5 blocks（−17%） | **−3.81%（勝ち）** |
| 63 | 6 | y 2 → 1 blocks（**−50%**） | **+2.51%（負け）** |
| 127 | 87 | y 2 → 1 blocks（**−50%**） | **−4.46%（勝ち）** |
| 255 | 28〜58（3 カーネル合計 156） | 3 → 2 blocks（−33%） | **−9.70%（勝ち）** |

p=63 と p=127 は**占有率の代金が全く同じ（y カーネルの 2 → 1 ブロック）**で、
違うのは賞金だけである（6 命令対 87 命令）。**同じ代金・違う賞金で符号が
反転している**ので、この 2 行は「代金一定の対照実験」として読める。
p=7 は代金が小さい側（6 → 5）で 8 命令が勝ち、p=255 は代金が中くらい
（3 → 2）で 156 命令が大きく勝つ。**4 点はすべて同じ 1 本の取引で並ぶ。**

逆方向（占有率を買って spill を増やす）は p=15 で +138.85%、p=31 で +19.63%
と、どちらも桁違いに負ける。p=15 の 720 B は 1024 スレッド全部が踏むので、
これは spill の代金が占有率 1 → 2 段で買えるものを大きく超える例である。

**測れていないこと（明記）**: `ncu` を当てていないので、(a) spill 命令が
ホットループの中にあるのか prologue/epilogue にあるのか、(b) 消えた stall が
`long_scoreboard` なのか `lg_throttle` なのか、(c) p=127 xz の残存 112 B が
その次数の DFMA 時間の何 % を占めるのか、は**いずれも未測定**である。
上表は命令数と占有率という 2 つの静的な量が実測の符号を説明する、という
以上の主張をしていない。`TODO.md` に残した。

> **2026-09-03 追記（`ncu` 後）。** 3 点は job `78612` で測定した（§10）。
> 本節の表と結論はそのまま残すが、**変数の取り方が誤っていた** ——
> 効く量は `LDL`/`STL` の**静的な本数**ではなく、**ホットループ内での

## 5. 2 つの分母は違うものを測っている

この節が本レポートの本題である。§2 の表の右 2 列は、**どちらが正しいかを
争っているのではなく、別の量を測っている**。

### 5.1 iso 分母（現行の公表値）が測っているもの

**「同一の日程・同一のレジスタ予算のもとで、内積を `mma.sync.m8n8k4` から
DFMA に替えると何倍になるか」。**

- 長所: `AGENTS.md` の定義そのもので、`FUSED_TC` に入った変更が自動的に
  `FUSED_DFMA` にも入る。分子だけが新しくなる事故（`p63_gap_study.md` §55 の
  p=127 で 3.62× → 2.46× になった件）が構造的に起きない。
  比べているのは**命令 1 つだけ**であることが、ソース上 1 か所の
  `if constexpr (UseTc)` で保証される（§55.3、本レポートの改修後も同じ）。
- 短所: **`__launch_bounds__` も共有されるので、DFMA は TC のために選ばれた
  レジスタ予算を強制的に着せられる。** DFMA は mma を使わない分だけ生きた値が
  多く、同じ予算では溢れる。したがって iso 分母は「mma 命令の差」だけでなく
  **「TC 向けの予算を DFMA に着せた代金」を上乗せしている**。上乗せは
  p=7 で 3.81%、p=127 で 4.46%、p=255 で 9.70%（p=15 / p=31 / p=63 では 0）。
  **2026-09-03 追記: この上乗せは `minBlocks` の軸だけを数えた値である。**
  スレッド数まで含めた上乗せは §12.9 の表を見ること（p=31 で 24.46%、
  p=63 で 7.88%、p=127 で 19.18%）。

### 5.2 単体最適分母が測っているもの

**「同じアルゴリズム・同じ日程を DFMA で書いたとき、実際に到達できる速度」。**

- 長所: `FUSED_DFMA` が「DFMA で書いたらこうなる」の代表値であるという
  読み方をするなら、こちらが正しい。TC 向けの予算に縛られた不利が落ちる。
- 短所: **予算が違えば日程は同一でない。** `__launch_bounds__` は SM あたりの
  ブロック数を決める ——
  p=7 で 6 → 5、p=63 / p=127 の y で 2 → 1、p=255 で 3 → 2 ——
  ので、レイテンシ隠蔽に使えるワープ数が変わる。命令列も別物になる
  （§4 の `LDL`/`STL`）。これは「mma だけの差」ではなく
  **「mma の差 ＋ 占有率の差」**であり、iso-schedule アブレーションという
  列の意味が失われる。
- **もう 1 つの短所（決定的）**: 単体最適でも**すべての代金は落ちない**。
  p=127 の xz カーネルは `minBlocks` がすでに最小で、512 スレッドのレジスタ
  上限 128 を使い切ったうえで **112 B を spill している**（§1）。
  この spill は launch bounds では除去できないので、**「単体最適」の 1390.88 も
  なお TC には無い代金を含んでいる**。「単体最適 ＝ DFMA の真の速度」という
  読み方は、少なくとも p=127 では厳密には成り立たない。
  **2026-09-03 追記:** その代金の大きさを §10.3 でアブレーションにより
  測った —— p=127 の DFMA 1 stage の **3.29%（直接測定、spill の 56% ぶん）
  〜 ≈5.8%（全部消した場合の線形外挿）**である。

### 5.3 共有が無料である次数があること

p=15 と p=31 では、**そもそも共有に代金が無い**。production はすでに
`minBlocks=1`（＝そのスレッド数で取りうるレジスタ数の上限）で、DFMA 側も
spill 0 だからである。p=63 では 16 B の spill はあるが、それを消す唯一の
掃引点が **+2.51% で負ける**ので、DFMA にとっての最適予算は production と同じ
である。**6 次数のうち 3 次数では 2 つの分母が同一値になる**（§2）。

これは「iso 分母は常に不当に重い」という読み方を否定する。代金は
**次数依存で、0 から 9.70% まで**である。

> **2026-09-03 追記（§12 の後）。本節の「共有が無料」は `minBlocks` の軸に
> ついてのみ成り立つ。** §12 は `__launch_bounds__` の**第 1 引数
> （スレッド数＝ワープ形）**も共有されていることを測り、それが spill を
> 経由せずに **shared オペランドロード ÷ mma** を通じて直接時間を決めることを
> 示した。**p=31 は本節が「代金 0」と書いた次数だが、ワープ形まで開くと
> `FUSED_DFMA` は −24.46% 速くなる**（job `79350`、xz ＋ y を 2×2、
> 12 ラウンド交互、レンジ非重複）。p=63 も同様に −7.88%（xz ＋ y `WN`=2、
> job `79344`）で、**その主要因 `p63_xz` は spill を 1 バイトも持たない**。
> 本節の表と結論は `minBlocks` の軸の測定値なのでそのまま残すが、
> 「2 つの分母が 3 次数で同一値になる」も同じ限定付きで読むこと。
> p=15 だけはワープ形のノブが構造的に無く、§12 でも未測定である。

## 8. 論文での扱い —— 採用した方針とその根拠（2026-09-03 決定）

**採用: 2 列（A_iso と A_opt を並記）。`AGENTS.md` の `FUSED_DFMA` の定義は
変えない。** 主比 A は従来どおり iso 分母のものを指し、単体最適分母の値は
その隣に並べる。以下は決定の記録であり、§10 の `ncu` 測定を踏まえている。

### 8.1 なぜ 2 列か

1. **本件の一次的な成果は「どちらが正しいか」ではなく、2 列の差そのもの**
   である ——「TC 向けに組んだ日程は、DFMA にとっては予算が足りない」。
   1 列にした瞬間に消える情報で、脚注では量として伝わらない。
2. **6 次数のうち 3 次数で 2 列が同じ値になる**（p=15 / p=31 / p=63、§2）。
   これは差が「一定の下駄」ではなく**次数依存の実費**であることの証拠で、
   §10.2 がその機構まで示した ——
   代金（占有率 1 段）はどの次数でもほぼ同じ形で発生するのに、賞金
   （spill 命令の**実行**回数）は次数によって 0 倍から 400 倍まで変わる。
   p=7 / p=63 は spill がループの**外**にあり 1 ワープあたり 3〜4 回しか
   実行されない（§10.1）。p=127 / p=255 は**チャンクループの中**で、
   1 ワープあたり 100〜422 回実行される。**この 2 桁の差が、そのまま
   3 次数で差ゼロ・3 次数で 3.81〜9.70% という分布の理由**である。
3. 主比 A の定義を動かさずに済む。iso-schedule の列が保たれたまま、
   「DFMA で書いたらどうなるか」という実用的な読みも同時に出せる。

論文本文では、A_iso を主比として提示し、A_opt を隣に置いて
**「iso 分母は mma 命令の差に加えて『TC 向け予算を DFMA に着せた代金』を
含む。その代金は 0〜9.70% で、spill がホットループの中にあるかどうかで
決まる」**と述べられる。2 つの値の違い自体を議論の対象にしてよい。

### 8.2 但し書き（省略できないもの）

- **A_opt は「予算の代金を完全に除いた値」ではない。** p=127 の xz は
  `minBlocks` が既に最小で、112 B の spill が単体最適形にも残る（§1）。
  §10.3 のアブレーションによれば、その残存分は p=127 の DFMA 1 stage の
  **3.29%（直接測定、spill トラフィックの 56% を消した分）**、
  全部消した場合の線形外挿で **≈5.8%** に相当する。
  したがって p=127 の A_opt 2.349 は、**代金を全部除けば 2.21 前後まで
  下がりうる**（§10.3 の外挿。数値不正なアブレーションに基づく推定値で
  あり、測定値ではない）。
- A_opt は日程が同一でない。`__launch_bounds__` の第 2 引数が変わると
  SM あたりのブロック数が変わり（p=7 6→5、p=63 / p=127 の y 2→1、
  p=255 3→2）、命令列も変わる。**A_opt は「mma の差」ではなく
  「mma の差 ＋ 占有率の差 ＋ spill の差」**である。

### 8.3 棄却した 3 案（理由を 1〜2 行ずつ）

- **選択肢 1（iso 据え置き ＋ 脚注）**: 公表値を一切変えずに済むが、
  3 次数で差ゼロという分布——本件の主要な結果——が脚注に潰れる。
  読者が「iso ＝ 命令だけの差」と読むのを脚注 1 つに委ねることになる。
- **選択肢 3（`AGENTS.md` の定義を変え、DFMA に独自予算を許す）**:
  iso-schedule アブレーションという列そのものを失う。加えて `FUSED_TC` を
  触るたびに DFMA 側の予算掃引をやり直す義務が生じ、しかも p=127 xz の
  112 B は定義を変えても消えない（§1、§10.3）ので、前提の
  「予算を開けば DFMA の真の速度が出る」が全次数では成り立たない。
- **選択肢 4（役割外の列を別に立てる）**: 言えることは選択肢 2 と同じだが、
  「役割外」の行は付録向きで、論文の主表に 2 列として置きにくい。
  経路名の契約を動かさない点は選択肢 2 も同じなので、利点が残らない。

### 8.4 単体最適形の再現手順

`DFMA_OWN_BPSM` は **既定 0・production dispatch 外**のままであり、
ソースの既定値は変えない。A_opt の再測定が要るときだけ、コンパイル時に
明示する:

```bash
module load nvhpc-hpcx
nvcc -O3 -std=c++17 -arch=sm_100 -Ithird_party/cutlass/include \
     --expt-relaxed-constexpr \
     -DDFMA_OWN_BPSM=1 -DP7_BPSM_DFMA=5 -DP63Y_BPSM_DFMA=1 \
     -DP127_Y_BPSM_DFMA=1 -DMINB255_DFMA=2 \
     -c cuda_dg_kernels_tc.cu -o cuda_dg_kernels_tc.o
# 残りのオブジェクトは既定ビルドのものを使い、リンクし直す
```

- `DFMA_OWN_BPSM=1` のときだけ `TCDFMA_BPSM(tc, dfma)` が
  `(UseTc) ? (tc) : (dfma)` に展開される。既定の 0 では `(tc)` に潰れ、
  SASS は改修前とバイト一致である（§7）。
- p=15 / p=31 / p=63 には単体最適の掃引点が無い（§1、§5.3）ので、
  `-D` は上の 4 つで全部である。
- 数値は動かない。全次数で単体最適形の owned `dqdt` は iso 形と
  **ビット一致**である（§6）。今回も p=127 で追試し、
  `CUDAFORTRAN_SPLIT` 対照の max abs 3.552714e-15 / 相対 4.340e-16 が
  iso 形と同値であることを確認した（§10.0）。

### 10.1 spill 命令はどこにあり、何回実行されるか

SASS 上の位置（後ろ向き分岐の内外）と、`ncu` の
`smsp__inst_executed_op_local_ld/st.sum` を 1 ワープあたりに直した値。
ワープ数は起動形状から確定し、**ループ外に置かれた命令の実行回数が静的な
本数と厳密に一致すること**で裏を取っている（p=7 の 4、p=63 y の 3、
p=255 DIR0 の `STL` 14）。

| カーネル（DFMA、iso 形） | 静的 `LDL`/`STL` | うちループ内 | 実行 `LDL`/`STL`（1 ワープ） | 実効ループ回数 |
|---|---:|---:|---:|---:|
| `p7_tile` | 4 / 4 | **0 / 0** | **4.0 / 4.0** | —— (SASS に後ろ向き分岐が 1 本も無い) |
| `p63_y` | 3 / 3 | **0 / 0** | **3.0 / 3.0** | —— (同上) |
| `p127_xz` | 14 / 26 | 14 / 14 | **100.0 / 112.0** | 7（`if (more)` で 1 回抜ける） |
| `p127_y` | 52 / 35 | 50 / 27 | **397.0 / 223.0** | 8 |
| `p255` DIR0 (F24 on) | 14 / 14 | 14 / **0** | **210.0 / 14.0** | 15 |
| `p255` DIR1 | 29 / 29 | 27 / 15 | **422.0 / 254.0** | 15〜16（`BK255=16`） |
| `p255` DIR2 | 29 / 29 | 27 / 15 | **422.0 / 254.0** | 同上 |

**答え: p=7 と p=63 は外、p=127 と p=255 は中。**

- p=7 の `p7_tile` と p=63 の `p63_y` は SASS に**後ろ向き分岐が 1 本も
  無い**（完全に展開されている）。spill は prologue/epilogue の直線コードで、
  1 ワープあたり 3〜4 回しか実行されない。
- p=127 xz は 14 本の `LDL` がすべてチャンクループの中にあり、1 ワープ
  あたり 100 回実行される（静的本数の 7.1 倍）。`STL` は 12 本が prologue、
  14 本がループ内で、112 = 12 + 14×7 + 2 と一致する。
- p=127 y は 397 / 223 回。**静的な 52 / 35 本の 7.6 倍 / 6.4 倍**である。
- p=255 の DIR1 / DIR2 は 422 / 254 回、DIR0 は `LDL` だけが 210 回で
  `STL` は prologue の 14 回のまま（`LDL`/`STL` 比がちょうど 15.0 になる
  ことが、`LDL` がループ内・`STL` がループ外であることの直接の証拠）。

**§4 への訂正注記。** §4 は「消える `LDL+STL`」を **静的本数**（p=7 で 8、
p=63 で 6、p=127 で 87、p=255 で 156）で数え、それが実測の符号を説明すると
書いた。**符号の説明としては今も正しいが、変数が誤っている。** 1 ワープ
あたりの**実行**回数で数え直すと:

| p | 消える実行回数（1 ワープ、DFMA 側のみ） | 占有率の変化 | 実測（§3、実時間） |
|---:|---:|---|---:|
| 7 | **8** | 6 → 5 blocks (−17%) | **−3.81%（勝ち）** |

p=7 と p=63 の賞金は 8 回と 6 回で**ほぼ同じ**であり、静的本数（8 対 6）

これに対し p=127 と p=255 の賞金は 620 回・1576 回と**2 桁大きい**。

実行回数で見ると **6 対 620、100 倍の差**になる（静的本数では 6 対 87 の
14 倍だった）。**§4 の定性的な結論は保たれ、量が 1 桁ぶん強くなった。**

### 10.3 p=127 xz の残存 112 B の時間寄与（アブレーション、**数値不正**）

`P127_XZ_MINB` は既に最小なので、この 112 B は `__launch_bounds__` では
消せない（§1）。天井を測るために、**数値を壊してレジスタ圧だけを下げる
アブレーション**を 2 つ作った。どちらも `fused_kernel_geom.h` の既定 0 の
コンパイル時ノブで、**production dispatch には入っていない**。

- `P127_XZ_ABLATE_AZ=8`: z 方向のアキュムレータ `az[16]` を `az[8]` に
  縮め、添字を 8 で剰余する。**mma・shared ロード・global ロードは
  1 本も減らない**（SASS で `DFMA` 624、`SHFL` 640、`LDG` 122、`LDS` 48、
  `STS` 32 が iso と同数であることを確認）。spill が **112 B → 48 B**。
- `P127_XZ_ABLATE_PF=1`: 二重バッファのプリフェッチレジスタ
  `pq/pu/pd[4]` を `[1]` に縮める。**`AZ=8` と併用すると spill は
  112 B → 8 B（実質ゼロ）**になるが、`pd[0]` が 4 回上書きされるため
  ptxas が `D1D` のロード 3 本を死コードとして消す。

**数値検証（`SCALE_DG_VARYING_COEFF=1`、owned `dqdt` 全点、
`CUDAFORTRAN_SPLIT` 対照、p=127）:** `AZ=8` は max abs **6.42e+00**、
`AZ=8,PF=1` は **7.49e+02**。**どちらも数値として不正であり、
天井の測定にしか使えない。** 同じ実行で iso 形と単体最適形は
max abs 3.552714e-15 で合格している。

実時間（job `78612`、node `c186`、**12 ラウンド交互**、
`CUDA device fused tendency` ÷ (99×3)、**6 版すべてレンジ非重複**）:

| 版 | 中央値 [µs/stage] | min–max | 対 iso | xz spill | xz の global ld セクタ | DRAM read |
|---|---:|---:|---:|---:|---:|---:|
| `FUSED_TC`（参考） | 593.01 | 593.0–594.2 | −59.30% | 0 | 5.328e7 | 6.778e8 |
| **DFMA iso（production）** | **1456.93** | 1455.8–1457.8 | —— | **112 B** | 5.328e7 | 6.783e8 |
| DFMA ＋ `AZ=8`（**数値不正**） | **1409.01** | 1408.0–1410.0 | **−3.29%** | 48 B | **5.328e7（不変）** | **6.779e8（不変）** |
| DFMA ＋ `AZ=8,PF=1`（**数値不正**） | 1317.14 | 1314.5–1317.9 | −9.59% | 8 B | 3.441e7（**−35%**） | 5.771e8（**−15%**） |
| DFMA 単体最適（y `BPSM`=1） | 1391.85 | 1390.6–1392.6 | −4.47% | 112 B | 5.328e7 | 6.780e8 |
| DFMA 単体最適 ＋ `AZ=8,PF=1`（**数値不正**） | 1252.18 | 1250.6–1253.2 | −14.05% | 8 B | 3.441e7 | 5.768e8 |

本ジョブは §2 の値を再現している —— `FUSED_TC` 593.01 対 592.22、
iso 1456.93 対 1455.74、単体最適 1391.85 対 1390.88（いずれも 0.1% 以内、
別ノード `c190` → `c186`）。

**天井の見積もり。**

- **交絡の無い直接測定は `AZ=8` の行だけである。** これは local ld セクタ
  を 2.517e7 → 1.101e7（**−56.3%**）、local st セクタを
  2.831e7 → 1.258e7（**−55.6%**）にし、**global セクタも DRAM バイトも
  動かさない**（`recipes.md` が要求する「触るデータ量が変わっていないか」の
  確認）。この **spill トラフィックの 56% の除去が、p=127 の DFMA
  1 stage 全体の 3.29%** に相当する。
- 100% 除去した場合を**線形外挿**すると **≈5.8%**（3.29 ÷ 0.563）。
  カーネル単体では `ncu` duration が 1729 → 1641 µs（−5.1%）なので、
  外挿すると xz カーネルの **−9.1%** に当たる（`ncu` の時間なので
  クロック固定バイアスを含む。採否には使っていない）。
- `AZ=8,PF=1` の **−9.59% は上限であって天井ではない**。global ld セクタ
  −35%・DRAM read −15% を巻き込んでいるからである。線形外挿の 5.8% を
  引いた残り ≈3.8% が、その巻き込んだ global トラフィック削減の寄与だと
  読める（両者が加法的だと仮定した場合）。
- 単体最適形の上に重ねた場合（1391.85 → 1252.18）は −10.03% で、
  同じ交絡を含む。

**結論（§5.2 と §8.2 への入力）。** 「単体最適 ＝ DFMA の真の速度」という
読みは p=127 では厳密には成り立たず、**その不足分は p=127 の DFMA
1 stage の 3.29%（直接測定、spill の 56% ぶん）〜 ≈5.8%（全部消した
場合の線形外挿）**である。全部消せたとすれば A_opt は
2.349 → **2.21 前後**まで下がりうる。**これは数値不正なアブレーションと
線形外挿に基づく推定値であり、測定値ではない。**

### 10.4 本節でも測れていないこと

- **交絡の無い「spill 100% 除去」点**。`AZ` を 6 / 4 / 2 まで縮めると
  spill はむしろ**増える**（それぞれ 200 / 200 / 352 B。mma の依存鎖が
  同じレジスタ対に集まって ptxas のスケジューリングが崩れる）ので、
  `AZ` だけでは 48 B より下に行けない。48 B → 8 B には `PF` が要り、
  `PF` は global ロードを消してしまう。
- **p=15 の `ncu`**。単体最適形が存在しない次数なので比較の相手が無く、
  対照は `p31_xz`（spill 0、L1/TEX 90.5%）1 点だけである。
- p=255 の 4 インスタンスのうち `DIR0`（F24 off）は `-s 12 -c 8` の
  範囲に入らず、プロファイルできたのは 3 本である。
- **占有率の代金だけを単独で測るアブレーション**は作っていない
  （spill を持たせたまま `minBlocks` だけ動かすことはできない —— 予算を
  動かすと spill も動く）。したがって §10.2 の「賞金 / 代金」の分離は
  stall の内訳による帰属であって、時間の分解ではない。

## 11. スレッド数まで DFMA 専用に組み直したらどこまで行くか（2026-09-03、job `79187`、**役割外**）

> **2026-09-03 追記（§12）。本節が §11.7 の末尾で「宿題」として残した
> p=63 xz の −4.89%（spill 0 なのに勝つ）には、§12 で機構が付いた** ——
> ワープ形は spill とは独立に **shared オペランドロード ÷ mma =
> `(TM+TN)/(TM*TN)`** を決めており、DFMA 側の xz カーネルは L1/TEX が
> 対ピーク 93.2% で飽和しているので、その比を 1.00 → 0.75 にすると勝つ
> （逆に 1.50 にすると +16.67% 負ける）。本節の測定値はすべてそのまま残すが、
> **到達点の 2 行は §12 で更新された** —— p=63 は 800.17（xz のみ）→
> **769.09（xz ＋ y、−7.88%）**、p=127 は 1180.57 → **1175.99
> （xz 4×4 ＋ y 8×4、−19.18%）**。さらに **§11 が 1 点も測っていなかった
> p=31 が −24.46% と最大**である（§12.8）。

§9 が「未測定」として残した 1 行 ——「DFMA 専用にスレッド数まで組み直した
場合の到達点」—— を測る。**これは主比 A が測る量ではない。**
`__launch_bounds__` の第 1 引数を動かすとブロック形が変わり、日程が同一で
なくなるからである。本節の値は **A_iso にも A_opt にも入らない**。
`AGENTS.md` の `FUSED_DFMA` の定義は本節でも変えていない。

**目的は 1 つだけ**: §8.2 の但し書き ——「A_opt は代金を全部は除いていない。
p=127 xz は `minBlocks` が既に最小で 112 B の spill が残り、それは 1 stage の
3.29〜≈5.8% に当たる（§10.3）」—— が、**スレッド数まで開いたときにどうなるか**
の材料を揃えることである。**本節は方針を決定しない。**

**`DFMA_OWN_SHAPE` は既定 0・production dispatch 外の役割外ノブである。**
既定ビルドの `cuda_dg_kernels_tc.o` を `cuobjdump -sass` して改修前と比べると
**差分ゼロ**（`ptxasOptions` の行を含めて 0 行）で、`TCDFMA_SHAPE(tc, dfma)` は
`DFMA_OWN_SHAPE=0` のとき `(tc)` に潰れる。`FUSED_TC` は 1 バイトも動いていない。

### 11.1 何を変え、何を変えていないか（妥当性の境界）

スレッド数を変えると shared のレイアウトやワープ形が変わりうるので、
**どこまでを「同じアルゴリズムの別のスレッド割り当て」と呼べるか**を先に
決めた。本節で変えたのは **ブロックの出力タイルをワープ／スレッドに切り分ける
比率だけ**である。具体的には:

**変えていないもの（全設定で同一）**

- **ブロックタイル**。p=127 xz は全設定で 128×64、p=127 y も 128×64、
  p=63 は 64×64、p=255 は `BM255`×`BN255` = 64×64。
- **shared メモリのパネルとその swizzle**。パネル寸法はブロックタイルと
  チャンク深さだけで決まり、スレッド数に依存しない
  （p=127 xz は `sFW` 64 KB ＋ `sFU`/`sD` 各 32 KB ＝ 128 KB、全設定で同じ）。
- **チャンク深さと二重バッファ**（`BKD127` / `BK63` / `BKDY127` / `BK255`、
  `P127_XZ_DB`）。
- **grid**。1 要素を覆うブロック数は変わらない。
- **各スレッドの内積の総和順序**。アキュムレータ 1 本が担う縮約はそのままで、
  **どのスレッドがどの出力を持つか**だけが動く。

**変わるもの**

- ワープ格子（`WM`×`WN`）とスレッド数。
- 1 スレッドが持つアキュムレータ本数と staging の反復回数。
  この 2 つは**スレッド数に反比例して増える**。
- スレッド数から決まるレジスタ上限（65536 ÷ (threads × minBlocks)、
  ただしハードウェア上限 255 で頭打ち）。

**p=7 だけ制限を付けた。** `P7_TC_KP=1` は
`tendency_fused_p7_tile_kernel` ではなく `tendency_fused_p7_kernel` という
**別のカーネル**を選ぶので、それはスレッド数の変更ではなくアルゴリズムの
変更である。したがって p=7 の掃引は **`KP` ∈ {2, 4}**（128 / 64 スレッド）に
限った。

**`FUSED_TC` 側（`UseTc=true`）は一切変えていない。** 変更は
`__launch_bounds__` の第 1 引数と、カーネル内の `constexpr` を
`TCDFMA_SHAPE(...)` 経由にしたことだけで、`UseTc=true` の展開は改修前と
同じ定数になる（§11.0 の SASS 差分ゼロ）。

### 11.2 ptxas の地図（時間を測る前に）—— **p=127 xz の 112 B はスレッド数でも消えない**

DFMA 側だけの reg / spill。**TC 側はどの行でも production のまま動かない。**
spill は cumulative stack size。

#### p=127 xz（`tendency_fused_p127_xz_kernel`、ブロックタイル 128×64）

| `TM`×`TN` | ワープ格子 | スレッド | DFMA reg | DFMA spill |
|---|---|---:|---:|---:|
| **2×4（production）** | 8×2 = 16 warp | **512** | 128 | **112 B** |
| **2×8** | 8×1 = 8 warp | **256** | 255 | **48 B** ← 最小 |
| 1×4 | 16×2 = 32 warp | 1024 | 64 | 80 B |
| 1×8 | 16×1 = 16 warp | 512 | 128 | 96 B |
| 4×2 | 4×4 = 16 warp | 512 | 128 | 224 B |
| 2×2 | 8×4 = 32 warp | 1024 | 64 | 336 B |
| 4×4 | 4×2 = 8 warp | 256 | 255 | **464 B** |
| 8×4 | 2×2 = 4 warp | 128 | 255 | 1552 B |
| 4×8 | 4×1 = 4 warp | 128 | 255 | 2760 B |

（`TM`=1, `TN`=2 は 2048 スレッドになりブロック上限 1024 を超えるので除外。
コンパイルは通るが起動できない。）

**答え: 消せない。** 9 通りのスレッド割り当てのうち **spill 0 に届くものは
1 つも無い**。最小は 2×8 の **48 B** で、production の 112 B の 43% である。

**機構（静的な量だけで言えること）。** スレッド数を半分にすると、
1 スレッドが持つアキュムレータ（`2*TM*TN`）と prefetch レジスタ
（`NSTAGE = PANEL/THREADS` × 3 本）が**ちょうど 2 倍**になる。一方
レジスタ上限は 128 → 256 と 2 倍になるはずだが **255 で頭打ちになる**うえ、
アドレス計算などスレッド数に比例しない固定分は半分にならない。
**需要はほぼ倍、供給は倍未満**なので、この取引に得は無い。実際
128 スレッドまで落とすと spill は 1552〜2760 B と桁で増える。
2×8 と 4×4 は**同じ 256 スレッド・同じアキュムレータ本数 32 本**なのに
48 B と 464 B に分かれるので、残った 48 B は容量の問題ではなく
**ptxas が特定のワープ格子でだけ良い割り付けを見つけている**ことによる。
**なぜ 2×8 だけが良いのかは測れていない**（`ncu` を当てていない）。

**この 48 B は §10.3 のアブレーションが到達した 48 B と同じ値である。**
`P127_XZ_ABLATE_AZ=8` は `az[16]` を `az[8]` に縮めて 112 B → 48 B に
したが **数値として不正**（max abs 6.42e+00）だった。**2×8 は同じ 48 B に
数値を保ったまま到達する**（§11.5 で iso 形とビット一致）。

#### p=127 y（`tendency_fused_p127_y_kernel`）

| 設定 | ワープ格子 | スレッド | blocks/SM | DFMA reg | DFMA spill |
|---|---|---:|---:|---:|---:|
| **4×2（production）** | 4×4 = 16 warp | **512** | 2 | 64 | **104 B** |
| **8×4** | 2×2 = 4 warp | **128** | 2 | 253 | **0** |
| 8×2 | 2×4 = 8 warp | 256 | 2 | 128 | 64 B |
| 4×4 | 4×2 = 8 warp | 256 | 2 | 128 | 72 B |
| 8×2 ＋ `BPSM_DFMA=1` | 2×4 = 8 warp | 256 | 1 | 180 | **0** |
| 8×4 ＋ `BPSM_DFMA=4` | 2×2 = 4 warp | 128 | 4 | 128 | 1320 B |

**この kernel は spill 0 に届く。** しかも **8×4 は `minBlocks=2` を保ったまま
0 になる**（253 レジスタ）。§1 の `minBlocks` 掃引では 0 にするのに
blocks/SM を 2 → 1 に落とすしかなかったので、**スレッド数の道は
「占有率の段を払わずに spill を消す」という、`minBlocks` の道には無い選択肢を
持っている**。

### 11.7 2 列方針（§8）への含意 —— **決定はしない。材料だけ**

§8 は「A_iso と A_opt の 2 列を載せる。`AGENTS.md` の定義は変えない」を
採用し、§8.2 に「**A_opt は代金を全部は除いていない**」という但し書きを
置いた。本節が用意した材料は 4 つである。

1. **但し書きの根拠だった 112 B は、`minBlocks` でも**スレッド数でも**

### 12.1 何が動くのか —— 内側ループの数え上げ（測る前に）

`tendency_fused_p63_xz_kernel` の k ループの本体は、1 スレッドについて

```
av[2], avz[2]          : 4 本の shared ロード（m 側、2 つのアキュムレータ集合）
bv[TN], bvz[TN]        : 2*TN 本の shared ロード（n 側）
mma                    : 2 * (2 * TN) 回
```

である。ブロックタイル（64×64）も shared パネルも grid も変わらないので、
ワープ形を変えても**ブロック全体が出す mma の総数は不変**であるのに対し、
**shared ロードの総数は `(2+TN)/(2*TN)` に比例して動く**:

| `P63_WN` | ワープ格子 | スレッド | `TN` | ロード ÷ mma | ブロック 1 回の k ステップの shared ロード |
|---:|---|---:|---:|---:|---:|
| 8 | 4×8 | 1024 | 1 | **1.50** | 6144（×1.50） |
| **4（production）** | 4×4 | **512** | 2 | **1.00** | 4096（基準） |
| 2 | 4×2 | 256 | 4 | **0.75** | 3072（×0.75） |

一般形は 2 次元レジスタブロッキングの教科書どおりで、
**`TM`×`TN` タイルのロード ÷ mma は `(TM+TN)/(TM*TN)`**。
per-thread タイルを広げるほど下がり、代金はレジスタ（アキュムレータ本数は
`TM*TN` に比例）である。**スレッド数はこの取引の従属変数にすぎない** ——
ブロックタイルが固定なので、per-thread タイルを 2 倍にすればスレッド数は半分になる。

この数え上げは `ncu` で検証できる（§12.4）。**実測の
`smsp__inst_executed_op_shared_ld.sum` は 8.389e6 / 6.291e6 / 1.258e7 で、
比は 1.00 / 0.750 / 1.500 と表の予測に完全に一致する。**

### 12.5 §5 の枠組みへの訂正 —— 代金は 2 項ある

§5 は iso 分母が上乗せしている代金を **「TC 向けのレジスタ予算を着せられた
ぶんの spill」** だと書き、§5.3 は「p=15 / p=31 では spill が無いので
**共有は無料**」と結論した。**本節の測定はこの結論を否定する。**
共有されているのは `__launch_bounds__` の**第 2 引数だけではなく第 1 引数
（スレッド数）も**であり、第 1 引数は spill を経由せずに
**ロード ÷ mma** を通じて直接時間を決める。

| 軸 | 何を共有させられているか | 賞金 | 代金 | spill が 0 でも効くか |
|---|---|---|---|---|
| §5 の軸 | `minBlocks`（レジスタ予算） | spill 命令の実行回数（§10.1） | 占有率 1 段 | **効かない** |
| **本節の軸** | **スレッド数（ワープ形）** | **shared ロード ÷ mma** | **レジスタ本数（＝ワープ数）** | **効く** |

2 つの軸は独立ではない（どちらもレジスタを取り合う）が、**符号を決める量が
違う**。§5 の軸では「spill 0 なら賞金 0」であるのに対し、本節の軸では
**spill が両側とも 0 でも賞金が出る**。p=63 xz と p=31 がその実例である。

### 13.1 §12 の式に足りない項 —— DFMA エミュレーションの shuffle は TM/TN 非対称

`mma_m8n8k4_f64<false>`（`cuda_dg_kernels_tc.cu` 冒頭）は 1 回の mma を

```
for k in 0..3:  ak  = shfl(a, ...)          # 1 本
                bk0 = shfl(b, ...)          # 2 本（アキュムレータ対 c0/c1 に別々の列が要る）
                bk1 = shfl(b, ...)
                acc0 = fma(ak, bk0, acc0);  acc1 = fma(ak, bk1, acc1)
```

で置き換える。`ak` は内側の `bb` ループ全体で共有できるが、`bk0/bk1` は
`bb` ごとに要る。したがって **1 k ステップあたりの SHFL は `8·TM + 16·TN`**
（`av`/`avz` と `bv`/`bvz` の 2 組ぶんを含む）であり、mma 数 `2·TM·TN` で割ると

> **`SHFL/mma = 8/TM + 4/TN`** —— **`TM` を増やすことは `TN` を増やすことの 2 倍の価値がある。**

これに対し §12 の shared ロードは `LDS/mma = (TM+TN)/(TM·TN)` で**対称**である。
2 つの式は `TM` と `TN` を入れ替えて等しいか否かで分かれ、そこが実測の分かれ目になる。

SASS（p=127 xz、DFMA インスタンス、1 スレッドあたり。二重バッファの
`buf ^= 1` があるので ptxas は `kk` ループを 2 倍展開し、本体に 8 ks ぶんが入る）:

| 形 | スレッド | `LDS/mma`＝`(TM+TN)/(TM·TN)` | `SHFL/mma`＝`8/TM+4/TN` | DFMA | SHFL | 予測 SHFL ＝ 8·(8TM+16TN) |
|---|---:|---:|---:|---:|---:|---:|
| **2×4（production）** | 512 | **0.750** | **5.00** | 624 | 640 | 640 ✓ |
| 2×8 | 256 | **0.625** | **4.50** | 1248 | 1152 | 1152 ✓ |
| 4×4 | 256 | **0.500** | **3.00** | 1248 | 768 | 768 ✓ |
| **8×2** | 256 | **0.625** | **3.00** | 1248 | 768 | 768 ✓ |
| 16×1 | 256 | **1.0625** | **4.50** | 1248 | 1152 | 1152 ✓ |

**予測は 5 形とも SASS と完全に一致する。** そして `2×8` と `8×2` は
**ロード比が同一（0.625）でスレッド数もレジスタ数も同一なのに SHFL が 1.5 倍違う**
—— これが §12 の枠組みでは区別できず、実測では 7.6 ポイントの差になる（§13.4）。

`ncu` の `smsp__inst_executed_op_shared_ld.sum` も予測どおりである
（production を 1 として **0.833 / 0.667 / 0.833 / 1.417**、予測
0.625/0.75 = 0.833、0.5/0.75 = 0.667、0.625/0.75 = 0.833、1.0625/0.75 = 1.417）。

> **この項は `FUSED_TC` には存在しない。** `mma.sync.m8n8k4` は shuffle を
> ハードウェアで行うので `SHFL/mma = 0` である。§12.6 が「形を変えても TC は
> 1 版も速くならない」と測った理由の半分はここにある：TC 側で動く項は
> `LDS/mma` の 1 つしか無く、そしてその屋根（L1/TEX 63.0%）に触っていない。

### 13.2 p=127 xz の spill は「何が」溢れているのか（SASS、**§11.8(a) を閉じる**）

§11.2 は「2×8 と 4×4 は同じ 256 スレッド・同じアキュムレータ本数（`NACC` =
2·TM·TN = 32）なのに 48 B と 464 B に分かれる」と書き、機構を未測定にした。
DFMA インスタンスの SASS を読み、**各 `STL` の値を誰が作り、各 `LDL` の値を
誰が使うか**を後方／前方走査で帰属した（スロット幅とオフセットも数えた）:

| 形 | spill | スロット数 | 8 B（double） | 4 B（整数） | `LDG` 由来（プリフェッチ `pq/pu/pd`） | `DFMA` 由来（アキュムレータ `ax/az`） | `LEA`/`IMAD` 由来（アドレス） |
|---|---:|---:|---:|---:|---:|---:|---:|
| 2×4（production） | 112 B | 14 | 12 | 2 | **24** | 1 | 1 |
| **2×8** | **48 B** | **12** | **0** | **12** | **1** | **0** | **11** |
| **4×4** | **464 B** | 66 | 50 | 16 | **48** | **26** | 16 |
| 8×2 | 120 B | — | — | — | 13 | 0 | 15 |
| 16×1 | **32 B** | — | — | — | 4 | 0 | 3 |
| 4×2 | 224 B | 31 | — | — | 24 | 13 | 3 |
| 1×8 | 96 B | 12 | — | — | 23 | 0 | 0 |
| 1×4 | 80 B | 11 | — | — | 12 | 2 | 2 |
| 8×4 | 1552 B | 207 | — | — | 96 | **224** | 1 |
| 4×8 | 2760 B | 291 | — | — | 96 | **240** | 1 |

**答え（3 つとも測定値）:**

1. **`2×8` の 48 B には浮動小数が 1 バイトも入っていない。** 12 個の
   **4 バイト**スロット（`0x0`–`0x2c`、ストライド 4）だけで、11 個は `LEA` が
   作ったアドレス値である。§10.3 の `P127_XZ_ABLATE_AZ=8`（**数値不正**）が
   到達した「48 B」と数値が同じなのは**偶然**であり、中身は別物である
   （あちらは FP データが残っている）。
2. **`4×4` の 464 B は本物の FP データである。** 50 個の 8 B スロット
   （`0x0`–`0x188`）のうち **48 個はプリフェッチレジスタ**
   （`LDG.E.64.CONSTANT` が作り、`P127_XZ_STORE` の `DMUL` / `STS.64` が
   使う ＝ 二重バッファの `pq/pu/pd`）、**26 個はアキュムレータ**
   （`DFMA` が作り `DFMA` が使う ＝ `ax`/`az`）である。残る 16 個は
   `0x190`–`0x1cc` の 4 B スロットで、`2×8` と同じアドレス spill である。
3. **判別しているのは容量ではなく `TM` である。** アキュムレータの spill
   （`DFMA` 由来）は **`TM` ≤ 2 の形では 0〜2 個、`TM` ≥ 4 で立ち上がる**
   （4×2 で 13、4×4 で 26、8×4 で 224、4×8 で 240）。`NACC` はどの
   256 スレッド形でも 32 で同じであり、内側で生きるオペランドは
   `2(TM+TN)` doubles ＝ **2×8 のほうが多い**（20 対 16）。
   **需要の総量では 2×8 のほうが厳しいのに、溢れるのは 4×4 のほうである。**

**なぜ `TM` なのか（SASS のライブレンジで測った）。** §13.1 のとおり
`ak` は内側 `bb` ループ全体で共有されるので、ptxas は **1 k ステップぶんの
a 側 shuffle 結果を巻き上げて `bb` ループの間じゅう保持する**。
その集合は `4 (k) × 2 (av, avz) × TM` doubles ＝ **16·TM レジスタ**である。
post-allocation SASS のライブレンジを数えると:

| 量（DFMA インスタンス） | 2×8 | 4×4 |
|---|---:|---:|
| 予測 a 側 shuffle 常駐 ＝ 16·TM [reg] | **32** | **64** |
| 実測ピーク時の SHFL 由来ライブレジスタ | **72** | **106**（＋34） |
| ピーク総ライブレジスタ | 314 | 311 |
| SHFL 定義の**ライブレンジ中央値** [命令] | **14** | **169**（12 倍） |
| SHFL 定義のライブレンジ総和 | 5.24e4 | **9.87e4**（1.88 倍） |
| 消費者数ヒストグラムの山 | 16–17（＝2·TN ✓） | 8–9（＝2·TN ✓） |

**予測差 32 レジスタに対し実測差 34 レジスタ。** `4×4` は `2×8` より
**33% 少ない shuffle しか発行しないのに、その結果を集計で 1.88 倍長く保持する**。
その 32 レジスタぶんが、プリフェッチレジスタと 26 本のアキュムレータを
local メモリに押し出している。**§11.8 の「容量ではなく ptxas の割り付け」
という記述は正しいが不完全で、割り付けを決めているのは
「a 側 shuffle 常駐集合 ＝ 16·TM レジスタ」という形の関数である。**

1. **`8×2` が −13.5% で単独最速。** `2×8` と**ロード比・スレッド数・レジスタ数が

   同時適用の実測は **−26.53%**（差 0.05 ポイント）。§12.3 の p=63 は
   0.74 ポイント sub-additive だったが、p=127 では加法性が成り立つ。

**分離の答え。**

- **`8×2` 対 `2×8`（L1/TEX の仕事が測定上同一）**: shared ld 命令も
  wavefront も同値なのに、**総命令数が 3.355e8 → 2.884e8（−14.0%）** で
  時間が −8.11%。**動いているのは shuffle だけである**（SASS で 1152 → 768、−33%）。
  したがって **`SHFL/mma` の項は実在し、単独で 8 ポイントを動かす。**
- **`8×2` 対 `4×4`（SASS の DFMA と SHFL が完全に同一）**: 違いは
  **local セクタ 1.343e7/8.323e6 対 5.662e7/5.348e7（spill トラフィック 4.2 倍 / 6.4 倍）**
  とロード比（0.625 対 0.500）。ロード比は `4×4` のほうが**有利**なのに
  7.77% 負けるので、**差の全部と、ロード比の不利ぶんの上乗せが spill の代金である。**
- **したがって §12.8 が「形がスピルより重い」と読んだ `4×4` 対 `2×8` の
  0.40% は、2 つの大きな逆向きの量の差し引きである** ——
  ロード比 0.500 対 0.625 の賞金と、spill 464 B 対 48 B の代金。
  `8×2` はその両方で有利な側を取っており、それが −13.5% の正体である。
- **DRAM read も global セクタも 5 版で同値**なので、どの比較でも
  「触るデータ量が変わっていない」という `recipes.md` の要件を満たす。

**代金の数値（線形回帰、5 点）。** `t = a·(LDS/mma) + b·(SHFL/mma) + c·spill[B] + const`
を上の 5 点に当てると **a ≈ 62 µs/単位、b ≈ 90 µs/単位、c ≈ 0.33 µs/B** で、
5 点とも 1% 以内に乗る。独立の裏取りとして、**同じ形のまま spill だけ減らす**
アブレーション `4×4 ＋ AZ=8`（464 B → 216 B、**数値不正**）が
1366.97 → 1286.42、すなわち **0.325 µs/B** —— 回帰の c と 2% 以内で一致する。

（`2×8 ＋ AZ=16` は 48 B → 8 B で −55.79 µs ＝ 1.395 µs/B と大きく外れる。
`AZ=16` は `az[]` の**本数を半分にする**ので、spill だけでなく生きている
アキュムレータ本数そのものを動かしており、§10.3 が `AZ=8` について確認した
「mma・shared・global が 1 本も減らない」条件をこの形では満たしていない。
**この 1 点は c の推定に使えない。**）

### 13.7 ロード比と時間の関数形（**§12.10(e) への回答**）

§12.10(e) は「5 点とも単調だが係数が次数ごとに違う。L1/TEX 対ピークの初期値で
説明できるかは測っていない」と書いた。**本節の答えは 2 つある。**

**(1) 係数が違って見えた理由の一部は、1 変数で書いていたことである。**
DFMA 側で形が動かす量は 3 つあり、§12 はそのうち 1 つしか見ていなかった:

| 項 | 式 | 何にぶつかるか | `FUSED_TC` では |
|---|---|---|---|
| shared オペランドロード | `(TM+TN)/(TM·TN)`（**対称**） | L1/TEX（`mio_throttle`） | 同じだけ存在するが屋根に届かない（L1/TEX 63%） |
| **shuffle** | **`8/TM + 4/TN`（非対称）** | **命令発行（総命令数）** | **存在しない**（`mma.sync` がハードウェアで行う） |
| spill トラフィック | ptxas の割り付け（主因は `16·TM` レジスタの a 側 shuffle 常駐、§13.2） | L1/TEX（local セクタ） | 多くの次数で 0 |

**(2) 屋根までの距離で正規化するという §12.10(e) の仮説は、測ると支持される。**
p=511 で L1/TEX 対ピークが 79% から 97% まで動く 5 点を同一 job で採ったところ、
**L1/TEX が 85% 未満の領域ではロード比に対してほぼ線形、95% を超えると
急に超線形になる**（§13.8 の表）:

| p=511 の版 | `LDS/mma` | **L1/TEX [%]** | `mio_throttle` | 対 iso |
|---|---:|---:|---:|---:|
| `iso` 4×4 | 0.500 | **79.09** | 3.23 | —— |
| `q82` 8×2 | 0.625 | **82.12** | 4.24 | +8.60% |
| `q28` 2×8 | 0.625 | **82.41** | 1.96 | +35.63% |
| `q42` 4×2 | 0.750 | **95.09** | **17.64** | +45.03% |
| `q22` 2×2 | 1.000 | **96.99** | **32.91** | +173.75% |

3 項の線形式（iso→`q82` から a、`q82`→`q28` から b を決める）で `q42` を予測すると
+35% に対し実測 +45%、`q22` は予測 +88% に対し実測 +174% で、
**どちらも L1/TEX が 95% に張り付いた側で実測のほうが大きく外れる。**
同じことは次数間の比較にも当てはまる —— ロード比 1.5 倍という同じ操作が
p=255 では +21.22%（§12.8）、p=511 では +51.52% で、
その 4×4 の L1/TEX は p=511 が 79.09%、p=255 側は §12 で測っていない。

**限界。** 本節が示せたのは「p=127 xz の 5 点は 3 項の線形式で 1% 以内に乗る」
「p=511 では 95% を超えると超線形になる」の 2 つだけで、
**a / b / c が p=31 / 63 / 255 で同じ値かは測っていない**
（各次数で `SHFL/mma` と `LDS/mma` が独立に動く 5 点以上を同一 job で
採る必要がある）。p=63 の既存 3 点は `P63_WN` が `TN` 側だけのノブで
2 項が比例してしまうので使えない（§13.11）。

### 13.8 p=511 のワープ形（**§12.10(b) を部分的に閉じる**）

#### ノブは存在する

p=511 は `tendency_p255_kernel<DIR, NQ=512, UseTc, FuseFace24>` を
`launch_tendency_dir_p255_nq<UseTc, 512>` から起動する（`p511_gap_study.md` §15）。
形のノブは **p=255 と同じ `TM255_DFMA` / `TN255_DFMA`** であり、
`TH255_SEL = 32·(64/(8·TM))·(64/(8·TN))` がスレッド数を決める。
ptxas の出力も **Nq に依存しない**（`Li256E` と `Li512E` のインスタンスで
reg / spill / smem が 1 バイトも違わない）—— ソースのコメントが主張している
「Nq は grid と縮約チャンク数にしか入らない」がここで確認できる。

#### 形の下限は 128 スレッドである（**新規、数値検証で発見**）

**`TH255_SEL < 128` の形は数値として不正になる。** 点変化係数で
owned `dqdt` 全点を比べた結果（§13.10）:

| 形 | スレッド | `LDS/mma` | `SHFL/mma` | spill（`Li256E`） | p=255 max abs | p=511 max abs |
|---|---:|---:|---:|---:|---:|---:|
| 4×4（production） | 128 | 0.500 | 3.00 | 56–80 B | 3.55e-15 | 3.55e-15 |
| 8×2 | 128 | 0.625 | 3.00 | 64 B | 3.55e-15 | 3.55e-15 |
| 2×8 | 128 | 0.625 | 4.50 | 96 B | 3.55e-15 | 3.55e-15 |
| 4×2 | 256 | 0.750 | 4.00 | 96 B | 3.55e-15 | 3.55e-15 |
| 2×4 | 256 | 0.750 | 5.00 | 80–152 B | 3.55e-15 | 3.55e-15 |

**原因は測って特定した。** `tendency_p255_kernel` の `DIR == 0` の分岐
（`p255_epilogue` の直前）は、面 2 と面 4 の値を `sA[0]` に段取りするのに
**スレッド数がちょうど 128 であることを前提にしたハードコード**を使っている:

```
const int j = m0 + (tid & 63);
const int fidx = efo + ((tid < 64) ? NQ2 : 3 * NQ2) + fp;
sA[0][tid] = flux_bnd[fidx];        // FuseFace24 のときは面 flux をその場で作る
```

`tid` 0–63 が面 2 を、64–127 が面 4 を埋める。**スレッドが 128 未満だと
面 4 の側が一度も書かれない**（64 スレッドなら半分、32 スレッドなら 4 分の 3 が
未初期化の shared のまま `p255_epilogue` に渡る）。128 以上なら 0–127 が
正しく埋め、余ったスレッドの書き込みは使われない領域に落ちるので無害である。
**これは §11.1 が引いた「同じアルゴリズムの別のスレッド割り当て」の境界を
ノブ側が守れていない例であり、p=255 / 511 の形掃引の構造的な下限である。**

**帰結: p=255 / 511 では production の `4×4` が既にロード比の最小である。**
128 スレッド以上という制約は `(8/TM)·(8/TN)·32 ≥ 128`、すなわち
`TM·TN ≤ 16` であり、その範囲で `(TM+TN)/(TM·TN)` を最小にするのは
`TM = TN = 4` の **0.500** である。**下げる余地が構造的に無い。**
`SHFL/mma` も `4×4` の 3.00 が最小である（`8×2` が同値で並ぶだけ）。
**この 2 次数だけは、production の形が 3 項すべてで最適な側にいる。**

#### p=767 / p=1023 は測れていない（構造的な理由）

**「測っていない」のではなく、現在のツリーでは起動できない。**

- `mod_advect3d_eq.f90` は `CUDAFORTRAN_FUSED_DFMA` / `FUSED_TC` を
  **`Nq = 8, 16, 32, 64, 128, 256, 512` に限って**受け付け、それ以外は
  `error stop` する。`namelists/` にも `perf_p767_fused_*` / `perf_p1023_fused_*` は
  無い（この 2 次数は GEMM 系 5 経路の namelist しか持たない）。
- C++ 側の `launch_tendency_dir_p255_impl` は `nq == 512` とそれ以外
  （＝ `NQ255 = 256`）の **2 つのインスタンスしか**実体化していない。
- **p=1023 は 32 bit ノード添字で表せない。** `tendency_p255_kernel` の
  `Escale + node + 2*npoint` は最大 `3·Np = 3·1024³ = 3.22e9` に届き、
  `int` の 2.147e9 を超える。ソース中のコメントもこの点を明記しており、
  64 bit オフセットは GEMM 経路にしか入っていない（`p1023_gap_study.md` §1）。
  **p=1023 のワープ形は、この kernel を 64 bit 添字に書き直さない限り測れない。**
- **p=767（Nq = 768）は原理的には届く**（`3·Np = 1.36e9 < 2.15e9`、
  grid は `(768/64)·(768²/64)·Ne = 110 592` ブロック）。必要なのは
  `launch_tendency_dir_p255_impl` に `nq == 768` の分岐を足し、Fortran 側の
  ゲートを緩めることだけで、**ワープ形のノブはそのまま効く**。
  **本節ではその変更を行っていない**（production の共有ソースに手を入れる
  変更になり、本節の「ソース変更なし」という妥当性の境界を越えるため）。
  **したがって p=767 は「測れない」ではなく「測っていない」である。**
- なお §13.8 の数え上げから、p=767 が測れたとしても**形を動かして速くなる
  可能性は低い**：`TM255/TN255` は Nq に依存しないので 128 スレッド下限も
  ロード比の最小 0.500 も p=255 / 511 と同じであり、production の `4×4` が
  そこにいる。**これは推測であって測定値ではない。**

### 13.9 spill 100% 除去点（**§11.8(f) / §10.4 への回答 —— 部分的**）

### 13.12 本節でも測れていないこと（推測で埋めない）

- **p=767 のワープ形。** ノブは効くが、`launch_tendency_dir_p255_impl` に
  `nq == 768` のインスタンスが無く、Fortran 側のゲートも `Nq ≤ 512` である。
  **production の共有ソースを変える必要があるので本節では行っていない。**
  「測れない」のではなく「測っていない」（§13.8）。
- **p=1023 のワープ形は測れない。** `tendency_p255_kernel` の `Escale` 添字が
  32 bit で、`3·Np = 3.22e9` が `int` に入らない（§13.8）。64 bit 化は
  この kernel の書き直しであり、§11.1 の妥当性の境界の外である。
- **p=15 のワープ形。** §12.8 のとおりノブが構造的に無い。変わらず未測定。
- **`TM > TN` 側の p=31 / p=255。** `SHFL/mma = 8/TM + 4/TN` が非対称である
  以上、`TM > TN` の側は独立に測る価値がある（p=127 で 7.6 ポイント動いた）。
  §12.8 の p=31 は `2×2` / `2×4` / `4×4` という `TM ≤ TN` 側しか見ていない。
  **p=31 の `4×2` / `8×2` は本節でも測っていない。**
  p=255 の `8×2` は数値検証だけ通してあり（§13.10）、**時間を測っていない**
  （p=511 では `q82` として測ってあり +8.60%）。
  p=63 は `P63_WN` が `TN` 側だけのノブで `TM` を動かせないので、
  **この次数では 2 項を分離できない。**
- **3 項モデルの係数の次数依存。** `a ≈ 62 / b ≈ 90 / c ≈ 0.33` は
  **p=127 xz の 5 点だけ**の当てはめである。p=31 / 63 / 255 / 511 で
  同じ 3 係数を出すには、各次数で `SHFL/mma` と `LDS/mma` が独立に動く
  5 点以上を同一 job で採る必要があり、**本節ではやっていない**。
  p=511 は 5 点あるが L1/TEX が 79 → 97% と動くので線形式が当てはまらない（§13.7）。
- **`SHFL/mma` の項が L1/TEX ではなく発行に当たっている、という帰属**は
  「shared ld 命令と wavefront が同値なのに総命令数が −14.0% で時間が −8.11%」
  という**差分による帰属**であって、shuffle だけを消したアブレーションは
  作っていない（消すと mma の意味が変わるので作れない）。
- **`FUSED_TC` での `DB=0`。** §13.9 は DFMA 側で二重バッファが 3 形とも
  損であることを測ったが、**TC 側は 1 点も測っていない。** TC 側は
  プリフェッチレジスタが spill しないので前提が違い、`AGENTS.md` の
  「TC と DFMA を内積以外で乖離させない」制約からも `DB` は共有される。
  **production 候補として測る価値はある。**
- **`8×2 ＋ DB=0 ＋ y 8×4`** の組み合わせ。`x82db0`（−16.46%）と
  `y84`（−13.00%）は別々に測っただけで、**同時適用は測っていない。**
  §13.4 の加法性から −29% 前後が期待されるが、**書けない。**
- **`FUSED`（CC 融合、production 経路）への横展開**は §12.10 と同じく
  1 点も測っていない。`cuda_dg_kernels_fused.cu` は自然順パネルと長さ `Nq` の
  内積という別の実装様式で per-thread タイルの概念がそのままは無い。
  **`FUSED` は production 経路なので、ここは開いた宿題のままである。**
