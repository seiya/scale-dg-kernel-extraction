# DG カーネル最適化ループ

`AGENTS.md` の数値コントラクトと `CLAUDE.md` の「速いだけでなく、なぜ速いか
を測って公開する」という目的が、この手順の前提である。両方に従うこと。

## 0. 対象の確定

引数は `p=<次数> [path=<DqdtKernel_Type>]`（例: `p=63 path=CUDAFORTRAN_FUSED_TC`）。

- path 未指定なら `reports/README.md` の「現時点の結論」で**その次数の最速パス**を
  対象にする。最速でないパスを最適化する場合は、それが**最速を抜きうる**根拠か、
  モデルを埋めるための測定であることを最初に述べる。
- `CUDAFORTRAN_FUSED` は CUDA core 向け融合（`cuda_dg_kernels_fused.cu` /
  `cuda_dg_kernels_fused_highp.cu`）。指定したらそのカーネルだけを起動する。
  `FUSED_DFMA` や `FUSED_TC` で代行してはならない。未実装次数なら error stop。
  独立に最速レースしない。`FUSED_TC` 効果の対照はこれであり、iso-schedule
  の DFMA ではない。
- `CUDAFORTRAN_FUSED_DFMA` と `CUDAFORTRAN_FUSED_TC` は同一 C++ ソース
  （`cuda_dg_kernels_tc.cu`、`UseTc` だけが違う）。DFMA を触る依頼は MMA
  命令の有無だけを測ることが目的であり、最速抜きを目標にしない。変更は
  必ず両方に同時に入る。TC の fragment レイアウトを `FUSED` に持ち込まない。
- `CUDAFORTRAN_GEMM_CUTE` は `GEMM_FUSED` の GEMM 本体（未融合）の対照である。
  独立に最速化しない。volume GEMM のタイルや `Nq<=64` の x ライブラリ分岐を
  変えるなら `GEMM_FUSED` と同じドライバ経由で変える。
- 対象 conf を特定する: 計測用 `conf_perf_p<N>[_tag].conf`、ncu 用 `*_ncu.conf`
  （`nstep` が短い）、検証用 `input_p<N>_val*.conf`。無ければ既存に倣って作る。
  **`NeX/NeY/NeZ`, `PolyOrder`, `dt`, `nstep` は比較の間ずっと固定**。

## 1. 既知の棚卸し（実装を触る前に必ず）

読む順:

1. `reports/README.md` — 索引と現時点の結論。ここが最も陳腐化しやすいので、
   本文の日付と各 gap study の最新節を突き合わせる。
2. 対象次数の gap study (`reports/p<N>_gap_study.md`) を**末尾の節から**。
   採用された変更と、**不採用の候補とその理由**を両方拾う。
3. **他の次数の gap study と横断レポート**（`overall_summary_report.md`,
   `tc_paper_survey_*.md`, `sm90_mma_shape_survey.md`, `tma_survey.md` …）。
   この repo では効いた知見はほぼ必ず次数をまたぐ（swizzle、末尾バリアの
   前送り、D1D のレジスタ常駐、パネルの outer-fast、half-warp `d mod 16`
   のバンク則、チャンクループ除去 …）。**他 p で効いて対象 p に未適用の
   ものが候補の第一の供給源**である。同じく、他 p で失敗した理由が
   対象 p では成り立たないなら、それも候補になる。
4. 実装本体 (`mod_cuda_dg_kernels.cuf` ほか) の該当カーネル。

棚卸しの出力は**「すでに試して落ちたもの」の一覧**である。これを候補表に
持ち込み、同じ道を二度歩かない。

## 2. ベースラインの再測定

- login node で直接実行してよい（`ncu`/`nsys` だけが sbatch 必須）。
- 同一 conf で **3〜5 回**走らせ、中央値を採る。`Main per step:` と device 時間
  （`Cal_tend:`）を分けて記録。`WarmupStep` により先頭ステップは計時外。
- ビルドし直したら測り直す。`make clean` を挟むモード切替に注意。
- ここで得た数値が、以降すべての比較の分母。commit hash と一緒に記録する。

## 3. 律速の確定（推測で候補を作らない）

`ncu` を sbatch で当てる。詳細なコマンドは `references/recipes.md`。

- 最低限: `--set full`（`--set basic` は Memory Workload Analysis を採らないので
  バンクコンフリクトが見えない）+ stall reason + shared/global wavefront 分離。
- 見るもの: 支配的な stall（`long_scoreboard` / `mio_throttle` / `barrier` /
  `lg_throttle` / `wait`）、L1/TEX と DRAM の対ピーク %、占有率とその決定要因
  （レジスタか shared か）、shared のバンクコンフリクト（ld/st 別）、
  命令数、sector/request。
- **必要なら SASS を読む**（`cuobjdump -sass`）。`LDS.64` / `STS.128` のマージ
  など、ソースからは見えない事実がしばしば結論を変える。
- 出力は 1 文で書けること: 「このカーネルは X が Y% で律速している」。
  書けないなら、書けるようになるまでメトリクスを足す。
- **`ncu` の時間で採否を決めてはならない。** `ncu` はクロックを固定するので、
  SM クロックが下がる分だけ **global メモリのレイテンシがサイクル数で見て短くなる**。
  その結果 `ncu` は **shared・レジスタ・命令の仕事を高く、global の待ちを安く**
  見積もる。shared を削る変更は過大評価され、shared を増やして global の待ちを
  隠す変更は過小評価され、DRAM レイテンシ律速のカーネルは 1 stage に占める割合まで
  過小に出る。`ncu` は**機構の同定**（どの stall が動いたか、コンフリクトが消えたか、
  DRAM が実際に何バイト動かしたか）に使い、**採否は手順 5 の実時間 A/B で決める**。
  **`ncu` ジョブをまたいだ比較も信用しない**（同一ジョブ内に変種を並べる）。
  根拠は `reports/p63_gap_study.md` §19.10 / §20.3 / §20.6 の 6 例で、
  5 例が一方向・1 例が逆方向であることが「一定のオフセット」ではなく
  この機構であることを示している。

## 4. 候補の列挙と優先度付け

候補表を作る。各行に:

| 候補 | 出所（他 p のレポート / プロファイル） | 効くと考える理由 | 期待効果の上限 | 上限を測るアブレーション | 数値コントラクト適合 |

- **期待効果の上限を先に見積もる。** 可能ならアブレーション（その仕事を
  丸ごと消した不正な版）を先に測って**賞金の天井**を出す。天井が測定誤差
  以下なら実装せずに落とす — それ自体が公開すべき結果である。
- `AGENTS.md` の契約を破る候補（代表スカラー特殊化など）は
  **「範囲外」として理由付きで表に残す**。実装はしない。
- 順序は「賞金の天井 ÷ 実装コスト」の降順。ただし他 p 由来の移植は
  実装が安いので先に片付く場合が多い。

## 5. 1 候補ずつ回す

候補ごとに、**変更は 1 つだけ**（2 つ混ぜたら効果は帰属できない）:

1. 実装する。テンプレート生成物 (`mod_dg_optr_kernel_opt1.f90`) を直接編集
   しない — `.erb` を直して `make`。
2. ビルド: `make clean && make CUDA=1 GPUFLAGS=-gpu=cc100`。
3. **数値検証**（省略禁止）: `SCALE_DG_VARYING_COEFF=1` で
   `SCALE_DG_DUMP_DQDT` を落とし、`_SPLIT` / `OPENACC_ASIS` などの参照実装と
   `dqdt(:,1:Ne)` を全点比較。ビット一致か、丸め誤差レベルであること。
   p=255 は `Ne=1` と `Ne>1` の両方。
4. 計測: 手順 2 と同じ条件・回数で中央値。**採否を決める計測は、Slurm で
   占有した GPU 上で変種を交互に 10〜12 回**走らせて中央値を採る（ログインノードの
   GPU は共有で、レンジが 0.5% ほど動く）。**レンジが重なる差は「差が無い」**と書く。
5. 判定と記録:
   - 速くなった → 採用。作業ノートに「変更・効果・**なぜ効いたか（測定で）**」。
     効いた理由が不明なら ncu を当て直す。理由不明の採用は defect。
   - 遅くなった / 変わらない → 元に戻し、**理由を測って**候補表に結果を書く。
     負の結果もレポートに載る一級の成果。
6. 効いた変更は律速を動かす。**手順 3 に戻ってプロファイルを取り直す**。

## 6. 候補の枯渇＝終了条件

終了してよいのは次のときだけ:

- 残る候補すべてについて、アブレーションで**賞金の天井が測定誤差以下**である
  ことを示した、または
- 残る候補が数値コントラクト違反（範囲外）である。

**「効果が小さそうだから」「最速パスは変わらないから」は終了理由にならない**
（`CLAUDE.md`）。逆に、天井を測って小さいと示せたなら堂々と終了する。

## 7. レポート更新とコミット

- 対象次数の gap study に節を追加。**過去の表は書き換えない**。結論が覆った
  箇所には訂正注記を足す。節には commit、Slurm job、input file、GPU を書く。
- `reports/README.md` の該当行と「現時点の結論」を更新。最速パスが変わった
  なら**それが README の最重要更新**。新規レポートを作ったら索引に行を追加。
- `git diff --check`。ステージは**明示的に**（`git add -A` 禁止）。
  ソース・`reports/` のみ。job スクリプト、`slurm-*.out`、ncu の csv/報告、
  一時 conf はコミットしない。
- コード変更と、それが無効化したレポートの更新は**同じコミット**に入れる。

## 8. 他次数への横展開

採用された変更ごとに:

- 他の p で前提が成り立つか机上で確認（Nq、1 平面の shared 量、レジスタ、
  面点率、`Ne`、x/z の出力写像の共有 …）。
- 成り立つ可能性があれば**実際に移植して測る**。効かなければ**効かない理由を
  測って**レポートに残す（p=15 の面 flux 別カーネル化、p=7 の D1D レジスタ
  常駐がその例）。
- 横展開の結果も手順 3〜7 を通す。ここで最速パスが交代することが実際にある。

## 待ち方

sbatch ジョブやサブエージェントは、バックグラウンドで **1 回だけ**起動して
ターンを終える。`squeue` やログの繰り返しポーリング禁止（ユーザ設定）。
待つ間は、独立して進む作業（レポート下書き、別バリアントのビルド）だけ
手を動かす。
